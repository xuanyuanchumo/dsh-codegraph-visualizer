# 第一部分：需求分析文档

## 一、项目背景

### 1.1 DSH 与"一切皆插件"生态

2026年8月13日，DeepSeek 开源了其 Agent 运行时框架 **DeepSeek Harness（DSH）**，基于 Cordis 组合框架构建，秉持 **"一切皆插件"** 的核心设计理念。DSH 的插件并非简单平铺，而是通过分层叠加的方式组成一棵完整的插件树，所有插件通过统一的 API 注册，通过共享的 `ctx` 上下文对象通信。

截至 2026-08-18，DSH 生态已收录精选插件 1661 个，监测生态仓库 1901 个，累计获得 Star 571,662。DSH 插件生态已形成工具（Tools）、UI、记忆（Memory）、视觉（Vision）、技能（Skills）和工作流（Workflow）六大主要方向。

### 1.2 问题陈述

在 DSH 当前生态中，代码理解与可视化分析领域存在显著的**功能空白**：

| 现有插件/能力 | 能力边界 | 与本插件关系 |
|--------------|----------|-------------|
| `dsh-codegraph`（jiangzhenguo） | 将 CodeGraph CLI 包装为模型可见的原生工具，**无可视化界面** | **数据源** |
| `dsh-tool-lens`（trench-xinxin） | AST 代码图谱与拓扑分析，**无可视化面板** | **数据源** |
| `dsh-web-ui` 的 Git 图谱 | 仅提供 Git 提交历史可视化，非代码关系图谱 | **UI 范式参考** |
| `dsh-mermaid-image-preview` | 仅将 Mermaid 代码块渲染为图片，非交互式图谱 | **渲染机制参考** |
| `dsh-git-graph` | 泳道式提交图，非代码调用/依赖关系图 | **UI 范式参考** |

**核心差距**：DSH 生态中已有代码图谱的数据生成能力（`dsh-codegraph`、`dsh-tool-lens`）和通用图谱渲染能力（Git 图谱），但**缺少一个专门用于"代码关系图谱可视化"的交互式面板插件**，将两者打通。

### 1.3 项目目标

1. **填补空白**：在 DSH Web UI 中提供**交互式代码图谱可视化面板**
2. **生态兼容**：深度兼容 `dsh-codegraph` 与 `dsh-tool-lens` 作为数据源
3. **实时体验**：实现代码变更后图谱**自动增量更新**
4. **开发者体验**：为开发者提供直观的代码结构感知能力，降低代码理解门槛

### 1.4 目标用户

| 用户类型 | 使用场景 | 核心诉求 |
|----------|---------|----------|
| **日常开发者** | 理解陌生代码库的调用关系 | 快速定位"谁调用了这个函数" |
| **架构师** | 评估模块依赖与耦合度 | 可视化依赖拓扑、识别循环依赖 |
| **重构工程师** | 评估修改影响范围 | 影响分析图谱、风险分级 |
| **AI Agent 开发者** | 为 Agent 提供代码结构上下文 | 图谱数据可作为 Agent 的决策依据 |

## 二、功能需求

### 2.1 核心功能（P0 — MVP 必达）

| 编号 | 功能 | 描述 | 验收标准 |
|------|------|------|----------|
| FR-01 | **图谱渲染** | 使用图可视化引擎渲染代码关系图 | 支持 5000+ 节点流畅渲染，FPS ≥ 30 |
| FR-02 | **多数据源接入** | 兼容 `dsh-codegraph` 与 `dsh-tool-lens` 作为数据源 | 两种数据源均可生成可视化图谱 |
| FR-03 | **图谱类型切换** | 支持调用关系图、依赖拓扑图 | 一键切换两种视图 |
| FR-04 | **节点交互** | 节点拖拽、滚轮缩放、平移 | 基础图交互全部可用 |
| FR-05 | **实时更新** | 代码变更后图谱自动刷新 | 变更后 < 5 秒内图谱更新 |
| FR-06 | **节点详情** | 点击节点显示符号详情 | 显示符号名、文件路径、行号 |

## 四、用户旅程（J1–J14）

> 对齐 `docs/anchor/cycles/项目迭代驱动验证流程.md` §6.1.2

| 旅程 | 名称 | 关键路径（正向） | 反向/异常场景 |
|------|------|-----------------|--------------|
| J1 | 仓库导入与图谱初始化 | 打开 DSH Web → 点击图谱面板 → 自动加载当前工作区图谱 | 空工作区（无代码）→ 引导提示；非 Git 仓库 → 提示初始化 |
| J2 | 图谱浏览与导航 | 拖拽/缩放/平移 → 浏览代码关系 | 极端节点数（>10000）→ 渐进式渲染 + 进度反馈 |
| J3 | 符号搜索与定位 | 输入符号名 → 高亮匹配节点 → 点击跳转源码 | 搜索词不存在 → 空结果提示；搜索词歧义 → 多结果列表 |
| J4 | 调用链追踪 | 点击节点 → 高亮入边/出边 → 递归展开 | 循环调用 → 检测并终止递归；跨文件调用 → 懒加载 |
| J5 | 依赖拓扑分析 | 切换依赖拓扑图 → 识别循环依赖 | 无依赖 → 空图提示；深层嵌套 → 折叠展示 |
| J6 | 布局切换 | 力导向 → 层次 → 树形 → 圆形 | 布局算法超时 → 降级为力导向 |
| J7 | 过滤器使用 | 按文件类型/符号类型筛选 → 实时更新图谱 | 过滤后无节点 → 空状态提示 |
| J8 | 图谱导出 | 选择格式 → 导出 → 下载 | 大图谱导出 PNG 超时 → 提示改用 SVG |
| J9 | 实时更新验证 | 修改代码 → 保存 → 图谱自动刷新 | 文件保存失败 → 不触发更新；Wasm 解析失败 → 降级显示 |
| J10 | 主题与个性化 | 切换 Light/Dark 主题 → 图谱颜色自适应 | 自定义颜色配置冲突 → 回退默认 |
| J11 | 多数据源切换 | 切换 CodeGraph/Lens 数据源 → 图谱重建 | 数据源不可用 → 降级到另一数据源 |
| J12 | 异常恢复与容错 | 断网/崩溃后重启 → 图谱与缓存恢复 | 缓存损坏 → 重新索引；Wasm 初始化失败 → 降级提示 |
| J13 | 插件生命周期合规 | 注册即 effect → dispose 清理 → 重载无泄漏 | 监听器泄漏 → 内存增长检测 |
| J14 | 生态集成验证 | 通过 better-sidebar 侧边栏访问 → `/` 斜杠命令搜索 → agent-teams 数据供给 | 集成插件未安装 → 优雅降级 |

### 5.2 插件分层（DSH 规范对齐）

依据 DSH 插件开发规范（九条红线），本插件采用 **Host + Client** 双层架构：

| 层级 | 职责 | 技术栈 | DSH 规范对齐 |
|------|------|--------|-------------|
| **Host 面** | 数据获取、聚合、工具注册、推送调度 | Node.js + Cordis | 注册即 effect、waterfall 必须委托、Branded ID、声明合并事件、ESM only、Host/Client 隔离、能力缝三角色、配置显式化 |
| **Client 面** | 图谱渲染、交互控制、状态管理 | React + Cytoscape.js | 同上 |
| **Rust-Wasm 内核** | **不需要** | — | 图谱构建由 `dsh-codegraph`/`dsh-tool-lens` 完成；布局算法由 Cytoscape.js 提供 |

### 5.3 能力缝设计（Capability Seam）

依据 DSH 架构规范，本插件的能力缝包含三角色：

| 角色 | 定义 | 本插件实现 |
|------|------|-----------|
| **Service Definition** | 接口契约 | `IGraphVisualizerService`（图谱数据获取、订阅、导出） |
| **Service Provider** | 实现 | Host 端 `GraphVisualizerService`（数据聚合、工具注册、推送） |
| **Consumer** | 使用方 | Client 端 React 组件、模型可见工具 `graph_search` |


#### 6.3.2 渲染引擎封装

选择 **Cytoscape.js** 作为主要渲染引擎，理由：
- 功能全面的图论分析与可视化库
- 丰富的交互（拖拽、缩放、点击高亮）
- 支持多种布局算法
- 有成熟的 React 封装 `react-cytoscapejs`

备选：**G6**（AntV），提供图的绘制、布局、分析、交互等完整能力。

## 七、数据模型

### 7.1 统一图谱数据模型

```typescript
interface UnifiedGraphData {
  metadata: {
    source: 'codegraph' | 'lens' | 'merged'
    timestamp: string
    nodeCount: number
    edgeCount: number
  }
  nodes: GraphNode[]
  edges: GraphEdge[]
}

interface GraphNode {
  id: string                    // 唯一标识（Branded 类型）
  label: string                 // 显示名称
  type: 'file' | 'class' | 'function' | 'method' | 'variable' | 'module'
  filePath: string
  lineStart?: number
  lineEnd?: number
  metadata?: Record<string, any>  // 数据源特定元数据
}

interface GraphEdge {
  id: string
  source: string                // 源节点 ID
  target: string                // 目标节点 ID
  type: 'calls' | 'imports' | 'extends' | 'implements' | 'contains'
  label?: string
}
```

### 7.2 数据转换流程

```
[codegraph export json] ──┐
                           ├──→ [数据融合器] ──→ [UnifiedGraphData] ──→ [Cytoscape.js elements]
[dsh-tool-lens 工具输出] ──┘
```

**转换规则**：
- CodeGraph 节点 → `GraphNode`（映射 `kind` → `type`）
- Lens 节点 → `GraphNode`（映射 `symbolType` → `type`）
- 重复节点去重策略：按 `id` 去重，保留元数据最丰富的版本

## 十、实时更新机制

### 10.1 底层保障

`codegraph` 上游项目内置**自动同步（Auto-Sync）** 机制：
- 使用操作系统原生文件事件
- **增量更新**：仅重新解析变更的文件
- **防抖处理**：文件变更后短暂等待再触发同步

### 10.2 实现方案

**推荐方案：前端轮询（Pull）**

```typescript
// Client 端定时轮询
useEffect(() => {
  const interval = setInterval(async () => {
    const status = await callTool('graph_status')
    if (status.changed || status.fileCount !== prevFileCount) {
      const data = await callTool('graph_data')
      updateGraph(data)
    }
  }, config.refreshInterval)  // 默认 3000ms
  return () => clearInterval(interval)
}, [])
```

**进阶方案：后端推送（Push）**

利用 DSH 的 WebSocket 能力：
```typescript
// Host 端监听 codegraph 变更
ctx.on('codegraph:synced', (data) => {
  ctx.broadcast('graph:update', data)
})
```

## 二十一、架构增强与七大原则对齐

### 21.1 软件工程七大原则落实

| 原则 | 落实方式 |
|------|----------|
| **单一职责（SRP）** | 每个模块单一职责：Adapter 仅转换、Merger 仅聚合、Renderer 仅渲染、Store 仅状态 |
| **开闭原则（OCP）** | 适配器接口稳定，新增数据源通过实现 `IGraphDataProvider` 扩展，无需修改现有代码 |
| **里氏替换（LSP）** | Branded 类型（`NodeId`/`EdgeId`）确保类型安全替换；适配器实现可互换 |
| **接口隔离（ISP）** | `IGraphVisualizerService` 拆分为数据获取、订阅、导出三个细粒度接口 |
| **依赖倒置（DIP）** | Client 依赖 Store 抽象而非具体实现；Host 依赖 Adapter 接口而非具体类 |
| **合成复用（CRP）** | GraphPanel 通过 `children` 组合而非继承；Renderer 通过 options 注入回调 |
| **迪米特法则（LoD）** | 组件仅与直接邻居通信：GraphPanel → Store → Renderer，不跨层访问 |

### 21.2 生产级架构增强

```
┌─────────────────────────────────────────────────────────┐
│                   增强架构层（v2.1+）                    │
├─────────────────────────────────────────────────────────┤
```

## 二十三、数据结构与算法分析（对齐迭代流程 §2.4）

> 关键路径必须声明复杂度预算；引入解析/搜索/缓存类能力先查选型决策表，遵循 P16 免重轮禁令。

### 23.1 核心数据结构

| 数据结构 | 用途 | 复杂度 | 选型理由 |
|----------|------|--------|----------|
| `Map<string, GraphNode>` | 融合器节点去重 | O(1) 查/插 | `Map` 哈希查找优于数组线性扫描 |
| `Map<string, GraphEdge>` | 融合器边去重 | O(1) 查/插 | 同上 |
| `Set<string>` | 调用链 BFS visited 标记 | O(1) 查/加 | `Set` 去重优于数组 `includes` O(n) |
| `Set<string>` | 循环检测 DFS recStack | O(1) 查/加 | 同上 |
| `Map<string, GraphNode>` | Renderer 节点数据缓存 | O(1) 查 | `getNodeData` 热路径 |
| Zustand Store | UI 状态 | O(1) 读 | 外部 store，`useSyncExternalStore` 安全并发 |

### 23.2 关键算法复杂度预算

| 算法 | 位置 | 时间复杂度 | 空间复杂度 | 说明 |
|------|------|-----------|-----------|------|
| 多源融合去重 | `GraphDataMerger.merge` | O(N+E) | O(N+E) | N=节点数, E=边数；Map 去重单次遍历 |
| 增量 Delta 合并 | `GraphDataMerger.applyDelta` | O(ΔN+ΔE) | O(N+E) | 仅遍历增量；Map.set 覆盖更新 |
| 调用链高亮 BFS | `CytoscapeRenderer.highlightCallChain` | O(V+E_out) | O(V) | BFS 遍历出边，visited 防环 |
| 循环检测 DFS | `CytoscapeRenderer.detectCycles` | O(V+E) | O(V) | 三色标记 DFS，recStack 路径回溯 |
| 符号搜索 | `CytoscapeRenderer.search` | O(N) | O(1) | 线性扫描 + `toLowerCase`；万级节点 < 50ms |
| 类型过滤 | `CytoscapeRenderer.filterByType` | O(N+E) | O(1) | batch 内单次遍历 |
| 增量数据更新 | `CytoscapeRenderer.updateData` | O(N+E) | O(N+E) | diff 新旧 id 集合，批量增删 |
| 工具摘要统计 | `summarizeGraph` | O(N+E) | O(T) | T=类型数；Map 计数 + slice(0,10) |

### 23.3 选型决策表（P16 免重轮）

| 能力需求 | 自研方案 | 成熟库方案 | 决策 | 理由 |
|----------|---------|-----------|------|------|
| 图渲染与交互 | — | **Cytoscape.js** | 用库 | 成熟、内置布局、React 友好、20k+ star |
| 层次布局 dagre | — | **cytoscape-dagre** | 用库 | dagre 算法成熟，自研无收益 |
| 状态管理 | — | **Zustand** | 用库 | 轻量、`useSyncExternalStore` 并发安全 |
| 循环检测 | DFS 三色标记 | — | 自研 | 标准算法，无成熟库适配 Cytoscape 元素 API |
| 调用链遍历 | BFS | — | 自研 | 标准算法，依赖 Cytoscape `edges()` 选择器 |
| 防抖搜索 | `useDebounce` hook | lodash.debounce | 自研 | 3 行 hook，引入 lodash 违反 ponytail |
| 文件导出 | Blob + URL | file-saver | 自研 | 6 行标准 API，无依赖 |
| 键盘快捷键 | window.addEventListener | mousetrap | 自研 | 原生事件 + 被动监听，无依赖 |

### 28.3 响应式适配

断点按**面板宽度**分档而非视口宽度：插件渲染在 DSH 面板里，面板宽度与窗口大小无关，因此
`src/client/styles/layout.css:24-25` 用 `container-type: inline-size; container-name: graphpanel`
把面板变成容器，`responsive.css` 用 `@container graphpanel` 查询；JS 侧由 `useElementWidth` 的
`ResizeObserver` 量出同一宽度，映射到 `src/shared/constants.ts` 的两个断点。
下表是**已实现**的行为（2026-02 实机扫描 300–900px 得到，非目标设想）：

| 面板宽度 | 生效机制 | 行为 |
|---------|---------|------|
| ≥ 768px | JS 宽档 | 工具栏三组完整：文字标签（`cose` / 视图名 / `L3`）、组间分隔线、独立搜索按钮 |
| 600–767px | JS compact 档（`data-cg-compact`） | 中心组三个触发器改图标（`LayersIcon`/`GraphIcon`/层级文本），`title` 保留当前值；分隔线隐藏 |
| 480–599px | CSS `@container graphpanel (max-width: 600px)` | 中心组整体隐藏 —— 三个图标触发器共需 150px，低于此会把层级触发器挤到换行并被裁；同时隐藏引导/鹰眼按钮与类型徽标 |
| < 480px | JS narrow 档（`data-cg-narrow`） | 独立搜索按钮收进"更多"菜单 |
| ≤ 380px | CSS `@container graphpanel (max-width: 380px)` | 再隐藏引导/鹰眼/图例按钮与分隔线；`@supports not (container-type: inline-size)` 时由等价 `@media` 兜底 |

收紧方向由 `.cg-toolbar-right { flex-shrink: 0 }` 与 `.cg-toolbar-center/.cg-toolbar-left { min-width: 0 }`
保证：左组统计文字先截断、中心组按档位让位，导出/更多/折叠永不离开可视区。JS 档位在
`ResizeObserver` 缺失（测得宽度 0）时一律按**宽档**渲染 —— CSS 容器查询（或 `@supports` 回退）
是唯一兜底，不会出现"JS 认为很窄、CSS 认为很宽"的半适配状态。两半的断点一致性由
`tests/unit/responsiveContract.test.ts` 钉住（见 `docs/测试体系.md` 的"响应式契约回归测试"）。

**已知取舍（≤ 600px 档）**：中心组隐藏后，布局切换仍有替代入口 —— `Ctrl+L` 按
`cose → fcose → dagre → circle → grid → radial → tree` 循环（`src/client/hooks/usePanelKeyboard.ts:77-83`），
`/` 命令面板的 `codegraph-layout` 命令也能设置布局（`src/client/integrations/CommandUiIntegration.ts`，
原 `SpotlightIntegration.ts:46` 已在 cycle-83 随幻影服务清除一并删除，见 §59.21/§59.22）；但**视图模式与
层级目前只有工具栏入口**，在 ≤600px 面板下会暂时不可达。这是"宁可让两个次要下拉消失，也不让
导出/更多/折叠被挤出可视区"的取舍结果；若要补齐，应在"更多"菜单里增加视图模式/层级子菜单，
而不是把中心组重新塞回 150px 都放不下的宽度里。

### 31.6 布局 Worker：从"路由假设"到可验证不变量（v2.10 收敛）

Round 6 的 J0 审计（`.cycles/` 下一次性脚本，不入库）证明**"代码里有 worker、路由也返回 200"都不等于
worker 可用**。三层缺陷叠加，每层都会静默退化成"主线程布局"：

1. **交付路径不存在**：`LayoutController` 按 `plugins/dsh-codegraph-visualizer/worker/layoutWorker.js`
   取 worker，而 DSH **不为插件自带的文件提供资源路由**（逐个 fetch `/plugins/...`、`/plugin-assets/...`、
   `/assets/...` 全部 404；客户端 JS 只出现在 `/plugins/??<pkg>/client.js&rev=<hash>` 多入口拼接串里）。
   实测该 URL 在真实宿主里连续 404 —— 网络面板里 **1000 条请求（25 页）全是同一个 404**。
   修法：worker 由**本插件自己的 HTTP 面**提供（`LAYOUT_WORKER.ROUTE_PATH =
   /api/v1/codegraph/worker/layoutWorker.js`，与客户端其余请求同源，web / 桌面 / dev 代理下都成立）。
2. **重试没有上界**：`new Worker(url)` 对不可达 URL **不抛错**（失败以异步 `error` 事件到达），而旧代码
   在"构造成功"时就把 `workerRetryCount` 清零 → `>= WORKER_MAX_INIT_RETRIES` 的上界永不触发，
   无限重建 + 每次布局白等 `LAYOUT_TIMEOUT_MS`（10 s）才回退主线程。修法：**只有收到 `onmessage`
   回复才复位预算**（回复是"bundle 真加载了"的唯一证据），另加 `WORKER_HANDSHAKE_TIMEOUT_MS`（5 s）
   给尚未证明自己的 worker、`workerGaveUp` 给预算耗尽与 `destroy()` 之后。
3. **产物在 Worker 里跑不起来**：bundle 由 rolldown 的 `__commonJS` 包装只传 `(exports, module)`，
   而 dagre → graphlib 的 UMD feature test 是 `if (typeof require === "function") try { … } catch (e) {}`
   接 `if (!graphlib) graphlib = window.graphlib;` → `require` 永远不是函数，必然跌到 `window.graphlib`，
   经典 Worker 里没有 `window`，于是 `Uncaught ReferenceError: window is not defined` 在**模块求值期**就杀死
   worker（服务端文件第 34740 行）。修法：入口 `src/client/worker/layoutWorker.ts` 第一行
   `import './workerShims.ts';`，该 shim 只补一个 `globalThis.require` 抛错桩（bundled 的真实 `require('…')`
   早已被静态改写成 `require_x()`，这个桩只服务于 feature test），**绝不伪造 `window`**。

不变量与 J0 判据由 `tests/unit/workerContract.test.ts`（9 条）+ `tests/unit/routes.test.ts` 新增的
注册序断言持有，变异自检 `.cycles/worker-contract-mutations.ps1` 6/6 变红；口径细节见
`docs/测试体系.md` 的"布局 Worker 契约回归测试"与 `docs/用户旅程.md` §3。**已知取舍**：worker 只在
"渲染节点 > 500 且非首次数据集"时才被使用（`useGraphRenderer.ts:195-197`），因此本项目自身在 L3 档
（50 个渲染节点）永远走主线程 —— J0 的判据因此写成"用真实路由起 worker 必须能应答"，
而不是"在页面里看到 worker 被调用"。

**同一类缺陷的第二处（Round 7 已修）**：`src/adapters/TreeSitterAdapter.ts` 的 `loadLanguageWasm` 原先在

`node_modules/web-tree-sitter/dist/${wasmFile}`、裸文件名与 `document.baseURI` 变体），而宿主可用的读取

### 31.9 路径形状口径统一 + "搜索/符号选中即可见"（Round 10）

**（a）同一宿主内两条路由的路径口径必须一致。** 旧 tree-sitter 路由用 `path.normalize(filePath) !== filePath`

`src/host/routes/shared.ts` 的 `triggerBackgroundBuild` 落快照时用的是


**（c）实现：纯内容派生的结构指纹。** 新增 `src/shared/graphFingerprint.ts`（136 行，LF），导出六个函数：

| 导出 | 作用 |
|------|------|
| `hash64(input: string): string` | 双 FNV-1a 32 位车道 + `Math.imul`，输出 16 位十六进制（64 bit） |
| `stableStringify(value: unknown): string` | 对象键递归排序、丢弃 `undefined` 值、`NaN`/`Infinity` → `null`，结构相等必同串 |
| `canonicalizeNode(node)` | `['n', id, label, type, filePath, lineNumber ?? 0, parentId ?? '', layer ?? '', stableStringify(properties)]` 以 `\u0001` 连接 |
| `canonicalizeEdge(edge)` | `['e', id, source, target, type, direction ?? '', weight, stableStringify(properties)]` |
| `computeContentHash(content: string): string` | `v<VERSION>:<hash64(content)>`，用于原始文本 |
| `computeGraphFingerprint(data: GraphData): string` | 节点头排序 + 边头排序 + header（`nodes/edges/totalNodes/totalEdges/truncated`）以 `\u0002` 连接后哈希 |

**关键决策一：`metadata.timestamp` 与 `metadata.repoId` 都不参与指纹。** 只有"内容变了指纹才变"才让快照写入幂等；
新测试用 `graph({ timestamp: 1 })` vs `graph({ timestamp: Date.now() })` 直接钉住这一点，变异 M1 把 timestamp 掺回 payload
后该用例立刻变红。`metadata.truncated`/`totalNodeCount`/`totalEdgeCount` **参与**（截断视图与全量视图不是同一份图），
缺省时回落到实测长度。

**关键决策二：不用 `node:crypto`。** `src/shared/**` 同时被 `tsconfig.client.json` 的 `include` 与
`scripts/build-client.mjs` 打进浏览器 bundle，引入 `node:crypto` 会直接炸掉客户端构建；`hash64` 是**变更检测**摘要而非
密码学摘要，FNV-1a 足够且零依赖。`FINGERPRINT.VERSION` 前缀保证换算法时旧快照 hash 不会被误认成当前值。

**关键决策一：空标识 fail-closed 而非 fail-open。** `sameRepoId` 首行
`if (!a || !b) return false;`——`repoScope.ts:25` 亦 `if (!payloadRepoId || !scopeRepoId) return false;`。
理由是**不能靠"不知道是谁"来放行**：负载不带 repoId 时无从判断归属，宁可多取一次也不能串台。
但守卫入口与判定原语的极性相反（`isForeignRepo` 里空标识返回 `false` = 放行），
因为**客户端在拿到 bootstrap 之前 store 里没有身份**，此时若拦下所有负载会导致永久空态。

与 `SSEEvents.test.ts:460 events are accepted while the store has no workspace identity yet`。

**关键决策二：盘符大小写只在双方都是盘符路径时忽略。** `pathUtils.ts:21` 为

### 31.15 跨工作区守卫的结构性收口：取数层守卫 + 唯一落库通道（Round 16）

**（a）缺口：同一缺陷第二次出现。** Round 15 为跨工作区污染加了六处守卫，但漏掉了 SSE 的
`graph-updated` 增量分支：`src/client/runtime/SSEEvents.ts:45-51`（Round 16 编辑前）只校验了**事件**里的
`data.repoId`（:33），随后

```ts
fetchGraphDataIncremental(store.lastUpdated).then((graphData) => {
  if (graphData && graphData.nodes && graphData.nodes.length > 0) {
    store.setGraphData(graphData.nodes, graphData.edges, graphData.metadata.repoId, graphData.metadata);
  }
})
```

对 **fetch 回来的** `graphData.metadata.repoId` 零校验。而 `/api/v1/codegraph/data` 正是 host 单槽、
不带 `workspace` 参数、不做过滤的那个端点（`src/host/routes/dataRoutes.ts:58-92`）。于是：SSE 事件带的
`repoId` 是正确的（守卫放行），但取回来的却是另一个工作区的图，并被无条件写入画布。

对照 `src/client/runtime/WindowEvents.ts:28-31` 的**同一模式却做了复核**——两处不对称。这就是 Round 15
J0 里"50 节点骨架被覆盖成 2 节点图"的**同类机理**，只是入口不同。按 R10（同一错误出现两次即须写入
规则），本轮不做"再补一处调用点守卫"，而是做**结构性收口**。

**（b）三层改造。**

| 层 | 文件 | 改动 |
|----|------|------|
| 判定原语 | `src/shared/graphScope.ts`（**新增** 30 行） | `isForeignRepo` 从 `src/client/runtime/repoScope.ts` **下沉**到 `shared/`。理由：`client/api/` 现在也要用它，而 `api/` 不允许反向依赖 `runtime/`（编辑前 `grep "from '../runtime" src/client/api/*.ts` 零命中，这条依赖方向是既有约束） |
| 取数层 | `src/client/api/index.ts:169-191` | `fetchGraphDataIncremental(lastUpdated, scopeRepoId)` 的 `scopeRepoId` 为**必填**参数（非可选）；`coerceGraphData` 之后即 `if (isForeignRepo(data.metadata.repoId, scopeRepoId)) { log.info(...); return null; }`。同时补上原先缺失的 `withAbortGuard` 第三参 `logContext` |
| 落库层 | `src/client/runtime/repoScope.ts`（重写为 re-export + 唯一通道） | 新增 `applyScopedGraphPayload(sink, data, scopeRepoId, source): boolean`：空负载/空 nodes → `false`；外来 → 记日志并 `false`；同源 → `sink.setGraphData(...)` 并 `true`。**运行时唯一**的图负载落库入口 |

两条通道（`SSEEvents.ts` graph-updated、`WindowEvents.ts` REFRESH 增量分支）都改为
`fetchGraphDataIncremental(store.lastUpdated, store.repoId)` + `applyScopedGraphPayload(store, data, store.repoId, source)`，
内联的 `isForeignRepo` 判定被删除。`src/client/hooks/useViewMode.ts:8` 的 import 一并改指 `shared/graphScope.ts`。

**（c）为什么 `scopeRepoId` 必填而非可选。** 可选参数意味着新增调用点可以"不回答自己期望哪个工作区"
而静默继承一个不设防的默认值——这正是 Round 15 漏网的成因（守卫写在调用点，新增通道时被漏掉）。
改为必填后，**类型检查会强制每个调用点表态**；`null` 必须显式书写，而 `null` 有明确语义（"我还不知道

**（d）顺带清理的死代码。** `src/client/api/index.ts` 原 `:110-116` 的 `fetchGraphData()` 全仓**零调用方**

`package.json` 的 `exports` 只暴露 `dist/index.js` 与 `dist/client.js`，`api/` 内部函数不对外，
**删除无兼容性风险**。

**（e）测试。** 新增 2 个套件、11 条用例：`tests/unit/graphScope.test.ts`（5 条，钉住判定原语极性：

## 四十、Cytoscape.js 渲染引擎兼容性修复

### 40.1 `:hover` 伪类选择器问题

**问题**：Cytoscape.js 不支持 CSS `:hover` 伪类选择器，控制台持续输出警告：

```
Warning: `node:hover` is not a valid selector
```

**根因**：Cytoscape.js 使用自定义选择器引擎（基于 `cytoscape` 的 `selector` 模块），仅支持元素属性选择器、类选择器和 ID 选择器，不支持 CSS 伪类（`:hover`、`:focus`、`:active` 等）。

**修复方案**：将 3 处 `:hover` 选择器替换为 `.hovered` 类选择器，并通过 `mouseover`/`mouseout` 事件监听器动态添加/移除 `.hovered` 类：

| 位置 | 原选择器 | 新选择器 | 事件绑定 |
|------|---------|---------|---------|
| `CytoscapeRenderer.ts` stylesheet | `node:hover` | `node.hovered` | `cy.on('mouseover', 'node', ...)` / `cy.on('mouseout', 'node', ...)` |
| `CytoscapeRenderer.ts` stylesheet | `node[isCluster]:hover` | `node[isCluster].hovered` | 同上（聚类节点复用同一事件） |
| `CytoscapeRenderer.ts` stylesheet | `edge[isCluster]:hover` | `edge[isCluster].hovered` | `cy.on('mouseover', 'edge', ...)` / `cy.on('mouseout', 'edge', ...)` |

**验证**：修复后 DSH 真实环境中控制台不再出现 `:hover` 选择器警告。

### 40.2 `ctx.provide` 类型声明缺失

**问题**：`src/types/index.ts` 中 `Context` 声明合并缺少 `provide` 方法，导致 TypeScript 编译错误：

```
error TS2339: Property 'provide' does not exist on type 'Context<...>'.
```

**根因**：Cordis 框架的 `Context` 接口通过声明合并（declaration merging）扩展，`provide` 方法未在项目的类型声明中定义。

**修复**：在 `src/types/index.ts` 的 `Context` 声明合并中添加：

```typescript
provide(name: string, service: unknown): () => void
```

### 40.3 `_hasPositions` 变量引用错误

**问题**：`CytoscapeRenderer.ts:331` 引用了 `hasPositions`（未声明），应为 `_hasPositions`（已声明于 327 行）。

**修复**：将 `hasPositions = false` 改为 `_hasPositions = false`。

### 59.20 ETag 身份定域与时钟域解耦（cycle-82）

> **级别**：P0（由 cycle-80 登记的 P3-R16-02「观察项」升级）
> **升级依据**：这是「**校验器不校验身份**」家族的**第三次复发**——前两次为 P0-R15-01（§31.14 跨工作区图负载污染）与 P0-R16-01（§31.15 守卫写在调用点被漏掉），触发技能 R10「同一错误不得犯第二次」。继续观察等于放任同类缺陷再犯一次。
> **改动规模**：22 个文件 / 557 insertions / 90 deletions；`src/` 11 文件、`tests/` 10 文件、`docs/` 1 文件；**无新增依赖、无新增文件**。

#### (a) 缺陷的两半

**(1) 宿主侧：校验值既无身份维度也无资源维度，且 4 条路由在身份解析之前就校验。**

改造前 `src/host/routes/shared.ts:206-214`：

```ts
export function returnIfEtagMatch(req, res, corsConfig, deps): boolean {
  const cachedData = deps.getLastGraphData();
  return !!cachedData && checkEtag(req, res, corsConfig, String(cachedData.metadata.timestamp));
}
```

三个缺陷叠加：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 无**工作区身份**维度 | host 只保留**一个** `lastGraphData` 槽，槽里可能装着别的工作区的图。两个工作区在毫秒级撞到同一 timestamp 就互相冒充 |
| 2 | 无**资源**维度 | `/data`、`/bootstrap`、`/children`、`/outline`、`/ast`、`/edges` 共用同一个单槽比对 ⇒ `/data` 的校验值能让 `/children` 回 304，即"这个资源没变"的假结论 |
| 3 | **调用顺序**把身份维度彻底丢掉 | `dataRoutes.ts` 的 children（`:197`）、outline（`:266`）、ast（`:320`）、edges（`:383`）四条路由的 `returnIfEtagMatch` 都在 `resolveWorkspaceFromRequest` **之前**执行，`?workspace=` 还没被读 |

**(2) 客户端侧：把展示时钟当 HTTP 校验器。**

`store.lastUpdated` 有四个写入点，**三个写 `Date.now()`（客户端时钟）、一个写 `metadata.timestamp`（服务端时钟）**：

| 写入点 | 改造前取值 | 时钟域 |
|---|---|---|
| `setGraphData` layered 分支 | `Date.now()` | 客户端 |
| `setGraphData` 非 layered 分支 | `Date.now()` | 客户端 |
| `setBootstrapData` | `metadata.timestamp` | **服务端** |
| `applyGraphDelta` | `Date.now()` | 客户端 |

而 `src/client/api/index.ts:175` 把它直接当 `if-none-match` 发出。两种失败模式同时存在：

- **304 永不命中**：客户端时钟远大于服务端 revision，比对必然不等 ⇒ 每次"增量取数"都是全量重传；
- **假 304**：bootstrap 路径刚好与服务端一致，但此后图已被补丁（`applyGraphDelta`）推进，客户端仍回传旧值 ⇒ 服务端认为"没变"，**一次真实更新被静默丢弃**。

#### (b) 修复：让校验值对三元组单射

**(1) 新增原语**（`src/shared/graphFingerprint.ts`）：

```ts
export type GraphEtagResource = 'graph' | 'bootstrap' | 'children' | 'outline' | 'ast' | 'edges';

export function computeGraphEtag(
  repoId: string | null | undefined,
  revision: number,
  resource: GraphEtagResource,
): string {
  return `W/"${revision}-${hash64(`${resource}\u0001${repoId ?? ''}`)}"`;
}
```

三个设计决定，各有明确理由：

- **`resource` 必填、不给默认值**：让类型检查强制每个新调用点回答"我校验的是哪一份资源"。这与 Round 16 把 `scopeRepoId` 设为必填是同一设计——**"新增调用点不表态"才是这类缺陷的复发机制**。
- **身份取「请求方声明的工作区」，revision 取「槽」**：两类错误的代价不对称。校验值多算一次不匹配，只是多回一次 200、少省一次传输；而假 304 会让客户端保留过期数据并**静默丢弃一次真实更新**。取请求方工作区只会让校验值更难撞上，方向是安全的。
- **刻意不用 `computeGraphFingerprint()`**：指纹要遍历全部节点与边，而 ETag 在每次 `/data` 请求上都会被计算。这里的目的是**身份定域**，不是内容寻址。§「ETag 保持 `String(metadata.timestamp)`，不换成指纹」的既有决策**依然有效**——本轮改的是身份与时钟域。

**(2) 宿主侧接入**：`returnIfEtagMatch(req, res, corsConfig, deps, resource, repoId?)` 计算 `computeGraphEtag(repoId ?? cachedData.metadata.repoId, cachedData.metadata.timestamp, resource)`；6 个调用点全部带资源名；4 处反序修正为「先 `resolveWorkspaceFromRequest` 再 `returnIfEtagMatch`」；`/data` 两处 200 写入点改用**与 304 比对同源**的 `computeGraphEtag(..., 'graph')`（否则客户端存下的值永远匹配不上）。

**(3) 客户端时钟域解耦**：新增 `graphEtag: string | null` 字段（**不持久化**——`graphStore.ts:160-170 partialize` 白名单未收录），`fetchGraphDataIncremental(clientEtag, scopeRepoId)` 首参由 `lastUpdated: number` 改为 `string | null | undefined`，返回 `IncrementalGraphResult { data, etag }`；无校验值时**完全不发** `if-none-match`。4 处写入点、3 处工作区动作、补丁路径全部显式表态：

| 位置 | 取值 | 理由 |
|---|---|---|
| `setGraphData` 两分支 | `metadata?.timestamp ?? Date.now()` + `metadata?.etag ?? null` | 服务端带了 timestamp 就用它，否则回落本地时钟（仅作展示） |

### 59.22 cordis 严格探测时序缺陷与上游命令目录缺陷（cycle-83 真机复核）

#### (a) 缺陷：`apply()` 里的 `ctx.get` 是一次性时序快照（P0，本插件侧）

`ClientCompatLayer.hasService(ctx, key)` 与 `ClientVersionDetector.hasService(ctx, key)` 原实现为

- `cordis/lib/index.js:763-772` `get(name, strict = true) { return getTraceable(this.ctx, this._getImpl(name, strict)?.value); }`，
  `_getImpl` 内 `if (strict && impl.fiber.state !== 2) return;`

本插件 `src/client/index.ts:71-85 apply(ctx)` 是**一次性同步**执行：`detectVersion` → `detectPlatform` →

#### (g) 教训（R10 候选）

1. **`ctx.get` 默认 `strict = true` 是「提供者 fiber 活跃」探针，不是「服务存在」探针。** 在
   `apply()` 里用它做能力快照，会把「稍后才活跃」的服务永久判死。存在性探测用 `strict = false`，
   时序等待用 `ctx.inject`。
2. **能力快照早退是「一瞬定生死」的缺陷放大器**：`if (!flags.x) return;` 一旦读错，功能永久缺失
   且**无任何报错**（本次只有一行 `flags` 日志能反证）。
3. **上游缺陷会让「插件已修好」表现为「仍然不工作」**：必须先证明本插件侧的修复生效
   （`commandUi contributions registered {count: 5}`），再把剩余症状归因上游，**并如实标注未闭环**。
4. **互斥通道不要异步化**：优先级链靠同步顺序成立，异步化会造成优先级反转。
5. **同一功能面既可能在宿主命令目录里、也可能在插件贡献里 —— 前者失败会连坐后者**，因为
   `candidates()` 在合并前 await。
