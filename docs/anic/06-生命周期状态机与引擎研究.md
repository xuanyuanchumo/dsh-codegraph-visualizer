# ANIC 插件：DSH 生命周期、状态机与引擎研究

## 1. Cordis 生命周期权威语义（ANIC 必须服从的宿主事实）

来自升级研究报告 §3.1（cordis 4.x 源码级确认）：

| API | 语义 | ANIC 用法 |
|---|---|---|
| `ctx.effect(setup, label?)` | 注册副作用，setup 的**返回值即 disposer**，随本 fiber 卸载时调用 | 所有状态机/监听/定时器/账本句柄的唯一注册通道（03 文档 §2.3） |
| `ctx.plugin(child)` | 挂子插件 fiber；父卸载时子递归 dispose，也可提前单独 dispose | 把"每次 cycle 的执行上下文"挂成子 fiber：cycle 结束/熔断时 `dispose` 该 fiber，天然回收该 cycle 的全部资源 |
| `ctx.on(event, cb)` | 订阅自动随 fiber 清理 | 门禁事件订阅（gate.arrived 等）不用手工退订 |
| `fiber.dispose()` | **递归**清理整棵子树 | 熔断降级时整棵丢弃"自主执行树"（L4 agent 循环的子 fiber），只留状态机/账本主干 |
| 定时器 | 必须在 effect 内创建，否则无人回收 | cycle 轮询/撤销窗口倒计时/补丁度量期计时器全部在 effect 内 |

**三条推论（设计决定）**：
1. **cycle = fiber**：`CycleRunner` 用 `ctx.plugin()` 挂每个 cycle 的运行时子树；熔断 8 条件之一命中 → `fiber.dispose()` 递归回收 → 主干状态机降级。这与技能"先修复后降级"哲学同构——降级不是状态切换，是**生命周期裁剪**。
2. **状态机主干比 cycle 长**：StateMachine/Ledger 挂在插件根 fiber（随插件启停），cycle 子树挂在其下——"进程内状态机、fiber 内执行"两层生命周期不得混淆（否则出现 dispose 竞态，见本仓库 disposeStore 系列教训）。
3. **同步 vs 异步 disposer 是两种契约**：升级报告 §3.2——`ctx.effect` 返回**同步** disposer，而 `ctx.connection.rpc.handle` / `intercept` / `fetch.register` 返回 **async disposer**。ANIC 的 HTTP 面若用 async disposer，必须在 async IIFE 内 await 收集，禁止当作同步 disposer 塞进同一数组（会得到未 settled 就被丢弃的清理）。

## 2. 客户端插槽生命周期（可视化面的存活边界）

来自升级报告 §3.3 客户端插槽树 + 兼容矩阵 §4：

```
root → main → conversation.session → conversation.view        ← ANIC 顶部标签挂这里
                  ├→ conversation.session.header / composer / composer.bar
                  └→ conversation.chat.node → tool.call.toolview
     → rightbar.session → sidebar.right.pane.tab (+title/guide/menu.item)  ← 审批卡增强位（gen2 探测）
     → shell.overlay                                           ← 熔断全屏警示（可选）
```

**核心规则**：子插槽仅在父挂载时存在 = **单一生命周期单元**。`conversation.view` 挂在 `conversation.session` 下——意味着 ANIC 标签**只在会话面板存在时存活**（会话切换/关闭 → 标签随父卸载）。

对 ANIC 的设计约束：
1. 标签内的 Zustand store **必须订阅父插槽卸载**：会话关闭时保存"视图状态快照"到 sessionStorage（轻量），重开时恢复；工作流**数据**永远以 `.cycles/` 文件为准（store 只是投影，不是真相——03 文档 §9 已定）；
2. 审批卡增强位（userQuestionPanels）缺席时静默回落标签内呈现——**gen2-only 面不得写进主路径**（兼容矩阵 §3：只有 pluginNavigation/userQuestionPanels 是 gen2-only 标记）；
3. 客户端生命周期与宿主进程**互相独立**：宿主重启后客户端标签可能仍挂着旧 SSE/事件流——所有事件回调必须携带 `runId`（cycle 运行代际），陈旧 runId 的事件丢弃（复用本仓库 expandGeneration/astRequestSeq 单调令牌模式）。

## 3. ANIC 自身的状态机研究（三层嵌套状态机）

ANIC 实际上需要**三个状态机**，彼此生命周期不同、通信只经账本：

| 状态机 | 生命周期 | 状态空间 | 持久化 |
|---|---|---|---|
| **M1 工作流图状态机**（节点级） | 插件全程（跨 cycle） | 每 Play/Gate 节点 ∈ {pending, running, awaiting-gate, done(done_status), blocked} | workflow-state.json + workflow-graph.yaml |
| **M2 门禁账本机**（记录级） | 永久（append-only） | 记录类型 {gate.passed, gate.rejected, patch.applied, patch.reverted, autonomy.changed, breaker.tripped} | gates/ledger.json 哈希链 |
| **M3 自主级机**（会话级） | 会话/撤销窗口 | {L1..L4} × {normal, breaker-tripped, reverted-window} | trust-state.json + 账本 |

**关键交互规则**（防止三机漂移成三个真相）：
- M1 的任何状态迁移**必须由 M2 的一条已验证记录驱动**（advance 消费账本——03 文档 §3.x 数据流）；
- M3 的任何迁移**必须写入 M2**（autonomy.changed / breaker.tripped 记录），撤销窗口回退也写（autonomy.reverted）；
- M1/M3 是 M2 的**纯函数投影**：给定完整账本 + 初始图，三机的当前状态可完全重建（这就是"崩溃恢复 = 重放账本"的算法基础，见 05 文档 §4）。

### 3.x 迁移合法性矩阵（workflow-state.mjs 规则的形式化）

`advance(node, record)` 合法当且仅当**全部**成立：
1. `record.gate === node.gate`（门匹配）；
2. `record` 在账本链上且 hash 验证通过（链匹配）；
3. `node.status !== done_status`（不重复推进）；
4. 存在指向 node 的 trigger 边，其源节点 done_status 已达成（触发边已批准）；
5. record.type ∈ 该门允许的记录集（gate.passed；patch/autonomy 记录**不得**推进工作流节点）。

违反任一条 → 拒绝并写 `advance.rejected` 诊断记录（**不进**账本主体，进独立诊断日志——账本只留权威事实，拒绝尝试是可观测性不是事实）。

### 3.y ANIC 特有研究点：状态机与 fiber 的竞态

- 熔断 `fiber.dispose()` 与进行中的 `advance()` 并发：dispose 先于 advance 完成 → advance 必须检查 fiber 存活性（canceled 检查），否则"账本已写、状态未推"的半迁移。对策：**账本写入与状态推进入同一个临界区**（Ledger.append 返回前不 emit），半迁移不可能发生——append 成功但进程崩溃时由重放账本恢复（05 文档 §4.3）；
- 撤销窗口（M3）与补丁度量期并发：撤销必须赢（04 文档 M5 纪律），用单一 governor 锁（进程内 async mutex）串行化 M3 变更。

## 4. 引擎研究：ANIC 需要哪些引擎、各活的多久

| 引擎 | 职责 | 生命周期 | 宿主依赖 |
|---|---|---|---|
| StateMachine 引擎 | §3 M1 的驱动器 | 插件根 fiber | 无（纯 TS + 文件） |
| Ledger 引擎 | 哈希链 append/verify/重放 | 插件根 fiber | 无 |
| GateBroker 引擎 | 证据包组装 + 双通道汇聚 | 插件根 fiber | ctx.webServer / ctx.tools |
| CycleRunner 引擎 | 单 cycle 的 L4 操作链执行（SKILL.md L4 链） | **每 cycle 一个子 fiber**（ctx.plugin） | ctx.tools（eval-run 等工具） |
| TrustModel / AutonomyGovernor | 信任分 + 自主级动态升降 | 插件根 fiber（跨 cycle 跨会话） | 无 |
| PatchEngine | 过程补丁全生命周期 | 插件根 fiber + **度量期计时器**（effect 内） | 无 |
| ReviewEngine | LLM 评审 + 启发式回落 | **调用点惰性**（无 apply() 快照）；`'llm'` 走增量 `ctx.inject` 接入，不进硬 `inject` | 宿主 `ctx.llm`（**M0-② 已证实**）或 MCP 外部循环 |
| BandDetector | Western Electric 规则漂移检测 | 按 cycle 调用（无状态函数） | band-history.json |

**结论**：ANIC 引擎族里只有 CycleRunner 是短命的，其余全部是长命主干；ReviewEngine 特殊——它**没有自己的生命周期**，挂在每次调用的调用点（这是能力探测纪律的自然结果：探测只 ON 不 OFF，快照禁用）。

## 5. DSH 破坏性变更研究（ANIC 视角的重读）

### 5.1 三层兼容架构（直接移植，升级报告 §7.1）

```
HostVersionDetector（检测层）→ HostVersionInfo{generation: gen1|gen2|unknown}
    ↓
FeatureFlags（开关层，12 位三套表 gen1/gen2/unknown）
    ↓
ApiCompatLayer（API 层）→ ToolNameMapping + fallback 链 + resolveToolName/isToolAvailable/getAvailableToolName
```

ANIC 移植时的**泛化决定**：本仓库三层的"能力清单"是 codegraph 工具名；ANIC 的对应物是**流程工具名 + 宿主 UI 面**两类：
- 流程工具面（anic_*）全代自有，无 fallback 需求；
- 宿主 UI 面（conversation.view 跨代一致 / userQuestionPanels+pluginNavigation gen2-only / slots 全代）→ fallback 链只有一层：gen2 增强缺席 → 标签内降级呈现。

### 5.2 ANIC 必须继承的版本纪律（基线 §6-§7 实测结论）

1. **DSH 无版本 API**：`detectFromContext` 4 候选全 undefined，真实 0.2.0-rc.2 宿主判 `unknown`（日志 `host version unknown, using conservative flags`）→ 运行时行为**不得以世代为门**（本仓库 triggerBackgroundBuild 的假阴性教训）：ANIC 的 gen2 增强（审批升级/多工作区）全部用 `ctx.get(key,false)` 调用点判定，FeatureFlags 降级为 `/status` 诊断字段；
2. **探测只开不关**：apply() 开头探测时兄弟插件可能未挂载（基线 §6 探测时机）→ ANIC 探测器对 any 能力只允许从 false→true；
3. **unknown 保守扣留高风险**：升级报告 §7.4——unknown 按 gen2 基线但扣留 `incrementalBootstrap` 级高风险特性；ANIC 对应物 = unknown 时**扣留 L4 自动链**（默认 L2），这是版本未知时的安全映射；
4. **peer 即承诺**：ANIC 实测**不声明** `@deepseek-ai/dsh*` peer（无该字段 ⇒ 兼容门必过）；父工程 dsh-codegraph-visualizer 的 peer 于 cycle-92 抬窗为 `^0.2.0-rc.2||^0.3.0-rc.2`，`engines.dsh` 与 DSH_SUPPORTED_RANGE 逐字相等并由测试钉死（其兼容矩阵 §6.2-§6.5）；cordis peer 故意宽 `^4.0.1` / devDep 严 `^4.0.4`；
5. **死声明删除优于补装**：ANIC 的 peer 只声明真正 import 的包（tools/llm/sessions 面），禁止"README 提过就声明"（兼容矩阵 §2.3 幻影教训）；
6. **前置插件按真实贡献判定**（基线 §7.6）：F13 深链判定 codegraph-visualizer 在场 = 检测其**真实注册的工具名**（不是猜名字）。

### 5.3 生命周期相关的破坏性风险与缓解（升级报告 §7.4 + ANIC 增量）

| 风险 | ANIC 增量缓解 |
|---|---|
| gen2 正式版与 rc.2 API 漂移 | 服务面探针 + fallback 链；不静态假设任何键存在 |
| async disposer 与 sync disposer 混用 | §1 推论 3：两类 disposer 分数组管理，async 一律 await 收集 |
| 子插槽随父卸载（会话关闭杀标签） | §2 设计约束 1：视图快照轻持久化，数据以文件为真相 |
| 插件更新/重载时旧账本句柄未释放 | Ledger 引擎的 disposer 负责 fsync+关闭文件句柄；重载后从账本重放恢复（05 文档 §4.3） |
| 桌面端 DOM 标记晚于 apply() | PlatformProbe 模式：每次调用重读 DOM + observeHostPlatform 通知 |
| node:sqlite IN 参数上限 | 账本分页查询按 MAX_IN_PARAMS 分批 + 内存切片 |
| peer 门比适配器模型更保守（0.4 模型支持但 peer 拒绝） | 文档如实记录语义漂移（兼容矩阵 §6.3），peer 收窄是显式决策非疏忽 |

## 6. 九条红线对照（DSH 规范合规自检，升级报告 §3.4）

| 红线 | ANIC 合规设计 |
|---|---|
| 注册即 effect | 全部注册在 ctx.effect 内，disposer 不丢弃（§1） |
| waterfall 委托 | 工具调用失败链：anic 工具 → MCP 垫片 → 启发式，逐级委托不吞错 |
| Branded ID | CycleId/GateId/PatchId/RecordId 全部 branded type（沿用本仓库 NodeId 纪律） |
| 声明合并事件 | dsh-anic/* 事件名走命名空间前缀，类型走 interface 声明合并扩展 |
| ESM only | type:module + .ts 扩展导入 |
| Host-Client 隔离 | tsconfig.host/client 分编译；共享类型入 shared/ |
| 能力缝三角色 | 每个 gen2-only 能力三件套：探测器 + 降级路径 + 诊断暴露 |
| 配置显式化 | cordis.patch.yml 显式 config（03 文档 §2.4），无魔法默认 |
| disposer 不丢弃 | 防御式收集 + typeof 检查 + async/sync 分组（§1） |

## 7. 研究结论（对 03 架构的三处修订指令）

1. CycleRunner 改为 `ctx.plugin()` 子 fiber 形态（§1 推论 1），熔断降级 = fiber.dispose() 生命周期裁剪；
2. 三状态机（M1/M2/M3）明确写入架构文档，通信只经账本、M1/M3 是 M2 纯函数投影（§3）；
3. HTTP 面 async disposer 单独管理；标签视图快照轻持久化；事件携带 runId 单调令牌（§1/§2）。

这三处已同步进 [03-架构设计草案.md](03-架构设计草案.md) 对应章节；数据结构与算法的深度展开见 [05-数据结构与算法设计.md](05-数据结构与算法设计.md)。
