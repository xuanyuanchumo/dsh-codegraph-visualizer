## 1. 研究背景与问题

用户核心问题：**是否应该逐步将项目技能全面的由技能插件原生实现——各流程插件化后拥有专属的流程状态流转机与对应的模块引擎？**

- 本技能插件主要用于给 DSH 的大模型开发项目时调用（调用时可视化透明化插件化自主化）
- 可通过大模型进行自举和开发人员查阅管理
- DSH 宿主下限版本不变定为 dsh-v0.2.0

## 4. 自举架构评估：是否全面插件化？

### 4.1 当前架构

```
项目技能（.dsh/skills/ai-native-iteration-cycle/）
  ├── 15 业务脚本（canonical implementation）
  ├── SKILL.md + references/ + templates/ + hooks/ + evals/
  └── Claude Code 侧运行

dsh-anic 插件
  ├── assets/skill/（63/63 字节相同副本）
  ├── src/host/（宿主集成层）
  │   ├── runtime/（stateMachine + cycleRunner + ledger + segmentedLedger + stackProbe）
  │   ├── evolution/（autonomyGovernor + bandDetector + fixLoop + orgStatus + patchEngine + trustModel + truthAudit）
  │   ├── governance/（archiver + budget + factBaseVerify + hitlAudit + planSync + prune + sweep）
  │   ├── llm/（multiAgentGate + reviewEngine）
  │   ├── selfBootstrap.ts（自举状态机：IDLE→EVALUATING→GATE_CHECKING→FIXING→VERIFYING→CONVERGED/EXHAUSTED）
  │   └── dualBootstrap.ts（双向自举：plugin + skill 互评）
  ├── src/client/（可视化层：WorkflowGraphPanel 六域分区图）
  └── 10 DSH 工具（anic_evaluate/iterate/gate_check/bootstrap/snapshot/self_check/hitl/install/status/skill）
```

### 4.2 评估结论：**是，应逐步全面插件化，但保留脚本作为规范实现层**

**理由**：

1. **脚本作为规范实现层**（single source of truth）：15 个业务脚本在 Claude Code skill 模式和 DSH 插件模式下共用，零分叉。全面插件化不意味着重写脚本，而是让插件成为脚本的**原生调用面 + 状态跟踪 + 可观测性层**。

2. **各流程拥有专属状态流转机**：当前 selfBootstrap.ts 是单一状态机跟踪整个插件。应改为**每流程一个状态机实例**——每次 anic_skill 调用创建一个 FlowTracker，跟踪 INVOKING → RUNNING → DONE/FAILED/TIMEOUT，持久化到 .cycles/ 供审计。

3. **模块引擎已就位**：evolution/（7 文件）、governance/（7 文件）、llm/（2 文件）、runtime/（5 文件）四个模块引擎已存在，应连接到脚本调用的输出解释和状态转移驱动。

4. **大模型自举路径**：selfBootstrap.ts → eval-runner.mjs → gate-check.mjs → auto-fix-loop.mjs 的自举链已设计，但需**实际连通**——当前 selfBootstrap 的状态转移是手动的，应改为自动调用 eval-runner 获取分数、gate-check 获取门禁判定。

5. **开发人员查阅管理**：anic_status + anic_snapshot + WorkflowGraphPanel 已提供可视化查询。应增加 FlowTracker 的实时状态查询能力。

### 4.3 架构演进路线图

| 阶段 | 目标 | 关键变更 |
|---|---|---|
| **M10-a** | 每流程状态跟踪 | 新增 FlowTracker：每次 anic_skill 调用创建独立状态机实例，持久化到 .cycles/flow-tracker.json |
| **M10-b** | 自举链连通 | selfBootstrap 自动调用 eval-runner + gate-check，状态转移由脚本输出驱动 |
| **M10-c** | 模块引擎接入 | evolution/governance/llm 模块引擎解释脚本输出，驱动状态转移和跨流程提案 |
| **M10-d** | 技能优先面 | 10 工具按技能域组织（evaluate/iterate/gate/bootstrap/skill），工具描述优化触发准确度 |
| **M10-e** | 持续学习层 | 记录每次调用的输入/输出/耗时/ verdict，形成可查询的调用历史 |

## 5. 本轮落地：M10-a 每流程状态跟踪

### 5.1 FlowTracker 设计

```typescript
type FlowStatus = 'INVOKING' | 'RUNNING' | 'DONE' | 'FAILED' | 'TIMEOUT';

interface FlowRecord {
  flowId: string;          // `${script}-${timestamp}-${counter}`
  script: string;          // 白名单脚本名
  workspace: string;       // 工作区路径
  args: string[];          // 调用参数
  status: FlowStatus;      // 当前状态
  startedAt: string;       // ISO 时间戳
  endedAt?: string;        // 完成时间戳
  exitCode?: number;       // 退出码
  stdout?: string;         // 截断输出（≤8000 字符）
  stderr?: string;         // 截断错误（≤4000 字符）
  durationMs?: number;     // 耗时
}
```

### 5.2 持久化

- 存储位置：`{cyclesDir}/flow-tracker.json`
- 格式：`{ flows: FlowRecord[], counter: number }`
- 原子写入（fs-safe.ts atomicWriteFileSync）
- 容量上限：保留最近 200 条（超出滚动淘汰）

### 5.3 可观测性

- `anic_status` 工具增加 `flows` 字段：最近 N 条流程记录
- `anic_snapshot` 工具增加 `flowTracker` 快照
- WorkflowGraphPanel 可选展示活跃流程

## 8. 结论

dsh-anic 应逐步将项目技能全面由技能插件原生实现，核心路径是：

1. **保留 15 脚本作为规范实现层**（零分叉，Claude Code + DSH 共用）
2. **每流程专属状态流转机**（FlowTracker，M10-a 本轮落地）
3. **自举链连通**（eval-runner → gate-check → auto-fix-loop 自动驱动，M10-b）
4. **模块引擎接入**（evolution/governance/llm 解释脚本输出，M10-c）
5. **技能优先面 + 持续学习**（M10-d/e）

与三大标杆对比，dsh-anic 的独特优势是**可视化六域分区图 + 双向自举 + truthAudit 安全审计**；主要差距是**自举链未连通 + 无持续学习层**，M10 路线图逐步消除。
