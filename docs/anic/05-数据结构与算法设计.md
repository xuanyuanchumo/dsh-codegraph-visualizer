## 1. 数据结构选型总表

> **v1.1 补充**：账本物理布局（分段 JSONL + head.json）、v2 记录形状（证据外置 + 幂等键）、索引与归档结构详见 [08-产物规模与生命周期治理.md](08-产物规模与生命周期治理.md)。本表仍是**逻辑结构**的选型依据。

| 数据 | 结构 | 关键决策 | 被否掉的替代 | 不变量（= 测试点） |
|---|---|---|---|---|
| 工作流图 | 有向图（CSR 邻接表：扁平数组 + offset） | 渲染与可达性分析都要 O(V+E) 遍历 | 邻接矩阵（稀疏图 8× 内存）、对象 Map（迭代顺序不稳，图布局会飘） | 每条 trigger 边源节点存在；节点 id 唯一；无自环（除显式 sub_gate） |
| 门禁账本 | append-only 哈希链（数组 + tail 缓存） | 崩溃恢复 = 重放；篡改可检测 | 可变 JSON 树（无法证明未被改写）、SQLite 表（外部依赖 + 顺序性弱） | prevHash 链式正确；hash = canonical(record‖prevHash)；永不原地改写 |
| 工作流状态 | 账本的**纯函数投影**（不独立持久化） | 消除第二真相 | 独立 workflow-state.json 作真相（技能现状，会与账本漂移） | 同账本重放两次结果相同（幂等） |
| 信任状态 | 定长桶 + 滞回计数 | O(1) 事件更新，文件小 | 时序全量（文件膨胀）、滑动窗口数组 | 降分系数 > 升分系数；同向 N 次才生效 |
| 补丁提案 | 队列 + 参数指纹索引 | 指纹去抖（30 天 2 次 revert → 冻结） | 无指纹（重复提案互相打架） | 同指纹并发提案串行；revert 先写记录再改文件 |
| 评估维度 | 注册表（有序数组 + 权重 Map） | 顺序即执行顺序，权重可进化 | 纯 Map（JSON 顺序不保证） | 每维有 evaluator 实现或显式 disabled；权重 ∈ [0,1] |
| 时间线 | 倒排索引（cycleId → 记录区间） | 76-cycle 量级毫秒级 | 全表扫描（M5 后十万级会退化） | 每个 gate 记录可反查 cycle |
| 会话视图状态 | sessionStorage 快照 | 标签随会话卸载（06 §2） | 内存（会话切换即丢） | 快照可丢，数据不可丢（真相在文件） |

## 2. 工作流图（`workflow-graph.yaml` → 图模型）

### 2.1 节点与边类型

```ts
type NodeId = string & { readonly __brand: 'AnicNodeId' };     // branded，防 GateId/NodeId 混用
type GateId = string & { readonly __brand: 'AnicGateId' };
type PatchId = string & { readonly __brand: 'AnicPatchId' };

interface GraphNode {
  id: NodeId; kind: 'play' | 'gate';
  produces: ArtifactRef[]; reads: ArtifactRef[];
  gate?: GateId; doneStatus?: string;          // gate 节点才有
  subGate?: GateId; subDoneStatus?: string;    // 子门（PR 合并等）
  triggers: NodeId[];
  autonomy: 'human' | 'auto';                  // 宪法：human 只能升不能降
}
```

### 2.2 CSR 邻接表（布局与遍历用）

```
nodes[] 顺序即声明顺序（稳定 → 布局可复现）
adjOffsets: Uint32Array(n+1)   // 前缀和
adjTargets: Uint32Array(m)     // 出边目标下标
inDeg:     Uint32Array(n)      // 入度，供拓扑可用性传播
```

- 选 CSR 而非 `Map<NodeId, NodeId[]>`：布局算法每帧遍历出边，CSR 缓存友好且分配零抖动；`Map` 方案在本仓库 Cytoscape 侧已验证过对象 Map 的迭代顺序问题（图布局漂移）；
- 布局稳定性沿用本仓库教训：**随机化布局不可固定**（cytoscape 无 randomSeed）→ ANIC 图用确定性布局（分层 + 节点序号做 tie-break），保证同一 workflow-graph 每次渲染位置一致（这直接决定视觉回归基线能否成立）。

### 2.3 可达性/阻塞传播算法（"什么被阻塞"）

```
available(n) = n.done 或 (kind=='gate' 且 (n.subGate 已过 或 无 subGate))
propagate():  // 从所有 available 出发沿 triggers 做 BFS
  queue ← 所有 available 节点
  while queue 非空:
    n ← pop
    for t in adj(n):
      if blocked[t] ≠ BLOCKED_BY_KNOWN: blocked[t] = upstream_unmet(adj(t)) 标记
```

复杂度 O(V+E)；76-cycle 项目 V≈80、E≈90，单次 <1ms，无需增量缓存。若图扩展到千级（多分支并行），引入**脏标记增量传播**（仅从状态变更点重跑 BFS）。

### 2.4 环检测（配置错误早报）

DFS 三色标记（white/gray/black），发现 gray 边即报环并指出环路；**加载期即拒绝带环的图**——技能护栏"边只自动化到门为止"在拓扑上意味着必须是 DAG，环是配置错误而非可运行状态。

## 3. 门禁账本（哈希链）

> **⚠ 存储布局已升级**：本节描述**逻辑记录结构与哈希规则**；物理存储从 v1 的单文件 JSON 数组改为**分段只追加 JSONL + head.json**（治 O(n²) 重写，实测 10k 条 ≈ 44 GB 累计写入），详见 [08-产物规模与生命周期治理.md](08-产物规模与生命周期治理.md) §3.1。逻辑规则不变，物理布局变。

### 3.1 记录结构

```ts
interface LedgerRecord {
  seq: number;                 // 单调递增，重放游标
  type: 'gate.passed' | 'gate.rejected' | 'patch.applied' | 'patch.reverted'
      | 'autonomy.changed' | 'autonomy.reverted' | 'breaker.tripped';
  ts: string;                  // ISO8601 UTC（技能现有格式）
  cycleId?: number;
  gate?: GateId; artifact?: string; commit?: string; approver?: string;
  evidence?: string;
  patchId?: PatchId; before?: string; after?: string;   // 补丁记录
  autonomy?: { from: AutonomyLevel; to: AutonomyLevel; trust: number; reason: string };
  prevHash: string; hash: string;
}
```

**v2 记录形状（证据外置，M2 定死 —— 宪法条款 7）**：

```ts
interface LedgerRecordV2 {
  version: 2;
  requestId: string;           // 幂等键（08 §3.3）：宿主 runId + 序号
  seq: number;
  type: 'gate.passed' | 'gate.rejected' | 'patch.applied' | 'patch.reverted'
      | 'autonomy.changed' | 'autonomy.reverted' | 'breaker.tripped';
  ts: string;
  cycleId?: number;
  gate?: GateId; artifact?: string; commit?: string; approver?: string;
  detailSummary?: string;      // ≤ 280 字符，硬上限（治实测 4.4 KB 单条极端值）
  detailRef?: string;          // 证据文件指针，相对 .cycles/ 根
  detailDigest?: string;       // sha256:…，内容寻址 → 证据去重（08 §3.2）
  evidenceBytes?: number;
  requestIdRef?: never;        // 保留位，禁止字段名漂移（避免两个近似字段名）
  prevHash: string; hash: string;
}
```

- **同链混代**：旧 v1 记录（无 `version`，含 4.4 KB 长 `detail`）与 v2 记录**同链共存**；verifier 按每条记录的 `version` 字段走各自 canonical 规则（无 `version` ⇒ v1）——这是「N2 零迁移」在记录级的落地；
- **为何在 M2 一次定死**：账本记录形状是**唯一无法事后修补**的数据结构（改形状 = 所有已写链 hash 全变 = 破坏性变更）；对比之下索引/归档/分页都是可增量补的运行期策略。

### 3.2 规范化哈希（**已实测钉死**，M0-③ 交付）

> **重要修正（M0-③ spike，2026-10-13）**：本节早期版本写的是「`sortedKeys` + `no whitespace` + `sha256(canonical + prevHash)`」——
> **这三条全部被实测否证**。以下是真实形式，由既有 56 条账本逐条反推得到（见 [spike/ledger-canonical-form.md](spike/ledger-canonical-form.md)）。

```
payload = JSON.stringify({ gate, gateName, result, detail, timestamp, previousHash })  // 固定键序，默认序列化
hash    = sha256(payload)   // hex；previousHash 是载荷中的一个字段，不是拼接后缀
```

- **固定键序，不是字典序**：实测字典序形式复现 **0/56**。顺序即载荷；
- **不做任何空白规范化**：去掉全部空白的形式复现 **1/56**——`detail` 等多行字段内部的换行/缩进**参与哈希**，任何"清理"立即断链；
- **不把 `hash` 放进载荷**（含 `hash` 整对象复现 0/56），也不把 `previousHash` 作为拼接后缀（它是载荷内字段）；
- **实测结论**：固定六字段键序 + `JSON.stringify` 默认序列化 → **56/56 复现**，`chainHead == 末条 hash`；链 **55/56**，唯一断点是 index 0 的 genesis（`previousHash` 非 null，历史形态）；
- **golden vector 已入库**（契约场景 K1，字面载荷 + 硬编码 hash `3d77e40f…`）：canonical 形式一经改动，K1 立即 HASH_MISMATCH——已用变异探针验证该守卫**确实能失败**（键序互换 → K1 + F1 双红）；
- **接续语义**：新记录的 `previousHash` 取既有 `chainHead`（而非重新 genesis）；genesis 断链以**显式 adoption 记录**处置，不隐式忽略；校验分 `verifyChain(strict)` 与 `verifyFromAnchor(anchor)` 两级；
- 拒绝"双链并存"方案（ANIC 自己的链 + 技能链）——那会制造第二真相，违反 N2。

### 3.3 校验与篡改检测

```
verify(records):  // O(n)，单遍
  prev = GENESIS
  for r in records:
    if r.prevHash ≠ prev: return FAIL(seq, 'chain-break')
    if sha256(canonical(r\{hash}) + prev) ≠ r.hash: return FAIL(seq, 'record-tampered')
    prev = r.hash
  return OK(tail=prev)

verifyIncremental(segments, head):  // O(1) 常规路径（分段布局，08 §3.1）
  读 head.json（O(1) 小文件）→ 只校验末段 JSONL → 返回 {ok, tail} 与 checkpoint 尾部比对
  // checkpoint 本身存于被校验链之外（head.json），损坏检测不依赖链内记录
  // 常规路径与总规模无关：10k 条账本仍只读末段 ≤1000 行
```

- 全链校验 500 记录 <500ms、10k 条 <1.5s（08 §4 预算，N3），逐段流式单遍足够，**不引入 Merkle 树**（收益只在十万级，而账本被人为压缩归档后规模有限）；
- **追加是 O(1) 写**：定位当前段（head.segCount）→ 追加一行 → 更新 head.json 的 chainHead → fsync。这与 v1 单文件数组的 O(n) 重写是**结构性差异**（08 §1.3：10k 条从 44 GB 降为 8.9 MB）；
- 篡改测试用 mutation probe：改一个字段 → verify 必须红（对齐本仓库 mutation 测试纪律：probe 需 `--exclude` 守护测试本身）。

### 3.4 崩溃恢复算法（"账本是唯一真相"的兑现）

```
recover(segments, head, graphFile):      // 分段布局（08 §3.1）
  if head.json 缺失:                     // 旧布局或首次运行
    legacy ← .cycles/gates/ledger.json   // 惰性迁移：流式转 seg-000000.jsonl + legacy/ 留存
  head ← readOrMigrate(head)
  if !verifyIncremental(segments, head): throw LedgerBroken   // 链断 → 停止自动推进，等人类裁决
  for seg in segments (seq 升序):         // 只读未 checkpoint 覆盖的段
    for line in seg:
      try records.push(parse(line))
      catch → quarantineLine(segNo, lineNo)   // 尾部半条 → 隔离不删除，可审计
  state ← project(records, graphFile)     // §4 重放
  head.json ← {chainHead: tail, segCount, entryCount, checkpointSeq}   // 推进 checkpoint
  return state
```

- 尾部半条记录（写入中断）**隔离而非删除**——可审计；
- 链断是硬失败：状态机停止推进，UI 红条提示并给出人工修复入口（N4 可靠性）；
- **惰性迁移是幂等的**：`head.json` 一旦存在就不再读 `legacy/`，重复打开不会二次迁移（M0-③ 反推交付的 canonical 规则保证 v1 段 hash 不变）。

## 4. 状态投影算法（三状态机的唯一计算入口）

### 4.1 重放（fold）

```
project(records, graph):        // 纯函数，无副作用，可测试
  nodes ← graph.nodes 初始状态（pending）
  trust ← TrustState.seed(records)      // 从账本种子化，历史一次算完
  autonomy ← config.autonomyLevel
  for r in records (seq 升序):
    match r.type:
      'gate.passed'      → nodes[r.gate.node] = done(r.gate.doneStatus)
                            trust.observe(role(r.gate), +Δ)
      'gate.rejected'    → nodes[r.gate.node] = blocked; trust.observe(role, −Δ)
      'patch.applied'   → patches[r.patchId] = APPLIED
      'patch.reverted'  → patches[r.patchId] = REVERTED; graph = restore(before)
      'autonomy.changed'→ autonomy = r.autonomy.to
      'breaker.tripped' → autonomy = L2（宪法：熔断优先于信任）
  return { nodes, trust, autonomy, patches }
```

复杂度 O(n)；n=500 时 <1ms。**幂等性**是它的核心性质：同一账本重放两次必等（测试：随机重排后重放两次比对）。

### 4.2 增量投影（运行中）

运行期不重放全链：Ledger.append 成功后返回新增记录，投影器对**单条**记录执行 fold 的 match 分支并 emit 事件。checkpoint 推进写入 `head.json`（每 50 条或每次 cycle 结束），保证重启只重读未覆盖的段。**注意**：分段布局下 checkpoint 不再是独立文件而是 head.json 内的一个字段（08 §3.1）——避免"账本真相在账本里、checkpoint 又在别处"的双源歧义。

## 5. 信任模型算法

### 5.1 滞回状态机（每角色独立桶）

```
observe(role, event):
  b ← bucket(role)
  b.pending ← event.direction            // '+' | '-'
  b.streak[b.pending] ← b.streak[b.pending] + 1
  b.streak[反向] ← 0
  if |b.streak[b.pending]| ≥ N (默认 3):
     b.score ← clamp(b.score + direction * (direction=='+' ? wUp : wDown))
     b.streak ← 0

wDown > wUp     // 非对称：错误成本 > 机会成本
```

- 为什么是**计数滞回**而非指数滑动平均：ANIC 事件稀疏（一个 cycle 几个门），EMA 需要大量样本才稳定；计数滞回 3 次即生效，与技能"连续 3 次修复失败即熔断"的既有语义同构（可对用户解释）；
- 冷却：一次升降后该桶 1 个 cycle 内不再评估（防止门密集的项目抖动）；`overall = Σ(role 权重 × bucket) / Σ权重`，权重可进化（F18）但**只在安全带内**。

### 5.2 自主级映射（信任 → 授权带内等级）

```
levelFor(trust, band):      // band = {floor, ceiling}，L4 永不在带内
  candidates = [L1,L2,L3].filter(l => l ≥ band.floor && l ≤ band.ceiling)
  pick 最大者 使 trustScore ≥ threshold(l)      // L1:0 L2:50 L3:75（可进化，带内）
  若 breakerActive → L2（熔断优先）
  若 不在带内 → 保持 floor（只报"信任已达上限，需人类授权进 L4"）
```

不变量：输出永远 ∈ 带内 ∪ {L2(熔断)}；任何单次事件不改变输出（滞回保证）。

## 6. 补丁引擎算法

### 6.1 提案 → 应用 → 度量 → 判定（状态机）

```
propose(p):     宪法检查(X8-X10) → 不合 → REJECTED(留痕) ；合 → PENDING
apply(p):       fingerprint = sha256(canonical(p.change))
                若 (fingerprint, 30d 内 revertCount ≥ 2) → FROZEN（需人类解冻）
                若 |change| ∈ 安全带 → APPLIED（原子写 + 账本 append）
                否则 → 路由到对应人类门（结构性/graph 变更 → spec_approve）
measure(p):     metricsPlan 对比 (applied 前后 N 个 cycle 的指标)
                keep → COMMITTED；degrade → 先 append patch.reverted，再恢复 before 文件
```

- **先写 revert 记录再改文件**：崩溃后重放账本能识别"已声明回退但文件未回退"，继续完成回退（N4）；
- 原子写：`写临时文件 → fsync → rename`（POSIX rename 原子），配合写前备份 `.bak`。

### 6.2 补丁依赖与冲突

```
conflicts(a, b):  a.change 与 b.change 触及同一 (surface, key) 且 未过期 → 冲突
  冲突处理：串行队列（同 key 一次只应用一个），后到者等前者 COMMITTED 或 REVERTED
```

无自动合并——两个补丁改同一参数时，合并语义无法证明正确，串行 + 人类可见是安全默认。

## 7. 评估与评审算法

### 7.1 维度注册表与聚合

```
runDimensions(ctx):   // 按注册表顺序执行，失败不中断（收集而非短路）
  results ← []
  for d in registry:                       // d = {id, kind:'E'|'Q', weight, evaluator, enabled}
    if !d.enabled: results.push(SKIPPED(d)); continue
    v ← d.evaluator(ctx)                   // LLM 或启发式（06 §4 调用点决策）
    results.push({ d, verdict: v.verdict, evidence: v.evidence, confidence: v.confidence,
                   source: v.source })      // source 必须落盘：'llm' | 'heuristic'（禁止假装 LLM，X4）
  score ← Σ w_d × confidence_d / Σ w_d    // 权重来自可进化配置（F18）
  return { results, score, weakest ← argmin(weight×confidence) }
```

- `weakest`（最弱维度）是进化引擎的主要输入：连续多轮同一维度最弱 → PatchProposal 指向该维度的权重/阈值/图结构（06 §5.4 的复盘回流）；
- 短路 vs 收集：**收集**——一次 eval 要给出全部 16 维视角，短路会丢掉诊断信息（本仓库"部分结果不得进完整缓存"同类教训的镜像：部分维度结果不是完整评估）。

### 7.2 控制带检测（band-detector 算法移植）

Western Electric 规则（连续 n 点超均值 ±kσ 等）在 ANIC 里作为**漂移信号**而非终止条件：输出 `driftSignals[]` → PatchProposal 来源之一（06 §5.4 修 P-2：band-history 从**不在自动化链上**变为被消费的派生序列，见 INV-18）。复杂度 O(n) 滑动统计，无需复杂时序库。

## 8. 并发与一致性

| 机制 | 规则 | 理由 |
|---|---|---|
| 单写者（single writer） | 只有 Ledger 模块能写 `.cycles/`；HTTP/工具/客户端全部经它 | 消除"两条路径写同一语义"（本仓库最高频缺陷模式） |
| 临界区 | `append(记录)` 全程在一个 async mutex 内，返回后才 emit | 杜绝"账本已写、状态未推"的半迁移（06 §3.y） |
| 幂等键 | 每条 v2 记录带 `requestId`；append 前查重，命中则返回既有记录 | 崩溃重试/事件重投/用户双击必然产生重复调用（08 §3.3） |
| 单调令牌 | 事件携带 `runId`（单调递增），客户端丢弃陈旧 runId | 防止旧 SSE/旧 cycle 的事件覆盖新状态（本仓库 expandGeneration 教训的通用化） |
| 文件监听 | 去抖 500ms + 内容 hash 比对（mtime 相同也要比） | 防止自写触发自循环（本仓库 watchDebounce 先例） |
| 只读快照 | 投影状态对象不可变；更新 = 新对象（React 友好） | 避免 UI 读到半更新状态 |

> **临界区之外为什么还要幂等键**：临界区只保证"一次调用内不交错"，而**重复调用本身是常态**（宿主崩溃重启后重投同一 requestId、用户双击、SSE 重连补发）。没有幂等键，账本里会出现语义重复的 gate.passed——而账本是唯一真相，重复即污染（08 §2 P-S10）。两者防的是不同的东西。

## 9. Schema 版本化与迁移（N10）

```
{ "schemaVersion": 2, ... }     // 所有工件顶层带 version
migrate(data):
  while data.schemaVersion < CURRENT:
     data ← MIGRATIONS[data.schemaVersion](data)      // 前向迁移链，逐版本
  if data.schemaVersion > CURRENT → 拒绝加载（写盘新格式的宿主读不了旧插件的工件）
  return data
```

- 迁移链为**显式函数数组**，每步一条测试（v1 fixture → v2 fixture 断言）；
- 账本最保守：**永不迁移既有记录格式**（哈希链格式变更 = 新链，与 06 §3.2 的兼容性反推绑定）——需要格式演进时用"新字段可选 + canonical 规则不变"；
- 未知版本 = 硬失败 + 明确报错（N2 零迁移的代价：插件必须能读旧数据，宿主不能读新插件数据是正常的方向性约束）。

## 11. 安全相关的数据处理

- **证据包不复制代码**：审批卡呈现的是 diff 摘要与报告摘要，正文按需从文件读（避免把敏感内容再落一份盘）。v2 记录进一步把 `detail` 正文外置为 `detailRef` + `detailDigest`（08 §3.2），链上只留 ≤280 字符摘要；
- **凭据不进账本**：`detailSummary` / 证据文件写入前经敏感模式过滤（`.env`/token/password 等，H1 同源规则），命中则截断为 `[redacted: <pattern>]` 并在记录里留 `redacted:true`——账本是审计物，不该成为泄密面。证据文件另有硬上限（>64 KB 拒绝并熔断，08 §3.2）；
- **路径越界**：`.cycles/` 读写全部经工作区根校验（拒绝 `../` 与符号链接逃逸），与本仓库 SecurityManager 的 workspace roots 纪律同构；`detailRef` 与归档移动同样受此约束（unmanaged 文件永不触碰）；
- **信任分不可被外部直接写**：只有账本事件驱动（HTTP 无直写 trust 的端点，只有人工覆盖工具，且人工覆盖本身写账本）。
