## 3. Tier A 结果与三项发现

### 3.1 发现 1（P0）：自主级变更**无法审计**

- incidents 声明 **2 次** `L4 → L3`；账本中对应记录 **0 条**；`config.yml` 至今仍是 **L4**。
- **诚实边界**：账本 genesis 断链（`previousHash` 指向已被裁剪的链头，M0-③ 已证），且两条事故时间戳**早于**账本首条 ⇒ 本仿真**只能判定"无法审计"，不能判定"从未记录"**——级别变更可能落在被裁剪的前缀里。
- **两种情形指向同一项设计确认**：级别变更（以及所有影响授权的动作）必须**每次都进同一条账本**，且**裁剪必须保留可审计路径**。这正是 [02](../02-需求分析.md) F33（效果即记录 Post-Verify）+ N2 与 [08](../08-产物规模与生命周期治理.md) §3.5（分层归档只移动不删除）+ INV-9 的设计动机——本轮第一次拿到**真实历史证据**说明它不是洁癖。

### 3.2 发现 2（P0 / 方法学）：**cycle 身份只存在于自由文本**，且这会把"解析假象"伪装成"账本缺陷"

同一份 56 条账本，两种归属方法给出**不同答案**：

| 归属方法 | 分组 | 门禁序列异常组 |
|---|---|---|
| ① 按 `detail` 文本里的 `cycle-N`（消费方最容易想到的） | 14 | **3 组**（cycle-78 只有 G0；cycle-79 只有 G0；cycle-80 = `G1,G0,G1,G2,G3`） |
| ② 按位置（追加顺序，`G0` 开启新 cycle） | 14 | **0 组**（14/14 严格 `G0→G1→G2→G3`） |

根因：**5 条 entry 的 `detail` 完全不含 cycle 号**；**15 条提到两个及以上 cycle**（如 G1 的文本「…登记流转至 cycle-80」会被误判给下一个 cycle）。

> **这是本轮最应当被记住的一条**：「门禁乱序」是**我的解析器**造出来的，不是账本的问题。
> 若我第一轮就把它写进报告，就会像 CLAUDE.md 里记载的那些事故一样——**把假象当缺陷，然后去"修"一个不存在的东西**。
> 正确动作是：并列两种方法 → 发现分歧 → 先判定哪种方法可靠 → 只把权威方法的结果当判据，并把分歧本身记为发现。

设计确认：进入 M2-b 的 **v2 记录形状必须携带结构化的 cycle/run 标识**（自由文本永远不是契约的一部分）。

**技能侧复核（谁该承担这条发现）**：扫描 `.dsh/skills/ai-native-iteration-cycle/scripts/**` 确认——**当前没有任何脚本从 `detail` 解析 cycle**：`lib/cycle.mjs:9/16/27` 解析的是**目录名**（`/^cycle-(\d+)$/` 作用于文件系统，权威来源），`archive-cycle.mjs:76` 的注释正记录着 iteration-4 删掉的 detail 解析 + 账本重写。所以 INV-21 今天在技能侧**成立**，它约束的是**未来 v2 账本形状**（必须显式带 cycle/run 字段）与插件投影（只读结构化字段），**不是**一项待修的技能缺陷——把它写成技能缺陷同样是"把假象当缺陷"。

### 3.3 发现 3：**门禁事件与人类门检查事件分处两个载体**，导致熔断史不可拼装

账本 56/56 全 PASS ⇒ 历史上的自主级回退**不可能由门禁结果触发**；而两条事故（H1 敏感文件、H3 门禁缺失）来自 **H1-H4 人类门检查**，只写入 `incidents/`。

- 于是"为什么降级"与"降级发生了什么"分处两处：门禁结果在账本，人类门结果在 incidents，级别变更又不在任何一处。
- 设计确认：**单一事件账本**（门禁事件 + 人类门事件 + 级别变更 + 补丁决定同链）——正是 [09](../09-结构优化与逻辑重构设计.md) 原则 3「一账本 + N 投影」与 F2 的语义。
