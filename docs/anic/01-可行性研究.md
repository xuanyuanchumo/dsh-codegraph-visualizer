## 1. 研究问题与方法

**研究问题**：把 `.dsh/skills/ai-native-iteration-cycle/`（下称 ANIC 技能）改造成一个**通用 DSH 插件**——任何项目、任何技术栈装上即用——实现**全自主自进化 / 自评审 / 可视化**的开发流程运行时：技术上有多少落地表面、技能本身还缺什么、按什么顺序补、值不值得做。

**方法**：三条证据链交叉验证，不采信任何"README 说有"的面：
1. **技能本体取证**：直接读取 SKILL.md（297 行）、`scripts/` 16 个 .mjs、`references/` 15 篇；
2. **宿主面取证**：`docs/research/dsh-0.2.0-插件API权威基线.md`（§1-§7）与 `docs/research/dsh-多代API规范差异与兼容矩阵.md`（§1-§11）的源码级结论；
3. **真实使用取证**：本仓库 `.cycles/` 已产生 **57 个 cycle 目录（编号至 cycle-91，非连续）+ 56 条账本记录**（工件齐全：config.yml、band-history.json、incidents/、gates/ 账本、retrospectives/、tech-debt/），既证明需求真实，也暴露了技能在真实重度使用下的不完善处（§2.6）。

### 2.2 工作流形态：已经是机器可读有向图（关键杠杆）

`references/graph.md`（128 行）把 SDLC 定义为**有向图而非线性管道**，四类节点：Play（工作单元）/ Artifact（产物）/ Gate（人类判断点，唯一不可跳过）/ Trigger（门通过触发的有向边）。机器可读形态是 `workflow-graph.yaml`（graph.md:59 起），节点携带 `{id, type, produces, gate, done_status, triggers, sub_gate, sub_done_status}`，门携带 `{id, type:human, role, consult, hook}`。`workflow-state.mjs` 把它当活状态机：`status / advance / check --strict`；advance 拒绝三类非法转移，**不自动启动下游节点**。

运行时闭环：`intent.md→(接受)→spec.md→(批准)→plan.md→(批准)→代码+测试→(PR合并)→release→(授权)→监控→(控制带突破)→新 intent.md`。

> **裁决输入 ①**：工作流数据模型（有向图+状态机+审计账本）已存在且是声明式 YAML——通用插件不需要发明格式，任何项目的工作流都能用它声明。**这是通用化的最大杠杆**。

### 2.3 门禁与账本

收敛门 G0(Q1+Q5)→G1(Q7)→G2(Q2)→G3(Q3+Q4) 由 `gate-check.mjs --quality` 执行；`gates/ledger.json` 哈希链账本（`gate-ledger.mjs record --gate … --artifact … --commit … --approver … --evidence …`）；HITL H1-H4（`hitl-audit.mjs` H1 = git diff + 敏感文件名模式 + .gitignore 检查，失败即 circuit:true）。

### 2.4 自主级与熔断

L1（每步确认）→ L2（每产物）→ L3（仅检查点）→ L4（仅事后审计）；8 熔断条件（先修复后降级）：连续 3 次修复失败 / 门禁存疑 / 真实用户数据无隔离 / 破坏性不可回滚 / 性能 1 轮未恢复 / 人类要求降级 / 会话 >24h 或上下文 >85% / 重试 >10 或熔断 >3；降级由 `org-status.mjs` 驱动。

### 2.5 关键发现 A：所有"智能"环节是启发式拟真（GAP-1 证据）

逐脚本取证——**技能中没有任何一处 LLM 调用**：

| 脚本 | 表称能力 | 实际实现 |
|---|---|---|
| `multi-agent-gate.mjs`（596 行） | 5 门 × 3 智能体评审，信任度 ≥70% | `evaluateIntentGate` 统计中文关键词（问题/用户/目标 等）+ 字数 ≥50 + markdown 小节数；confidence = 关键词占比；trustScore = round(avg confidence×100)；`--auto-approve` 旁路 |
| `auto-fix-loop.mjs`（342 行） | 失败模式分析→根因诊断→修复 | 正则 `/失败[：:]\s*(\d+)/` 解析中文报告；max-retries 3 |
| `hitl-audit.mjs`（386 行） | H1-H4 审计 | 文件名模式 + git 命令 |
| `eval-runner.mjs`（473 行） | E1-E8/Q1-Q8 | config 正则 `match(/test_cmd:\s*"([^"]+)"/)` 真跑 test/lint/build（**真实执行**），spec/doc 检查是文件存在性启发式。**复评修正**：该正则所读文件是 `.cycles/cycle-config.yml`（`:52`），而 `init-workflow` 只创建 `.cycles/config.yml`（`init-workflow.mjs:56`）——于是**取不到命令**：`test_cmd` 缺失 → 测试维 FAIL，`lint_cmd`/`build_cmd` 缺失 → **`{pass:true,'…(skipped)'}`（`:71-72`/`:83`）即构建与静态检查维度恒 PASS**。见 §2.8 S-1 |

> **裁决输入 ②**：通用插件必须把评审/诊断环节接到真实模型能力；启发式降级为 LLM 不可用时的保底（与熔断哲学一致）。注意通用性含义：关键词启发式还**隐含中文假设**，对英文项目失真——LLM 化同时修复这个通用性缺陷。

### 2.6 关键发现 B：技能不完善清单（插件化必须补齐，GAP-6/7/8 证据）

真实重度使用（57 个 cycle 目录 / 56 条账本记录）+ 源码对照暴露的完善度缺口：

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| P-1 | **信任分是死端**：multi-agent-gate 产出 trustScore（≥70% 门），但没有任何机制把分数**累积**到下一次决策——每次评审都是重新掷骰 | mcp-server.mjs 工具清单无 trust 持久化；.cycles/ 无 trust-state 工件 | "自进化"没有状态基础 |
| P-2 | **band-history 不在自动化链上**（v1.2 更正：原表述"只写不读"不准确，`org-status.mjs:50/406` 确实读它）：band-detector 用 Western Electric 规则检测复杂度/性能漂移并写 `band-history.json`，但 **SKILL.md 的 L4 op chain 不含 band-detector**，于是 76 个 cycle 实测只有 **1 条**快照——控制带几乎从未被触发 | `band-detector.mjs:80-94` 读写同一文件；SKILL.md L4 链；`.cycles/band-history.json` 实测 1 条 | 漂移检测无法触发修复/降级 |
| P-3 | **复盘不回流**：retrospectives/ 与 tech-debt/ 工件会生成，但没有机制把复盘结论转成下一次 cycle 的计划约束或工作流调整 | SKILL.md L4 链中 org-status review 是终点 | 经验不积累，同样的坑反复踩 |
| P-4 | **自主级静态**：autonomy_level 是 config.yml 里的一个常量（本仓库实测 L4），不会随表现动态升降；SKILL.md 只有"人类要求"这条路径改它 | config.yml `autonomy_level: L4` | L4 无人值守风险敞口恒定，好表现不奖励、坏表现只熔断不调级 |
| P-5 | **评估维度硬编码**：E1-E8/Q1-Q8 与权重写死在脚本里，无法按项目类型调整（前端项目 vs 纯后端 vs 文档库需要不同侧重） | eval-runner.mjs 维度表内联 | 通用性受损 |
| P-6 | **非 Node 项目不友好**：eval-runner 靠 config 正则取命令，非 JS 项目手填易错；多处检查有 npm/Node 约定痕迹 | eval-runner.mjs 命令解析 | 通用插件必须做成 init 向导 + 多栈探测 |
| P-7 | **工件 schema 无版本**：ledger.json / workflow-state.json / workflow-graph.yaml 都没有版本字段，演化格式将破坏旧项目 | 全部工件文件 | 插件迭代的地雷，必须 v1 就加 version |
| P-8 | **多智能体评审是单视角拟真**：名义 3 agent，实际一个函数数关键词——没有真正多视角（对抗/红队/独立证据核查） | multi-agent-gate.mjs | LLM 化时需重新设计为真多角色 |

> **裁决输入 ③**：P-1..P-4 共同指向同一个结论——技能的"自进化"目前只有**数据痕迹，没有闭环机制**。这正是插件化要补的核心功能（动态自主进化，F16-F22）。

### 2.7 需求真实性

本仓库是首个重度用户：57 个 cycle 目录、56 条真实账本记录、真实事故（incidents/incident-2026-09-18T03-06-52-033Z.md）。`autonomy_level: L4` + `control_bands: disabled` 说明用户想要全自主但**技能给不了可控的全自主**（P-4：只能静态 L4 + 靠熔断兜底）——这正是动态自主进化的需求原点。

## 3. DSH 宿主面事实（可用的落地表面）

### 3.1 兼容与清单契约（能不能装）

- **唯一强制兼容门是 peerDependencies**（`@deepseek-ai/dsh*`），`engines.dsh`/`dsh.manifestVersion` 纯声明无人读取（兼容矩阵 §6.1）。**ANIC 实测状态（cycle-92 核对）**：`dsh-anic/package.json` **完全没有 peerDependencies 字段** ⇒ 兼容门必过（`dsh-anic/README.md:71` 亦如此记载）。父工程 dsh-codegraph-visualizer 的 peer 范围已于 cycle-92 抬窗为 `^0.2.0-rc.2||^0.3.0-rc.2`（gen1 降为容忍不承诺），可作为 ANIC 将来若声明 peer 时的对齐参考；
- 清单硬契约：main 可解析、`exports["./client"]` 缺失即 throw、`dsh.client.platform==='web'`、bundle.patch 类型受检、icon ≤256KiB、locale/{en,zh}.json `{meta:{title,description}}`（基线 §2、兼容矩阵 §7）；
- 无桌面平台：web/desktop 共 bundle（兼容矩阵 §5.1）。

### 3.2 Host 服务面（逻辑跑在哪）——全部有本仓库先例，模式可整体迁移到任何项目

- `inject=['tools','webServer','sessions']`（src/index.ts:30；workspaceRegistry gen2-only 刻意不注入、`ctx.get` 探测）；
- `ctx.tools.register(tool)` 返回 disposer，ctx.effect 内注册 8 个 graph_* 工具（src/index.ts:52-62）→ ANIC 工具面照此注册；**tools 面本来就是通用机制，与项目无关**；
- `ctx.webServer.register` HTTP 路由 + `ctx.emit` 事件先例（'codegraph-visualizer/prerequisite/status' 轮询，MAX_POLLS 6）→ ANIC 状态广播照此发 `dsh-anic/*`；
- conversation.view 槽位 = 顶部标签栏唯一权威来源，kind 'list' 多条目共存（基线 §1、兼容矩阵 §4）；sidebar.right.pane.tab 契约见兼容矩阵 §9；
- **SlotRegistry.register 必须保持原型方法**（兼容矩阵 §7 CRITICAL）。

### 3.3 LLM 能力面（自评审引擎）——**M0-② 已证实：存在且可达**

原先按**幻影对待**（本仓库全部 src/ 与 dsh-llm 的接触仅 `import { ToolCallId } from '@deepseek-ai/dsh-llm'`，src/tools.ts:4，类型层面无调用先例）。**M0-② spike 推翻了该判定**，双向证据齐备：

- **提供侧**：`constructor(ctx) { super(ctx, "llm") }`（`@deepseek-ai/dsh-llm/lib/index.js:1800-1802`）；活动 profile 的 base bundle 里 `- id: llm / name: '@deepseek-ai/dsh-llm'` 是真实装配行（asar `@deepseek-ai/dsh-base/cordis.patch.yml:34-35`，适配器 `:525-529`）。
- **消费侧**：官方三包的真实调用点——`dsh-session-title-llm/lib/index.js:226`、`dsh-compaction-basic/lib/index.js:323`、`dsh-experimental-auto-review/lib/index.js:415`；后者 `inject = ["approval","llm","permissionPresets","sessions","tools"]`（`:45-51`）是最同构的样板（LLM 替代人类审批 + 闭合 JSON 协议 + fail-closed）。
- 全 asar 扫描：12967 条目中 50 处 `ctx.llm` 命中、11 处调用点级，分布 12 个官方包。

细节与契约（`GenerateOptions` 字段、错误码、`purpose` 闭合枚举、`llm/stream` waterfall）见 [spike/host-llm-service.md](spike/host-llm-service.md)。**形态结论不变**：LLM 评审是**增益**而非主体，不阻塞裁决——① 工具/HTTP/可视化面不依赖 LLM；② 服务缺失或不可用时按错误码降级启发式；③ MCP 通道（15 工具）让宿主外 agent 循环照常驱动；④ **绝不把 `'llm'` 写进硬 `inject` 数组**，否则无适配器的宿主会让整个插件不激活。

### 3.4 多代兼容策略

- ctx 上无版本 API（基线 §6）→ only-ON 运行时能力探测、调用点决策；
- 代际判别唯一可靠信号：`pluginNavigation`/`userQuestionPanels` 为 gen2-only 标记；`sidebarRightTabs`/`slots` 跨代存在不能当标记（兼容矩阵 §3）；
- 本仓库 `src/shared/dshGeneration.ts` 的 DSH_GENERATION_PROBES 模型可整体移植为插件兼容层。

## 6. 备选方案对比与选型

| 方案 | 形态 | 优点 | 缺点 | 裁决 |
|---|---|---|---|---|
| A. 维持现状 | skill + 16 脚本 + MCP | 零成本 | 无 UI；拟真评审；无进化闭环；跨项目靠人肉拷贝技能目录 | 否 |
| B. 插件皮 + 脚本芯 | 插件只做 UI/状态展示，逻辑 execSync 调技能脚本 | 快；行为与 skill 一致 | 双份真相；进化/LLM 缺口原样；插件退化成皮肤 | 仅作 M1 过渡 |
| C. 通用插件完整化 | TS 重写状态机/账本/门禁为 Host 服务面；工件格式带 version 兼容 `.cycles/`；**账本物理布局一次定死**（分段只追加 + v2 记录形状）；LLM 评审增强层；**信任模型+过程补丁进化引擎**；产物索引/归档/预算；init 向导多栈 | 单一真相；事件驱动；可视化原生；**补齐技能全部 P-1..P-8 缺口**；产物增长不随时间退化 | 工程量最大 | **选 C，经 B 过渡** |

**选 C 决定性理由**：方案 B 把双份真相制度化（本仓库 CLAUDE.md 缺陷模式的复刻）；且 P-1..P-4 的进化闭环**只能**在持续运行的 Host 服务面里实现——脚本形态每次 execSync 都是无状态进程，天然做不了"累积信任、度量补丁、动态调级"。**这正是"插件化比技能形态强的本质理由"**。

**GAP-9 为什么不构成否决项**：产物规模问题的根因是**形状**（单文件数组 + 无界证据字段 + 每次调用必建目录），而不是宿主能力；形状在 M2-b 一次定死后，治理三件套（分段/幂等/归档）都是插件内自持逻辑，已由实测数据给出判别式（追加 N 条 ≤ N × 1 KB）。它反而**加强了方案 C 的理由**：脚本形态连"换布局"都要改 16 个文件并同时迁移既有工件。
