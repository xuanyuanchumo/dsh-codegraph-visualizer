## 0. 复评结论（先看这一节）

1. **01 的 GO 裁决不变，但前置条件必须加强。** 01 的判断是"技能能跑、缺的是进化闭环与产物治理"。复评推翻了"能跑"这半句：**技能的确定性门禁层当前处于"静默失效或直接不可运行"状态**——不是缺功能，是在特定现实条件下**不执行**，而且不报错。
2. 复评发现 **11 项结构性缺陷（S-1..S-11）**，其中 3 项达到正确性/安全级：
   - **S-1（P0）**：3 个核心脚本读的配置文件名，`init-workflow` 从来不创建 → `gate-check` 直接 `exit(1)`，`eval-runner` 的构建/静态检查维度**恒 PASS**（真实命令明明存在却读不到）。
   - **S-7（P0）**：自主级降级用**正则字符串改写 YAML**，且降级日志与事故记录**无条件写出**——正则没匹配上时，"已降级"的记录照样落盘。
   - **S-11（P1）**：未知维度/未知门禁标识**静默丢弃**（`--dimensions E9` 不报错）。
3. **这 11 项没有一项能被技能自己的测试面发现（S-3）**：`evals/evals.json` 是 5 条 prompt 触发评测、全部 `"files": []`，不执行任何脚本；`trigger-eval.json` 同理。技能有"评测"，但**没有一行执行契约测试**。这是 S-1 能在 76 个 cycle 里存活的真正原因，也是移植时最大的传染风险。
4. **根因不是"某处写错"，而是 5 个结构性根因（§3）**：同一个标识符有多个定义源、正则即接口、状态多副本、派生状态被当真相源、安全机制无执行契约。
5. 所以本轮交付的是：**目标结构**（§4 分层 L0-L5 + 七条结构原则）、**逐条改法**（§5 一张 S→结构改法→不变量→守卫 的对齐表）、**逻辑级优化**（§6 八项算法/判定改动）、**守卫与不变量清单**（§7）、**迁移路径**（§8）。对既有文档的修订影响列在 §9。
6. **对移植决策的直接影响**：技能不能"逐脚本搬运"。16 个脚本各自 loadConfig、各自解析 YAML、各自拼路径，搬运等于把 S-1/S-2/S-8 的**复发机制**一起搬进来。必须先落 §4 的契约层，再让每个能力变成契约层之上的一个纯函数或端口适配器。

## 2. 结构性缺陷清单

> 命名说明：本篇用 **S-n**（Structure）。与 [08](08-产物规模与生命周期治理.md) 的 **P-S1..P-S10**（规模失效模式）无关，与 [01](01-可行性研究.md) 的 **GAP-n**（能力缺口）是不同维度——GAP 说"缺什么功能"，S 说"现有功能的骨架错在哪"。

### 2.1 总表

| 编号 | 名称 | 严重度 | 类别 | 一句话 |
|---|---|---|---|---|
| **S-1** | 配置发现路径漂移 | **P0 正确性** | 常量重复 | 3 个脚本读一个永不存在的配置文件名 |

### 2.2 S-1 配置发现路径漂移（P0 正确性）

**【证据】**
- `scripts/init-workflow.mjs:56` — `[join(configDir, 'config.example.yml'), join(cyclesDir, 'config.yml')]`：唯一被创建的配置文件是 `.cycles/config.yml`；`:75-76` 打印的也是 `Config: .cycles/config.yml`。
- 读 **`.cycles/config.yml`**：`auto-fix-loop.mjs:21`、`hitl-audit.mjs:19`、`multi-agent-gate.mjs:20`、`mcp-server.mjs:48`、`org-status.mjs:97/154/591/612`。
- 读 **`.cycles/cycle-config.yml`**：`eval-runner.mjs:52`、`gate-check.mjs:20`、`band-detector.mjs:29`。
- 全技能 `rg cycle-config` = **4 命中**，且**三份参考文档与两份配置模板中 0 命中**——即这不是"文档写错了"，而是代码内部三对五的分裂。

**【机制】** 配置路径是**在 11 个文件里各写一遍的字符串常量**，没有解析器、没有常量表、没有契约测试。任一处写错都不会被任何东西发现。

**【影响】**（三种后果，按危险程度递增）
1. `gate-check.mjs:21-23`：文件不存在即 `console.error('No .cycles/cycle-config.yml found. Run init-workflow first.')` + `process.exit(1)`。**提示本身是错的**（init-workflow 不产生该文件），而后果是 **G0-G3 整套门禁不可运行**。
2. `eval-runner.mjs:53`：文件不存在即 `return ''`，随后：
   - `:58-59` 无 `test_cmd` → 测试维度 **FAIL**（在配置完全正确的仓库里）；
   - `:71-72` 无 `lint_cmd` → **`{ pass: true, output: 'No lint command configured (skipped)' }`**；
   - `:83` 无 `build_cmd` → **`{ pass: true, output: 'No build command configured (skipped)' }`**。
   
   即：**构建/静态检查类维度恒 PASS**。而本仓库 `.cycles/config.yml:11/13/14` 明明白白写着 `build_cmd: "pnpm run build"` / `lint_cmd: "pnpm run lint"` / `test_cmd: "pnpm run test"`——命令存在，只是**读的是另一个文件名**。
3. `band-detector.mjs:224`：`configContent ? getComplexityBudget(...) : 100` → 静默用默认预算 100，而不是配置里的 `complexity_budget`。**默认值兜底把配置错误伪装成正常行为**。

**【为何长期不可见】** 三条后果都是"看起来正常的输出"：门禁不可运行只在一类脚本上显现；构建维度恒 PASS 与"构建真的通过"在报告里长得一样；预算 fallback 的数字 100 是个合理值。且 S-3 保证没有任何测试会发现它们。

**【严重度】P0** —— 这是"门禁系统在最需要它的场景下失效"的经典形态，且失效方向是**放行**。

### 2.3 S-2 E1-E8 双词汇表（P0 契约）

**【证据】** 同一个标识符空间 `E1..E8` 有两套**完全不重叠**的名字：

| 来源 | E1 | E2 | E3 | E4 | E5 | E6 | E7 | E8 |
|---|---|---|---|---|---|---|---|---|
| **A 族**：`eval-runner.mjs:14-21`、`SKILL.md:125` | 意图对齐 | 规格符合 | 测试覆盖 | 代码质量 | 性能基线 | 安全检查 | 文档同步 | 回归完整性 |
| **B 族**：`references/evaluation.md:10-141`、`assets/config/config.example.yml:31-54`、本仓库 `.cycles/config.yml:31-54` | 功能覆盖 | 架构健康 | 技术债务 | 测试成熟度 | 性能与稳定 | 安全与可访问 | 创新差异化 | 多源对照增强 |

**并且 `references/quality-review.md:256-263` 的 Q→E 映射表是按 B 族写的**（"Q1 ↔ E1 功能覆盖"、"Q2 ↔ E4 测试成熟度"、"Q5 ↔ E2 架构健康"、"Q7 ↔ E3 技术债务、**E4 代码质量**"）——最后一行同时出现 B 族的"技术债务"和 A 族的"代码质量"，**映射表自身也混用了两套词表**。

**【机制】** 维度既是**配置项**（用户在 config.yml 里给 E1 起名 `功能覆盖`），又是**代码常量**（`DIMENSIONS.E1.name = '意图对齐'`），而**没有任何东西把两者对齐**。`config.yml` 的 `evaluation:` 段被写出来、被用户维护、被文档引用，**却从未被 `eval-runner` 读取**（它只读该文件的 `test_cmd` / `lint_cmd` / `build_cmd` 三个正则）。

**【影响】**
- 报告以 A 族名字输出（`eval-runner.mjs:328/338` 用 `DIMENSIONS[dim].name`），而用户的配置、验收文档、`evaluation.md` 的检查清单全部是 B 族 → **eval 报告无法与规格逐条对账**。
- 用户按文档传 `--dimensions E3` 意为"技术债务"（`evaluation.md:246` 就是这么举例的），代码执行的是"测试覆盖" → **静默语义错位**。
- G 门禁的维度归属（SKILL.md:146-149：G0=Q1+Q5、G1=Q7、G2=Q2、G3=Q3+Q4）说的是 Q 维，而 Q 维本身两套词表一致（`eval-runner.mjs:22-29` ↔ `SKILL.md:131-138` ↔ `quality-review.md:23-213`，仅标签长短有别）——**漂移只发生在 E 维**，这让它更容易被误判为"文字差异"。

**【机制本质】** 这是本项目 CLAUDE.md 已记录过的同一类缺陷："两个或更多份顺序/枚举列表**一定**会漂移，且漂移是静默的"。技能里恰好有一个反例可抄：`Object.freeze` 单源 + 源码级守卫测试（带反向自检）。

**【严重度】P0** —— 契约错位会让"评估"这件事本身失去意义，而评估正是这个技能的卖点。

### 2.4 S-3 无执行契约测试（P0 防复发）

**【证据】** `evals/evals.json` 全文 35 行：`skill_name` + 5 条 `{id, prompt, expected_output, files: []}`，全部是"用户这么问，技能该不该被触发"。`evals/trigger-eval.json` 同类。

**【机制】** 技能的"测试"考的是**技能是否被想起**，不是**被想起后是否算对**。16 个脚本 4,300+ 行没有一行被测。

**【影响】** S-1/S-2/S-11 这类"不报错、只算错"的缺陷天然免疫于任何非执行型测试。76 个 cycle 的实际运行也没暴露它们——因为**运行是人工驱动的**：人会在 `.cycles/` 里补文件、会在意报告好看，但不会去核对 `cycle-config.yml` 是否存在。

**【结论】** 移植时这一项必须**先补**，否则插件只是把同样的静默失效搬进宿主进程。守卫形态见 §7。

**【严重度】P0（防复发级）** —— 它不是缺陷本身，而是其余 10 项缺陷的**存活条件**。

### 2.5 S-4 门禁结果 5 副本（P1）

**【证据】** 一次门禁结论会被写到 5 个地方：

| # | 落盘物 | 写者 | 形状 | 可校验 |
|---|---|---|---|---|
| 1 | `.cycles/gates/ledger.json` | `gate-ledger.mjs:42-47` | `{entries[], chainHead}`，sha256 链 | ✅ 唯一有链校验 |
| 2 | `.cycles/gates/ledger.md` | （实测存在，41,670 B） | markdown 表 | ❌ |
| 3 | `cycles/cycle-N/审计日志.md` | `multi-agent-gate.mjs:469-476` **字符串拼接追加** | markdown 表 | ❌ |
| 4 | `cycles/cycle-N/test-reports/multi-agent-gate-report.md` | `multi-agent-gate.mjs:480-496` | markdown | ❌ |
| 5 | `.cycles/workflow-state.json` | `workflow-state.mjs:36/44` | JSON 状态 | ❌ |

且 `multi-agent-gate.mjs:471` 用一个**表头字符串 `| 时间 | 检查点 | 结果 | 详情 | 状态 |` 是否存在于文件中**来决定是"追加行"还是"补表头"——**表头即协议**。

**【影响】** 五个副本必然漂移（本项目 CLAUDE.md 的原话："多个副本一定会漂移，且漂移是静默的"），而**只有副本身份模糊时才有害**：当有人问"T 时刻门禁结论是什么"，答案取决于读哪一个副本。

**【结构根因】** 缺少"**一个追加型记录 + N 个纯投影**"的划分。markdown 报告本应是 ledger 的**投影**，现在却是**独立写者**。

**【严重度】P1** —— 在 [08](08-产物规模与生命周期治理.md) 里已相应决定"账本唯一真相 + 单写者"，本篇补上**投影必须可重算**这一半（§6.8）。

### 2.6 S-5 信任分由硬编码常量驱动（P0 决策质量）

**【证据】**
- `multi-agent-gate.mjs:211` `const trustScore = Math.round(avgConfidence * 100);`
- 而 `confidence` 的来源是**逐分支写死的字面量**：`:423` 0.9 / 0.2，`:432` 0.8 / 0.3，以及 `evaluateIntentGate` 里由**关键词命中比例**算出的分数。
- `:417-422` 的 `gatekeeper` 代理判据是 `allGatesPassed && ledgerExists`，`detail` 里那句 `'All gates green, ledger verified'` 中的 **verified 只是 `existsSync(ledgerPath)`**——**账本存在被当成账本完整**。

**【机制】** "全自主 + 信任度 ≥70% 自动批准"（[02](02-需求分析.md) F16 族的前置）其**唯一输入是脚本里的常数**。举证责任被反转了：不是"证据够不够所以信任"，而是"代码写了 0.9 所以信任"。

**【影响】** 三项后果：
1. `--auto-approve` 一旦开启，**批准与否由常量表决定**，与工件质量无关；
2. 信任分**不会因为证据变差而下降**（它没有感知证据的通道）；
3. "verify" 一词在报告里被用于**存在性检查**，会向人类灌输"已校验"的错误印象——这正是本项目 CLAUDE.md 记录过的"验证器可达 ≠ 验证值可达"的同族缺陷。

**【注】** `multi-agent-gate.mjs:156-207` 的"3 个 Agent"是关键词计数（中文词的 `includes` + 字数 ≥50 + markdown 小节数），本轮复评维持 [01](01-可行性研究.md) 的判断：**它不是多智能体评审，是关键词拟真**。这一点在 S-5 里被量化了：既然置信度是常量，那么"多 Agent"只贡献了**叙事**。

**【严重度】P0（决策质量）** —— 它决定"哪些变更会不被人类看一眼就通过"。

### 2.7 S-6 非原子写 + 多写者（P1）

**【证据】**
- `gate-ledger.mjs:42-47` `saveLedger`：`writeFileSync(ledgerPath, JSON.stringify(ledger, null, 2))`——**整文件重写，无临时文件 + rename，无锁**。
- `gate-ledger.mjs:49-80` `appendEntry`：`loadLedger` → push → 全量 `saveLedger`。**读-改-写三步之间没有临界区**。
- 至少 6 个脚本会读账本（`gate-ledger/hitl-audit/multi-agent-gate/org-status/archive-cycle/workflow-state`），2 个会写（`gate-ledger` 写，`workflow-state.mjs:44` 写自己的 state）。

**【影响】** 两个 cycle 并发、或 `org-status auto-fallback` 与 `gate-check` 同时跑，后写者覆盖先写者 → **哈希链分叉或丢记录**，而链校验只会在下一次 `verify` 时才报"hash 不匹配"，归因极难。

**【结构根因】** 状态写路径没有**单一所有者**。与 [08](08-产物规模与生命周期治理.md) §3.1 的分段只追加结合后，风险从"整文件覆盖"降级为"段内追加交错"，但**临界区仍然必须存在**（[05](05-数据结构与算法设计.md) §8 已登记；本篇 §7 把它升为不变量 INV-12）。

**【严重度】P1** —— 单机单 cycle 时不显现；一旦 L4 全自主（多个 cycle / 多个 worktree）就是必然事件。

### 2.8 S-7 自主降级用正则改写 YAML，且记录与效果解耦（P0 安全）

**【证据】** `org-status.mjs:590-597`：

```js
if (currentLevel === 'L4') {
  const configPath = join(projectDir, '.cycles', 'config.yml');
  if (existsSync(configPath)) {
    let content = readFileSync(configPath, 'utf-8');
    content = content.replace(/autonomy_level:\s*L4/, 'autonomy_level: L3');
    writeFileSync(configPath, content);
    console.log(`Autonomy downgraded: L4 → L3`);      // ← 无条件打印
  }
  // …:603-607 无条件写 incidents/incident-auto-fallback-*.md
  //   :606 事故正文含「| 事件 | 熔断自动回退 L4 → L3 |」「自主级别回退：L4 → L3」
  process.exit(2);
}
```

**【机制】** 三件事被拆成互不校验的三步：**改文件**、**打印**、**写事故记录**。打印与事故记录取的是**意图**（`if (currentLevel === 'L4')`），不是**效果**（正则是否真的替换了）。`String.replace` 在无匹配时**静默返回原串**，于是：

| 现实写法 | 正则是否匹配 | 实际自主级 | 事故记录 |
|---|---|---|---|
| `  autonomy_level: L4` | ✅ | L3 | "已回退" |
| `  autonomy_level: "L4"` | ❌ | **仍 L4** | "已回退" |
| `autonomy_level: L4  # 全自主` | ✅ | L3 | "已回退" |
| 被包在引号/数组/其他键名下 | ❌ | **仍 L4** | "已回退" |

**【影响】** 这是**安全机制（熔断降级）**的失效模式：系统在"它以为自己降级了"的状态下继续以 L4 全自主运行，同时留下一条声称已降级的审计记录。**记录与效果解耦**使问题不可审计——查事故记录只能看到"一切按设计执行"。

**【同族先例】** 本项目 CLAUDE.md："**'入口存在'不等于'入口可达'**"、"**一个 REVERT 写入的能力守卫是静默失效模式**"、"**降级默认必须拒绝，而不是承诺**"。S-7 是这三条合起来的一个实例，且落在**自主性**这个最需要保守的位置上。

**【结构改法】** 自主级不是配置文本，是**状态迁移事件**：必须走账本追加（`autonomy.downgraded`），且**写入后回读校验**，校验失败即失败并保持原级（§6.6）。

**【严重度】P0（安全）**。

### 2.9 S-8 正则即接口 / 中文文件名即接口（P1）

**【证据】** 脚本之间没有模块边界，通信靠三种隐式协议：

1. **YAML 用正则解析**（16 个脚本各写一遍）：`configContent.match(/test_cmd:\s*"([^"]+)"/)`（`eval-runner.mjs:58`）、`/lint_cmd:\s*"([^"]+)"/`（`:70`）、`/build_cmd:\s*"([^"]+)"/`（`:82`）、`/complexity_budget:\s*(\d+)/`（`band-detector.mjs:35`）、`/autonomy_level:\s*(L[1-4])/`（`mcp-server.mjs:55`、`org-status.mjs:103`）。
2. **测试报告用中文正则解析**：`auto-fix-loop.mjs` 用 `/失败[：:]\s*(\d+)/` 之类从中文 markdown 里抠失败数。
3. **中文文件名即 API**：`项目评估报告.md`（`gate-check.mjs:44`）、`审计日志.md` / `交付清单.md` / `非功能验证报告.md`（`multi-agent-gate.mjs:410-412`）、`任务清单.md`、`当前循环总规划.md`。

**【影响】**
- 正则方案**不认 YAML 语法**：`test_cmd: 'pnpm test'`（单引号）、多行字符串、注释掉的键、键名带前缀（`build.test_cmd`）都会静默失配——失败方式与 S-1 完全相同（读不到 → 兜底/跳过）。
- 值里出现 `"` 会截断（`[^"]+`）。
- 中文文件名 + 中文正则把**语言**变成了**接口**：任何 i18n（本项目强制"所有面向用户文本走 `t()`"）都会同时打断脚本间通信。对一个要成为**通用插件**的东西，这是直接阻碍。
- 无法复用：16 份解析器 = 16 份漂移面。

**【严重度】P1** —— 它不制造错误结论，但保证**错误结论迟早出现且原因多样**。

### 2.10 S-9 无条件脚手架（P2）

**【证据】** `init-workflow.mjs:36-48` 无条件 `mkdirSync` 8 个目录；`init-cycle.mjs` 同理无条件建八件套目录结构。实测后果见 [08](08-产物规模与生命周期治理.md) §1.1：**57 个 cycle 目录中 12 个完全为空**（cycle-5/17/18/25/26/33/34/37/39/42/43/54，其中 6 个还带空子目录），且技能的 `archive` 能力实测 0 次运行。

**【机制】** "创建"与"有内容"之间没有约束：目录在**意图**阶段创建，永远不因**从未发生**而回收。

**【结构改法】** 目录**惰性创建**（首次写入时建），并把"空目录"降级为 `anic_sweep` 只读报告中的一类发现（[08](08-产物规模与生命周期治理.md) §3.7）。**永不自动删除**（宪法条款 6）。

**【严重度】P2** —— 观感与索引噪声，不产生错误结论。

### 2.11 S-10 band-detector 不在自动化链上（P2）

**【证据】** SKILL.md 的 L4 op chain 为：`quick-validate + fact-base-verify + eval-runner → workflow-state check → 拆测 → eval-runner --dimensions → auto-fix-loop → gate-check --gate all --quality → multi-agent-gate → hitl-audit → org-status auto-fallback → org-status review → workflow-state advance`——**不含 `band-detector`**。实测：76 个 cycle 之后 `.cycles/band-history.json` 只有 **1 条**快照。

**【复评修正】** [01](01-可行性研究.md) 的 **P-2** 曾措辞为"band-history 只写不读"。**这条措辞不准确**：`org-status.mjs:50/406` 确实读它。准确表述是——**band-detector 不在自动化链上，因此控制带（Western Electric 规则）在 76 个 cycle 里几乎从未被触发**，快照数 1 即为证据。P-2 已按此更正。（注：P-4 是"自主级静态"，与 band-history 无关，勿混淆。）

**【结构改法】** 控制带是"维持阶段"的**触发器源**，应当并入 cycle 终点的固定投影（由账本派生的时序序列计算，见 §6.7），而不是一个需要人记得去跑的独立脚本。

**【严重度】P2** —— 它让一整类"缓慢退化"信号从未被采集。

### 2.12 S-11 未知维度/未知门禁静默丢弃（P1）

**【证据】**
- `eval-runner.mjs:369`：`dimsToRun = args.dimensions.split(',').map(s => s.trim()).filter(s => DIMENSIONS[s]);` → `--dimensions E9` 或 `--dimensions E1,E9` **不报错**，未知项被静默剔除；若全部未知，`dimsToRun = []`，`:379` 的循环体不执行，报告没有任何维度行，脚本仍正常结束。
- 对比：`multi-agent-gate.mjs:542-545` 对未知 gate **打印**报错并列出合法值（`Unknown gate: … Valid gates: …`），但随后 **`continue` 跳过**——若这是唯一被检门，`allResults = []`、`avgTrustScore = Math.round(0/0) = NaN`、`allPass` 保持 true、**`process.exit(0)`**（契约测试 B2 场景实测，旧版复现）。即"有报错"不等于"有失败"：它的实际效果比 eval-runner 的静默丢弃**更危险**（打印了错误却以成功收场）。**同一个技能里三种相反策略**（静默剔除 / 报错后照常成功 / 正确失败），证明这不是有意的设计决策，而是 16 个独立脚本的偶然产物。

**【影响】** "我加了 E9 维度"在报告里表现为"这项没显示"，与"这项通过了"难以区分。对**全自主**流程尤其危险：一个拼错的维度名会静默缩小评估面，而缩小后的评估更容易通过。

**【结构改法】** 统一为 **fail-loud**：未知标识符 = 非零退出 + 列出合法值（借用 `multi-agent-gate.mjs:542` 已有的正确形态作为范式）。

**【严重度】P1**。

## 3. 根因归纳：五个结构根因

S-1..S-11 不是 11 个独立 bug，而是 5 个结构根因的 11 次显影。**修 bug 修不掉根因**，这是本篇存在的理由。

| 根因 | 表述 | 显影为 | 结构性解法 |
|---|---|---|---|
| **R-A 同名标识符多源定义** | 一个名字（配置路径、E 维名、门禁名、artifact 路径、状态文件名）在多个文件里各写一遍 | S-1、S-2、S-4、S-8、S-9 | **单一事实来源（SDP）**：标识符空间 = 一个冻结的数据模块；源码级守卫断言无裸字面量（§4.2 原则 1） |
| **R-B 正则即接口** | 用"文本长得像"替代"结构相同"来传递语义 | S-1（路径）、S-2（名字）、S-8（解析）、S-4（表头协议） | **类型化边界**：唯一 loader 产出类型化对象；跨模块只传对象，不传文本（原则 5） |
| **R-C 状态多副本且均为独立写者** | 一份结论 5 种落盘、4 个状态文件、多个写者 | S-4、S-6、S-10 | **一账本 + N 纯投影**：状态变更只经账本追加；报告/图表/状态文件全部是账本的**纯函数投影**（原则 3、4） |
| **R-D 派生状态被当真相源** | `workflow-state.json`、`ledger.md`、`band-history.json` 可被单独修改并反过来影响判断 | S-4、S-6、S-10 | **派生可重算**：删除任何派生文件后可由账本+工件重建出逐字节相同内容；守卫断言"重算 = 原文件"（原则 4） |
| **R-E 安全机制无执行契约** | 降级/门禁/校验只写"意图记录"，不校验"实际效果" | **S-7**、S-5、S-11、S-1 | **效果即记录**：每个安全动作必须**Post-Verify**（写入后回读断言），失败即失败（原则 7） |

> **R-E 是复评里最值得单独强调的一条。** S-7 与 S-5 是同一个病的两种症状：**"我打算这么做"被当成"事情已经这样了"**。在一个把"自主"当目标的系统里，这条根因的代价最高，因为人类恰恰**不在场**——这正是记录失去校验对象的时刻。

## 4. 目标结构设计

### 4.1 分层与依赖方向（L0-L5）

**依赖方向严格单向向下：L5 → L4 → L3 → L2 → L1 → L0，任何反向依赖（尤其 L1 碰 fs / L0 碰环境）视为架构违规。**

| 层 | 名称 | 允许做的事 | **禁止** | 内容（ANIC 通用插件视角） |
|---|---|---|---|---|
| **L0** | `contracts/` | 只导出冻结的常量与纯类型 | I/O、`Date.now`、环境读取、语言相关字符串 | `dimensions.ts`（E/Q 唯一词表）、`gates.ts`（门禁与维度归属）、`artifacts.ts`（路径注册表）、`schema.ts`（记录形状 v2）、`autonomy.ts`（级别与熔断条件常量） |
| **L1** | `core/` | 纯函数：输入→输出，无副作用 | fs / net / child_process / 时钟 / locale | 状态投影 `project()`、哈希链 `canonical()`+`hash()`、信任模型 `TrustModel`、门禁判定 `evaluateGate()`、控制带 `detectBands()`、维度评估的**判定逻辑**（不含取数） |
| **L2** | `store/` | 文件 I/O，**唯一写者** | 业务判定、格式决策 | 分段账本追加（段文件 + head.json）、工件读写、索引、原子写（temp+rename）、临界区 |
| **L3** | `engine/` | 编排：多步骤、跨模块、调用外部命令/模型 | 直接拼路径字符串、直接写状态文件（必须经 L2） | `CycleRunner`（每 cycle 一个子 fiber）、`FixLoop`、`AutonomyGovernor`、`ReviewEngine`（Tier-1 确定性 + Tier-2 模型）、`InitWizard`（多栈探测） |
| **L4** | `ports/` | 适配宿主：**把同一 engine 接到不同宿主** | 业务逻辑 | `DshHostPort`（tools/routes/slots）、`CliPort`（16 个脚本语义的 CLI 映射）、`McpPort`（15 个工具） |
| **L5** | `projections/` | 纯函数：`(contracts, ledger, artifacts) → 视图` | 写文件（由 L2 代写）、独立状态 | markdown 报告投影、控制带时序投影、图（workflow DAG）投影、Web UI 数据投影 |

**这张表是本篇的核心交付。**它同时回答了三个问题：
- **通用性从哪来**：L0-L3 零项目假设、零宿主假设（[02](02-需求分析.md) 的通用性要求）；
- **插件化从哪来**：DSH 只是 L4 的一个适配器，而非逻辑的住处（[03](03-架构设计草案.md) §3 因此不需要为 DSH 复制一份逻辑）；
- **16 个脚本语义怎么保**：它们是 L4 的 `CliPort` 子命令，不是各自独立的程序（S-1/S-8 的复发机制被取消）。

### 4.2 七条结构原则

| # | 原则 | 直接消灭 | 可验证形式 |
|---|---|---|---|
| **1** | **单一事实来源（SDP）**：每个标识符空间在一处定义、冻结、被引用 | R-A → S-1/S-2/S-9 | 源码守卫：全仓扫描断言无裸字面量数组/路径常量，**并带反向自检**（防止守卫自身写错而永久为绿） |
| **2** | **纯核 / 命令壳**：判定逻辑在 L1（纯），取数与副作用在 L2/L3 | 判定不可测、判定随环境变形 | L1 的单元测试**不需要仓库、不需要 fs、不需要时钟** |
| **3** | **一账本 + N 投影**：一切状态变更 = 一次账本追加 | R-C → S-4/S-6 | 任何"状态"若不在账本里，就是派生 |
| **4** | **派生可重算**：删掉派生文件后能重建出等价内容 | R-D → S-4/S-10 | 守卫：`delete 派生 → rebuild → 深比较原文件` |
| **5** | **类型化边界**：跨模块传对象，不传"长得像"的文本 | R-B → S-1/S-2/S-8 | 唯一 loader；跨模块接口不出现 `string` 形式的配置/维度/路径 |
| **6** | **端口-适配器**：宿主差异只在 L4 | 移植时逻辑分叉 | 同一 engine 的契约测试对 3 个端口各跑一遍 |
| **7** | **效果即记录（Post-Verify）**：安全动作写入后必须回读断言 | **R-E → S-5/S-7/S-11** | 每个安全动作产出 `{intent, observed, ok}`，`observed` 与意图不符即失败；**失败不得写"已完成"记录** |

> **原则 7 在实现上有一个最小形态**：所有"声明式动作"（改配置、降级、应用补丁、归档移动）必须返回**观察值**而非布尔。本项目 CLAUDE.md 已给出同构教训："`etagGuard` 返回 `{handled, etag}` 使'只做一半'在结构上不可能"。

### 4.3 目录树（通用插件，非本仓库特有）

```
src/
  contracts/        # L0 冻结数据：dimensions / gates / artifacts / schema / autonomy
  core/             # L1 纯函数：project / canonical+hash / TrustModel / evaluateGate / detectBands
  store/            # L2 唯一写者：segmented-ledger / artifact-store / index / atomic-write / lock
  engine/           # L3 编排：cycle-runner / fix-loop / autonomy-governor / review-engine / init-wizard
  ports/
    dsh/            # L4a 宿主适配：tools.ts / routes.ts / slots.ts
    cli/            # L4b 16 脚本语义 → 子命令
    mcp/            # L4c 15 工具
  projections/      # L5 纯投影：reports / bands / graph / webview
client/             # DSH 客户端半：tab / graph / approval / evolve / store
```

与 [03](03-架构设计草案.md) §3 的差异：03 按**功能域**分（runtime/evolve/init/tools/routes/llm/shared），09 按**依赖方向**分。两者不冲突——09 是 03 的**约束条件**：03 的 `runtime/` 应落在 L2/L3，`evolve/` 的判定部分应在 L1、应用部分在 L3，`shared/` 即 L0。§9 记录了这次对齐。

## 5. 逐条优化方案（S → 结构改法 → 不变量 → 守卫）

## 6. 逻辑级优化（"优化相关逻辑"的算法/判定部分）

§5 是骨架，本节是骨架上的判定逻辑本身怎么改。

### 6.1 评审引擎：关键词计数 → 证据覆盖度（Tier-1 + Tier-2）

现状（`multi-agent-gate.mjs:156-207`）：`evaluateIntentGate` 统计中文关键词（问题/用户/目标）命中数 + 字数 ≥50 + markdown 小节数 → 置信度。这条路径的问题不是"不准"，而是**它的输出与工件质量之间没有因果**：加几句"用户/目标"即可提高信任分。

**改法（两级，职责分离）**：

- **Tier-1 确定性检查（L1 纯函数）**：能精确判定的必须精确判定，且**产出证据 id**。例：
  - intent 引用是否存在且可解析（`intent.md` 的字段完整性）；
  - spec 是否覆盖 intent 的每条需求（RTM 单向闭包）；
  - plan 的每个任务是否有归属层与验收判据；
  - 每个 E/Q 维度的**取数来源**是否声明（`source: 'deterministic' | 'model'`）。
- **Tier-2 模型评审（L3 `ReviewEngine`，经端口调用）**：只处理 Tier-1 **判不了**的语义问题（如"意图是否被忠实实现"），且必须输出**结构化结果**：
  ```
  { verdict: 'pass'|'fail'|'doubt', confidence, evidenceIds: [...], counterexamples: [...] }
  ```
  `confidence` 由模型给出但**必须与 `evidenceIds` 一同落盘**；`evidenceIds` 为空的高置信度**视为无效**（S-5 的结构性防御）。

**宿主现实（M0-② spike 补，2026-10-13）**：`ctx.llm` 已由双向证据证实可用（见 [spike/host-llm-service.md](spike/host-llm-service.md)），但**宿主不提供 JSON 结构化输出保证**——官方做法是"提示词强制闭合 JSON + 本地严格校验 + 任何异常即拒绝"（`dsh-experimental-auto-review/lib/index.js:20-41` 的协议、`:353-375` 的 `parseDecision`、`:377-397` 的块结构校验、`:448-454` 的 `failed()`）。因此补充四条编码级规则：

1. **注入即白名单**：Tier-1 把可引用的 `evidenceIds` 连同证据摘要一起送进提示词；返回中任何**不在该集合内**的 id ⇒ 该维度判 `doubt`。
2. **非法即保守**：JSON 解析失败、顶层非对象、**重复成员**、形状不在闭合枚举内、块结构不符（除"若干 reasoning + 恰一个 text"外）、终止块 `reason.kind ≠ stop` ⇒ 一律 `doubt`（**不是 `fail`，更不是 `pass`**）。
3. **请求与响应都要留痕**：调用前写 `{provider, model, promptDigest, evidenceIds}`，返回后写 `{verdict, confidence, rawDigest}`——即原则 7「效果即记录」在模型调用上的形态；官方样板是 `dsh-session-title-llm:216-223`（调用前 `session.append`）。
4. **不用 `purpose` 归因**：`GenerateOptions.purpose` 是闭合枚举 `'compaction' | 'session-title'`（`types.d.ts:530`），归因只能落在本插件账本。

**为什么必须两级**：把"能精确判定的"交给模型，等于用概率去替代事实，同时丢失可审计性；把"判不了的"交给正则，等于用叙事替代判断。技能的现有实现对前者过度信任（关键词）、对后者完全缺失（无模型）。

### 6.2 信任分：从常量到派生 + 滞回

- `trustScore` = 证据覆盖度的加权（`core/TrustModel`），**输入是 `evidenceIds` 集合与 Tier-1 通过率**，不是分支常量；
- 引入**滞回**（[05](05-数据结构与算法设计.md) 已定：上升需 3 次确认、下降立即且权重更大，`wDown > wUp`），使"偶发高分"不能打开 `--auto-approve`；
- `--auto-approve` 的前置从"信任分 ≥70%"改为"**信任分 ≥70% 且证据集合非空且无 doubt 项且账本链校验通过**"——四个条件的合取，消除 S-5 里"existsSync 即 verified"的偷换。

### 6.3 门禁评估：存在性 → 完整性

`multi-agent-gate.mjs:417-422` 与 `gate-check.mjs:36-48`（`checkG0` 只查 `项目评估报告.md` 是否存在）都用**存在性**替代**完整性**。"报告存在"与"报告覆盖了全部维度且链可校验"是两件事——后者才是 G0 的定义（`SKILL.md:146`："评估报告已产出且**覆盖范围**"）。

**改法**：门禁判据 = `existsSync` ∧ `parse 成功` ∧ `维度覆盖完备` ∧ `引用的证据 id 均可解析` ∧ `账本链校验通过`。每一子项独立产出证据 id，并在报告中可展开（本项目 CLAUDE.md 的教训："**'响应有数据'在丢了一个字段时照样通过**"——同一形状）。

### 6.4 维度/门禁/参数解析：fail-loud

- `--dimensions` 未知 → 非零退出 + 合法值列表（S-11）；
- 配置未知键 → 拒绝（schema-first，见 6.5）；
- 门禁记录的维度 id 若不在契约内 → 拒绝写入（防止账本被写进无法对账的结论）。

理由：**在全自主流程里，"静默缩小评估面"等价于"降低标准"，而降低标准的方向恰好是让流程更容易通过。**这是与 [08](08-产物规模与生命周期治理.md) §1 的"偏向便宜的错误方向"不同的一种情形——这里两个方向不对称，必须偏向**响亮失败**。

### 6.5 配置：唯一 loader + schema 版本 + 未知键拒绝

- 一个 loader（L2）把 `.cycles/config.yml` 解析为**类型化对象**，含 `schemaVersion`；
- 未知键 → 报错（拒绝静默忽略：当前的"未知键被忽略"正是"用户以为配了、其实没生效"的来源）；
- 缺失必填项 → 报错（**禁止用默认值兜底**：`band-detector.mjs:224` 的 `: 100` 把配置错误伪装成正常）；
- 配置中**不再重定义维度语义**（只允许引用 id 覆盖显示名，S-2）；
- 迁移：`legacy config.yml` 惰性迁移（与 [08](08-产物规模与生命周期治理.md) §3.4 的 `recover()` 同一机制）。

### 6.6 自主级：状态迁移走账本，禁止字符串改写

- 自主级是**状态**，不是配置文本：迁移 = `autonomy.changed{from, to, reason, evidenceIds, observed}` 账本事件；
- **Post-Verify**：写后回读实际级别，`observed !== to` 即失败并保持原级（S-7）；
- 人类恢复 L4 也走同一条路径（记录谁在何时恢复），使"降级—恢复"成为可审计序列；
- 配置里的 `autonomy_level` 降级为**初始值/上限声明**，运行时真值来自账本投影。**这条同时修正了 org-status 直接改写用户配置文件的行为**（修改用户文件却由插件自行决定，属于越权写入）。

### 6.7 控制带：从独立快照文件 → 账本派生序列

- 取消 `band-history.json` 作为**独立写者**；复杂度/规模指标作为**账本事件的度量字段**（或独立追加型指标流），控制带由投影计算（`core/detectBands`，Western Electric，O(n)）；
- 收益：① 消除一个状态副本（R-C/R-D）；② band-detector 进入自动化链（S-10）而不需要人记得跑；③ 指标与它所属的 cycle 天然对齐（当前快照只有 timestamp，无法归因到 cycle）。

### 6.8 报告：从投影生成，不再互相读取

- `项目评估报告.md` / `审计日志.md` / `交付清单.md` / `multi-agent-gate-report.md` 全部降级为 **L5 投影**；
- `auto-fix-loop` 不再正则解析中文测试报告，而是消费**结构化失败事实**（`projections` 或账本事件里的 `failures: [{id, message, severity}]`）；
- 收益：① 消除 S-8 的中文接口；② i18n 可自由实施（本项目红线要求所有用户文本走 `t()`）；③ 报告格式变化不再影响判定。

## 8. 迁移路径（与里程碑映射）

**总原则：先立骨架，再迁逻辑；每一步都以"旧脚本仍可用"为回退条件**（对应 [04](04-开发计划与里程碑.md) 的方案 B 过渡）。

|---|---|---|---|
| **M1** | 立 L0 契约层 + 唯一 loader + `CliPort` 薄壳（16 脚本语义不变，但都经契约层取路径/配置） | S-1、S-2、S-8（部分） | 既有 `.cycles/` 上跑旧命令，输出与迁移前**逐字节无差异**；且 `--dimensions E9` 响亮失败 |
| **M2-a** | 状态单一真相接管：账本为唯一写者，`workflow-state.json` 降为 checkpoint，`audit/gate` 报告改投影 | S-4、S-6 | INV-13/INV-15 用例通过；删派生文件可重建 |
| **M2-b** | 记录形状 v2 定死 + `requestId` 幂等 + 证据外置 + 索引（与 [08](08-产物规模与生命周期治理.md) §3 合并执行） | S-6、S-4 | INV-15；v1/v2 混代 hash 逐条全等；追加 N 条 ≤ N×1KB |
| **M3** | 读路径：分页、健康报告、控制带派生投影（`band-history` 退场） | S-10 | INV-18；10k cycle 首屏 <100ms |
| **M4** | Tier-2 模型评审（条件项：受宿主 LLM 面可用性约束） | S-5 | INV-14；空证据不得 auto-approve |
| **M5** | 进化引擎（信任/补丁/回放）与自主级事件化 | **S-7** | INV-16；引号用例不产生"已降级"记录 |
| **M5-a** | 规模侧收口（归档/预算/`anic_sweep`/`anic_prune`） | S-9 | 空目录可见化；INV 回归全绿 |

**回归纪律（沿用并加强）**：
- 每一步都跑**"旧命令 vs 新命令"三跑对比**（clean HEAD / 迁移前 / 迁移后），确认失败清单只减不增；
- INV 用例进常驻测试；**涉及安全的 INV（14/16/19）单独进定时任务**，防止无声回退；
- 宿主升级后按 [07](07-DSH开发规范与破坏性变更适配.md) 九步 checklist 复验。

## 10. 收益、代价与风险

### 10.1 收益

1. **失效方向反转**：现状是"读不到配置 → 跳过检查 → 通过"；目标结构下"读不到配置 → 响亮失败"。对门禁系统，这一条比任何功能都重要。
2. **可移植性**：L4 端口化之后，"技能脚本 / CLI / MCP / DSH 插件"是同一引擎的四个适配器，而不是四份逻辑（[02](02-需求分析.md) 通用性要求的结构性保障）。
3. **可测性**：L1 纯函数使判定逻辑可以在**没有仓库、没有时钟、没有网络**的条件下单元测试——这是 4,300 行脚本从未拥有过的能力。
4. **可审计性**：一账本 + N 投影 + Post-Verify 让"发生过什么"与"记录了什么"重新对齐（S-7 的直接解药）。

### 10.2 代价

| 代价 | 量级 |
|---|---|
| 契约层与端口层的前置工作量 | M1 独立里程碑（不含任何新功能） |
| 迁移期双形态并存 | 旧脚本保留为 `CliPort` 语义基线；需三跑对比 |
| 报告投影化会改变既有文件生成路径 | 既有 `.cycles/` 工件需惰性迁移，不改历史内容 |

### 10.3 风险（续 [04](04-开发计划与里程碑.md) 的 R1-R22）

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|

| **R20** | 契约层沦为"再一份副本"（守卫缺失时） | 中 | S-1/S-2 复发 | GUARD-1/3 带反向自检；CI 常驻 |

## 11. 结论

1. 复评**不改变**"值得插件化"（[01](01-可行性研究.md) 的 GO），但把它的**前置条件**从"补进化闭环"升级为"**先重构结构**"：现有技能的确定性门禁层在真实条件（配置文件名、引号写法、拼错维度）下会静默失效或不可运行，而技能的测试面**结构上不可能发现**这类缺陷（S-3）。
2. **11 项结构缺陷归因于 5 个根因（§3）**，其中最危险的是 **R-E 安全机制无执行契约**——它把"打算做"当成"已经做了"，而全自主流程恰恰最依赖记录与效果一致。
3. 目标结构是**分层单向依赖的 L0-L5**（§4.1）加**七条结构原则**（§4.2）；`contracts/` 唯一来源解决 R-A，类型化边界解决 R-B，一账本+N 投影解决 R-C，派生可重算解决 R-D，效果即记录解决 R-E。
4. 逻辑层面的优化集中在四组判定：**评审两级化**（确定性 + 模型，证据绑定）、**信任派生化**（常量 → 证据 + 滞回 + 四条件合取）、**门禁完整化**（存在性 → 完整性）、**失败响亮化**（未知标识符一律非零退出）。
5. 全部改动可被 **10 条新不变量（INV-10..19）与 6 类守卫**约束，且每条守卫都遵守本项目已付代价的三条纪律（反向自检、不匹配自身样例、扫写侧）。
6. 迁移按 M1 → M2-a → M2-b → M3/M4/M5 → M5-a/M6 推进，**M1 不含任何新功能**，其退出判据是"新旧逐字节等价"——这是把"重构"与"改行为"分开的唯一办法。

> 一句话：**技能的 15 条规则与 6 阶段流程是对的，错的是承载它们的 16 个各自为政的脚本。**插件化要做的不是把脚本搬进宿主，而是把它们的**契约**抽出来，让 16 个程序变成 1 个引擎的 4 个端口。
