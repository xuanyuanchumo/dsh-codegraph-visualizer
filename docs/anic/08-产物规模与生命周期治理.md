# ANIC 产物规模与生命周期治理

> 文档族：`docs/anic/`（导航见 [README.md](README.md)）· 版本 v1.1 · 2026-10-13
> 触发：用户 m00196「要考虑多次调用插件的大量产物的问题」。
> 定位：本文是**规模与保留**的专篇。数据结构在 [05](05-数据结构与算法设计.md)（账本形态在此深化），生命周期在 [06](06-生命周期状态机与引擎研究.md)，里程碑归属在 [04](04-开发计划与里程碑.md)，本篇只回答一个问题：**插件被反复调用、cycle 累积到数千/数万次时，`.cycles/` 会变成什么样、会不会崩、怎么不崩**。
> 里程碑对应：**M2-b = 规模地基**（§3.1-3.4，账本形状一次定死）；**M3 = 读路径**（§3.5-3.7 归档读路径、分页、健康报告）；**M5-a = 写路径与预算**（§3.5 归档执行、§3.7 处置、§4 预算告警）。
> 关联（复评轮）：本篇的治理机制全部**依赖 [09](09-结构优化与逻辑重构设计.md) §4 的 L0 契约层与 L2 单写者**——分段布局、内容寻址、幂等键、白名单都要求"路径/形状只有一个来源"（INV-10/INV-13/INV-15/INV-18）。若按技能的现状（每个脚本各写一份路径与解析，S-1/S-8）直接搬运，本篇的设计无从落地。
> 全部规模数字为本仓库 `.cycles/` **实测**（57 个 cycle 目录、编号至 cycle-91 非连续、账本 56 条、2026-10-13 采样），非估算。

## 0. 结论先行

1. **当前体量毫无压力，但增长曲线是二次的**：`gates/ledger.json` 是 `{entries[], chainHead}` 的**单文件 JSON 数组**——每追加一条就要**重写整个文件**。N 条记录的累计写入量 = N²/2 × 单条字节。按实测单条 893 B 推算，**10,000 条账本记录 ≈ 44 GB 累计写入**（对比分段追加的 8.9 MB，差 5000 倍）。这是当前设计里唯一真正会崩的点，且**必须在写第一行代码前修**——哈希链格式事后改 = 破坏性变更。
2. **单条 `detail` 无界**：实测最后一条 G3 记录 `detail` 约 4.4 KB，占整个 50 KB 账本的 9%。字段无上限 = 链体积无上限 = 传输/渲染/校验三重放大。
3. **双份存储**：`ledger.json` 50,018 B 与 `ledger.md` 41,670 B 是同一内容的两种渲染（83% 冗余），且两者会漂移。
4. **孤儿目录**：57 个 cycle 目录中 **12 个完全为空**（cycle-5/17/18/25/26/33/34/37/39/42/43/54，其中 6 个还带空子目录）——`init-cycle` 建了目录但 cycle 从未提交，且**永不清除**。
5. **scratch 污染**：`.cycles/` 根目录混入了大量一次性研究产物（`probe-*.mjs`、`token-*audit.mjs`、`commit-c*.txt`、`pkg.bak.json`、`*.ps1`、`dsh-asar/`、`j0probe/`）。插件若"扫描全目录建索引"，这些会被当工件。
6. **无索引、无分页、无保留策略**：`archive/`、`evals/`、`retrospectives/`、`tech-debt/` 实测**均为 0 文件**——归档能力从未真正跑过。
7. **对策不是"定期清理"，而是四条结构性约束**：**分段只追加账本**（O(1) 追加 + O(1) 增量校验）、**证据外置 + 链上只留摘要与指针**、**幂等键消灭重复调用产物**、**索引 + 分层归档 + 只索引不删除**。

## 1. 实测基线（2026-10-13，`.cycles/`）

### 1.1 体量与构成

| 指标 | 实测值 |
|---|---|
| 总文件 / 总字节 / 总目录 | 264 / 1,627,878 B（1.55 MB）/ 121 |
| `cycles/` | 57 个 cycle 目录，174 文件，1.03 MB |
| `gates/` | 6 文件：`ledger.json` 50,018 B、`ledger.md` 41,670 B、4 个 `G{n}-{ISO时间戳}.md` |
| `dsh-asar/`（spike 残留） | 7 文件 0.04 MB |
| `j0probe/`（spike 残留） | 8 文件 0.01 MB |
| 空目录 | 12 个 cycle 目录（6 个含空子目录） |
| 空归档目录 | `archive/` `evals/` `retrospectives/` `tech-debt/` 均 0 文件 |

### 1.2 单 cycle 产物体积的**增长趋势**（这是"多次调用"的直接指纹）

| cycle 区间 | 每 cycle 文件数 | 每 cycle 字节 |
|---|---|---|
| cycle-1..16 | 1–9（含 test-reports） | 1.1–17.7 KB |
| cycle-41..56 | 1–3 | 1.1–7.6 KB |
| cycle-69..76 | 2–4 | 3.7–15.6 KB |
| **cycle-77..91（近期）** | **稳定 5–8** | **27.6–80.8 KB** |

近期每 cycle 产出**八件套固定结构**（以 cycle-91 实测）：`项目评估报告.md` 10,560 B、`当前循环总规划.md` 6,711 B、`任务清单.md` 8,893 B、`审计日志.md` 8,598 B、`当前循环页面状态.md` 4,661 B、`非功能验证报告.md` 6,281 B、`交付清单.md` 15,705 B、`test-reports/测试报告.md` 14,707 B —— 单 cycle **76,116 B ≈ 74 KB**。

> **趋势解读**：单 cycle 体积在 15 个 cycle 内涨了 5 倍（早期 3.7 KB → 近期 74 KB）。这不是 bug，是"评估维度/门禁/测试面变多"的真实代价。**按近期口径线性外推**：1,000 cycle ≈ 72 MB、10,000 cycle ≈ 720 MB。归档不是优化项，是必需项。

### 1.3 账本实测（这是唯一会崩的结构）

```
ledger.json 顶层形状： { "entries": [ ... ], "chainHead": "a99ac6bd…" }   ← 单文件数组
entries 条数：56      平均单条：893 B（50,018 / 56）
字段全集（56/56 条全部存在，无缺字段）：gate, gateName, result, detail, timestamp, previousHash, hash
末条 detail 实测：约 4.4 KB（一整段交付清单级别的正文塞进单个字符串字段）
```

**二次写入量推导**（追加第 n 条需重写前 n 条）：

| 账本规模 | 单文件重写方案累计写入 | 分段只追加方案 |
|---|---|---|
| 56 条（现状） | ≈ 1.4 MB | 50 KB |
| 1,000 条 | ≈ 447 MB | 0.9 MB |
| 10,000 条 | ≈ **44.7 GB** | 8.9 MB |

同时 `verify` 在单文件方案下每次都要全量解析 JSON（10,000 条 ≈ 9 MB 文本解析），无法做增量校验。

## 2. 规模失效模式清单（P-S1..P-S10）

| # | 失效模式 | 证据 | 后果 | 归属 |
|---|---|---|---|---|
| P-S1 | 账本单文件 O(n) 重写 | §1.3 | 累计写入 O(n²)，10k 条 ≈ 44 GB；写放大 + GC 压力 + 掉电时全文件损坏 | 结构缺陷，**M2-b 必修** |
| P-S2 | `detail` 字段无上限 | 末条 4.4 KB / 9% | 链体积不可控；UI 表格卡顿；账本不可传输；单条异常值主导 | 结构缺陷，M2-b 必修 |
| P-S3 | 账本双份存储 | json 50 KB vs md 41.7 KB | 83% 冗余 + 两份真相漂移（md 是手写还是生成不明） | 结构缺陷，M2-b 必修 |
| P-S4 | 无保留/归档策略 | `archive/` 0 文件 | 线性无限增长；1k cycle ≈ 72 MB（§1.2 外推） | 策略缺失，M3 读 / M5-a 写 |
| P-S5 | 孤儿目录永存 | 12 个空 cycle 目录 | 目录扫描成本上升；UI 时间线出现空节点；"这个 cycle 怎么了"无法回答 | 策略缺失，M3 报告 / M5-a 处置 |
| P-S6 | scratch 与工件混放 | `.cycles/` 根 probe-*.mjs / commit-*.txt / dsh-asar/ / j0probe/ | 索引把非工件当工件；归档误移；schema 校验噪音 | 策略缺失，M2-b（索引白名单） |
| P-S7 | 单目录平铺文件 | `gates/` 4 个 `G{n}-{ts}.md` | 门通过 N 次 = N 个文件；1k cycle = 4k 文件同目录，NTFS 枚举退化 | 结构缺陷，M5-a |
| P-S8 | 无索引 | 无 index/manifest，每次查询全目录扫描 | 查询成本 O(目录数 × 文件数)；10k cycle 不可用 | 结构缺陷，M2-b |
| P-S9 | UI 无分页契约 | 现设计按 `?cycle=&tail=` 取数 | 一次性传输 10k 条 = 9 MB，前端卡死 | 结构缺陷，M3 |
| P-S10 | 重复调用产生重复证据 | 无幂等键；同一 gate 反复写同结论 | 同一证据多份副本；账本出现语义重复条目 | 结构缺陷，**M2-b 必修（幂等）** |

**关键判断**：P-S1/P-S2/P-S10 属于**"多次调用"直接放大的缺陷**，必须在 M2-b 写第一行账本代码时解决——因为它们改的是**哈希链记录形状**，事后修改 = 所有已写账本失效 = 破坏性变更（R14，宪法条款 7）。P-S4..P-S9 是**运行期策略**：读路径在 M3 补，处置与预算在 M5-a 补。

## 3. 治理设计

### 3.1 分段只追加账本（M2-b，替换单文件数组）

```
.cycles/gates/
├── head.json                    # { version, chainHead, segCount, entryCount, updatedAt }   ← O(1) 小文件
├── seg-000000.jsonl             # 第 1 段：每行一条记录，≤ SEG_MAX(=1000) 条
├── seg-000001.jsonl             # 第 2 段
└── legacy/
    └── ledger.json              # 旧单文件账本（惰性迁移后只读留存，见 §3.6）
```

- **追加**：定位当前段 → 追加一行 → 更新 `head.json`（链尾指针）→ fsync。**O(1) 写**，与总量无关；
- **段边界**：段写满（1000 条）才开新段；段内每行自带 `previousHash`/`hash`，**链在段内与跨段连续**（段首行的 `previousHash` = 上一段末行 `hash`）；
- **增量校验**：`verifyIncremental(head)` = 读 `head.json` → 校验末段 → 返回「账本有效且末行 hash = chainHead」。常规路径 O(1000)；全量 `verify` 仍可用（流式逐段，O(n) 但常数极小）；
- **迁移惰性**：首次打开旧 `ledger.json` 时流式转写为 `seg-000000.jsonl`（原文件移入 `legacy/` 保留），`head.json` 记录 `migratedFrom`。**绝不原地删除**（审计数据，宪法条款 6）；
- **同链混代**：迁移后旧记录（v1，含长 `detail`）与新记录（v2，`detailRef`）**同链共存**，verifier 按记录的 `version` 字段分别走 canonical 规则（v1 无 `version` 视为 v1）。**这是 N2 零迁移在记录级的落地**。

### 3.2 证据外置：链上只留摘要与指针（M2-b）

```
v2 记录形状：
{
  "version": 2,
  "gate": "G3", "gateName": "构建收敛门", "result": "PASS",
  "detailSummary": "P3-R18-02 ETag 闭环闭环完成；门禁全绿；6 条未验证遗留已披露",  // ≤ 280 字符，硬上限
  "detailRef": "gates/evidence/2026-10/G3-2026-10-13T03-46-57-371Z.md",         // 指针，可空（无证据时）
  "detailDigest": "sha256:ab12…",                                                // 内容寻址，去重键
  "evidenceBytes": 4371,
  "timestamp": "…", "previousHash": "…", "hash": "…"
}
```

- **链上 ≤ ~600 B/条**（vs 实测 4.4 KB 极端值），10k 条账本 ≈ 6 MB，可整体传输；
- **正文按需读**：UI 展开一条时才 `GET /anic/evidence?ref=…`；
- **内容寻址去重**（治 P-S10 的存储侧）：`detailDigest` 相同 ⇒ 证据文件复用同一份（`.cycles/.index/digests.jsonl` 记录 digest→path）；多次调用产出相同证据只存一份；
- **超限强制**：正文 > 64 KB 或疑似二进制/含凭据 ⇒ 拒绝写入证据目录并**熔断**（命中 X9/N5：凭据不入库）；
- **redacted 字段**：证据文件头部写 `source: llm|heuristic|human`、`redacted: true/false`（N5：明文凭据一律 `<REDACTED>`）。

### 3.3 幂等键：消灭「重复调用」的重复产物（M2-b，第一道防线）

- 每次流程调用携带 `requestId = <宿主 runId>-<序号>`（06 §2 runId 机制）；
- **账本 append 前查重**：同一 `requestId` 已存在 ⇒ 返回既有记录，**不追加、不重跑门禁、不重生成证据**；
- **工具级**：`anic_gate_check` / `anic_eval_run` / `anic_ledger_record` 均按 `requestId` 去重（宿主在崩溃重试、事件重投、用户双击时必然产生重复调用——这不是假想场景）；
- **幂等测试**：同一 `requestId` 连调 10 次 ⇒ 账本条目数 +1、证据文件数 +1（**这是 A8 的硬判据**）。

### 3.4 索引 + 白名单（M2-b，治 P-S6/P-S8）

```
.cycles/index.jsonl              # 追加式索引：{cycleId, dir, firstSeg, lastSeg, entryRange, digest, fileCount, bytes, mtime, closed}
.cycles/.index/digests.jsonl     # 内容寻址表：{digest, path, bytes, firstSeen}
```

- **白名单目录**：插件只索引 schema 声明的目录集（`cycles/ gates/ incidents/ retrospectives/ tech-debt/ evals/ archive/ intent/`），**其余（`dsh-asar/`、`j0probe/`、根目录散落 `probe-*.mjs`）标记 unmanaged：不索引、不归档、不删除**（实测这些是研究残留，用户资产，插件无权处置）；
- **查询路径**：时间线/最近 cycle = 读 `index.jsonl` **尾部 N 行**（O(N) 行，非 O(目录数)），不扫目录；
- **索引是派生物**：可随时由工件全量重建（`anic_index --rebuild`），丢了不丢信息；不作为真相来源（真相是工件 + 账本）。

### 3.5 分层归档与「只移动不删除」（M3 读路径 / M5-a 写路径）

| 层 | 范围 | 存储 | 访问 |
|---|---|---|---|
| 热 hot | 最近 `hotCycles`（默认 20）cycle | 原位 `.cycles/cycles/cycle-N/` | 全量（正文 + 证据） |
| 温 warm | 冷却期外的已完成 cycle | 原位但索引只留摘要 | 详情按需；正文按需读 |
| 冷 cold | 超过冷却期（默认 `ageCycles=60` **或** `ageDays=90`，取先到） | `archive/cycle-N/` + `archive/index.jsonl` | 仅索引可见；正文需显式展开 |

- **归档 = 移动 + 索引**，不是删除（宪法条款 6）；
- 归档**不断链**：账本记录不随归档移动，链尾与 verify 与归档策略完全解耦（**归档失败不得影响账本可用性**）；
- **归档必须保留可审计路径（INV-22，M0-④ 实测驱动）**：`.cycles/` 的历史里，2 次被声明的自主级回退在账本中 **0 条记录**，而 genesis 已被裁剪 ⇒ 今天**只能判定"无法审计"**。分层归档因此不只是"省体积"：被移出热层的每一条门禁/级别/补丁事件，都必须**可由 `archive/index.jsonl` 重建**；UI 对账本起点之外的时间窗必须显示"不可审计"，**不得显示为"无降级记录"**；
- `anic_prune` **默认 `--dry-run`**，输出「将删除 X MB / Y 文件」清单；真删需 `--apply` 且**永不删 `gates/ledger*` 与 `archive/index.jsonl`**；
- **删除的真相源永远是索引**：`index.jsonl` 里没有的（unmanaged）永远不会被 prune 触及——这条规则同时解决了 P-S6。

### 3.6 UI 分页契约与数据预算（M3）

- HTTP 面统一游标分页：`?cursor=<segNo:lineNo>&limit=50`（默认 50，上限 500）；**响应带 `nextCursor`/`totalHint`**（`totalHint` 是估算值不是 COUNT(*)——大表 COUNT 本身就是慢查询）；
- 时间线首屏 = `index.jsonl` 尾部 50 条 + 最近 cycle 详情（不扫 archive）；
- 账本表格虚拟滚动（本仓库 VirtualViewportController 模式）+ **只加载展开行的证据**；
- **存储预算告警**：config 加 `artifactBudgetMb`（默认 512）+ `warnRatio=0.8`；超阈 → 状态条告警 + 建议归档，**绝不自动删**（A9 判据）。

### 3.7 孤儿与残留的可见化（M3 报告 / M5-a 处置）

`anic_sweep`（只读报告，默认在 UI "工件健康"面板可点）：

- 空 cycle 目录（实测 12 个）→ 列出「声明了但无任何工件、无账本记录」的 cycle，问「删目录 or 补标记 `abandoned`」；
- 空子目录 → 建议随父目录一并处理；
- 超龄未闭合 cycle（声明后 N 天无账本推进）→ 挂起提醒（避免"看起来在跑其实死了"）；
- scratch 残留（unmanaged 文件计数/字节）→ **只报告不处置**（用户资产）。

## 4. 性能与规模预算（写入门禁）

| 场景 | 规模 | 预算 | 手段 |
|---|---|---|---|
| 账本追加 | 任意规模 | O(1) 写 + O(1) fsync | 分段 JSONL + head.json |
| 账本增量校验 | 10k 条 | < 100 ms | `verifyIncremental` 只读末段 |
| 账本全量校验 | 10k 条 | < 1.5 s | 逐段流式 |
| 时间线首屏 | 10k cycle | < 100 ms / 不扫目录 | `index.jsonl` 尾部读 |
| 冷启动（不扫 archive） | 1k cycle + 10k 记录 | < 2 s | 白名单 + 索引 + 只读 head |
| 单 cycle 产物 | 1 个 | ≤ 256 KB 告警 | 八件套体积监控（实测近期 74 KB） |
| `.cycles/` 总占用 | — | 默认预算 512 MB | 超阈告警 + 建议归档 |
| UI 账本页 | 10k 条 | 首屏 50 条 / 交互 60 fps | 游标分页 + 虚拟滚动 + 证据按需 |

## 5. 迁移与兼容计划

| 阶段 | 动作 | 验收 |
|---|---|---|
| M0-③ | 反推既有账本 canonical 形式（键序/空白/字段集/hash 输入），**用既有真实账本 56 条逐条重算 hash 全等**，交付 `ledger-canonical-form.md` | 56/56 重算一致；不一致则明确记缺陷（04 R11） |
| **M2-b** | 规模地基：分段 JSONL + `head.json`（§3.1）+ v2 记录形状与惰性迁移 + 同链混代 verifier + 证据外置与内容寻址（§3.2）+ 幂等键（§3.3）+ 索引与白名单（§3.4） | 迁移 56 条后 verify 绿、旧记录 hash 不变、追加 v2 后旧链完整；同 requestId ×10 ⇒ 账本 +1、证据 +1；index 可重建；INV-6..INV-9 全绿 |
| M3 | 读路径：游标分页 + 虚拟滚动 + 归档读路径 + `anic_sweep` 报告面板（§3.5/3.6/3.7） | 10k 条首屏 <100 ms；归档内容可按需读 |
| **M5-a** | 写路径与预算：归档执行 + `anic_prune --dry-run` + 存储预算告警 + 门记录分桶（§3.5/3.6/3.7） | 归档后热区体积下降且 verify 绿；prune 默认不删；预算超阈告警 |

**兼容红线**：哈希链记录形状**只在 M2-b 一次定死**。此后任何"再加个字段"的诉求都必须走 v3 规范（canonical 规则明确该字段是否入 hash），**不得就地改 v2**——否则所有已写链失效（R14 / 宪法条款 7）。新增需求一律表达为**可选字段 + canonical 规则不变**。

## 6. 验收标准（新增）

- **A8 规模与幂等（P0，M2-b/M3）**：
  1. 10,000 条账本记录 + 1,000 个 cycle 目录下，`verifyIncremental` < 100 ms、冷启动不扫描 `archive/`（M2-b）；
  2. UI 账本首屏 50 条 < 100 ms，滚动无卡顿（M3）；
  3. 同一 `requestId` 连调 10 次 ⇒ 账本条目 +1、证据文件 +1（M2-b）；
  4. 相同 `detailDigest` 的证据只存一份（M2-b）；
  5. append N 条的累计写入量 ≤ N × 1 KB（分段方案的实测证明，非估算）（M2-b）。
- **A9 归档与预算（P1，M5-a）**：
  1. 冷却期归档后热区文件数/字节下降，账本链 verify 仍绿（INV-9）；
  2. `anic_prune` 默认 dry-run，`--apply` 不触碰 `gates/ledger*`、`archive/index.jsonl`、任何 unmanaged 文件；
  3. 预算超阈产生告警且**未删除任何文件**；
  4. 12 个实测空 cycle 目录在 sweep 报告中全部可见。

## 7. 宪法条款追加（与 03 §5.1 进化宪法并列）

6. **插件永不自动销毁用户工件**：归档 = 移动 + 索引；删除仅经显式 `--apply`（默认 dry-run）；真相源（账本、索引、归档索引）永不删除；unmanaged 文件永不触碰。
7. **账本形状一次定死**：M2-b 之后的任何记录形状变更走版本化规范，不就地改旧版本——否则已写链全部失效（这是本篇最贵的一条，代价是 M0-③ 的反推必须做对）。

## 8. 一句话总结

**「大量产物」在 ANIC 里不是清理问题，是三个结构问题**：单文件数组账本（O(n²) 写）、无界证据字段（单条可主导全链）、无幂等键（重复调用直接翻倍）。在 M2-b 用「分段只追加 + 证据外置 + 幂等键」一次性解决，之后的规模增长就退化成归档与分页的常规工程问题（M3 读路径 / M5-a 写路径与预算）。实测数据表明：当前 1.55 MB / 57 cycle 完全健康，但近期单 cycle 已达 74 KB（比早期涨 5 倍），**1,000 cycle ≈ 72 MB 是必须做归档的分界线**。
