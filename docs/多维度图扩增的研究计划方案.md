## 一、研究背景与目标

### 1.1 现状

当前项目支持两种视图模式：
- **code** — 代码图谱，展示函数/类/变量间的 call/import/extend/implement/contains 关系
- **dependencies** — 依赖图谱，展示第三方包依赖关系

现有图谱分析能力包括：循环依赖检测、影响分析、继承链高亮、调用链高亮、路径查找、架构健康评分、规则引擎等。

### 1.2 扩展目标

引入多维度图谱类型，从"单一拓扑视图"扩展为"多维分析视图体系"，让用户可以从不同视角理解代码结构：

- **宏观地图**（CodeGraph 主战场）：类图、组件/包图、依赖关系图、调用图、继承树
- **微观指南**（AST 主战场）：时序图（UML 2.0 序列图 + 组合片段）、控制流图、流程图

### 1.3 排除范围

本次研究暂不包含以下高复杂度图谱，留待后续按需扩展：
- 数据流图（DFG）— 需作用域分析，复杂度极高
- ER 图 — 仅适用于 ORM 项目，需专用解析器
- 部署图 — 与代码图谱核心定位距离较远

## 二、总体架构设计

### 2.1 核心分工原则

**CodeGraph 画宏观地图**：利用 SQLite DB 中已有的节点和边拓扑数据，快速定位"谁包含谁、谁依赖谁、谁调用谁"。CodeGraph 的优势在于全局拓扑的完整性和查询速度（单次 O(N+E) 查询获取全图）。

**AST 画微观指南**：利用 TreeSitter 解析函数/类内部结构，深入"代码怎么跑、顺序是什么、分支有哪些"。AST 的优势在于结构化信息的精确性（每个语法节点都有明确的类型和位置）。

### 2.2 图谱分类体系

| 大类 | 图谱类型 | 主数据源 | 核心价值 |
|------|---------|---------|---------|
| 结构静态图 | 类图 | CodeGraph 80% + AST 20% | 展示类/接口的继承层次与成员签名 |
| 结构静态图 | 组件/包图 | CodeGraph 100% | 宏观架构俯瞰，模块间依赖关系 |
| 结构静态图 | 依赖关系图 | CodeGraph 100% | 文件/函数间的调用依赖（已实现） |
| 行为动态图 | 时序图 | CodeGraph 定位 + AST 90% | 对象间消息传递的时间顺序 |
| 行为动态图 | 控制流图（CFG） | CodeGraph 定位 + AST 90% | 函数内所有可能执行路径 |
| 行为动态图 | 流程图 | CodeGraph 定位 + AST 90% | 业务逻辑步骤的抽象展示 |
| 调用层级图 | 调用图 | CodeGraph 100% + AST 可选 | 函数间调用层级，逆向追溯入口 |
| 调用层级图 | 继承树 | CodeGraph 100% + AST 可选 | 类从基类到子类的纵向展开 |

### 2.3 数据流架构

整体数据流分为三层：

**第一层 — 数据获取**：CodeGraph DB 提供宏观拓扑数据（节点、边、签名），TreeSitter AST 提供微观结构数据（控制流、调用顺序、类成员细节）。两者通过文件路径和行号进行关联。

**第二层 — 数据组装**：每种图谱类型有一个专属的 Assembler（数据组装器），负责将 CodeGraph 数据和 AST 数据按照该图谱的数据模型进行组装。Assembler 是图谱类型与数据源之间的适配层。

**第三层 — 渲染展示**：大多数图谱类型复用 Cytoscape 渲染器（通过 IRenderer 接口扩展），时序图因其特殊的"生命线 + 消息"布局范式，需要专用的 SVG 渲染器。

### 2.4 ViewMode 扩展

当前 viewMode 仅有 'code' 和 'dependencies' 两个选项。扩展后新增六种视图模式：'inheritance'、'callgraph'、'package'、'class'、'cfg'、'flowchart'、'sequence'。每种视图模式拥有独立的数据获取逻辑、布局策略、样式规则和交互行为。

## 三、结构静态图（CodeGraph 主战场）

### 3.1 类图（Class Diagram）

#### 3.1.1 目标

展示类/接口的继承层次、组合关系、方法与属性签名，以 UML 三段式（类名/属性/方法）呈现。

#### 3.1.2 数据获取策略

**CodeGraph 定位（宏观）**：

从 codegraph.db 查询所有 kind 为 class/interface/type_alias 的节点，获取类名、文件路径、行号、签名、是否导出等信息。查询所有 kind 为 extend/implement 的边，获取继承和实现关系拓扑。查询所有 kind 为 method/property/constant 的节点，通过 parentId 或 file_path 关联到所属类。

CodeGraph DB 的 nodes 表已包含 signature 和 docstring 字段，可直接提供方法签名。但 CodeGraph 不提供可见性修饰符（public/private/protected）和组合关系（A 持有 B 的实例），这两项需要 AST 增强。

**AST 深入（微观）**：

对每个类节点，用 TreeSitter 重新解析其所在文件，定位到 class_declaration AST 节点（按 lineNumber 匹配）。遍历 class body 子节点，提取以下信息：

- method_declaration 节点 → 方法名、参数列表、返回类型
- property_declaration / field_declaration 节点 → 属性名、类型注解
- accessibility_modifier 子节点 → public/private/protected 可见性
- constructor 节点 → 构造函数参数

分析属性的类型注解，若引用了另一个已知类节点，则标记为组合关系。

#### 3.1.3 AST 节点类型映射

不同语言的 AST 节点类型有差异，需为每种支持的语言建立映射表：

| 语言 | 类节点类型 | 方法节点类型 | 属性节点类型 | 可见性节点类型 |
|------|-----------|------------|------------|-------------|
| TypeScript | class_declaration | method_definition | property_declaration | accessibility_modifier |
| JavaScript | class_declaration | method_definition | property_identifier | 无（JS 无修饰符） |
| Python | class_definition | function_definition（类体内） | assignment（类体内） | 下划线前缀约定 |
| Java | class_declaration | method_declaration | field_declaration | accessibility_modifier |
| Rust | struct_declaration | function_declaration（impl块内） | field_declaration | visibility_modifier |
| Go | type_declaration | function_declaration（receiver） | field_declaration | 首字母大小写约定 |

#### 3.1.4 渲染方案

利用 Cytoscape 的 compound nodes（嵌套节点）实现 UML 三段式类框。每个类是一个 parent node，其属性段和方法段是 child nodes。

类名段用顶部条带显示，颜色按类型区分（class=蓝色，interface=绿色，abstract=灰色）。属性段用 +（public）、-（private）、#（protected）符号标注可见性。方法段标注 async、abstract 等修饰符。

继承边用空心三角箭头（UML 标准），实现边用虚线空心三角箭头，组合边用实心菱形箭头。

布局采用 dagre（层次布局），rankDir=BT（从下到上，根类在顶部）。

#### 3.1.5 交互设计

双击类节点展开/折叠属性和方法段。单击方法在侧边栏显示方法签名详情。右键类节点提供"查看继承树"和"查看调用图"的快捷入口。选中类时复用现有的 highlightInheritance 功能高亮所有继承/实现关系。

#### 3.1.6 边界情况处理

| 边界情况 | 处理策略 |
|---------|---------|
| 类过大（50+ 方法） | 默认折叠方法段，仅显示前 5 个方法 + "...N more" 提示 |
| 泛型类 | 在类名中保留泛型参数，不影响拓扑结构 |
| 嵌套类 | 用 compound nodes 的嵌套层次表示 |
| 跨文件继承 | 正常处理，CodeGraph DB 已跨文件索引 |
| 无继承关系的独立类 | 显示为孤立节点，不强制连接 |
| Python 鸭子类型 | 无法静态识别，仅显示显式继承 |
| JavaScript 无修饰符 | 所有成员默认标注为 public |

#### 3.1.7 可行性评估

数据可得性高：CodeGraph DB 已有约 80% 的数据（类节点、继承/实现边、方法签名）。AST 增强量中等：仅需对 class_declaration 做深度遍历提取成员。渲染基于 Cytoscape compound nodes，已有基础设施。主要风险是 parentId 的准确性——需验证 CodeGraph DB 中 method 节点的 parentId 是否指向 class 节点而非 file 节点。

综合可行性：4/5 星。

### 3.2 组件/包图（Component/Package Diagram）

#### 3.2.1 目标

展示项目目录划分和模块间依赖关系，提供宏观架构俯瞰视角。

#### 3.2.2 数据获取策略

**纯 CodeGraph 数据，无需 AST**：

从 codegraph.db 查询所有 kind 为 module/file 的节点，从 file_path 字段提取目录层次构建目录树。查询所有 kind 为 import/dependency 的边，按源-目标目录聚合：同一目录对的多条 import 边聚合为一条加权边，权重等于聚合的原始边数。

统计每个目录下的节点类型分布（function/class/variable 数量），计算每个包的入度（被依赖次数）和出度（依赖他人次数）。

#### 3.2.3 与现有聚类策略的关系

当前 clusterLevel='directory' 已实现目录级聚类，组件/包图是其增强版。区别在于：现有聚类是单层目录展示，组件/包图是多层嵌套目录树（可展开/折叠）；现有聚类仅显示 childCount，组件/包图还显示类型分布、入出度、复杂度等统计信息；现有聚类的边是简单聚合，组件/包图的边按权重映射粗细，双向依赖特殊标注。

#### 3.2.4 渲染方案

使用嵌套 compound nodes 实现多层目录树：根目录 → 子目录 → 文件 → 符号（四层嵌套）。

内部包用圆角矩形，背景色按层级渐变。外部包用虚线边框矩形区分。包大小用节点面积映射（符号数越多节点越大），包复杂度用边框颜色映射（高复杂度=红色边框）。

依赖边粗细按聚合边数的对数映射，边颜色按依赖类型区分（import=绿色，dependency=黄色），双向依赖用红色虚线标注。

布局采用 radial（径向布局），根目录在中心，子目录向外辐射。

#### 3.2.5 边界情况处理

| 边界情况 | 处理策略 |
|---------|---------|
| 深层嵌套目录（10+层） | 默认展开前 3 层，深层折叠 |
| 循环依赖（A→B→A） | 红色高亮 + 警告图标 |
| 零依赖的独立模块 | 灰色显示，不强调 |
| 外部依赖混入 | 用不同样式区分（虚线边框） |
| 超大项目（1000+目录） | 启用虚拟滚动（已有机制） |

#### 3.2.6 可行性评估

数据完全来自 CodeGraph DB，零 AST 依赖。现有 directory 聚类策略已实现约 70% 功能。渲染基于 Cytoscape compound nodes，已有基础设施。是性价比最高的扩展方向。

综合可行性：5/5 星。

### 3.3 依赖关系图（Dependency Graph）

#### 3.3.1 现状

已完整实现，是当前 viewMode='code' 的核心功能。支持 graphType='all'（所有边类型）、graphType='call'（仅调用边）、graphType='dependency'（仅依赖边），以及 viewMode='dependencies'（第三方依赖图谱）。循环依赖检测、跨层调用检测均已实现。

#### 3.3.2 增强方向

不需要新建图谱类型，在现有基础上增强视觉效果：边权重可视化（边粗细映射调用频率）、依赖方向标注（区分单向/双向依赖）、依赖强度热力图（节点颜色映射依赖密度）、模块边界可视化（用虚线框标注模块边界）。

综合可行性：5/5 星（已实现，仅需视觉增强）。

## 四、行为动态图（AST 主战场）

### 4.1 时序图（Sequence Diagram — UML 2.0 序列图 + 组合片段）

#### 4.1.1 目标

展示对象间消息传递的时间顺序，采用 UML 2.0 序列图规范，通过组合片段（Combined Fragment）机制表达异步、分支、循环等复杂逻辑。

#### 4.1.2 UML 2.0 组合片段机制深度研究

UML 2.0 引入组合片段（Combined Fragment / Interaction Fragment）专门解决传统时序图无法表达复杂控制逻辑的问题。组合片段是序列图中的矩形区域，包含一个操作符（Operator）和若干交互操作数（Interaction Operand），用于在消息序列中标注条件分支、循环、并行等控制结构。

**UML 2.0 组合片段类型完整列表**：

| 操作符 | 名称 | 语义 | 对应代码结构 | 解决的问题 |
|--------|------|------|------------|-----------|
| alt | 条件分支 | 多个互斥条件分支，每个分支有独立的 guard 条件 | if-else / switch-case | 条件分支无法表达 |
| opt | 可选执行 | 相当于只有一个分支的 alt，guard 条件满足时执行 | if（无 else） | 单条件可选执行 |
| loop | 循环 | 重复执行区域内的交互，可指定最小/最大次数和 guard 条件 | for / while / do-while | 循环结构无法表达 |
| par | 并行执行 | 多个区域并行执行，区域间用水平虚线分隔 | Promise.all / 并发任务 | 并行/并发无法表达 |
| break | 异常退出 | 当 guard 条件满足时，退出当前封闭交互 | break / early return / throw | 异常退出无法表达 |
| critical | 原子区域 | 区域内的操作不可被中断，必须原子完成 | 锁保护区域 / 事务 | 原子性约束无法表达 |
| neg | 不可能发生 | 标注不可能出现的交互序列 | 不可达代码 / 断言失败 | 无效路径标注 |
| assert | 必须发生 | 标注必须出现的交互序列 | 契约验证 / 后置条件 | 契约约束无法表达 |
| ignore | 忽略 | 标注不重要的交互，不在当前关注范围内 | 日志 / 调试代码 | 次要交互干扰主线 |
| consider | 关注 | 标注需要关注的交互，与 ignore 配合使用 | 核心业务逻辑 | 突出关键交互 |

**组合片段与代码结构的映射关系**：

alt（条件分支）映射 if-else 语句：每个 else-if 分支对应 alt 的一个操作数，每个操作数有独立的 guard 条件（如 [x > 0]、[x <= 0]）。switch-case 也映射为 alt，每个 case 对应一个操作数，default 对应最后一个操作数。

opt（可选执行）映射 if 语句（无 else）：guard 条件对应 if 的条件表达式。当条件满足时执行区域内的消息，否则跳过。

loop（循环）映射 for/while 语句：loop 片段可指定循环约束（如 loop[min,max] 或 loop[condition]）。for 循环映射为 loop[0,n]，while 循环映射为 loop[condition]，do-while 映射为 loop[1,n] + condition。

par（并行）映射异步并发：Promise.all 对应 par，多个 async 任务并行执行。每个 Promise 对应 par 的一个区域，区域间用水平虚线分隔。当所有区域完成后，后续消息继续。

break（异常退出）映射 break/return/throw：当 guard 条件满足时，break 片段内的消息执行完毕后退出当前封闭交互（如退出 loop 或 alt）。这正好解决了"早期返回"和"异常退出"在时序图中的表达问题。

critical（原子区域）映射锁保护/事务：标注区域内的消息序列必须原子完成，不可被其他交互中断。适用于数据库事务、锁保护区域。

**组合片段嵌套规则**：

组合片段可以嵌套。例如，一个 loop 片段内部可以包含 alt 片段（循环体内有条件分支），一个 alt 片段内部可以包含 par 片段（不同条件下并行执行不同的任务）。嵌套层次通过矩形框的嵌套表示，内层片段完全包含在外层片段的矩形区域内。

**组合片段对之前提到的挑战的解决**：

| 之前提到的挑战 | UML 2.0 组合片段解决方案 |
|-------------|------------------------|
| 条件分支无法表达 | alt 片段：每个分支有独立 guard 条件，清晰标注不同条件下执行的消息序列 |
| 循环结构无法表达 | loop 片段：标注循环约束（次数或条件），循环体内的消息序列重复执行 |
| 异步调用时序 | par 片段：并行执行多个异步任务，区域间虚线分隔，完成后汇合 |
| 异常退出 | break 片段：guard 条件满足时退出当前交互，清晰标注异常路径 |
| 早期返回 | break 片段：标注 return 语句导致的退出路径 |
| 并行/并发 | par 片段：多个区域并行执行，直观展示并发行为 |
| 原子性约束 | critical 片段：标注不可中断的操作序列 |

#### 4.1.3 数据获取策略

**CodeGraph 定位（宏观入口）**：

用户选择入口函数（通过搜索或点击 code 视图中的节点），CodeGraph 提供该函数的 filePath、lineNumber、callees（call 边的目标）。codegraph_trace 工具提供两个函数间的调用路径。codegraph_context 工具提供函数的业务上下文描述。

**AST 深入（微观时序）**：

用 TreeSitter 解析入口函数所在文件，定位到 function_declaration 或 method_declaration AST 节点。遍历函数体（body/block），按源码书写顺序提取所有 call_expression，为每个调用确定源参与者、目标参与者、参数列表、是否异步。

识别控制流结构并转换为 UML 2.0 组合片段：

- if_statement → alt 片段，每个分支有独立 guard 条件
- if_statement（无 else） → opt 片段
- for_statement / while_statement → loop 片段，标注循环约束
- try_statement → critical 片段（try 块） + break 片段（catch 块的异常退出路径）
- switch_statement → alt 片段，每个 case 对应一个操作数
- await_expression → 标注消息为异步，关联 par 片段
- Promise.all → par 片段，多个并行区域
- return_statement → break 片段（从当前交互退出）
- throw_statement → break 片段（异常退出路径）

递归处理：对每个 callee 函数，重复上述解析过程，限制递归深度不超过 3 层。

#### 4.1.4 参与者识别策略

从 call_expression 中识别参与者的规则：

- this.userService.findById(id) → 参与者 = UserService 类（从 this 的属性类型推断）
- db.query(sql) → 参与者 = Database 类（从变量声明类型推断）
- new HttpClient() → 创建新参与者，类型 = HttpClient
- fetch(url) → 参与者 = 外部系统（标注为 external 类型）
- callback(data) → 参与者 = 回调函数（标注为 callback 类型）
- self.method() → 自调用（弧形箭头）

#### 4.1.5 数据模型

时序图数据模型包含三类核心元素：

**参与者（Participant）**：每个参与者有唯一 ID、名称、类型（class/module/external/instance）、所属类名、文件路径、生命线起始和结束的消息序号、是否在序列中被创建或销毁。

**消息（Message）**：每条消息有全局递增的时序编号、源参与者、目标参与者、方法名、参数列表、返回类型、是否异步、是否自调用、是否返回消息、是否创建消息、所属组合片段 ID、源码行号。

**组合片段（Fragment）**：每个片段有唯一 ID、类型（alt/opt/loop/par/break/critical/neg/assert/ignore/consider）、条件表达式、起始和结束消息序号、父片段 ID（支持嵌套）、替代分支列表（alt 的多个操作数）。

#### 4.1.6 渲染方案

**推荐：专用 SVG 渲染器**

时序图的布局范式（生命线 + 水平消息 + 组合片段框）与 Cytoscape 的图模型差异太大，强行适配会牺牲交互体验。需要基于 SVG 手动绘制时序图。

**SVG 渲染元素设计**：

参与者头部：矩形 + 文本标签，位于顶部水平排列。点击参与者头部可跳转到对应的类图视图。

生命线：从参与者头部向下延伸的垂直虚线。悬停生命线时高亮该参与者的所有消息。

消息箭头：水平实线（同步调用）或水平虚线（返回消息），带箭头标记。自调用用弧形箭头。异步消息用斜线箭头。点击消息箭头显示参数和返回类型详情。

组合片段框：矩形边框 + 左上角操作符标签（如 "alt"、"loop[0,n]"）。alt 片段内用水平虚线分隔不同分支，每个分支左侧标注 guard 条件。loop 片段左上角标注循环约束。par 片段内用水平虚线分隔并行区域。break 片段用红色边框。critical 片段用加粗边框。

**布局算法**：

参与者按首次出现顺序水平排列，间距固定（如 150px）。消息按时序编号垂直排列，间距固定（如 30px）。组合片段框自动计算包围范围（根据其包含消息的起止序号）。嵌套片段通过矩形框嵌套表示，内层片段完全包含在外层片段的矩形区域内。

#### 4.1.7 适用场景与局限性

| 适用场景 | 不适用场景 |
|---------|-----------|
| 同步顺序代码（HTTP 请求处理流程） | 纯事件驱动代码（addEventListener） |
| 服务层方法调用链 | Promise 链式调用（.then().then()） |
| 单入口函数分析 | 回调地狱 |
| 简单 CRUD 流程 | 复杂异步竞态条件 |
| 包含条件分支的业务逻辑 | 运行时动态分发 |
| 包含循环的处理流程 | 反射调用 / eval |
| try-catch 异常处理流程 | Web Worker 通信 |

**关于异步代码的表达**：

UML 2.0 组合片段中的 par 片段可以表达 Promise.all 等并行异步操作。await 表达式可以标注为异步消息，并在 par 片段中表示等待并行任务完成。但 Promise.then 链式调用的精确执行顺序无法静态确定——因为 then 的回调取决于 Promise 的 resolve 时机，这是运行时行为而非静态可分析的。对于这类场景，时序图应标注"异步回调，执行顺序不确定"的提示。

#### 4.1.8 边界情况处理

| 边界情况 | 处理策略 |
|---------|---------|
| 递归调用 | 限制递归深度不超过 3 层，递归调用用特殊标记标注 |
| 动态分发（接口方法调用） | 列出所有可能实现类作为候选参与者，标注为 virtual |
| 跨文件调用链 | 懒加载：仅解析用户选定的入口函数 + 直接 callees |
| 函数体过大 | 支持折叠中间消息，仅显示关键调用 |
| 嵌套组合片段 | 矩形框嵌套表示，内层完全包含在外层内 |
| 无返回值的函数 | 不绘制返回消息箭头 |
| void 方法 | 标注返回类型为 void |

#### 4.1.9 可行性评估

数据获取方面：AST 顺序遍历可行，组合片段映射逻辑清晰。异步/动态调用的精确时序还原有根本限制，但 UML 2.0 组合片段机制（特别是 par、break、critical）已大幅提升了表达能力，使时序图能够覆盖大部分常见代码模式。

渲染方面：需定制 SVG 渲染器，工作量较大，但 SVG 渲染技术成熟，交互能力（缩放、点击、悬停）可实现。

价值方面：对同步代码和包含条件分支/循环的业务流程非常有用，是理解函数调用行为的最直观图谱。

综合可行性：3/5 星（数据获取有挑战但组合片段机制解决了核心表达问题，渲染需定制但技术成熟）。

### 4.2 控制流图（Control Flow Graph, CFG）

#### 4.2.1 目标

展示函数内所有可能执行路径（if/else、循环、异常），是逆向分析与漏洞挖掘的核心图。

#### 4.2.2 数据获取策略

**CodeGraph 定位**：用户选择目标函数，CodeGraph 提供函数的 filePath、lineNumber、signature，可选提供函数的 callees（用于标注 call 语句）。

**AST 深入**：用 TreeSitter 解析目标文件，定位到目标函数的 AST 节点，将函数体转换为基本块（Basic Block）序列。

基本块切分算法的核心思路：顺序语句合并为一个基本块；遇到控制流语句（if/for/while/switch/try/return/throw）时，结束当前块并创建新的条件块和分支块；每个分支块递归处理其内部语句；分支汇合处创建汇合块；return/throw 语句生成出口块。

具体处理规则：

- if_statement → 条件块 + true 分支块 + false 分支块 + 汇合块
- for_statement / while_statement → 条件块 + 循环体块 + loop-back 边 + 退出块
- switch_statement → 条件块 + 每个 case 块 + default 块
- try_statement → try 块 + catch 块 + finally 块 + exception 边
- return_statement / throw_statement → 出口块（后续语句不可达）
- break → 跳出循环的边
- continue → loop-back 边

#### 4.2.3 数据模型

CFG 数据模型包含三类核心元素：

**基本块（Basic Block）**：每个块有唯一 ID、简要标签描述、包含的语句列表、是否入口块、是否出口块、嵌套深度。

**语句信息（StatementInfo）**：每条语句有类型（assignment/call/return/throw/condition/declaration/break/continue）、简化文本、行号。

**CFG 边（CFGEdge）**：每条边有源块 ID、目标块 ID、类型（fallthrough/true/false/case/default/exception/loop-back/break/continue）、可选的条件表达式。

#### 4.2.4 渲染方案

基于 Cytoscape + dagre 布局：

入口块用绿色边框矩形 + "Entry" 标签。出口块用红色边框矩形 + "Exit" 标签。条件块用黄色填充菱形。过程块用蓝色填充矩形。true 边用绿色实线 + "T" 标签。false 边用红色实线 + "F" 标签。loop-back 边用紫色弧形虚线 + "loop" 标签。exception 边用橙色虚线 + "catch" 标签。fallthrough 边用灰色实线。

布局采用 dagre，rankDir=TB（从上到下），入口在顶部，出口在底部。条件块的 true 分支向左，false 分支向右。

#### 4.2.5 交互设计

单击基本块在侧边栏显示完整语句列表。双击条件块高亮 true 路径和 false 路径（不同颜色）。右键基本块提供"查看此块的数据流"和"跳转到源码"的快捷入口。悬停边显示条件表达式详情。

#### 4.2.6 边界情况处理

| 边界情况 | 处理策略 |
|---------|---------|
| 空函数体 | 单个 Entry→Exit 块 |
| 无限循环（while(true)） | 标记为 "infinite loop"，无 false 退出边 |
| 早期返回（多个 return） | 每个生成独立出口块 |
| 嵌套 try/catch/finally | try 块 + 每个 catch 块 + finally 块，exception 边连接 |
| switch 的 fall-through | case 块间用 fallthrough 边 |
| break/continue | break → 跳出循环的边；continue → loop-back 边 |
| 不可达代码 | 标记为 "unreachable"，灰色显示 |
| 函数体过大（100+语句） | 支持折叠子路径，仅显示主干 |

#### 4.2.7 可行性评估

AST 解析逻辑成熟，基本块切分算法是编译器经典问题，有大量参考实现。渲染完全基于 Cytoscape + dagre，已有基础设施。复杂度适中：单个函数的 CFG 通常 10-50 个基本块。主要风险是异常处理路径的完整建模较复杂（特别是嵌套 try-catch-finally）。

综合可行性：4/5 星。

### 4.3 流程图（Flowchart）

#### 4.3.1 目标

展示业务逻辑步骤，比 CFG 更抽象，面向业务理解而非路径分析。

#### 4.3.2 与 CFG 的关键区别

| 维度 | CFG | 流程图 |
|------|-----|--------|
| 粒度 | 每条语句一个节点 | 每个业务步骤一个节点（可能聚合多条语句） |
| 关注点 | 所有执行路径 | 业务逻辑步骤 |
| 条件标注 | 具体条件表达式 | 业务语义描述 |
| 循环 | 精确 loop-back 边 | "循环处理"抽象节点 |
| 目标受众 | 安全分析/逆向工程 | 业务理解/需求验证 |

#### 4.3.3 数据获取策略

先构建 CFG（复用 CFG 的基本块切分逻辑），然后在 CFG 基础上做语义聚合：

- 连续的过程块聚合为单个 "process" 步骤（如：变量初始化 + 数据准备 → "数据准备"步骤）
- 条件块转换为 "decision" 节点（如：if (user.role === 'admin') → "是否管理员?"）
- 循环转换为 "loop" 节点（如：for (item of items) → "遍历所有项目"）
- 函数调用转换为 "subprocess" 节点（可点击展开子流程）
- return/throw 转换为 "end" 节点

语义标注来源：变量名 + 函数名推导（如 findById → "查找"）、条件表达式语义化（如 x > 0 → "是否大于零"）、CodeGraph 的 docstring 字段。

#### 4.3.4 渲染方案

标准流程图符号 + Cytoscape：

- start/end：椭圆（绿色/红色）
- process：矩形（蓝色）
- decision：菱形（黄色）
- loop：六边形（紫色）
- io：平行四边形（青色）
- subprocess：双边框矩形（橙色）
- error：红色矩形

布局采用 dagre（rankDir=TB），已有。

#### 4.3.5 与 CFG 的关系

流程图是 CFG 的高层抽象版本，两者共享 AST 解析基础设施。实现策略是先由 CFGAssembler 产出精确的 CFGData，再由 FlowchartAssembler 在其上做语义聚合，产出 FlowchartData。流程图和 CFG 可以共享渲染基础设施，只是节点形状和标签不同。

#### 4.3.6 可行性评估

基于 CFG 构建，AST 解析基础设施可复用。渲染基于 Cytoscape + dagre，已有。语义标注可借助 CodeGraph 的 docstring 或 AI 辅助。主要风险是语义标注的准确性依赖启发式规则，对命名良好的代码效果好，对命名不佳的代码效果差。

综合可行性：4/5 星。

## 五、调用层级图（混合定位与深入）

### 5.1 调用树/调用图（Call Graph）

#### 5.1.1 目标

展示函数间的调用层级（谁调用了谁），支持逆向追溯入口。

#### 5.1.2 数据获取策略

**CodeGraph 定位（宏观拓扑）**：

从 codegraph.db 查询所有 kind 为 function/method 的节点，查询所有 kind 为 call 的边。计算入度为 0 的函数（没有其他函数调用它）作为入口函数（root nodes）。BFS 计算每个节点的 depth（从入口到该节点的最短路径长度）。检测递归调用（存在从节点到自身的路径）。

入口函数识别策略：导出函数（is_exported=1）、HTTP 处理器（名称匹配 handler/controller/route）、事件处理器（名称匹配 on/listen/subscribe）、CLI 入口（名称匹配 main/cli/run）、测试入口（文件路径匹配 test/spec）、无调用者的函数（入度为 0）。

**AST 深入（微观增强，可选）**：

对每条 call 边，解析调用位置的 AST，提取 call_expression 的 arguments 作为参数列表。识别动态调用（obj.method() vs staticFunc()）并标注调用类型。

#### 5.1.3 数据模型

调用图数据模型包含调用图节点和调用图边。

调用图节点包含：函数名、类型（function/method/constructor/arrow_function/async_function）、文件路径、行号、调用层级深度、入度（被多少函数调用）、出度（调用了多少函数）、是否递归、是否入口函数、入口类型、函数签名。

调用图边包含：调用者 ID、被调用者 ID、调用位置（文件路径+行号）、调用类型（direct/virtual/callback/async）、参数列表。

#### 5.1.4 渲染方案

tree 布局（已有），从入口函数向下展开调用树。

节点样式：入口函数用特殊图标标注（HTTP、test、export 等），普通函数用圆形节点，递归函数用红色边框 + 循环标记，高入度函数（callerCount >= 5）用大节点 + 热点标注。

边样式：direct call 用实线箭头，virtual call 用虚线箭头，async call 用双线箭头，callback 用点线箭头。

交互设计：双击函数节点展开/折叠子调用树。右键函数提供"逆向查看调用者"（反转树方向）。单击边显示调用位置详情。

#### 5.1.5 与现有功能的关系

当前 highlightCallChain(nodeId) 展示的是从某节点出发的局部调用链，调用图是全局视角的调用关系。graphType='call' 仅显示 call 边但不组织为层级树，调用图则以入口函数为根组织为树形结构。codegraph_trace 工具追踪两点间的调用路径，调用图提供全局拓扑。

#### 5.1.6 边界情况处理

| 边界情况 | 处理策略 |
|---------|---------|
| 递归调用环 | 检测后标注红色边框，不展开无限循环 |
| 多入口（多个 root） | forest 布局（多棵树并列） |
| 调用链过深（depth > 10） | 默认展开前 3 层，深层折叠 |
| 动态分发（接口方法调用） | 列出所有实现类作为虚拟子节点 |
| 回调函数（参数传递的函数） | 标注为 callback 类型边 |
| 函数指针/反射调用 | 无法静态分析，标注"dynamic dispatch" |

#### 5.1.7 可行性评估

CodeGraph DB 已有全部 call 拓扑数据，tree 布局已有，渲染基础设施完备。AST 增强可选，不影响核心功能。是性价比最高的扩展方向之一。

综合可行性：5/5 星。

### 5.2 继承树（Inheritance Tree）

#### 5.2.1 目标

展示类从基类到子类的纵向展开。

#### 5.2.2 数据获取策略

**CodeGraph 定位（宏观拓扑）**：

从 codegraph.db 查询所有 kind 为 class/interface/type_alias/struct 的节点，查询所有 kind 为 extend/implement 的边。计算入度为 0 的类（无父类）作为根类。BFS 计算继承深度。检测多重继承和接口实现。

**AST 深入（微观增强，可选）**：

对每个类节点，解析 AST 获取方法列表。对父子类，比较方法签名标记是否为覆盖（isOverride）。识别抽象方法（abstract 修饰符）标记 isAbstract。识别接口默认方法标记 isDefault。

#### 5.2.3 数据模型

继承树数据模型包含继承节点和继承边。

继承节点包含：类名、类型（class/interface/abstract/struct/type_alias）、文件路径、继承深度、父类/接口数、直接子类数、所有后代类数、方法列表（含覆盖/抽象标记）、是否抽象类。

继承边包含：子类 ID、父类/接口 ID、边类型（extend/implement）。

#### 5.2.4 渲染方案

tree 布局（已有），从根类向下展开继承树。

节点样式：class 用蓝色矩形，interface 用绿色矩形 + "<<interface>>" 标签，abstract class 用灰色矩形 + 斜体名称，struct 用紫色矩形。

边样式：extend 用空心三角箭头 + 实线（UML 标准），implement 用空心三角箭头 + 虚线。

方法显示：默认折叠方法列表，展开后显示方法名 + 覆盖/抽象标记。覆盖方法用 @Override 标注，抽象方法用斜体标注。

#### 5.2.5 与现有功能的关系

当前 highlightInheritance(nodeId) 已实现单节点的继承链高亮（双向遍历 extend/implement 边，向上找父类，向下找子类，dim 非相关元素）。继承树视图将其从单节点视角扩展为全局视角：不从某个节点出发，而是展示完整的继承森林，支持多根类（forest 布局），显示方法覆盖关系。

#### 5.2.6 边界情况处理

| 边界情况 | 处理策略 |
|---------|---------|
| 多重继承（C++/Python） | 多条 extend 边，正常展示 |
| 接口多重实现 | 多条 implement 边，正常展示 |
| 继承环（A extends B, B extends A） | 检测后标注红色警告 |
| 深层继承链（depth > 10） | 默认展开前 3 层 |
| 无继承关系的独立类 | 显示为孤立树 |
| 泛型基类 | 保留泛型参数在名称中 |
| Mixin / Trait | 标注为特殊关联类型 |

#### 5.2.7 可行性评估

CodeGraph DB 已有全部 extend/implement 拓扑数据，highlightInheritance 已实现核心遍历逻辑，tree 布局已有，AST 增强可选。与类图共享数据基础，可同时实现。

综合可行性：5/5 星。

## 六、实施路径与优先级排序

### 6.1 四阶段实施路径

**Phase 1（P0）— 继承树 + 调用图**

纯 CodeGraph 数据，零 AST 增强。复用 tree 布局和现有的 highlightInheritance / highlightCallChain 逻辑。工作量最小，价值最高。这两种图谱直接利用现有数据即可呈现，无需新增数据源或解析能力。

**Phase 2（P1）— 组件/包图 + 类图**

组件/包图纯 CodeGraph 数据，增强现有 directory 聚类。类图 CodeGraph 80% + AST 20%（类成员提取）。复用 compound nodes + dagre 布局。工作量中等。

**Phase 3（P2）— CFG + 流程图**

CFG 需 AST 深度解析（基本块切分），CodeGraph 仅定位入口。流程图基于 CFG 聚合 + 语义标注。复用 dagre 布局，新增 AST 深度解析模块。工作量中-高。

**Phase 4（P3）— 时序图（UML 2.0 序列图 + 组合片段）**

AST 深度解析（调用顺序还原 + 组合片段映射）+ 专用 SVG 渲染器。异步/动态调用的精确时序还原有根本限制，但 UML 2.0 组合片段机制（alt/opt/loop/par/break/critical）已大幅提升表达能力。需新建渲染器，不复用 Cytoscape。工作量高。

### 6.2 综合对比矩阵

| 图谱 | 数据来源 | AST 增强量 | 渲染方案 | 布局 | 可行性 | 价值 | Phase |
|------|---------|-----------|---------|------|--------|------|-------|
| 继承树 | CodeGraph 100% | 可选 | Cytoscape | tree | 5/5 | 高 | P0 |
| 调用图 | CodeGraph 100% | 可选 | Cytoscape | tree | 5/5 | 高 | P0 |
| 组件/包图 | CodeGraph 100% | 无 | Cytoscape | radial | 5/5 | 高 | P1 |
| 依赖关系图 | CodeGraph 100% | 无 | Cytoscape | cose/dagre | 5/5 | 已实现 | — |
| 类图 | CodeGraph 80% + AST 20% | 中等 | Cytoscape | dagre | 4/5 | 高 | P1 |
| CFG | CodeGraph 定位 + AST 90% | 高 | Cytoscape | dagre | 4/5 | 中 | P2 |
| 流程图 | CodeGraph 定位 + AST 90% | 高 | Cytoscape | dagre | 4/5 | 中 | P2 |
| 时序图 | CodeGraph 定位 + AST 90% | 很高 | 专用 SVG | 自定义 | 3/5 | 高 | P3 |

### 6.3 关键架构决策

**ViewMode 扩展**：viewMode 从当前的 'code' | 'dependencies' 扩展为包含六种新视图模式的联合类型。每种 viewMode 有独立的数据获取逻辑、布局策略、样式规则和交互行为。

**数据组装器（Assembler）体系**：每种图谱类型有一个专属的 Assembler，负责将 CodeGraph 数据和 AST 数据按照该图谱的数据模型进行组装。Assembler 是图谱类型与数据源之间的适配层，新增图谱类型只需新增 Assembler，不修改现有 Adapter。

**AST 深度解析扩展**：在现有 TreeSitterAdapter（浅层符号提取）基础上，新增 TreeSitterDeepAdapter（深度 AST 解析），提供 parseClassDetail、parseControlFlow、parseCallSequence 等深度解析方法。

**渲染器扩展策略**：大多数图谱类型复用 CytoscapeRenderer（通过 IRenderer 接口扩展新方法）。时序图因其特殊的布局范式，需要独立的 SVG 渲染器（SequenceDiagramRenderer），实现 IRenderer 的子接口。

**主题样式扩展**：每种图谱类型在 ThemeStylesheet 中新增对应样式规则，包括节点形状、颜色、边样式、特殊标记等。

## 七、风险评估与缓解策略

### 7.1 数据层风险

| 风险 | 严重度 | 影响范围 | 缓解策略 |
|------|--------|---------|---------|
| CodeGraph DB parentId 准确性 | 高 | 类图（method 的 parentId 是否指向 class 而非 file） | 验证上游 codegraph 的数据模型；如 parentId 指向 file，则通过 file_path + kind 联合定位 |
| AST 解析精度 | 中 | 所有 AST 增强型图谱 | TreeSitter 是语法树而非语义树，类型推断可能不准确；对 TypeScript/Java/Rust 效果好，对 Python/JS 效果差 |
| 跨文件调用链性能 | 中 | 时序图、调用图 | 懒加载：仅解析用户选定的入口函数 + 直接 callees，不一次性解析全部 |
| 组合片段映射准确性 | 中 | 时序图 | AST 的 if/for/while 结构映射明确，但 try-catch 和 async 的映射需仔细验证 |

### 7.2 渲染层风险

| 风险 | 严重度 | 影响范围 | 缓解策略 |
|------|--------|---------|---------|
| 时序图 SVG 渲染器工作量 | 高 | 时序图 | 分阶段实现：先实现基本生命线+消息，再逐步添加组合片段、交互功能 |
| Cytoscape compound nodes 性能 | 中 | 类图、组件/包图 | 大类图（50+类）时 compound nodes 可能影响性能；支持折叠/展开缓解 |
| 组合片段嵌套渲染 | 中 | 时序图 | SVG 矩形框嵌套，需精确计算包围范围；限制嵌套深度不超过 3 层 |

### 7.3 交互层风险

| 风险 | 严重度 | 影响范围 | 缓解策略 |
|------|--------|---------|---------|
| 视图模式切换的数据加载延迟 | 中 | 所有图谱 | 每种视图模式独立加载数据，切换时显示 loading 状态；CodeGraph 数据可复用，AST 数据按需加载 |
| 时序图与代码视图的联动 | 低 | 时序图 | 点击时序图消息可跳转到源码行；从代码视图选择函数可生成时序图 |

### 7.4 时序图特殊风险

| 风险 | 严重度 | 缓解策略 |
|------|--------|---------|
| 静态分析无法还原运行时调用顺序 | 高 | 明确标注"基于源码顺序"；alt 片段表示条件分支的不确定性；par 片段表示并行执行 |
| Promise.then 链式调用顺序不确定 | 高 | 标注"异步回调，执行顺序不确定"；仅展示 await 形式的异步调用 |
| 动态分发无法确定具体目标 | 中 | 列出所有可能实现类作为候选参与者，标注为 virtual |
| 递归调用产生无限循环 | 中 | 限制递归深度不超过 3 层，递归调用用特殊标记 |
| 事件驱动代码不适合时序图 | 中 | 在 UI 中明确提示适用场景，引导用户选择合适的图谱类型 |

## 八、总结

本次研究覆盖了八种图谱类型的深度分析，核心结论如下：

1. **Phase 1（继承树 + 调用图）是最佳起点**：纯 CodeGraph 数据，零 AST 增强，复用现有 tree 布局和 highlightInheritance / highlightCallChain 逻辑，工作量最小、价值最高。

2. **CodeGraph 宏观地图的四种图谱**（继承树、调用图、组件/包图、依赖关系图）数据完全可得，渲染基础设施完备，是性价比最高的扩展方向。

3. **AST 微观指南的三种图谱**（CFG、流程图、时序图）需要新增深度解析模块。其中 CFG 最可行（基本块切分算法成熟），时序图采用 UML 2.0 序列图 + 组合片段机制后，表达能力大幅提升，能够覆盖条件分支（alt）、可选执行（opt）、循环（loop）、并行（par）、异常退出（break）、原子区域（critical）等复杂逻辑场景。

4. **类图是混合型图谱的代表**：CodeGraph 提供 80% 数据，AST 补充 20%（可见性修饰符、组合关系），两者协作效果最好。

5. **时序图需要独立的 SVG 渲染器**：Cytoscape 的图模型不适合时序图的"生命线 + 消息 + 组合片段框"范式，强行适配会牺牲交互体验。UML 2.0 组合片段机制是时序图可行性的关键提升点——它将时序图从"只能表达线性顺序"升级为"能表达分支、循环、并行、异常等复杂控制逻辑"，大幅扩展了适用场景。
