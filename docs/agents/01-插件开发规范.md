> 适用范围：`dsh-codegraph-visualizer` 全部源码（`src/**`、`tests/**`、`scripts/**`）。

## 1. 工程硬约束

| # | 约束 | 依据 / 守卫 |

## 2. 宿主版本承诺（cycle-92 裁定）

### 2.1 三处声明必须一致

| 位置 | 当前值 | 读取者 |
|---|---|---|
| `package.json:20` `engines.dsh` | `">=0.2.0-rc.2 <0.4.0"` | **无**（纯声明） |
| `src/shared/dshGeneration.ts:65` `DSH_SUPPORTED_RANGE` | `'>=0.2.0-rc.2 <0.4.0'` | 本插件自身 |
| `package.json:57-58` `peerDependencies` 的 `@deepseek-ai/dsh-llm` / `dsh-tools` | `"^0.2.0-rc.2 \|\| ^0.3.0-rc.2"` | `dsh-app-boot`（**唯一强制门**） |

**守卫**：
- `tests/unit/dshGeneration.test.ts:124` `expect(pkg.engines?.dsh).toBe(DSH_SUPPORTED_RANGE)`
- `tests/unit/dshGeneration.test.ts:129-132` engines 与两个 peer 均**不得**含 `0.1.`，且必须含 `^0.2.0-rc.2`
- `tests/unit/manifest.test.ts:136` `narrows peerDependencies on @deepseek-ai/dsh* to the same floor as engines.dsh`

### 2.2 「被建模」≠「被承诺」——两清单恰好划分

`src/shared/dshGeneration.ts` 同时导出三个清单，**不要混用**：

| 常量 | 行 | 含义 |
|---|---|---|
| `DSH_GENERATIONS` | `:19` | 分类器**能识别**的代际：`['gen1','gen2','gen3']` |
| `DSH_PROMISED_GENERATIONS` | `:52` | 窗口**实际覆盖**、作为验收对象的代际：`['gen2','gen3']` |
| `DSH_LEGACY_GENERATIONS` | `:62` | **容忍但不承诺**的代际：`['gen1']` |

**守卫**：`dshGeneration.test.ts:139-156` 断言两清单**恰好划分** `DSH_GENERATIONS` 且不相交；
`manifest.test.ts:59-64` 的循环刻意用 `DSH_PROMISED`（用全集会让守卫在抬高下限后仍然绿）。

> ⚠️ **不要把 `DSH_GENERATIONS` 用作 `engines.dsh` 的生成源**。这正是 cycle-92 之前
> 潜在的自相矛盾：分类器认得 gen1，但窗口已不覆盖它。

### 2.3 保留 gen1 分类器的理由

不要因为「不承诺 gen1」就删除 `generationOfVersion`（`src/shared/dshGeneration.ts:97`）的
`minor === 1 → 'gen1'` 分支。理由（源码 `:58-60` 已注释）：

- 把**可识别的宿主**报成 `unknown`，会让能力探针失去保守基线的依据；
- 删除它反而制造「本插件以为自己在 gen2」这类**静默降级**。

正确的做法是：分类器如实分类，**安装门负责拒绝**（peer 范围已去掉 `^0.1.7-rc.2`）。

### 2.4 版本检测的诚实边界

`src/host/compat/HostVersionDetector.ts` 的三路启发式**全部**可能落空，此时返回
`unknownDshVersion()` 并 `log.info('host version unknown, using conservative flags')`：

| 候选 | 探测键 | 现实 |
|---|---|---|
| 一 | `ctx.hostVersion` / `ctx.version` / `ctx.app?.version` / `ctx.runtime?.version` | `@deepseek-ai/*` 全树 **零命中**（前向兼容探测） |
| 二 | `DSH_HOST_VERSION` / `DSH_VERSION` / `CODEARTS_HOST_VERSION` | 同样零命中；DSH 只注入 `DSH_HOME`/`DSH_SHELL`/`DSH_SESSION_ID`/`DSH_PROFILE`/`DSH_PROFILE_DIR` 给 shell 工具子进程 |
| 三 | `codegraph_incremental`/`codegraph_bootstrap` → gen2；`codegraph_status`/`codegraph_graph` → gen1 | 本机 `dsh-codegraph@0.1.3` 只贡献 `mcp__codegraph__codegraph_explore`，**一个都不匹配** |

⇒ **真机同样落到 `unknown` + 运行时能力探针**。任何「版本检测可靠」的说法都不成立，
不要据此写死分支。

## 3. 插件清单声明（`package.json` 的 `dsh` 块）

```jsonc
"dsh": {
  "manifestVersion": 1,                       // 纯声明，无人读取
  "bundle": { "patch": "./cordis.patch.yml" },// 装配补丁入口
  "client": {
    "platform": "web",                        // dsh-client-modules 只在 === 'web' 时加载客户端半
    "inject": [
      "@deepseek-ai/dsh-client-ui-conversation",
      "@deepseek-ai/dsh-client-ui-renderer",
      "@deepseek-ai/dsh-client-ui-sidebar-right"
    ]
  }
}
```

**权威依据**（context7 `/deepseek-ai/deepseek-harness`，`packages/util/package-manifest/README.md`）：
`DshPackageManifest` 的 types 在**编译期擦除**，不做运行时 JSON 校验、也不生成文件。
因此清单写错不会有任何报错，只会在加载期表现为「插件没出现」。

**关键推论**：
- `dsh.manifestVersion` 与 `engines.dsh` **都没有读取者**（`dsh-package-manifest/README.md:93` 逐字：
  "Compatibility is declarative."）；
- `dsh.client.platform === 'web'` 是**硬开关**：DSH 没有独立的 desktop 客户端平台，
  桌面端与网页端共用同一份 bundle。**唯一的按平台差异来自 DOM 标记**
  （`<html data-platform="darwin">` / `data-windows-titlebar`）与 `--dsh-frame-*` CSS 变量。

## 4. Cordis 生命周期规范

### 4.1 `ctx.effect()` 必须返回 disposer

所有副作用注册（tool、route、slot、事件监听、定时器）都要包在 `ctx.effect` 里并返回清理函数：

```ts
// src/index.ts —— 8 个 tool 的注册
ctx.effect(() => {
  const d1 = ctx.tools.register(graphStatusTool);
  // …
  return () => { d1(); /* … */ };
}, 'codegraph: tool registrations');
```

**不要丢弃 `ctx.slots.inject()` 的返回值**——它返回 disposer，必须存入
`IntegrationState.trackSlotDisposer()`（`src/client/integrations/IntegrationState.ts:49`）。

### 4.2 `inject` 只声明**必需**服务

| 入口 | `inject` | 理由（源码注释已写明） |
|---|---|---|
| `src/index.ts:30` | `['tools','webServer','sessions']` | `workspaceRegistry` 是 gen2-only，写进静态 inject 会让 gen1/minimal 宿主**整插件 INACTIVE**，故只在 `src/host/prerequisites.ts` 用 `ctx.get()` 可选探测 |
| `src/client/index.ts:44` | `['slots']` | `betterSidebar`/`commandUi` 是可选集成；`sidebarRightTabs` 两代都有故也只动态探测 |

**可选项一律动态探测，不写进 `inject`。**

### 4.3 `ctx.get(key)` 的严格模式陷阱

`ctx.get(name)` 默认 `strict = true`，语义是**"提供者 fiber 当前活跃"**，不是"服务存在"
（`cordis/lib/index.js:763-772`；`reflect.d.ts:16`）。

> **历史事故**：在同步 `apply()` 里探测一次，永久杀死了所有当时仍处于 state 1（loading）
> 的服务提供者——5 个 slash command 全部未注册，而更早加载的 `slots` 读取正常。

规范：
- 判断**存在性**用 `ctx.get(key, false)`；
- 需要**顺序**用 `ctx.inject([key], cb)`；
- **绝不**用一次性能力快照去 gate 一个集成（`if (!flags.commandUi) return;` 会静默删掉整个功能且无报错）。

### 4.4 异步注入只用于「叠加型」贡献面

`ctx.inject` 的回调**晚于**同步链执行。因此：

- **互斥**通道（`conversation.view` / `sidebar.right.pane.tab` / `better-sidebar` / `sidebar.footer.action` / 浮动面板）
  必须留在**同步优先级链**里——它们共同占用 `navButtonRegistered`，异步化会造成优先级反转，
  让**更差**的通道抢先拿到唯一入口；
- 只有**附加型、非互斥**的贡献面才允许异步注入。

`src/client/index.ts:71` 的 `apply()` 集成顺序**即优先级**，不要重排。

## 5. 多代适配器规范

### 5.1 判断「某服务键是否存在」需要**双向证据**

必须同时满足：
1. 静态 `provide(` 扫描命中；
2. 存在真实的 `ctx.get` 调用点。

仅凭「某插件 README 提到过」或「命名惯例像」会造出**永不执行的分支**和虚假兼容叙事。

### 5.2 识别代际只能用**独占**服务

`sidebarRightTabs` / `documentPreviews` / `slots` 在 gen1 与 gen2 都存在
（`dsh-client-ui-slots` 的 `lib/index.js` 跨代逐字节相同），**无法识别代际**。

目前确认的 gen2-only 标记只有两个：`pluginNavigation`、`userQuestionPanels`。

### 5.3 幻影服务必须删除，不能留桩

`IntegrationState` 曾有 `remoteWebUiApi` / `remoteWebUiPanelId` / `openRemoteWebUiPanel()`
三个成员服务于一个名为 `remoteWebUI` 的服务——cycle-83 逐条核验后确认**该服务在任何 DSH 代
与本机全部已装插件中都不存在**，已删除（源码 `:22-24` 留了历史注释）。

真实 `dsh-remote-web-ui` 只在 `sidebar.footer.action` 占席位并写 DOM 适配标记，
所以「远程窄屏」是**版面适配维度**，不是独立通道。

### 5.4 平台检测必须惰性求值

Electron preload 写 `<html data-platform="darwin">` / `data-windows-titlebar`，
**可能晚到 DOMContentLoaded**。因此：
- 每次调用都**重新读 DOM**，不缓存；
- 用 `MutationObserver` 重新求值；
- **不要**用 `process.versions.electron`——`@deepseek-ai` 全部 JS 里零命中。

## 6. 测试规范（写代码时就要想好的那部分）

### 6.1 测试分层归属

| 层 | 位置 | 触发命令 | 放什么 |
|---|---|---|---|
| L1 单元 | `tests/unit/**` | `pnpm run test` | 纯函数、控制器、store slice |
| L2 组件 | `tests/unit/**`（jsdom） | 同上 | React 组件、hooks |
| L3 契约守卫 | `tests/unit/*Contract.test.ts` | 同上 | **源码形态**扫描（见 6.3） |
| L4 E2E 冒烟 | `tests/e2e/user-journey\|plugin-install\|search-and-analysis\|realtime\|integration-and-lifecycle` | `pnpm run test:e2e` | 主路径 |
| L4 E2E 回归 | `on-demand-loading` / `conditional-requests` | `pnpm run test:web` | **定量契约**（必须留在回归集） |
| L4 视觉 | `tests/e2e/visual-screenshots.spec.ts` | `pnpm run test:visual` | 像素比对 |
| L4 性能 | `tests/e2e/performance.spec.ts` | `--project=performance` | J35–J38 |

### 6.2 断言必须绑到真实调用形状

- **不要**为了「让测试稳定」把断言放宽到无法鉴别。反例（P3-R27-03）：
  `tests/e2e/performance.spec.ts:92` 原为 `expect([200, 304]).toContain(response2.status)`，
  含 200 故**恒真**。
- 组件测试断言「方法 X 被调用」时，必须绑定到**组件实际持有的那个实例**——默认 mock
  每次返回新对象会让 `mock.results[0].value` 不是点击时的对象，断言读到
  `Number of calls: 0`。用稳定 fixture（如 `makePanelStateForLayerTests`）。
- 「按钮 → 网络请求」链条必须断言**请求参数**，只断言渲染或本地 UI 变化会让
  「入口存在但不可达」的缺陷全绿通过。

### 6.3 源码形态守卫（Contract Test）规范

凡是**行为测试看不见**的缺陷（死 CSS 选择器、幻影 import、缺失的确定性安装）都靠这类守卫。
写这类测试的三条铁律：

1. **必须剥离注释并保留换行**：把块注释逐字符替换为空格，而不是删除——否则所有报告的
   行号整体上移，指向错误位置。（本仓库已三次踩坑：`e2eSelectorContract.test.ts:25-28`、
   `a11yFormSemantics.test.ts:87-89`、`visualBaselineContract.test.ts`）
2. **守卫不能匹配到自己的样本字面量**：用字符串拼接构造样本
   （`const REQ = 'requ' + 'ire';`），使文件里不存在连续的待匹配形态。
3. **必须带反向自检**：断言扫描到的文件集非空（如 `files.length > 100`），
   并含一条「负样本不应命中」的用例——否则一个坏正则会让守卫永远绿。

### 6.4 变异探针要求

修一个缺陷后，必须**证明测试能翻红**：把修复处改成缺陷形态，跑一次，确认对应用例失败，
再改回。变异脚本放 `.cycles/`（不进 `src/`），并 `--exclude` 掉被观测的守卫测试本身，
否则守卫失败会导致 vitest 退出 1、不产出覆盖率报告，探针读不到文件而看起来像工具错误。

### 6.5 E2E 排障铁律

**`timeout` 是症状，永远不是诊断**。定位落空 / CSS 隐藏 / `visible=false` / 桩数据被装配器过滤
全部表现为几秒后的 `TimeoutError`。

排查顺序：
1. 先读错误上下文里的 page snapshot；
2. 确认元素**是否存在于 DOM**；
3. **之后**才考虑超时。

> 历史事故：TODO-02 被误诊为「Playwright 超时」达 8 轮，真实原因是选择器漂移 + dev-server 桩缺口
> （`docs/需求分析.md` §59.19）。

### 6.6 dev-server 桩的约束

`scripts/dev-server.mjs` 的桩图必须满足视图装配器：`CallGraphAssembler` **只保留 `function` 节点**
（`CALL_NODE_TYPES`），因此 E2E 用到的任何环或可选节点都必须是 `function`——
经过 `class` 节点的环会**静默消失**，面板永远不渲染。

**桩图只有一处真源**（`MOCK_GRAPH`）；页面内联副本与服务端副本**不得漂移**。

## 7. 契约变更检查清单

改任何一处 `export` 前，逐条确认：

- [ ] 是否影响 `package.json` 的 `exports` 映射？（`.` / `./client`）
- [ ] 是否需要同步 `docs/agents/02-宿主API参考.md` 或 `03-客户端API参考.md`？
- [ ] 是否有对应的 `*Contract.test.ts` 需要更新？
- [ ] 是否触发了 `vi.mock` 的工厂式 mock？（新增导出会让
      `No "X" export is defined` 报错——应改用
      `vi.mock(path, async (importOriginal) => ({ ...await importOriginal(), x: mock }))`）
- [ ] 若改了 HOST 路由：**必须重启宿主进程**，只重建不够（运行中的进程持有旧 bundle）
- [ ] 若改了 `engines.dsh` 或 peer 范围：同步 `DSH_SUPPORTED_RANGE` 与两个测试
- [ ] 是否新增了「设置值 + 能力守卫」对？→ 检查二者方向是否互相回滚

## 8. 无机器守卫的条款（必须靠评审）

以下条款**没有自动化测试能发现违规**，评审时必须人工检查：

1. 中文注释（C7）
2. `t()` 全覆盖（C4）
3. `cg-` 前缀（C5）
4. 禁止 `console.*`（C6）
5. 「集成顺序即优先级」不被重排（§4.4）
6. 幻影服务不被重新引入（§5.3）

> 把这些列出来的目的：**让"没有守卫"这件事可见**，而不是让它看起来像有保护。
