## 1. 一个口径，两条出口，不许两套实现

关键词查询在**同一份纯函数**上长两个出口：

```
src/xuanji/query/keyword-query.ts       ← 唯一实现（纯函数，零宿主依赖）
        │
        ├──→ src/tools.ts:744-764        LLM 面：graph_query 工具
        │       tokenizeQuery → selectSeeds → renderSubgraphText
        │
        └──→ ⟨待 T3⟩ src/host/routes/queryRoute.ts   人面：GET /api/v1/codegraph/query
                （必须复用同三个函数，不得复制）
```

**为什么「不许两套」不是洁癖**：三个函数里有**两个独立的口径决定**——
`estimateTokens` 的 CJK 系数与 `selectSeeds` 的每词保底。任何复制都会让两个出口
在边界输入上给出不同答案（「工具说 fits、面板说 truncated」），而这种分歧
**没有任何现有测试会变红**（两侧各自测各自的实现，都绿）。

`src/xuanji/index.ts` 的模块注释把这条写成了库的承诺：*"库边界：本文件只重新导出
src/xuanji 内部模块"*（`index.ts:11`）；`keyword-query.ts:6` 的分工原文：
*"宿主（`src/tools.ts` 的 `graph_query`）只负责取图与序列化"*。

## 2. token 预算口径（最容易被抄错的一条）

### 2.1 官方口径：CJK 1 字 = 1 token，其它 3.5 字符/token

```ts
// src/xuanji/query/keyword-query.ts:101-107
export function estimateTokens(text: string): number {
  if (text.length === 0) return 0;
  let cjk = 0;
  for (const ch of text) if (CJK.test(ch)) cjk++;
  const other = text.length - cjk;
  return Math.ceil(cjk * 1 + other / 3.5);
}
```

`CJK` 正则（`:91`）：`/[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]/`——含扩展 A 区
（`3400-4dbf`）与兼容表意区（`f900-faff`），不只是 `4e00-9fff`。

### 2.2 为什么**不能**用 `len/3`

`keyword-query.ts:15-16` 的原文（照抄）：

> *"**中文 token 估算不能抄 `len/3`**：那个系数按英文校准，中文会被少算 2~3 倍，
> 于是截断永不触发、调用方以为看全了。"*

用 `len/3` 的具体症状：

| 输入 | `len/3` 估算 | 实际（1 字/token） | 后果 |
|---|---|---|---|
| 300 个汉字 | 100 | **300** | 预算 200 时 `len/3` 判「装得下」，实际超 50% |
| 300 汉字 + 混合英文 | 少算 2~3 倍 | — | 截断分支**永不触发** |

「截断永不触发」是最坏的一类——它不报错、不缺数据，只是悄悄多塞进上下文，
直到某次 LLM 调用因超长失败，而失败点离根因很远。

### 2.3 偏向高估是刻意的

`keyword-query.ts:99` 原文：*"**偏向高估**：宁可早截断，也别让调用方以为看全了"*。

这条是**方向性决定**，与 ETag 的「宁可多回一次 200，不要假 304」同族：
两种错误的代价不对称时，往便宜的一侧偏，并把偏向写进注释——
否则下一轮「优化」会把它「修」成对称的。

### 2.4 预算与上限的实际取值

| 参数 | 库缺省 | 工具上限（`src/tools.ts:763` `clampInt`） | 路由（⟨待 T3⟩） |
|---|---|---|---|
| `tokenBudget` | **1200**（`keyword-query.ts:233`） | `50 .. 8000` | ⟨待 T3⟩ |
| `depth`（跳数） | **1**，库内硬上限 **3**（`:232` `Math.min(3, …)`） | `0 .. 3` | ⟨待 T3⟩ |
| `maxSeeds` | **3**（`:165`） | `1 .. 10` | ⟨待 T3⟩ |

> **库内上限与工具上限是两道独立的门**：库 `Math.min(3, …)` 是硬编码的
> （`keyword-query.ts:232`），工具侧 `clampInt(a.depth, 0, 3, 1)` 是参数校验。
> 改其中一道不会影响另一道——这也是「参数加了没人传」的常见藏身处。

## 3. 种子选择：分级 + 断层 + 每词保底

### 3.1 四级打分（`keyword-query.ts:86-89`、`:141-147`）

| 档位 | 分值 | 条件 |
|---|---|---|
| 精确 | `SCORE_EXACT = 1000` | `label === term` |
| 前缀 | `SCORE_PREFIX = 100` | `label.startsWith(term)` |
| 子串 | `SCORE_SUBSTRING = 1` | `label.includes(term)` |
| 路径 | `SCORE_PATH = 0.5` | `filePath.toLowerCase().includes(term)` |

多词查询的得分是**各词得分之和**（`:169-181`），并记录命中词
（`matchedTerms`，用于解释「为什么它被选中」）。

### 3.2 断层截断（`:52-56`、`:186-188`）

总分低于 `最高分 × gapRatio`（缺省 **0.2**）的候选**不进主力**。
`gapRatio <= 0` 时关闭断层截断。

### 3.3 每词保底（这条最容易漏，也最容易做错）

`:13` 的原文：*"**每词保底一个种子**：多词查询不能被单个精确命中劫持（否则第二个词
等于没查）"*。

具体机制（`:193-202`）：**每个词各自的最佳候选无条件入选**，即使它低于断层阈值。

**`maxK` 只约束非保底部分**（`:157`）——保底条目**可以超出 `maxK`**。这是多词查询的
必然结果，不是 bug。写测试时不要断言 `seeds.length <= maxK`。

### 3.4 输出顺序是完全确定的（`:156`、`:206-208`）

```
得分降序 → label 升序（localeCompare） → id 升序
```

确定性来自**排序键全覆盖**：任何两条不同条目在三个键上必有一处分出先后。
这也是「同图两次调用 `toEqual`」能够成立的原因（变异探针的基线）。

### 3.5 分词规则（`tokenizeQuery`，`:117-138`）

| 输入形态 | 切法 |
|---|---|
| 连续 CJK（如「依赖环」） | **整体词 + 逐字词**（`依赖环`、`依`、`赖`、`环`） |
| ASCII 标识符（如 `buildForwardAdjacency`） | 按 `[A-Za-z0-9_$]+` 取**整段**为一个词 |
| 长度 < 2 的纯 ASCII 词 | **丢弃**（`MIN_TERM_LENGTH = 2`，`:83`）——单字母会匹配一切 |
| CJK 单字 | 保留（中文没有空格，单字召回是唯一可靠做法） |

去重且**保持首次出现顺序**（`:123`）。顺序是确定性的一部分——
「按类别分两趟拼」会让同一查询在不同实现下得到不同词序。

## 4. 渲染的三分支与「截断必须可见」

`renderSubgraphText`（`keyword-query.ts:227-351`）返回
`{ text, tokens, truncated, reason, nodeCount, edgeCount }`，
`reason: 'fits' | 'nodes-only' | 'truncated'`（`:68`）。

| 分支 | 触发条件 | 输出 | 行 |
|---|---|---|---|
| `fits` | 全量文本 ≤ 预算 | 原样返回 | `:303-312` |
| `nodes-only` | **节点全装得下、边装不下** | 全部节点 + 一行 over-budget 告示 | `:314-328` |
| `truncated` | 连节点都装不下 | `[!] TRUNCATED` 头 + 按优先级逐个塞节点 | `:330-350` |

### 4.1 中间那支为什么最容易做错

`keyword-query.ts:222-223` 的原文：

> *"`nodes-only`：**所有节点装得下、边装不下** ⇒ 返回全部节点 + 一行 over-budget 告示
> （这是最容易做错的一支：丢掉节点等于让调用方以为图里没这些节点）"*

错误实现通常是「超预算就砍到只剩节点列表的一半」——图里明明有这些节点，
调用方却以为不存在。**丢弃边**是降级，**丢弃节点**是撒谎。

### 4.2 告示里的预算值必须「真的够用」

`:225` 的原文：

> *"并给出**真的够用**的预算值（整份文本的估算值），否则告示在骗人
> （graphify 自己的 issue 2784 就是这样被发现的）"*

所以 `truncated` 分支的头部是
`[!] TRUNCATED (token_budget=N; full=M)`（`:331`），`M` 是**整份未截断文本**的估算值。
写一个「猜的」预算值会让用户按告示调大到 `M` 之后仍然被截断。

### 4.3 无种子时不渲染空壳（`:267-277`）

```ts
if (hop.size === 0) {
  return { text: `No seed matched. (token_budget=N)`, …, reason: 'fits', nodeCount: 0, edgeCount: 0 };
}
```

注意 `reason` 是 `'fits'` 而**不是** `'truncated'`——「没匹配到」不是「被截断」。
把它们混成一个状态，UI 就会对「查无此词」显示「结果太多已截断」。

### 4.4 节点排序（`:279-287`）

```
跳数升序 → 度数降序 → id 升序
```

种子永远在最前（`hop = 0`）。这条顺序是**确定性的一部分**：
它让同一份图上的渲染结果逐字节可复现，从而使「截断位置」也可断言。

### 4.5 注入防护（`:211-215`）

`sanitize` 去掉 `\u0000-\u001f` 与 `\u007f` 控制字符（含换行）——标签来自用户代码，
标签里塞换行可以伪造 `NODE` / `EDGE` 行，从而**伪造图结构**给 LLM 看。

## 5. `/query` 路由契约

> **状态：⟨待 T3 落地后回填⟩**。下面给出的是**任务书约定的契约**（T3 的
> `src/host/routes/queryRoute.ts`），不是已实测的实现。凡是能从既有路由族类推出的
> 部分（中间件、etag 头、错误码）都已标注依据；纯属新设计的只有响应形状。

### 5.1 参数

| 参数 | 必填 | 缺省 | 上限 | 校验 |
|---|---|---|---|---|
| `q` | **是** | — | ⟨待 T3⟩（任务书 ≤ 512） | 空/超长 ⇒ 400 |
| `depth` | 否 | 2（路由侧；库缺省是 1，见 §2.4） | 5（路由侧；库硬上限 3） | 越界 ⇒ 夹紧或 400，⟨待 T3 定稿⟩ |
| `tokenBudget` | 否 | 800（路由侧） | 4000 | 同上 |
| `workspace` | 否 | 当前工作区 | — | 走 `validateWorkspacePath`（`src/host/security.ts`） |

⚠️ **路由缺省与库缺省不同是刻意的**（路由 2/800 vs 库 1/1200）：人在界面上要
「看多一点」，LLM 在工具里要「省一点」。但**上限必须服从库**：库的 `depth` 硬上限
是 `Math.min(3, …)`（`keyword-query.ts:232`），路由允许到 5 的话，传 5 会被库静默
夹到 3——这是**看不见的行为差异**，⟨待 T3 决定是改库上限还是把路由上限对齐到 3⟩。

### 5.2 响应形状（必须能让客户端画出高亮，而不只是文本）

```jsonc
{
  "query": "依赖环",
  "seeds": [{ "id": "…", "label": "…", "score": 1000, "matchedTerms": ["依赖环"] }],
  "nodes": [ /* GraphNode[] */ ],
  "edges": [ /* GraphEdge[] */ ],
  "text": "seeds=…\nNODE …",
  "tokens": 42,
  "truncated": false,
  "reason": "fits",
  "meta": { "depth": 2, "tokenBudget": 800, "source": "slot" }
}
```

- `nodes`/`edges` 是**给界面用的**（点了种子要选中/高亮）。只返回 `text` 就是
  「工具面冒充界面面」——人能读文字，但点不动。
- `meta.source` 区分 `'slot'`（缓存图槽）与 `'fetched'`（现场取图）——
  这是排障的唯一线索：同样查询在两种来源下结果不同时，先看这一格。

### 5.3 etag 身份维度（少一维 = 假 304）

| # | 维度 | 为什么必须 |
|---|---|---|
| 1 | **工作区**（请求方声明的 `repoId`） | 同一个 `q` 在两个工作区是两份不同载荷 |
| 2 | **`q`** | 参数化路由的第一维度；漏掉则 A 词的 304 会答给 B 词 |
| 3 | **`depth`** | 改变子图规模 |
| 4 | **`tokenBudget`** | 改变 `text` / `tokens` / `reason` |
| 5 | **图 revision** | 图变了，种子与子图都变 |

派生要求（与既有路由族类完全同形，见 [02](./02-宿主API参考.md) §3.4 / §3.5）：

- 走 `etagGuard(req, res, corsConfig, deps, resource, repoId, requestKey)`
  ——**一次调用同时给「handled」与「etag」**，结构上不可能只做一半；
- 200 响应必须 `sendJson(res, 200, payload, req, corsConfig, etagHeaders(etag))`
  （绕过 `extraHeaders` 会丢 CORS，跨源静默失效）；
- 必须在 `tests/unit/etagCoverageContract.test.ts` 的 `DECISION_MATRIX` 登记
  `RouteClass`，否则该守卫红。

**这个家族的缺陷形状**（三次复发，不是理论）：

| 变体 | 漏掉的维度 | 症状 |
|---|---|---|
| `metadata.timestamp` 当校验器 | 身份维度整体 | 假 304 静默丢更新 |
| `children(nodeA)` 与 `children(nodeB)` 同校验值 | 请求键 | B 永远加载不出来 |
| `/query` 漏 `q` | 请求键的**一个**成员 | 换词查询返回上一个词的 304 |

⇒ **偏差方向**：维度宁多勿少。多一维只会退化成「每次 200、少省一次传输」，
少一维会产生**永久空白且无错误**。

## 6. 客户端面板：四态与键盘

> **状态：⟨待 T3 落地后回填⟩**（`src/client/components/KeywordQueryPanel.tsx` 尚不存在；
> `ls src/client/components/ | grep -i keyword` = 空）。

### 6.1 四种状态都必须可见

| 态 | 触发 | 必须呈现 | 反模式 |
|---|---|---|---|
| **空查询** | `q.trim() === ''` | 「请输入关键词」类提示 | 什么都不做（用户以为按钮坏了） |
| **无结果** | `seeds.length === 0` | 「未匹配」+ 建议换词 | 空白列表（与加载中不可区分） |
| **请求失败/超时** | fetch 失败 / 超时 | 错误文案 + 重试 | 空白（与无结果不可区分） |
| **截断** | `truncated === true` | 显式提示 + `reason`（`nodes-only` / `truncated`） | 悄悄只显示一部分 |

「无结果」与「失败」必须**视觉可区分**——这条在 `keyword-query.ts:267-277` 的
`reason: 'fits'` + `No seed matched` 里已有数据支撑：服务端能如实说「没匹配」，
客户端不要把它渲染成错误。

### 6.2 键盘与可访问性

| 交互 | 要求 |
|---|---|
| `Enter` | 提交 |
| `Esc` | 关闭面板 |
| 输入框 | `role="searchbox"` + `aria-label` |
| 结果变化 | `aria-live="polite"` 播报结果数（不是每次按键都播） |
| 种子项 | `Tab` 可达；点击后选中图节点 |
| 窄档（`data-cg-narrow`） | 输入框**不得** icon-only 消失——搜索是核心操作（[01](./01-插件开发规范.md) 的常驻原则） |

### 6.3 点击种子必须真的选中图节点

这条要单列为一条，因为它是「入口存在但不可达」的高发点（本仓已有多次先例）：
按钮渲染、`onClick` 触发、局部状态变化全都对，但**没有发出选中动作**。

判据（可机械核对）：点击种子后，`useGraphStore.getState().selectedNodeId`
等于该种子的 `id`，且图上有对应的选中/高亮**可观测标记**。

### 6.4 状态必须进 store

本仓纪律：**store 是单一状态源**（[03](./03-客户端API参考.md) §5）。
面板的 `loading` / `error` / `result` 放 store 切片，组件内不留业务状态。
理由不是风格——组件内状态在面板被卸载重挂时丢失，用户会看到「刚查的结果没了」。

## 7. 与 `graph_query` 工具的关系

| 维度 | `graph_query` 工具 | `/query` 路由（⟨待 T3⟩） |
|---|---|---|
| 消费者 | LLM | 人（面板） |
| 实现来源 | `src/xuanji/query/keyword-query.ts` | **同一份** |
| 输出重点 | `text`（token 预算内的文本子图） | `nodes`/`edges`（可点击）+ `text` |
| 注册点 | `src/index.ts:63` `ctx.tools.register(graphQuery)` | ⟨待 Lead 在 `src/host/routes.ts` 注册⟩ |
| 参数校验 | `clampInt`（`src/tools.ts:751,763`） | `withRouteMiddleware` + 字段校验 |

**共同的三个函数，逐行对照**（工具侧调用点）：

```ts
// src/tools.ts:729
const terms = tokenizeQuery(a.query);
// src/tools.ts:744-752
const seeds = selectSeeds(nodes, terms, { maxK: clampInt(a.maxSeeds, 1, 10, 3) });
// src/tools.ts:753-764
const rendered = renderSubgraphText({ nodes, edges }, seeds,
  { depth: clampInt(a.depth, 0, 3, 1), tokenBudget: clampInt(a.tokenBudget, 50, 8000, 1200) });
```

**不许在路由里重写这三步**。如果路由需要不同的缺省值，改**参数**，不要改**实现**。

### 7.1 工具面的一个诚实说明

`graph_query` 在 `data.nodes.length === 0` 时**返回 `null`**（`src/tools.ts:727`）——
不是「空结果」，是「没有图」。渲染层把它呈现为 `No seed matched the query.`
（`:701`）——**这两件事被压成了同一句话**。

这是已知的呈现粗糙点（不是本轮缺陷）：LLM 拿到 `null` 时无从区分「图里没有这个词」
与「图是空的」。登记为已知限制，不声称已区分。

| 4 | `graph_query` 无法区分「无匹配」与「空图」 | `src/tools.ts:727` 返回 `null`，渲染统一成一句话（`:701`） | 已知限制 |
| 5 | 路由上限（depth 5）与库硬上限（3）不一致 | `keyword-query.ts:232` `Math.min(3, …)` | ⟨待 T3 定稿⟩ |
| 6 | **UI 面可达性无任何守卫** | 见 [测试体系 §2.28](../测试体系.md)：可达性守卫只覆盖库层与工具层 | 结构性 |

第 6 条是本节最重要的一条：即便 T3 把 `/query` 与面板全部交付，
**「有人在生产里真的点过这个面板」仍然没有守卫**。
现有的 `xuanjiReachability.test.ts` 比对的是「库符号有没有宿主调用点」；
`graph_query` 有调用点（`src/index.ts:63`），所以它是绿的——
而客户端 0 引用这件事，那个守卫**看不见**。
