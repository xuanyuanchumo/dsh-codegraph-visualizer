## 1. 承诺分三层，只有一层是门

DSH 侧「我们声明了什么」有多个键，但**只有一个真正拦截安装**。把三层混为一谈，是历次
「声明支持、实际装不上」或「以为会被拒、其实装上了」的根因。

| 层 | 字段 | 位置 | 谁读它 | 强度 |
|---|---|---|---|---|
| **真门** | `engines.dsh` | `package.json:20` = `">=0.2.0-rc.2 <0.4.0-0"` | **`dsh-app-boot` 的 `unmetRequirements()`**（见 §1.1） | 决定「能不能装/能不能加载」 |
| 真门的替身 | `peerDependencies` 的 `@deepseek-ai/dsh-*` | `package.json:56-62` = `"^0.2.0-rc.2 \|\| ^0.3.0-rc.2"` | 同一个 `unmetRequirements()`，**仅在 `engines.dsh` 缺席时**才被逐条检查 | 只在没有 `engines.dsh` 时生效 |
| 纯声明 | `dsh.manifestVersion` | `package.json:147` = `1` | **零读取者**（见 §1.2） | 无 |

### 1.1 `engines.dsh` 有读取者，而且**单独决定**

运行中的宿主 `D:/DSH/DeepSeek Harness/resources/app.asar` 内 `dsh-app-boot` 的
`unmetRequirements(fields, runtimeVersion)`（按函数名定位，字节偏移随宿主构建漂移）：

```js
const engines = Object.hasOwn(fields, "engines") ? objectOf$1(fields.engines, …) : {};
if (Object.hasOwn(engines, "dsh")) {
  const range = engines.dsh;
  if (typeof range !== "string") throw new Error("Plugin manifest engines.dsh must be a string");
  return satisfies(runtimeVersion, range) ? {} : { "engines.dsh": range };
}
if (!Object.hasOwn(fields, "peerDependencies")) return {};
// 之后才逐条检查 @deepseek-ai/dsh 与 @deepseek-ai/dsh-*
```

函数注释原文：**"An own `engines.dsh` range decides alone and peerDependencies are ignored;
otherwise every @deepseek-ai/dsh or @deepseek-ai/dsh-* peer must match."**

⇒ 本项目**声明了** `engines.dsh`，所以宿主**根本不看**我们的 peer 范围。
**`engines.dsh` 才是真承诺，`peerDependencies` 只是它的替身。**

同一规则在第三方市场插件里有一份镜像实现：`<profile>/node_modules/dshmarket/lib/verify.js`
的 `peerGateAt()`（注释自述 "the host's rule, read from unmetRequirements in
`@deepseek-ai/dsh-app-boot`"），`dshmarket/lib/discovery-compatibility.js:38-56` 亦按
`engines.dsh` 优先计算展示兼容性。

> ⚠️ **文档与代码不一致（必须知道）**：asar 内的 `dsh-package-manifest` README 仍写着
> "Compatibility is declarative. Current installers and loaders do not enforce
> `dsh.manifestVersion` or `engines.dsh`"。该句对 `manifestVersion` 成立，对 `engines.dsh`
> **在本次宿主构建上不成立**。遇到两者冲突，以**代码**为准（本项目 R 系列教训之一：
> 结论要能指到执行路径，而不是指到一段说明文字）。

复现命令：

```bash
# 1) 找到读取者（宿主 app.asar，只读）
grep -a -c "unmetRequirements" "D:/DSH/DeepSeek Harness/resources/app.asar"
# 2) 找市场镜像实现
grep -n "engines\?\\.dsh" "<profile>/node_modules/dshmarket/lib/verify.js"
# 3) 宿主自述版本
python -c "…"   # 或直接读 asar 内 dsh/desktop-runtime.json 的 dsh.version
```

### 1.2 `dsh.manifestVersion` 零读取者

```bash
grep -a -o "manifestVersion" "D:/DSH/DeepSeek Harness/resources/app.asar" | wc -l
# 6 —— 全部 6 处都落在 dsh-package-manifest 的 README 正文（中英两份）里，没有一处是可执行读取
```

⇒ 该字段**不产生任何行为**。它只是给「清单格式版本」留的位置；
本项目由 `tests/unit/manifest.test.ts:103` 钉死它的值，防止被顺手改坏，但它**不构成兼容承诺**。

## 2. 声明范围 vs 已验证版本（两列，不得混写）

「我们声明支持什么」与「我们实际在什么宿主上跑通了」是**两个不同的事实**，
混写会把「已验证」写成「已承诺」或反之。

| 代际 | 代表版本 | 声明范围（`engines.dsh`） | 是否承诺 | 是否真机验证过 |
|---|---|---|---|---|
| gen1 | `0.1.7-rc.2` | **窗口外** | 否（容忍分类，不承诺） | 是（历史基线，已抬出窗口） |
| gen2 | `0.2.0-rc.2` | 窗口内 | **是** | 是 |
| gen2 补丁 | `0.2.1-rc.3` | 窗口内 | 是 | **是（当前运行宿主，见下）** |
| gen3 | `0.3.0-rc.2` | 窗口内 | **是** | 否（**无真机证据**） |
| gen4 预发布 | `0.4.0-rc.1` | 窗口外（`<0.4.0-0`，cycle-110 收紧，见 §3.2） | 否 | 否 |

- 「当前运行宿主 = `0.2.1-rc.3`」的取证：宿主 asar 内 `dsh/desktop-runtime.json` 的
  `dsh.version` 字段为 `"0.2.1-rc.3"`（同文件另有 `nodeVersion: 24.21.0`、
  `pnpmVersion: 11.28.5`、`hostProtocolVersion: 4`）。
- **`0.2.1-rc.3` 不是下限**。项目下限是 `0.2.0-rc.2`（`src/shared/dshGeneration.ts:119`
  `DSH_SUPPORTED_RANGE`），由 `tests/unit/dshGeneration.test.ts:125` 与
  `tests/unit/manifest.test.ts:107-135` 双实现钉死。写文档时下限只能写 `0.2.0-rc.2`。
- 代际划分由 `src/shared/dshGeneration.ts` 的三个清单描述，**三者不可混用**：
  `DSH_GENERATIONS`（可识别 `:47`）、`DSH_PROMISED_GENERATIONS`（承诺 `:80`，`['gen2','gen3']`）、
  `DSH_LEGACY_GENERATIONS`（容忍不承诺 `:90`，`['gen1']`）。两清单的「恰好划分」由
  `tests/unit/dshGeneration.test.ts:136` 断言。

## 3. 破坏性变更的判定流程

判据只有一条主线：**这条变更会不会让「本应加载的插件不加载 / 加载了但能力静默消失」**。
按下列 6 步走，每步都要留下可复现命令或 file:line，不接受「看起来没问题」。

| 步 | 动作 | 产出 |
|---|---|---|
| 1 | 用 `docs/research/dsh-round110-规范与破坏性变更.md` 的「变更面 → 影响判定」表定位本次涉及的变更面 | 涉及面清单 |
| 2 | 对每个面做**两向证据**：静态 `provide(` 扫描 + 真实 `ctx.get(key, false)` 调用点（规范见 [01](./01-插件开发规范.md) §5.1） | 服务键存在性的结论 |
| 3 | 判断它属于「互斥通道」还是「叠加贡献面」——前者只能同步注入，后者才允许 `ctx.inject`（[01](./01-插件开发规范.md) §4.4） | 注入方式 |
| 4 | 若涉及版本窗：跑 §3.1 的三处一致性守卫 + §3.2 的**预发布边界探针** | 窗是否仍然正确 |
| 5 | 若涉及宿主行为：在**运行中的宿主**上复验（探针/日志/`/api/v1/codegraph/health`），不要只看单测 | 真机证据 |
| 6 | 把结论写回本文件 §5 案例库与 §6 预警清单；**未验证的必须写「未验证」** | 台账更新 |

### 3.1 三处一致性守卫（改版本窗时必跑）

```bash
pnpm vitest run tests/unit/dshGeneration.test.ts tests/unit/manifest.test.ts
```

两文件**刻意各写一份** `compareWithinRange` 助手（互不 import），一边改坏另一边仍会红。
断言点：`engines.dsh` 与 `DSH_SUPPORTED_RANGE` **完全相等**（不是「覆盖」）、
两个 peer 必须仍含 `^0.2.0-rc.2` 与 `^0.3.0-rc.2` 且**不得**含 `0.1.`、
gen1 代表版本必须落在窗口**外**、`0.4.0` 必须在窗外。

### 3.2 预发布边界探针（cycle-110 **发现并已闭环**）

**发现的洞**：本轮开始时 `engines.dsh = ">=0.2.0-rc.2 <0.4.0"`（旧值）。在宿主同一
`semver.satisfies(..., {includePrerelease:true})` 口径下实测（`node_modules/.pnpm/semver@7.8.5`）：

```
版本          旧范围判定          peer 判定
0.1.7-rc.2     false             false
0.2.0-rc.2     true              true     ← 声明的下限
0.2.1-rc.3     true              true     ← 当前运行宿主
0.3.0-rc.2     true              true
0.4.0-rc.1     true   ← 分歧       false
0.4.0          false             false
```

`0.4.0-rc.1`（gen4 预发布）被旧 `engines.dsh` **放行**，却被 peer 拒绝。由于
`engines.dsh` 单独决定（§1.1），宿主会**接受**一份声明为「不承诺 gen4」的安装。
旧守卫只探 `0.4.0`（`0.4.0` 确实是 false），所以这个洞**没有任何测试会红**——
典型的「探针只探了邻位、没探预发布」。

**修法（本轮已落地，与本文档同轮）**：

| 改动 | 值 |
|---|---|
| `package.json:20` `engines.dsh` | `">=0.2.0-rc.2 <0.4.0-0"` |
| `src/shared/dshGeneration.ts:119` `DSH_SUPPORTED_RANGE` | `'>=0.2.0-rc.2 <0.4.0-0'` |
| `src/shared/dshGeneration.ts:131` `DSH_UNSUPPORTED_PROBE` | `'0.4.0-rc.1'`（最近的一个被排除版本） |
| `src/shared/dshGeneration.ts:139` `DSH_UNSUPPORTED_PROBES` | `['0.4.0-rc.1', '0.4.0', '1.0.0']`（单点探针 → 多点探针） |

`<0.4.0-0` 是 semver 的「排除整个 0.4.0 预发布序列」写法。修后实测：

```
0.3.0-rc.2  true
0.4.0-0     false
0.4.0-rc.1  false
0.4.0       false
```

对应守卫：`tests/unit/dshGeneration.test.ts:128` 断言 `DSH_UNSUPPORTED_PROBE === '0.4.0-rc.1'`，
`:167` 遍历 `DSH_UNSUPPORTED_PROBES` 全部必须为 false（一个点只能证明「这一格被排除」，
多点才钉住整段）。

**沉淀的判定原则**：两个方向的错误代价不对称——**误放行**的代价是宿主上的崩溃/数据损坏，
**误拦截**的代价只是少装一个版本。故版本窗必须偏向拦紧，且每次抬窗都要问
「新窗口的上界在 `includePrerelease` 下会不会把下一代预发布放进来」。

## 4. 多代适配矩阵（本项目实际实现，不是愿望）

| 能力 | 探测方式 | gen1 | gen2 | gen3/未知 | 降级行为 |
|---|---|---|---|---|---|
| 宿主版本 | `detectHostVersion(ctx)` 三路启发式 | 可识别 | 可识别 | 可识别 | 全落空 ⇒ `unknownDshVersion()` + 保守 flags |
| 宿主能力 | `createHostCapabilityProbe(ctx)` + `createFeatureFlags` | 按探测 | 按探测 | 按探测 | **探针只开能力，不做 gate** |
| 宿主 API 差异 | `src/host/compat/ApiCompatLayer.ts` | 走兼容分支 | 直通 | 直通 | 未知代走保守分支 |
| 客户端 API 差异 | `src/client/compat/ClientCompatLayer.ts` | 走兼容分支 | 直通 | 直通 | 同上 |
| 平台（web/桌面） | `src/client/compat/PlatformProbe.ts` 惰性读 DOM | — | — | — | 读不到 ⇒ 按 web 处理 |
| 上游 `dsh-codegraph` | `checkPrerequisites()` + `CODEGRAPH_TOOL_EVIDENCE` | — | — | — | 缺失 ⇒ 回落 builtin 数据源 |

铁律（每条都有失败案例，见 §5）：

1. **版本检测不可靠是设计前提，不是缺陷**。`ctx.hostVersion`/`ctx.version`/`env` 在
   `@deepseek-ai/*` 全树零命中，真机必然落到 `unknown`（[01](./01-插件开发规范.md) §2.4）。
   任何「按版本写死分支」的代码都是在赌。
2. **能力探测用 `ctx.get(key, false)`**，`ctx.get(key)` 的默认 `strict=true` 语义是
   「提供者 fiber 当前活跃」，不是「服务存在」。
3. **绝不用一次性能力快照 gate 集成**（`if (!flags.x) return;` 会静默删掉整个功能且无报错）。
4. **识别代际只能用独占服务**：`pluginNavigation` / `userQuestionPanels` 是仅有的 gen2 标记；
   `slots` / `sidebarRightTabs` / `documentPreviews` 两代都有，不能用来判代。
5. **上游插件不兼容 ≠ 本项目不兼容**，两者要在报告里分开写（§5 案例 1）。

## 5. 案例库（真实发生过的破坏性变更 / 误判）

### 案例 1：上游 `dsh-codegraph@0.1.3` 在 0.2.1-rc.3 下被宿主跳过（cycle-110 实测）

- 现象：`prerequisites.codegraph = false`，本插件回落 `builtin` 数据源，功能可用但数据面降级。
- 机制（可证的静态事实，不靠猜）：`<profile>/node_modules/dsh-codegraph/package.json` 为
  `version: 0.1.3`，`engines = { "node": ">=20" }`（**无 `engines.dsh`**），
  peer 为 `@deepseek-ai/dsh-agent|dsh-llm|dsh-system-prompt|dsh-tools = ^0.1.0-rc.6`。
  按 §1.1 的代码路径：无 `engines.dsh` ⇒ 走 peer 分支 ⇒ `^0.1.0-rc.6` 在 `0.2.1-rc.3` 上不满足 ⇒ 宿主拒绝加载。
- 结论：这是**上游插件**停留在 gen1 peer 的结果，**不是本项目的兼容缺陷**。
  本项目的行为（探测到缺失 → 降级到 builtin）正是「探测 + 降级」策略的**成功案例**。
- 教训：把「上游被跳过」写成「我们不支持该宿主」是错误归因。

### 案例 2：幻影服务 `remoteWebUI`（cycle-83）

一个在任何 DSH 代与本机全部已装插件中都不存在的服务，被三个成员和一段集成代码「服务」着。
它不会报错，只会让集成**永不执行**。已删除，源码留历史注释（[01](./01-插件开发规范.md) §5.3）。

### 案例 3：`ctx.get` 严格模式杀死 5 个 slash command

在同步 `apply()` 里探测一次，永久杀死当时仍处于 loading 的服务提供者。
⇒ 存在性用 `ctx.get(key, false)`，顺序用 `ctx.inject([key], cb)`。

### 案例 4：`dsh.client.platform` 是硬开关，桌面端不是独立平台

`dsh-client-modules` 只在 `dsh.client.platform === 'web'` 时加载 client 半；web 与桌面**共用同一份 bundle**。
插件能观察到的唯一平台差异是 DOM 标记（`<html data-platform="darwin">` / `data-windows-titlebar`）
与 `--dsh-frame-*` CSS 变量。`process.versions.electron` 在全部 `@deepseek-ai` JS 里零命中。

### 案例 5：顶部标签「不在标签栏里」不等于注册失败（cycle-110）

`dsh-client-ui-conversation` 计算 `visibleTabs = preferred.slice(0, visibleViewLimit)`，
limit 来自标签行上的 `ResizeObserver`，其余标签落进「更多会话视图」菜单（`pinned: !unpinned.includes(id)`）。
实测：窗口 1540 px 时四个同级标签全部可见（对话 / 轨迹 / **代码图谱** / ANIC）；440 px 时代码图谱在溢出菜单里。
⇒ 诊断「标签没出现」必须先看 `document.querySelectorAll('[role="tab"]')` **加窗口宽度**，
再去怀疑 slot 注册代码。把「不可见」当成「没注册」会去改一段本来正确的注册逻辑。

## 6. 预警清单（改任何「宿主相关」代码前逐条打勾）

- [ ] 我改的是**声明**还是**真门**？改了 `engines.dsh` 就必须同步 `DSH_SUPPORTED_RANGE` 与两个测试
- [ ] 新增/删除 `@deepseek-ai/dsh*` peer 时，确认 `engines.dsh` 仍然「覆盖每一个承诺代际且不越界」
- [ ] 任何新版本探针都要探**预发布边界**（`X.Y.Z-0` / `X.Y.Z-rc.1`），不能只探 `X.Y.Z`（§3.2 就是这个洞）
- [ ] 新集成是否依赖某个服务键？⇒ 静态 `provide(` + 真实 `ctx.get(key, false)` **两向证据**都要有
- [ ] 该集成是**互斥通道**还是**叠加贡献面**？前者留在同步优先级链，后者才用 `ctx.inject`
- [ ] 有没有出现「能力快照 gate 集成」的早退？有则改掉
- [ ] 平台判定是否**每次读 DOM**（不缓存、`MutationObserver` 重求值）？
- [ ] 上游工具/服务探测是否会把「上游变更」误记成「本项目不兼容」？
- [ ] 改完 HOST 路由后是否**重启宿主进程**（只重建不够，进程持有旧 bundle）
- [ ] 真机验证是否走了 `scripts/start-dsh-test.mjs`（cycle-110 修了三处启动缺陷：Electron 垫片解析、
      认证 URL 等待窗口、桌面宿主进程名白名单）——**不要**自己再写一套启动脚本

## 8. 自检（本文件每条断言的可执行抽验）

