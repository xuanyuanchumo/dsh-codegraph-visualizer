## 1. 库的定位与唯一入口

### 1.1 一句话定位

`src/xuanji/**` 是**零宿主依赖**的图算法库：它只认识 `string` 形式的 id、`label`、边类型，
不感知 cytoscape / React / cordis / branded type。宿主的一切类型转换都发生在
`src/shared/analysis/XuanjiAdapter.ts`——**那是唯一与宿主耦合的模块**
（`XuanjiAdapter.ts:5-6` 自述「这是唯一与宿主耦合的模块」）。

### 1.2 唯一入口是 barrel，不是内部路径

```ts
// ✅ 宿主只从这里导入
import { GraphSpace, enumerate, selectSeeds } from '../xuanji/index.ts';

// ❌ 不得深挖内部模块
import { GraphSpace } from '../xuanji/core/graph-space.ts';
```

- barrel 文件：`src/xuanji/index.ts`（39 行，只做 `export * from './<层>/<模块>.ts'`）。
- 该文件的模块注释原文：*"宿主只从这里导入，不深入内部模块路径"*（`index.ts:5-6`）；
  *"本文件只重新导出 src/xuanji 内部模块，不引入任何宿主/第三方依赖"*（`index.ts:11`）。

**但实测与那句注释不符——宿主里有 3 个模块深挖内部路径**（cycle-111 实测）：

| 宿主文件 | 行 | 深挖的模块 |

| `src/shared/analysis/XuanjiAdapter.ts` | `:28`、`:29`、`:30`、`:31`、`:36`、`:37` | `core/graph-space`、`core/path-rule`、`index/path-index`、`index/incremental`、`query/query-engine` |

| `src/tools.ts` | `:16` | `query/keyword-query` |

复验命令：

```bash
grep -rn "from '.*xuanji/\(core\|index\|query\|ops\|registry\)/" src/ \
```

- `XuanjiAdapter.ts` 是**边界模块**，它需要精确控制「哪个符号来自哪一层」（`CycleDFS.ts`

## 3. `GraphSpace` 的契约

### 3.1 边键与幂等

边键 = `source->target->type`（`graph-space.ts:54-56`）。`addEdge` 对同键**幂等**：
「同 (source,target,type) 只保留第一条」，返回 `false` 表示已存在
（`graph-space.ts:116-119`）。**不要**用「加了几次边」来推断 `edgeCount`。

### 3.2 版本号只为结构变化递增

`addNode` 里有一条容易读漏的判断（`graph-space.ts:85-93`）：

```ts
addNode(id, attrs) {
  const isNew = !this.nodes.has(id);
  this.nodes.set(id, attrs);
  if (isNew) {
    this._version++;
    this.log.push({ kind: 'add-node', node: { id, attrs }, version: this._version });
  }
}
```

**属性覆盖不递增版本号**（注释原文：*"版本号只为「结构变化」递增：属性覆盖不改变可达性"*，
`:89`）。这是 `PathEntry.version` 一致性判定与不变量 I5 的前提——
如果你需要「属性变化也算变化」，那是 `lastSyncStamp` 的职责（§5.3），不是 `version` 的。

### 3.3 `GraphSpace.log` 的上界与 `drainChangeLog` 语义

**这是本轮（cycle-111）的 P0 发现，读完再改这个类。**

#### 3.3.1 缺陷的形状（为什么它是「回归」而不是「既有设计」）

| 事实 | 证据（修前） |
|---|---|
| `log` 是**无上界**的数组 | `private readonly log: ChangeEvent[] = []` |
| 四处增删都 `push` | `addNode` / `removeNode` / `addEdge` / `removeEdge` |
| `drainChangeLog()` 存在且语义清晰 | 取出并清空 |
| **全仓 0 消费方** | `grep -rn "drainChangeLog" src/` → 只有定义处 |
| `XuanjiAdapterPool` 让适配层**按 repoId 常驻** | `src/tools.ts:254` 构造；`:205-208` 用同一实例 `applyDelta` |

**为什么从「无害」变成「缺陷」**：cycle-109 把 `XuanjiAdapterPool` 接进
`src/tools.ts` 之后，`GraphSpace` 的生命周期从**每次工具调用新建**变成**按 `repoId` 常驻**。
同一份代码，在「短命对象」下是「随对象回收的临时缓冲」，在「常驻对象」下是
**随进程增长的无界内存**。

⇒ **同一个代码在不同生命周期下的缺陷性质可以相反**（这是本轮的测试体系教训，
见 [测试体系 §2.28(a)](../测试体系.md)）。

#### 3.3.2 修法：有界环形 + 截断可见

| 项 | 实现 | 位置 |
|---|---|---|
| 上界常量 | `MAX_CHANGE_LOG = 10_000`（**常量，不是可选项**） | `graph-space.ts:73` |
| 存储结构 | `log: ChangeEvent[]` + **逻辑起点偏移** `logHead` | `:107`、`:109` |
| 追加 | `record(event)`：未满则 `push`；**已满则就地覆盖最旧一条**并 `logHead` 前移、`_droppedChangeEvents += 1` | `:135-145` |
| 当前未消费条数 | `get pendingChangeEvents()`（恒 ≤ `MAX_CHANGE_LOG`） | `:130-132` |
| 累计丢弃条数 | `get droppedChangeEvents()` | `:125-127` |
| 消费 | `drainChangeLog()`：按 `logHead` 一次性**拉直**成普通数组后清空 | `:277-286` |
| 重置 | `clear()` 同时清 `logHead` 与 `_droppedChangeEvents` | `:288-298` |

**为什么是「覆盖式环形」而不是 `push` + `splice(0, over)`**（`:103-105` 的原文）：

> *"用「覆盖式环形」而不是 `push` + `splice(0, over)`：满之后每次写入都要搬动整个数组，
> 10 000 条时单次开销已可测（本文件的首版实现就是这样，一次批量装载实测 350 ms）。
> 环形下 record 是 O(1)，只有 drain 需要 O(n)——而 drain 本来就要复制整份结果。"*

⇒ 这是一个**实测驱动的实现选择**，不是风格偏好。改动前先量。

**`logHead` 不是死代码**：`drainChangeLog` 里的
`logHead === 0 ? [...] : [...slice(head), ...slice(0, head)]`
（`:278-282`）正是多次回绕后的**顺序拉直**。它只在发生过回绕时才走非零分支，
所以必须有一条「多次回绕后 drain 的顺序仍等于写入序」的用例，否则这段逻辑永远不被执行。

#### 3.3.3 `drainChangeLog()` 的确切语义

**不变的部分**：返回**自上次 drain 以来**的事件，顺序即**写入序**，`version` 严格递增。

**变了的（也是唯一变了的）部分**：**条数可能少于真实事件数**。
溢出时被丢弃的只会是**最旧**的事件，所以返回序列**仍然连续且单调**，
但差额不由返回值体现，而由 `droppedChangeEvents` 给出（`:269-276` 的原文）。

```
真实发生   E1 E2 E3 E4 E5 E6 E7      MAX_CHANGE_LOG = 5
保留       [   E3 E4 E5 E6 E7 ]      droppedChangeEvents = 2
drain 返回 E3 E4 E5 E6 E7            （连续单调，但比真实事件短 2 条）
```

**`droppedChangeEvents` 的三条语义（容易写错，逐条钉死）**：

| 问题 | 答案 | 依据 |
|---|---|---|
| 会被 `drainChangeLog()` 清零吗？ | ❌ **不会**。清零会掩盖「这条适配层从未被消费过」的事实 | `:123` 的注释原文 |
| 会被 `clear()` 清零吗？ | ✅ **会**。clear 后实例等价于新建，旧实例的截断历史不再属于它 | `:295-296` |
| 它是「当前丢失条数」还是「累计丢弃数」？ | **累计**（自构造/clear 起） | `:118` |

⇒ **不要写「语义与旧版完全一致」**。准确措辞是：*「返回序列仍连续单调，
但溢出时会比真实事件短，差额见 `droppedChangeEvents`」*。

#### 3.3.4 你现在写调用方时必须遵守的纪律

1. **常驻的 `GraphSpace` 应有人定期 drain**。有上界只保证内存不爆，
   不保证「你没读到的事件还在」——重放窗口是 `MAX_CHANGE_LOG` 条。
2. **不要用 `droppedChangeEvents > 0` 判定「日志坏了」**。它是**设计内的截断信号**，
   含义是「你读得太晚了」，不是「数据损坏」。
3. **不要用 `log.length` 当版本号**。版本号是 `this._version`；条数在上界内也 ≠ 版本数
   （`clear()` 会把版本归零，见 §3.4）。
4. **不要假设 `pendingChangeEvents` 会一直增长**。它恒 ≤ `MAX_CHANGE_LOG`，
   「涨到上界后不再涨」是正确行为。

## 4. `InvariantChecker`：I1–I5 与接线点

### 4.1 五项不变量的确切含义

来源：`src/xuanji/ops/invariants.ts:7-12` 的文件头 + 各 `checkI*` 的 JSDoc。

| ID | 断言 | 阈值 | 实现行 |
|---|---|---|---|
| **I1** | `rule.edgeTypes` 中每类边至少出现在**一条 live 物化路径**的相邻边上 | 无（`missing.length === 0`） | `:84-106` |
| **I2** | 图中每种角色（`attrs.role`，缺省 `tags[0]`）至少出现在一条 live 路径中 | 无 | `:115-143` |
| **I3** | 按边类型聚合的 live 路径平均长度，`max - min ≤ thetaDepth` | `thetaDepth` 缺省 **2**（`:77`） | `:149-201` |
| **I4** | `counters.stale / counters.total ≤ thetaStale` | `thetaStale` 缺省 **0.3**（`:76`） | `:204-224` |
| **I5** | 抽样 100 条：`entry.version ≤ graph.version`，且非 stale 条目的每条相邻边仍存在 | 无 | `:230-259` |

`checkAll` 按 I1→I5 顺序返回数组（`:262-270`）。

### 4.2 三条「看起来该报错但其实不该」的语义边界（照抄，不要自己推断）

1. **I2 不声称 `nodeConstraint` 被满足**。原文（`:110-113`）：
   *"`nodeConstraint` 是**不可反推的任意谓词**——无法从它推导出「哪些角色必须覆盖」"*。
   I2 只统计「图中实际存在的角色」在 live 路径里的覆盖率。图里没有任何角色声明时，
   I2 **空真通过**（`detail` = `'no node in the graph declares a role; I2 is vacuously satisfied'`，`:135`）。
2. **I3 在少于两类边时视为达标**（`:167-174`，`violations: 0`）。所以「I3 绿」
   不等于「深度分布健康」，可能只是**没有可比对象**。
3. **I1 对空 `edgeTypes` 不谎报失败**（`:81-82` 注释：*"空 edgeTypes 视为「无可覆盖项」"*）。
   这条与 `validateRule` 的告警互补，不要拿 I1 当「规则合法」的判据。

### 4.3 接线点（cycle-111 已落地）

| 项 | 内容 |
|---|---|
| 接线位置 | `XuanjiAdapter.applyDelta` **末尾**（`src/shared/analysis/XuanjiAdapter.ts:432-434`）：所有增删落地后调 `this.checkStaleInvariant(degraded)` |
| 检查内容 | 对**每条已注册规则**跑 **I4**（stale 比例）；不达标 ⇒ `index.clear()` + 记入 `degradedRules`（`:455-470`） |
| 实现方法 | `private checkStaleInvariant(degraded): DeltaInvariantReport`（`:455`） |
| 结论可读性 | `lastInvariantReport` getter（`:439-442`）返回 `{ byRule, violated }`；`applyDelta` 的返回值也带 `invariants`（`:436`） |
| I4 的分母口径 | `index.counters.total`（**含已 stale 的条目**），与 `incremental.ts` 的 `onEdgeRemovedDetailed` **同源**（`:447-450` 的注释） |
| 阈值 | `InvariantThresholds` 注入（`thetaStale` 缺省 0.3，与 `DEFAULT_THETA_STALE` 一致） |

**为什么放在 `applyDelta` 末尾而不是每条边上**（`:432-433` 原文）：

> *"放在最后而不是每条边上：I4 问的是「这条规则现在还能不能用」，那是 delta 的**终态**。"*

**接线前必须知道的那条真缺陷**（`:250-263` 的模块注释，实测取证）：

> 删节点**从来没有在索引上留下任何痕迹**。旧实现只做 `space.removeNode(id)`，而
> `removeNode` 内部删掉的相邻边**不经过** `dropEdge`，于是 `index.counters.stale` 纹丝不动。
> 实测（3 节点 a→b→c、物化 2 条路径后删 b）：`counters = {total: 2, stale: 0}`，
> 而索引里两条条目都指向已不存在的 b。

⇒ **I4 读的正是 `total`/`stale` 这两个计数**，所以它会对一个**全线失效**的索引给出
`ok: true`——分母含 stale 却看不出失效。这与 `incremental.ts` 里「用过滤后的 live 当分母，
于是 0% 失效」是**同一个坑的镜像**。

**修法**（`:412-418`）：删节点分支改成「先按真实邻接**逐边走 `dropEdge`**（与删边同一条
stale 通道），再删节点」：

```ts
for (const node of delta.removedNodes) {
  for (const ej of this.incidentEdges(node.id)) dropEdge(ej);
  this.space.removeNode(node.id);
}
```

`incidentEdges` 必须是**快照**（`:474-478` 的注释：`dropEdge` 会改动邻接表，
边遍历边删会漏元素——与 `GraphSpace.removeNode` 里 `Array.from` 的理由相同）。

**与 `onEdgeRemovedDetailed` 的关系**（`:264-267`，否则会觉得这道检查重复）：
两者阈值同为 `0.3`，在**纯删边**的 delta 上判定等价；I4 真正多覆盖的是
「**删/改节点**」以及「一次 delta 里**多种变更叠加**后的终态」——那时的失效
不是任何单条边删除的结论。

> **教训（可复用）**：给一个「没人用的检查器」接线时，**先确认它要检查的计量本身是对的**。
> 如果 `counters` 的写入路径有缺口，接上线只会让检查器把一个坏索引判成健康——
> 「接了个永远返回 ok 的检查」比「没接线」更危险，因为它会产生**虚假的安全感**。

### 5.2 `syncGraph` 的三态

`XuanjiAdapter.syncGraph(data): 'full' | 'delta' | 'none'`（`:260`，返回类型 `:114`）。

判定顺序（`:246-258` 的 JSDoc，逐条可核对）：

| # | 条件 | 返回 | 动作 |
|---|---|---|---|
| 1 | 从未装载（`!this.loaded`） | `'full'` | `loadGraph(data)`（`:261-264`） |
| 2 | 结构戳（`timestamp` + `nodeCount` + `edgeCount`）与上次相同 | `'none'` | 什么都不做（`:266-269`，戳比较 `:587-593`） |
| 3 | 与图空间**逐节点属性 + 逐边三元组**完全一致 | `'none'` | 只刷新戳（`:272-276`） |
| 4 | **纯增补**（旧节点/边全在且属性未变，只多出新节点/边） | `'delta'` | 造一条真实 delta 走 `applyDelta`（`:278-290`） |
| 5 | 其余（删除 / 属性变化 / 悬空边） | `'full'` | `loadGraph` 重建（`:292-293`） |

`SpaceDiff` 三型定义在 `:205-214`：`identical` / `additive` / `incompatible`。

**判定原则：不确定就全量重建**（`:15`）。返回值是给调用方与测试看的**判定证据**——
如果你在测试里发现 `syncGraph` 永远拿不到 `'none'`，说明每次都在重建，池化没生效。

**一个必须知道的方向性**：`applyDelta` 一开始就把 `lastSyncStamp = null`（`:311-312`），
因为增量之后图空间不再等于任何已知修订。所以「`applyDelta` 之后紧接着 `syncGraph`」
拿不到快路径 `'none'`——那是**正确**的，不是 bug。

### 5.3 `applyDelta` 的降级契约

`applyDelta(delta): DeltaApplicationResult`（`:306`，返回类型 `:124`）
→ `{ addedPaths, stalePaths, degradedRules }`。

| 事件 | 行为 |
|---|---|
| 删边 | `onEdgeRemovedDetailed` 只把经过该边的物化路径标 stale（O(k)），不重建索引（`:319-329`） |
| 增边 | `onEdgeAdded` 用「前缀 × 新边 × 后缀」物化新路径（`:331-343`） |
| 某规则 stale 比例 > 0.3，或增量枚举超工作预算 | 该规则索引被 `clear()` 并记入 `degradedRules`，本次 delta 内不再向它写入（`:314-317`、`:338-342`） |

**为什么「清空」比「半成品」安全**（`:302-304` 注释原文）：留一个**空索引**比留一个
「看起来完整、实际只含新边路径」的半成品安全——查询层据此回退全量枚举。

`wasLastIncrementalDegraded(index)`（`incremental.ts:103`）读的是**该索引的实例态**，
不是模块级全局（`XuanjiAdapter.ts:339-341` 注释：*"A 的降级会被 B 的正常调用清掉"*）。

### 5.4 `canApplyDelta`：池层的前置条件

`XuanjiAdapter.canApplyDelta(delta)`（`:368-383`）检查三件事，任一不满足就返回 `false`：

1. 删除/修改的**节点**都在当前空间里；
2. 删除/修改的**边**三元组都在；
3. 新增/修改边的**端点**可解析（在空间里，或在本次 `addedNodes` 里）——`:377-381`。

池层 `applyDelta`（`:684-693`）在 `false` 时**直接 `invalidate(repoId)` 并返回
`DELTA_SKIPPED`**，不尝试修补。理由（`:682`）：*"正确性优先于命中率"*。

### 5.5 规则校验的两个闸门

| 闸门 | 位置 | 何时执行 | 生产调用点 |
|---|---|---|---|
| `registerRule` | `:414-425` | 程序化注册时；`errors` 非空 ⇒ 不注册、`index` 返回 `null` | **0**（`:408-410` 自述） |
| `assertRule` | `:571-578` | `findPathsBetween` / `cycles` **每次调用** | **有**（生产必然执行的校验关口） |

`assertRule` 内部调 `validateRule`（`:397-400`），后者委托库的
`validateRuleSpec`（`:30` 导入自 `core/path-rule.ts:80`）。

> **不要把 `registerRule` 当成「唯一入口」**：它在生产上没有调用点。生产上的必然校验
> 是 `assertRule`。这条自述写在源码里（`:408-410`），文档若写成「注册即校验」就是造假。

## 6. 截断契约（XJ-07）

### 6.1 两种策略，显式选择

`EnumerateOptions.truncation`（`query/query-engine.ts:82`）：

```ts
readonly truncation?: 'dfs-order' | 'top-k-weight';   // 缺省 'dfs-order'
```

| 策略 | 语义 | 何时停 | 确定性 |
|---|---|---|---|
| `'dfs-order'`（缺省） | 达到 `maxPaths` **立刻停** | DFS 序 | 确定、可复现（DFS 序） |
| `'top-k-weight'` | 先收**全部**候选，再按权重降序取前 `maxPaths` | 候选集预算耗尽时**抛错** | 同分稳定保持 DFS 序（`topK` 的稳定性） |

**关键认知**（`:74-81` 的 JSDoc 原文）：*"`maxPaths` 只表示条数上限，本身不承诺
「保留最重要的那些」；要保权重必须显式选 `'top-k-weight'`"*。

### 6.2 `'top-k-weight'` 的候选集预算

`TOP_K_CANDIDATE_BUDGET = 100_000`（`query-engine.ts:38`），可用
`options.candidateBudget` 覆盖（`:84`、`:40-43`）。

超预算时**抛 `RuleCompositionError`**（`:139-143`），**不静默退回 DFS 序**。
理由（`:33-37`）：*"静默降级会让调用方以为拿到了高权重结果（与 XJ-10「非法规则不得
静默近似」同一立场）"*。

未知策略同样抛错（`:113-115`）：`unknown truncation strategy "..."`。

### 6.3 路径权重从哪来

`pathWeight`（`:51-63`）= 各步边的 `XJEdge.weight ?? 0` 之和。未标注权重的边贡献 **0**，
于是「所有权重都是 0」时 top-k 分数全相同、`topK` 的稳定性让它**退化为 DFS 序**——
确定且可复现（`:45-50`）。

> `XJEdge.weight` 目前**在生产数据里没有生产者**（宿主适配层 `xjEdge()` 不写 `weight`）。
> 所以 `'top-k-weight'` 现在是「契约已就位、数据未喂」的状态。改这个之前先问：
> 谁会给边打权重？没有答案就不要在文档里写「按权重保留最重要路径」。

### 6.4 `nfa.ts` 的现状（XJ-08）

`compileLengthNfa` 的实现只有 `states = lMax - lMin + 1`（`core/nfa.ts:38` 起的函数体），
**0 生产调用点**，豁免表登记 `owner: 'XJ-08'`
（`tests/unit/xuanjiReachability.test.ts:503` 附近）。

**cycle-111 的处理结论：选方案 A —— 删除**。

| 项 | 状态 |
|---|---|
| `src/xuanji/core/nfa.ts` | **已删除**（`ls src/xuanji/core/` 只剩 `graph-space.ts` / `path-rule.ts` / `path-entry.ts`） |
| barrel 导出 | 已移除；`src/xuanji/index.ts:11-12` 留了一段注释说明「已移除的模块（cycle-111 / XJ-08）」及理由 |
| 死符号豁免表 | `compileLengthNfa` / `NfaCompileResult` 两条**仍在表里**（实测 `tests/unit/xuanjiReachability.test.ts:502` / `:703`）——待 T1 一并清掉，或按「模块已删、符号不复存在」的语义改写 |
| 防复活 | 需要「负向导出断言 + `readdirSync('src/xuanji/core')` 文件清单断言」两条一起，否则模块可能被重建而无人发现 |

**为什么选 A**：它只有 `states = lMax - lMin + 1` 一个减法，而 `existsWalk`（`query-engine.ts:289`）
已经覆盖了「存在性」这个实际需求。方案 B（乘积存在性）的收益没有实测支撑——
为一个没有测量过收益的优化保留一个死模块，是「为不存在的问题写代码」的典型。

> ⚠️ **不要**因为「将来可能用得上」而恢复这个模块。若真需要，先给出复杂度对照数据。

### 6.5 长度上界只有一个实现

`effectiveMaxEdges(rule, |V|)`（`core/path-rule.ts:137`）是**唯一**的长度上界实现：

- 有限 `lMax` ⇒ 用它；
- 无界 + `simple` ⇒ 用 `|V|` 兜底；
- **无界 + 非 simple ⇒ 非法规则，直接抛错**（`query-engine.ts:99-101` 引用）。

`existsWalk` **刻意不用它**（`query-engine.ts:300-304`）：walk 存在性判定要在
「调用方违约的规则」上仍给出可靠的**否定**下界，无界时用 `|V|` 终止比抛错更有用。

**别把这两个函数的边界搞混**：`enumerate` 遇到无界非简单规则会**抛错**，
`existsWalk` 会**返回结果**。同一个规则对象，两个函数的反应不同，且都是有意的。

## 11. graph_integrity：白盒可观测面（cycle-132）

### 11.1 调用契约

```
graph_integrity({ repoId: string, drainChanges?: boolean })
→ {
    loaded: boolean,             // 未装载时其余字段全是零值——用它区分「空图」与「没装载」
    graph: { nodes, edges, version },
    changeLog: { pending, dropped, drained },  // drained 仅 drainChanges:true 时非 null
    rules: [{ name, counters: { total, stale } }],  // 注册序；休眠态为 []
    incrementalIdle: boolean,    // loaded && 零注册规则
  }
```

### 11.2 三条语义边界（调用方必读）

1. **默认只读**：`drainChanges` 缺省 false，报告只读水位。`drainChanges: true`
   会**消费掉**未读事件（drain 语义 = 取走即失）。把 `drainChanges: true`
   当「顺手刷新」用是错的——那会把内存问题换成数据丢失问题。
2. **I1/I2 刻意不跑**：覆盖型不变量在截断索引上必然伪违规（「少枚举了」≠「索引
   坏了」）。需要覆盖性验证时走测试 oracle（`tests/unit/xuanji/invariants.test.ts`），
   不要在工具层加。
3. **`incrementalIdle: true` 是正常态**：生产枚举（graph_path_enumerate /
   graph_cycles）用一次性内联索引，注册面恒空。它披露的是机理，不是故障告警。

### 11.3 宿主集成形状（守卫已钉）

| 接线点 | 守卫 |
|---|---|
| 工厂返回 `graphIntegrity` | tools.test.ts 集合守卫（12 项） |
| 入口 `ctx.tools.register(graphIntegrity)` | plugin.test.ts（工厂集合 == 注册集合 + 12 计数） |
| execute 先 `fetchMergedGraph` + `syncGraph` 再报告 | 与其余读法工具同链路（报告最新状态，不是陈旧健康度） |
| Skill 选择表第 7 条 | hostSkillContribution.test.ts |

### 11.4 D-06 关闭裁决

`drainChangeLog()` 的生产消费点 = `integrity({ drainChanges: true })` 的**显式**
排水路径。只读路径不消费事件——「报告」与「消费」两个动作在类型上分离
（`drained: number | null`），不会出现「查一下就把日志查没了」。

## 12. 路径模式 ρ：边类型序列正则（cycle-134）

> 本节接 §6 的截断契约与 §8 的禁止事项。研究对象是
> `src/xuanji/core/path-pattern.ts`（633 行）与它在适配层的桥
> `XuanjiAdapter.pathsByPattern`（`src/shared/analysis/XuanjiAdapter.ts:836`）。
> 完整的形式化推导、复杂度实测与诚实边界见
> [`docs/research/璇玑图路径模式-边序列正则研究.md`](../research/璇玑图路径模式-边序列正则研究.md)。

### 12.1 它解决什么：扁平 `edgeTypes` 的缺口

| | 扁平 `edgeTypes` | ρ |
|---|---|---|
| 表达 | 「每一步可以走这些类型之一」 | 「第一步 call、第二步 import、第三步 dependency」 |
| 判据位置 | `isLegalPath` 的 `hasEdgeOfType`（`core/path-rule.ts:315-317`） | `pathConstraint`（`core/path-rule.ts:319`） |
| 同一张图 `a-call->b-import->c` 与 `a-import->b-call->c` | 两条都返回 | 只有前者返回 |

**判据（什么时候用 ρ、什么时候用扁平 `edgeTypes`）**：

> 需要区分「多条边**各走一次**」与「任意一条边**重复走**」时用 ρ；
> 只需要「只能走这几类关系」时用扁平 `edgeTypes`。

具体地：

| 需求 | 用什么 | 理由 |
|---|---|---|
| 「调用传递闭包」`call+` | **扁平即可**（`edgeTypes: ['call']`, `lMin: 1`） | 单类型，序列约束退化为无约束；ρ 只是多付一次终判 |
| 「依赖闭包，不区分 import/dependency」 | **扁平即可** | `edgeTypes: ['import','dependency']` 语义完全相同 |
| 「先调用若干层，再跨文件导入」 | **必须 ρ** | 需要「切换」这个位置信息 |
| 「环枚举」 | **扁平**（`cycles()` 已封装） | 见 §12.4.1 的闭合差异 |
| 「只想知道有没有」 | **都不是**，用 `existsWalk` | 见 §12.3.5 的边界 |

### 12.3 常见错误（每条都有实测后果）

#### 12.3.1 把 `call+` 写成 `calls+`（类型名是单数）

Σ 的 9 个值是**单数**：`call / import / extend / implement / dependency / contains /
association / aggregation / composition`（`src/types/index.ts:64`）。
`tokenize` 不归一化大小写与词形（`core/path-pattern.ts:129-135`），所以
`calls` / `Call` 会被当作**两个不存在的类型**。

实测后果（三节点图，一条 `call` 边）：

```
ρ = "call+"   → OK, total=1
ρ = "calls+"  → OK, total=0   types=calls
ρ = "Call+"   → OK, total=0   types=Call
```

**三者返回面完全相同**（都是 `paths: []`、都没有 `error` 字段）。原因在
`XuanjiAdapter.ts:855-862`：ρ 合法但类型在当前图上不存在 ⇒ **合法零结果**，不抛错
（裁剪会把 `call . deadtype` 静默降级成 `call`，抛错会把合法空查询误判成非法规则——
两者都比零结果更糟）。

⇒ 调用方**必须读 `patternEdgeTypes`**（`XuanjiAdapter.ts:860` 回显）才能区分
「写错了」与「真的没有」。

> **无机器守卫**：没有用例断言「拼错类型名时返回什么」。
> `tests/unit/patternEnumerationAdapter.test.ts` 与 `tests/unit/xuanji/path-pattern.test.ts`
> 均无 `calls+` / `Call+` 形态的用例。上面这三行输出是本文的实测记录，
> **不是**被测试钉住的行为。

#### 12.3.2 把 `*` 用在无界 `lMax` 上

`call*` 的 `minEdges = 0`、`maxEdges = ∞`。`compilePathRule` 的处理
（`core/path-pattern.ts:588-604`）：

- `lMax` 留作 `Infinity`，交给 `effectiveMaxEdges`（`core/path-rule.ts:137`）用 `|V|` 兜底；
- **同时把 `simple` 强制为 `true`**（即使调用方传了 `simple: false`）。

第二点没有选择余地：无界 + 非 simple ⇒ 路径集合无限 ⇒ `validateRule` 判非法
（`core/path-rule.ts:99-101`），`enumerate` 直接抛错（`core/path-rule.ts:137-152`）。
强制 `simple` 而不是把 `lMax` 收到 `|V|` 的理由写在 `core/path-pattern.ts:585-587`：
后者会让「长度 ≤ |V| 的任意路径」冒充「简单路径」。

实测代价（600 节点链，`ρ = call*`）：878 ms 返回 300 条。它**能跑完**，
但代价与 `|V|` 同阶——图大了不该用无界 ρ，应写 `call{1,N}`。
用例：`tests/unit/xuanji/path-pattern.test.ts:337-352`。

#### 12.3.3 以为 `{n,m}` 的 `m` 是主要成本

`repeat` 的 `max` 在**编译期展开成 m 份拷贝**（`core/path-pattern.ts:281-287` 的注释）。
实测 `|Q|`：`call{1,8}` = 18、`call{1,50}` = 102、`call{1,500}` = 1002（≈ `2m + 2`）。

但**运行期终判成本几乎不变**（6 步路径上，`call+` 的 6 状态与 `call{1,500}` 的
1002 状态都是 ≈ 3.5–4 µs/条）。真正贵的是并列标签数与路径条数：

| ρ | \|Q\| | 标签/步 | 终判 ns/条（6 步） |
|---|---|---|---|
| `(call\|import)+` | 14 | 2 | ≈ 7 500 |
| `(call\|import\|extend\|implement\|dependency)+` | 26 | 5 | ≈ 15 000 |

⇒ 想省时间请收窄**并列标签数**（少用 `|`）与**路径条数**，而不是收窄 `m`。

#### 12.3.4 以为「语法错」与「零结果」长得一样

两者的返回面**必须**不同，且已经实现：

| 情形 | 返回 | 证据 |
|---|---|---|
| ρ 语法错（`call.`、`(call`、`call{3,2}`） | **抛 `PathPatternError`** | `core/path-pattern.ts:84`、`:626` |
| 工具层捕获后 | `{ paths: [], error: 'Invalid path pattern: …', diagnostic: '…^…' }` | `src/tools.ts:796-806` |
| 类型不在图上 / 真的没路径 | `{ paths: [], total: 0 }`，**无 `error` 字段** | `XuanjiAdapter.ts:855-862` |

工具层用 `instanceof PathPatternError` 判定（`src/tools.ts:802`），
不用 `e.name === 'PathPatternError'`（`src/tools.ts:16-18` 的注释说明：
`name` 可以被任意 Error 伪造）。
用例：`tests/unit/tools.test.ts:414-431`（语法错误带诊断）、`:433-450`（render 区分两态）、
`tests/unit/patternEnumerationAdapter.test.ts:163-174`。

#### 12.3.5 在 ρ 规则上调 `existsWalk`

`existsWalk`（`query/query-engine.ts:324`）**不检查 `pathConstraint`**
（其头注 `:311-317` 明说）。实测：

```
图：a --import--> b --call--> c
ρ = call . import
enumerate       → []         （顺序不对，拒绝）
existsWalk(a→c) → true       （顺序反了也说"存在"）
```

`existsWalk` 的 `false` 是可靠的否定下界，`true` **不代表**存在合法简单路径。
用 ρ 规则做「先判存在再枚举」会多枚举一轮——不是错误，但会白花钱。

### 12.4 两条语义边界（不是缺陷，但必须知道）

#### 12.4.1 闭合 ρ 与 `cycles()` 的条数不同

> **无机器守卫**：`tests/unit/patternEnumerationAdapter.test.ts` 全文不含 `closed`
> 字样；`tests/unit/xuanji/path-pattern.test.ts` 里 `closed` 不作为选项出现。

## 13. 拼错类型名诊断（`unknownEdgeTypes`）与语法预检（cycle-135）

本节接 §12.3.1 的「把 `call+` 写成 `calls+`」——cycle-134 只说明了这是常见错误，
**没有给机器守卫**；cycle-135 把诊断做成一等公民。

### 13.1 为什么「拼错」与「缺失」必须分开

适配层的早期实现只有一句 `absent = [...compiled.edgeTypes].filter(t => !present.has(t))`：
「Σ 里没有的类型」与「Σ 里合法但这张图上没有的类型」被混在同一个集合里。两者都产出
`paths: []`，但**诊断含义与用户下一步动作完全不同**：

| ρ | `unknownEdgeTypes` | 语义 | 用户该做什么 |
|---|---|---|---|
| `calls+` | `['calls']` | Σ 里没有 `calls`（拼错） | 改用 `call` |
| `Call+` | `['Call']` | 同上（不归一化大小写） | 改用 `call` |
| `contains+`（本图无 contains 边） | `[]` | 合法的零结果 | 这是正常答案 |
| `association . aggregation . composition` | `[]` | 同上（Σ 成员但全仓无生产者） | 正常答案 |

⇒ **判断口径是 `KNOWN_ADAPTER_EDGE_TYPES`（Σ 全集），不是「图上有没有」。**
若把两者混在一个集合里返回，调用方无法区分「我写错了」与「图上没有」，必然误判。

### 13.2 API 面（已落地，按实际签名写）

#### 13.2.1 适配层（`src/shared/analysis/XuanjiAdapter.ts`）

| 符号 | 行 | 契约 |
|---|---|---|
| `KNOWN_ADAPTER_EDGE_TYPES` | `:74` | `ReadonlySet<AdapterEdgeType>`，Σ 全集（9 值） |
| `PatternEnumerationResult.unknownEdgeTypes` | `:180` | `readonly string[]`；非空 ⇒ `paths` 必为 `[]` |

`pathsByPattern` 的判据顺序（**不可颠倒**）：

```ts
const unknownEdgeTypes = [...compiled.edgeTypes]
  .filter((type) => !KNOWN_ADAPTER_EDGE_TYPES.has(type as AdapterEdgeType)).sort();
const absentFromGraph = [...compiled.edgeTypes]
  .filter((type) => KNOWN_ADAPTER_EDGE_TYPES.has(type as AdapterEdgeType) && !present.has(type)).sort();
if (unknownEdgeTypes.length > 0 || absentFromGraph.length > 0) {
  return { paths: [], ..., unknownEdgeTypes };
}
```

**这同时绕开 `assertRule` 的 Σ_R ⊆ Σ 静态校验**：那个校验按「边类型必须出现在图里」
判非法规则，对 ρ 会把「合法的零结果」误判成「非法规则」。

#### 13.2.2 路由层（`src/host/routes/pathsRoute.ts`）

| 符号 | 说明 |
|---|---|
| `PATH_PATTERN_SYNTAX_ROUTE_PATH` | `/api/v1/codegraph/path-pattern/syntax` |
| `/paths?pattern=` 200 响应 | 增 `unknownEdgeTypes: result.unknownEdgeTypes` |
| `/path-pattern/syntax?pattern=` | 200 `{ ok:true, pattern, edgeTypes }` 或 `{ ok:false, pattern, error, diagnostic, edgeTypes }` |

**两条路由的职责边界**（不可混淆）：

- `/paths?pattern=`：回答「这条 ρ 在**这张图**上能匹配到什么」→ 会返回
  `unknownEdgeTypes`（依赖图上的边）。
- `/path-pattern/syntax`：回答「这条 ρ **文本**能否被解析」→ **不**返回
  `unknownEdgeTypes`（拼错类型名语法合法，只有枚举才能发现）。它也不碰工作区解析
  （没有图可查），因此宿主还没建索引时就能用。

#### 13.2.3 工具层（`src/tools.ts`）

`graph_path_pattern` 的 `render`：`unknownEdgeTypes` 非空时渲染
「Unknown edge type(s): …。Valid types: …」，**不**显示「No path found」。

#### 13.2.4 客户端（`src/client/api/pathPattern.ts`）

- `fetchPathsByPattern(params)` → 判别联合 `data | invalid | not-found | timeout | failed`。
- `fetchPathPatternSyntax(pattern)` → 单形状 `{ ok, pattern, edgeTypes, ... }`。
  刻意不用判别联合：宿主用 **200** 表达语法对/错，调用方总是先读 `ok`。

### 13.3 客户端面板的终态（`pathPatternStatus`）

`idle / loading / ready / empty / invalid / not-found / unknown-types / error / timeout`。

**核心不变量**：`unknownEdgeTypes` 非空 ⇒ 终态 `'unknown-types'`，渲染
`.cg-pathpattern-unknown`（黄边），**绝不**渲染 `.cg-pathpattern-empty`。

### 13.4 常见错误（每条都有实测后果）

#### 13.4.1 把 `calls` 当成「图上没有 call 边」

- **症状**：`unknownEdgeTypes` 恒为 `[]`，面板显示「没有匹配」。
- **实测后果**：M1 变异（`unknownEdgeTypes: string[] = []`）⇒ 9 例中 **5 例变红**。
- **修法**：判据用 `KNOWN_ADAPTER_EDGE_TYPES`，不要用 `present.has(...)`。

#### 13.4.2 在语法预检路由里返回 `unknownEdgeTypes`

- **症状**：`calls+` 被误报成语法错（`ok: false`），用户以为模式写法有问题。
- **实测后果**：`tests/unit/pathsRoute.test.ts`「预检不返回 unknownEdgeTypes」用例变红。
- **修法**：拼错类型名**语法合法**，只有枚举才能发现。预检只回答「能不能解析」。

#### 13.4.3 客户端硬编码 Σ 类型名列表

- **症状**：Σ 在宿主侧改动后，客户端提示区与之静默分叉。
- **修法**：Σ 是宿主侧事实，用 `/path-pattern/syntax` 回显的 `edgeTypes` 渲染提示区。

#### 13.4.4 用 `!res.ok` 判断 400

- **症状**：语法错被当成网络失败（`kind: 'failed'`），UI 显示「查询失败」而非诊断。
- **实测后果**：`tests/unit/pathPatternApi.test.ts`「400 + diagnostic ⇒ kind: invalid」变红。
- **修法**：400 必须在 `!res.ok` **之前**判出。
