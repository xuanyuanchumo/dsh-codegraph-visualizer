## 1. 状态四态（与评估体系的三态对齐）

| 状态 | 含义 | 允许出现在结论里吗 |
|---|---|---|
| `PASS` | 有阈值、有命令、实跑通过，且**失败会真的变红**（有变异探针或反向用例） | 是 |
| `部分` | 机器只证「存在/形状」，**不证质量**（例如「有 `aria-` 属性」不等于可访问） | 是，必须写清它证到什么程度 |
| `待收尾` | 本轮（cycle-110）正在改，收尾时复核 | 收尾后必须转 PASS 或如实降级 |
| `无机器守卫` | 没有任何自动化能发现违规，只能靠评审 | **必须**显式标注，不得省略 |

**判据的判据**：一条判据如果删掉被测代码仍然通过，它就不是判据。
本仓库已发生三次同类事故（`visualBaselineContract` 自匹配、`dropdown` 定位、`defineTool` presenter 短路），
故凡「源码形态守卫」都必须带反向自检与「扫描文件集非空」断言（规范见 [01](./01-插件开发规范.md) §6.3）。

## 10. effect 内 setState 的引用守卫（cycle-113）

**教训**：在 `useEffect` 内无条件 `setState` 写**新对象/数组引用**，即使值语义不变，
也会让 React 18 `renderHook` / StrictMode 环境反复重渲染直至 OOM（heap out of memory）。
实证：cycle-113 的 `useAnalysisPanels` godModule 扫描态 effect，10 行最小探针即可复现。

**判据（评审必查）**：

```ts
// 反例（OOM）：值不变也写新引用
setGodModuleScan({ scanned: false, nodeCount: 0 });

// 正例：值不变时返回原引用
setGodModuleScan((prev) => (prev.scanned || prev.nodeCount !== 0 ? { scanned: false, nodeCount: 0 } : prev));
setGodModules((prev) => (prev.length === 0 ? prev : []));
```

**测试信号**：单个 hook 测试文件 OOM（`Reached heap limit`），且 `git stash` 对照后旧代码绿——
先怀疑 effect 内 setState 引用循环，再怀疑被测代码本体。
## 9. 判据的维护规则

1. 改任何阈值，必须同步改**三处**：`vitest.config.ts` / `scripts/perf-gate.mjs` 的 `BUDGET` 或本文件表格 /
   对应守卫测试的断言。三处不同步时，以测试断言为准（它是唯一会变红的地方）。
2. 新增一条判据时，**先写失败用例**再写实现；只有「删掉实现会红」的判据才配写 `PASS`。
3. 本文件与 [`docs/测试体系.md`](../测试体系.md) 的分工：测试体系写「有哪些测试层、怎么组织」，
   本文件写「达到什么数值才算过、用什么命令验」。两者引用同一批用例文件，不复制断言代码。
4. 收尾时把 `待收尾` 逐条转成 `PASS` 或降级为 §8 缺口，不允许留空。
