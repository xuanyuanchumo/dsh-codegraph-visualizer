## J0 前置检查（真机验证前必做）

J0 是唯一在**真实 DSH 宿主**里跑的旅程，本仓库的 `./scripts/start-dsh-test.mjs` 已把下面两项
做成启动期检查，但手工验证时仍需人工确认结论。

### 1. 认证 URL 只能从 DSH 的 stdout 取，不能猜

`dsh web` 的令牌只打印在 stdout（形如 `dsh web: http://127.0.0.1:3080/?token=<token>`），
参数名就是 `token`（**不存在** `web_token` / `DSH_WEB_TOKEN`，真实读取者在
`@deepseek-ai/dsh-client-connection/lib/index.js:226`，令牌存在进程内存里，不落盘）。
Windows 上 `dsh.cmd` 是 npm 垫片，`detached` 启动时 stdout 会被丢弃，因此启动器改为
**直接用 `process.execPath` 拉起 `@deepseek-ai/dsh/lib/bin.js`** 并解析日志行
（`DSH_URL_LINE_RE = /dsh web:\s*(https?:\/\/\S+)/`），只在解析失败时才回退 `cmd.exe`。
若 J0 页面出现 `authentication required`，先看启动日志里有没有 `认证 URL 已捕获`。

### 2. 安装锚点里不能存在本插件的旧副本

DSH 解析 bundle 元数据用的是 `@deepseek-ai/dsh-app-boot/lib/index.js:889-907 resolveBundleDir`，
顺序是 **安装目录（running dsh 自身所在的 `node_modules`）优先，profile 目录其次**。
只要安装锚点里有一份同名旧副本，bundle 级 `version` / `meta`（locale 标题）/ `icon`
**全部来自那份旧副本**，而 profile 里的 `link:` 只在 `rows[]` 与客户端半边生效 ——
表现为插件列表显示**包名**而非 locale 标题、版本号诡异（例：实测被
`D:\JetBrains\nvm\node_global\node_modules\dsh-codegraph-visualizer` 的 2.1.0 旧副本遮蔽，
改名让路后同一 RPC 立即返回 `version:"0.2.0"`、`meta.title:{en,zh,zh-cn}`、`iconLen:1494`）。
启动器会在启动时打印 `!!! 安装锚点存在本插件的另一份副本…` 告警；它不是清单缺陷，
把该副本**改名让路**（不要删除，可逆）后重新拉取即可。

### 3. J0 通过判据（真机实测口径）

- `window.__DSH_BOOT__.entries` 中存在 `{ id: "dsh-codegraph-visualizer", inject: [...3 条官方边] }`；
- 顶部标签栏出现与 `对话`/`轨迹` **同级**的 `代码图谱` 标签（`[role="tab"]`，`aria-selected="true"`）；
- `.cg-graph-panel` 存在、`.cg-graph-container` 高度 > 0、`canvasCount === 3`；
- 插件列表条目渲染为 `代码图谱可视化` + 本地化描述，且图标为 base64 `data:image/svg+xml`；
- 状态栏显示 `✓ 图谱完整 (N 节点)`；
- **工具栏在任意面板宽度下都不得"看起来在、点不到"**：把 `.cg-graph-panel` 的宽度从日常宽度扫到 300px，
  在每个宽度上对工具栏内**所有可见**控件做 `elementFromPoint` 命中测试，被裁控件数必须为 0
  （中心组在 ≤600px 档由 `@container graphpanel` 主动隐藏，属设计内隐藏而非被裁）。实测口径与
  修复前的证据见 `docs/测试体系.md` 的"响应式契约回归测试"。
- **装饰性文字与状态色必须随主题真的变化，不能"看着有样式、其实没生效"**：在浅色与深色之间来回切换，
  至少核对 `.cg-tour-step-description` 的文字色（应命中 `--cg-text-secondary`，而不是继承色）、
  `.cg-deadcode-stat-badge.cg-confirmed` 的底色（浅 `#e74c3c` / 深 `#f87171`）与
  `.cg-tour-step-layer[data-layer="api"]` 的底色（浅 `#2196f3` / 深 `#42a5f5`）。修复前这三处的

  `tests/unit/tokensContract.test.ts` 持有（见 `docs/需求分析.md` §31.5）。

  `performance.getEntriesByType('resource')` 里 `.wasm` 请求必须为 **0 条** —— tree-sitter 只在宿主

### 4. 不要指望上游 `dsh-codegraph` 的工具（Windows 上桥会被拉起但随即死亡）

J0 里 `prerequisite status` 报 `codegraph: false` 属于**预期**，不是回归：上游 `0.1.3` 的
MCP 桥包装器 `lib/codegraph/serve.js` 其实**会被插件正常拉起**（`config.js:43` 的 `mcpEnabled`
默认 `true`；实测进程 `node.exe …\dsh-codegraph\lib\codegraph\serve.js` PID 11396 / 父进程 DSH 10480），
但它自己 spawn CLI 时解析到 npm 生成的 POSIX shim `…\node_global\codegraph`（无扩展名），以
`spawn …\node_global\codegraph ENOENT` 失败并退出（进程一分钟后消失），`tools/list` 永不完成，故
`mcp__codegraph__codegraph_explore` 从不注册（复现与根因见
`docs/research/dsh-0.2.0-插件API权威基线.md` §5.2）。因此 J0 的验收必须建立在**内置扫描**上：
`.codegraph-visualizer/viz.db` 存在、状态栏 `✓ 图谱完整 (N 节点)`、画布真的画出节点与边，
而不是"上游工具可用"。
