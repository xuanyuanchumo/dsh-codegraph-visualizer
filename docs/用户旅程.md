> 本文件只做三件事：①每条旅程的**可执行判据**与**自动化锚点**；②真机（J0）前置检查；③「文档说有、代码没有」的显式登记。
> 口径：2026-10-28 / cycle-111。**自动化锚点由脚本反向扫描 `tests/**` 的 `J<n>` 标注得出，不是人工回忆**；
> 复核命令见文末 §复核。上一版（J0–J48）的旅程文本已逐条保留，只补字段不删事实。

> **优先级说明**：P0=核心旅程（必须100%通过），P1=重要旅程，P2=增强旅程，P3=辅助旅程

## 一、模板与状态约定

每条旅程六个字段：**前置条件**（S 代号）、**步骤**（关键路径，`→` 之后即期望）、**证据**（门禁归属）、
**自动化锚点**（`spec :: describe 标题`）、**关联用例 ID**（`J<n>@<文件>`）、**反向/异常**。

| 状态 | 判定标准（必须能机械核对） |
|---|---|
| `automated` | 存在**标题级** `J<n>` 标注的用例，且所在 project 在默认门禁内（`pnpm run test` 或 `--project=regression`） |
| `automated（门禁外）` | 有用例，但所在 project 不在 CI / 默认命令里（本文件仅 `performance`） |
| `manual` | 只有真机清单，没有任何自动用例 |
| `gap` | 文档承诺、代码没有可执行覆盖；含「本轮并发交付中」 |

| 前置条件代号 | 含义 |
|---|---|
| `S1` | dev-server 就绪：`setupPluginPage` 成功（MOCK_GRAPH 21 节点已载入、`.cg-graph-panel` 可见） |
| `S2` | S1 + **必须切到行为层**（`setupPluginPageInBehavioralLayer`）——目标面板在 structural 层不渲染 |
| `S3` | 真实 DSH 宿主（§J0.1–J0.5 全过）+ 真机 Chrome 或桌面端 |
| `S4` | 纯单测环境（`pnpm run test`，node/jsdom），不需要浏览器 |
| `S5` | 真实 git 仓库（`HAS_GIT`；无 git 时整组 `skipIf` 跳过，不是失败） |

### J0.1 启动器三条实测修复（cycle-110，失败时先查这里）

`scripts/start-dsh-test.mjs` 本轮修掉三个**都由真机实测暴露**的启动缺陷。它们的共同症状是「60s 未就绪」，

| # | 缺陷 | 旧行为 | 现实现 | 失败时的可观测证据 |
|---|---|---|---|---|
| 1 | **Electron 垫片解析** | 按 `<bin>/node_modules/@deepseek-ai/dsh/lib/bin.js` 解析桌面运行时的 `dsh.cmd` → 失败 → 回退 `cmd.exe` 垫片 → stdout 被丢弃 | 新增 `resolveElectronShim()`：识别 `set ELECTRON_RUN_AS_NODE=1` + `DeepSeek Harness.exe --expose-internals …app.asar\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\cli.js` 形态，用同一个 exe + `ELECTRON_RUN_AS_NODE=1` 拉起 | 日志里没有 `认证 URL 已捕获`，且进程是 `cmd.exe`；**实际 DSH 30s 内就能起**，被判成 60s 未就绪 |

### J0.2 认证 URL 只能从 DSH 的 stdout 取，不能猜

`dsh web` 的令牌只打印在 stdout（形如 `dsh web: http://127.0.0.1:3080/?token=<token>`），
参数名就是 `token`（**不存在** `web_token` / `DSH_WEB_TOKEN`，真实读取者在
`@deepseek-ai/dsh-client-connection/lib/index.js:226`，令牌存在进程内存里，不落盘）。
Windows 上 `dsh.cmd` 是 npm 垫片，`detached` 启动时 stdout 会被丢弃，因此启动器改为
**直接用 `process.execPath` 拉起 `@deepseek-ai/dsh/lib/bin.js`** 并解析日志行
（`DSH_URL_LINE_RE = /dsh web:\s*(https?:\/\/\S+)/`），只在解析失败时才回退 `cmd.exe`。
若 J0 页面出现 `authentication required`，先看启动日志里有没有 `认证 URL 已捕获`。

### J0.3 安装锚点里不能存在本插件的旧副本

DSH 解析 bundle 元数据用的是 `@deepseek-ai/dsh-app-boot/lib/index.js:889-907 resolveBundleDir`，
顺序是 **安装目录（running dsh 自身所在的 `node_modules`）优先，profile 目录其次**。
只要安装锚点里有一份同名旧副本，bundle 级 `version` / `meta`（locale 标题）/ `icon`
**全部来自那份旧副本**，而 profile 里的 `link:` 只在 `rows[]` 与客户端半边生效 ——
表现为插件列表显示**包名**而非 locale 标题、版本号诡异（例：实测被
`D:\JetBrains\nvm\node_global\node_modules\dsh-codegraph-visualizer` 的 2.1.0 旧副本遮蔽，
改名让路后同一 RPC 立即返回 `version:"0.2.0"`、`meta.title:{en,zh,zh-cn}`、`iconLen:1494`）。
启动器会在启动时打印 `!!! 安装锚点存在本插件的另一份副本…` 告警；它不是清单缺陷，
把该副本**改名让路**（不要删除，可逆）后重新拉取即可。
