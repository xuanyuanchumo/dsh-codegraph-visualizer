## J0 前置检查（真机验证前必做）

J0 是唯一在**真实 DSH 宿主**里跑的旅程，本仓库的 `./scripts/start-dsh-test.mjs` 已把下面两项
做成启动期检查，但手工验证时仍需人工确认结论。

### 1. 认证 URL 只能从 DSH 的 stdout 取，不能猜

`dsh web` 的令牌只打印在 stdout（形如 `dsh web: http://127.0.0.1:3080/?token=<token>`），
参数名就是 `token`（**不存在** `web_token` / `DSH_WEB_TOKEN`，真实读取者在
`@deepseek-ai/dsh-client-connection/lib/index.js:226`，令牌存在进程内存里，不落盘）。
Windows 上 `dsh.cmd` 是 npm 垫片，`detached` 启动时 stdout 会被丢弃，因此启动器改为
**直接用 `process.execPath` 拉起 `@deepseek-ai/dsh/lib/bin.js`** 并解析日志行
（`DSH_URL_LINE_RE = /dsh web:\s*(https?:\/\/\S+)/`），只在解析失败时才回退 `cmd.exe`。
若 J0 页面出现 `authentication required`，先看启动日志里有没有 `认证 URL 已捕获`。

### 2. 安装锚点里不能存在本插件的旧副本

DSH 解析 bundle 元数据用的是 `@deepseek-ai/dsh-app-boot/lib/index.js:889-907 resolveBundleDir`，
顺序是 **安装目录（running dsh 自身所在的 `node_modules`）优先，profile 目录其次**。
只要安装锚点里有一份同名旧副本，bundle 级 `version` / `meta`（locale 标题）/ `icon`
**全部来自那份旧副本**，而 profile 里的 `link:` 只在 `rows[]` 与客户端半边生效 ——
表现为插件列表显示**包名**而非 locale 标题、版本号诡异（例：实测被
`D:\JetBrains\nvm\node_global\node_modules\dsh-codegraph-visualizer` 的 2.1.0 旧副本遮蔽，
改名让路后同一 RPC 立即返回 `version:"0.2.0"`、`meta.title:{en,zh,zh-cn}`、`iconLen:1494`）。
启动器会在启动时打印 `!!! 安装锚点存在本插件的另一份副本…` 告警；它不是清单缺陷，
把该副本**改名让路**（不要删除，可逆）后重新拉取即可。

### 3. J0 通过判据（真机实测口径）

- `window.__DSH_BOOT__.entries` 中存在 `{ id: "dsh-codegraph-visualizer", inject: [...3 条官方边] }`；

- **工具栏在任意面板宽度下都不得"看起来在、点不到"**：把 `.cg-graph-panel` 的宽度从日常宽度扫到 300px，

  Round 9 把类型表改成**按语法**声明（只收录实测可得到真实标签的类型），并给 `extractName` 补上
  `name` → `type` → 首个 identifier 子节点的回退链。J0 判据：`POST /api/v1/codegraph/tree-sitter?workspace=<仓库>`
  用**内联** rust 源码 → 200 且 nodes 含 `function:main/method/area`、`class:Bar/Color/Shape`、
  `variable:x/LIMIT` 且**不含 `<impl_item>`**；内联 ts 源码 → `class:Bar` / `variable:y`（不得出现
  `<variable_declaration>`）。注意该路由在 Windows 上原先**只接受反斜杠相对路径**（正斜杠 → 400
  `INVALID_FILEPATH`，与 `/ast` 路由口径不一致）；**Round 10 已修**，判据改为"与 `/ast` 同口径"：
  `src/App.tsx` / `src/client/App.tsx` / `src\App.tsx` 都必须 200，而 `../secrets.ts`、
  `C:\Windows\win.ini` 必须 400 `INVALID_FILEPATH`（含 NUL 的 `filePath` 在字段层就被丢弃，返回
  `FILEPATH_AND_CONTENT_REQUIRED`）。机制与回归锁见 `docs/测试体系.md` 的
  "多语法符号抽取回归测试"与"路径形状口径 + 搜索选中即可见回归测试"。
- **悬停展开子节点不得崩、且布局要真的跑完（Round 9 已修）**：把布局切到 **cose**（原崩溃布局）后对文件节点
  依次 `n.emit('mouseover')` 触发 children 增量加载，节点数必须增长，且
  `window.__cgErrors`（`error` + `unhandledrejection` 监听）必须为空、控制台不得出现 `incremental layout failed`。
  Round 8 曾在此处收到 1 条未捕获 `TypeError: Cannot read properties of undefined (reading 'children')`
  （根因：只把**新增**节点交给子集布局，其复合父不在集合内 → Cytoscape 核心 `cose` 的
  `layoutInfo.idToIndex[parent_id]` 为 undefined；见 `docs/需求分析.md` §31.8）。回归锁见
  `docs/测试体系.md` 的"增量布局复合回归测试"。
- **CFG 微图的节点/边必须是自洽的、`invalid endpoints` 属绘制期警告（Round 9 改判）**：选中函数节点 →
  详情面板点 **CFG** → 微图必须渲染出节点与边、0 未捕获异常；对活的 Cytoscape 实例按 id 核对，边集合中
  **不得有任一 dangling 边**（Round 9 实测 12 节点 / 13 边、`cfg-edge-0..12` 全在图中）。控制台出现的
  `Edge 'cfg-edge-N' has invalid endpoints` 是 Cytoscape 的 `checkForInvalidEdgeWarning`
  （`client.js:35440`，文案自带"两节点重叠时的预期行为"），不是数据缺陷 —— 同一实例里该边两端节点真实存在
  且位置不同。装配层的不变量由 `tests/unit/cfgIntegrity.test.ts`（13 条）持有。
- **搜索结果 / 符号选中必须把节点带进视野（Round 10 已修）**：搜索命中的节点若已被 `hideNode` 隐藏
  （`src/client/renderer/CytoscapeRenderer.ts:245-247` 设 `display: none`），旧行为只更新选中态与详情面板，
  用户看到的是"点了没反应"。J0 判据（真机，L3 视图 50 节点 · 6 边）：①把目标节点的 `display` 置 `none`
  （与 `hideNode` 等价，`CytoscapeRenderer.ts:246` 就是这一句）后搜索并选中该结果 → `display` 回到 `element`，
  且节点渲染坐标 = 视口中心（距中心 `(0,0)`）；②先 `cy.pan({x:0,y:0})` 把节点挪出视口
  （实测渲染坐标 `(-282.16,-15.81)`、距中心 `(-692,-194)`），再选中同一结果 → `pan` 必须回到让该节点居中的
  偏移（实测 `{692.16, 194.31}`、节点回到中心 `(0,0)`）；③**负例**：在"筛选与连接数"面板取消勾选该节点类型
  （该视图 50 个节点全是 `module`）后选中结果 → 详情面板仍更新选中语义，但**视口不得移动**（`pan` 保持不动）、
  节点仍不可见，且控制台必须出现
  `[codegraph:panel] search result is not revealable in the rendered graph`（设计内行为，不是缺陷）。
  机制与回归锁见 `docs/需求分析.md` §31.9 与 `docs/测试体系.md` 的"路径形状口径 + 搜索选中即可见回归测试"。
- **路径类判据（Round 8 已修复，判据改为"必须 200"）**：Round 7 实测 `/api/v1/codegraph/ast` 对任何
  `filePath`（含 `package.json`、活动工作区内的真实文件）都返回 403 `SYMLINK_ESCAPE`，
  `/api/v1/codegraph/dependencies` 无论带不带 `path` 都返回 403 `WORKSPACE_PATH_NOT_ALLOWED`，**连活动
  工作区自身也被拒**（根因：allowlist 在 `apply()` 冻结一次 + 相对路径按 `workspaceRegistry.list()[0]` 解析）。
  Round 8 修复后 J0 判据是：`GET /api/v1/codegraph/workspace` → 200 且暴露 `allowedRoots`（须含当前仓库）/
  `rootSource`/`resolvedFrom`；`POST /api/v1/codegraph/ast?workspace=<仓库>`（真实文件）→ **200**、响应不含
  `"ERROR"`（真实文件里 `.ts`/`.tsx` 的 AST 必须无 ERROR 节点）；不带 `?workspace=` 时对"不在活动工作区
  内的相对路径"仍应 403 —— 这正是客户端必须钉住工作区的原因；`GET /api/v1/codegraph/dependencies?workspace=<仓库>`
  → 200。界面闭环判据：切到目标仓库后选中函数节点、在详情面板点 **CFG**，发出的请求必须带
  `?workspace=<仓库>` 且微图能渲染出节点/边。机制与回归锁见 `docs/需求分析.md` §31.7 与
  `docs/测试体系.md` 的"工作区路径契约回归测试"；Round 8 在该处附带暴露的 Cytoscape 增量布局异常与
  `invalid endpoints` 警告，已在 Round 9 查清并处置（见上面的多语法、悬停展开、CFG 自洽三条判据与
  `docs/需求分析.md` §31.8）。

### 4. 不要指望上游 `dsh-codegraph` 的工具（Windows 上桥会被拉起但随即死亡）

J0 里 `prerequisite status` 报 `codegraph: false` 属于**预期**，不是回归：上游 `0.1.3` 的
MCP 桥包装器 `lib/codegraph/serve.js` 其实**会被插件正常拉起**（`config.js:43` 的 `mcpEnabled`
默认 `true`；实测进程 `node.exe …\dsh-codegraph\lib\codegraph\serve.js` PID 11396 / 父进程 DSH 10480），
但它自己 spawn CLI 时解析到 npm 生成的 POSIX shim `…\node_global\codegraph`（无扩展名），以
`spawn …\node_global\codegraph ENOENT` 失败并退出（进程一分钟后消失），`tools/list` 永不完成，故
`mcp__codegraph__codegraph_explore` 从不注册（复现与根因见
`docs/research/dsh-0.2.0-插件API权威基线.md` §5.2）。因此 J0 的验收必须建立在**内置扫描**上：
`.codegraph-visualizer/viz.db` 存在、状态栏 `✓ 图谱完整 (N 节点)`、画布真的画出节点与边，
而不是"上游工具可用"。
