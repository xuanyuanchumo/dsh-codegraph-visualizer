# 璇玑图思维 → 本项目数据结构与算法优化方案

> 基于 `docs/research/璇玑图思维算法.md`（v1.0 规范）对本项目 `dsh-codegraph-visualizer` 现有代码的研究分析。
> 原则：**不造轮子**——将璇玑图范式映射到项目既有结构，复用既有依赖（graphology / cytoscape / FNV 哈希 / GraphDelta），不引入平行实现。

---

## 一、璇玑图思维核心提炼

璇玑图规范的本质是一个**图空间路径枚举与索引维护范式**，其可迁移的思维内核有六条：

| # | 思维内核 | 规范出处 | 一句话 |
|---|---------|---------|--------|
| X1 | **内容与规则分离** | §2.2、§3.1 | 图数据与"怎么读"的规则解耦，规则声明式、可组合、可热插拔 |
| X2 | **增量优先于全量** | §5.2、§5.3 | 边变化时只维护受影响路径，而非全量重建 |
| X3 | **长度分桶裁剪** | §4.2、§5.2 | 按路径长度分桶，增量配对时只遍历合法长度组合，避免全笛卡尔积 |
| X4 | **不变量驱动局部重组** | §4.4、§5.5 | 用 O(1) 计数器监控索引健康，违规只触发 1-hop 邻域重组 |
| X5 | **输出敏感而非输入敏感** | §5.1、§六 | 复杂度按输出规模 |O_R| 而非输入规模 b^l 衡量 |
| X6 | **规范化幂等 + 滚动哈希** | §2.3、§5.2 | Booth O(L) 规范化 + 滚动哈希 O(1) 组合，替代排序去重 |

## 二、项目现状盘点

### 2.1 核心数据结构

| 文件 | 结构 | 现状复杂度 | 璇玑图对应 |
|------|------|-----------|-----------|
| `AdjacencyList.ts` | `Map<ID, ID[]>` forward/backward/undirected | 构建 O(V+E)，查询 O(deg) | §4.1 `outAdj`/`inAdj` |
| `AdjacencyCache.ts` | forward/backward/undirected/edgeIdMap + 单布尔 `valid` | 全量重建 O(V+E) | §4.1 `GraphSpace`，但缺 `edgeMap` 多重边键 |
| `QuadTree.ts` | 四叉树空间索引 | 插入/查询 O(log n) | （璇玑图不涉及，空间索引独立） |
| `Trie.ts` | 前缀树 | 插入/搜索 O(L) | （搜索专用，与路径索引正交） |
| `graphDelta.ts` | added/removed/modified × nodes/edges | apply O(N+E) | §5.2 增量结构，但只到图层不到路径层 |
| `graphFingerprint.ts` | FNV-1a 64-bit 全图内容哈希 | O(V+E) | §5.2 滚动哈希的"全图版" |

### 2.2 核心算法

| 文件 | 算法 | 现状复杂度 | 璇玑图对应 / 差距 |
|------|------|-----------|------------------|
| `CycleDFS.ts` | 迭代 DFS 环检测 | O(V+E) 最坏，去重用 `sort().join('|')` O(L log L) | §5.1 枚举；**去重应改 Booth O(L)** |
| `GraphBFS.ts` | BFS 最短路 / 前沿扩展 / 可达计数 | O(V+E) | §5.1 枚举的 l_max=∞ 退化 |
| `PathFinder.ts` | 双向 BFS 最短路 | O(b^(d/2)) | §5.4 查询；**每次从零算，无物化索引** |
| `ImpactAnalyzer.ts` | BFS 影响传播（按深度分层） | O(V+E) per query | §5.1 枚举的 l_max=depth 特例；**无缓存** |
| `DeadCodeAnalyzer.ts` | 从入口 BFS 可达性 | O(V+E) | §5.1 枚举；**全量重算** |
| `CoreFunctionAnalyzer.ts` | 逐节点 BFS 影响范围 + 递归调用链深度 | O(V×(V+E)) **输入敏感** | §5.1；**X5 可改为输出敏感** |
| `HotspotAnalyzer.ts` | 入度 × churn 打分 | O(V+E) | （打分专用，与路径正交） |
| `HealthScorer.ts` | 耦合/内聚/环率/模块度 | O(V+E) per dim | §4.4 不变量思路可复用 |
| `GraphologyAdapter.ts` | Louvain 社区 + 度中心性 + BFS | 依赖 graphology | §5.6 NFA 存在性可替代部分全量遍历 |
| `incrementalCluster.ts` | 增量聚类（变化比例阈值降级） | O(ΔV+E) | §5.5 局部重组思路已部分实现 |
| `incrementalUpdate.ts` | 文件级增量图 diff | O(ΔV+ΔE) | §5.2 增量，但**只到图层不到派生分析层** |

### 2.3 关键差距（grep 确认项目中不存在的璇玑图结构）

```
edgeToPaths  — 无（删除/失效时无法 O(k) 定位受影响路径）
startIndex   — 无（无按起点+长度分桶的路径索引）
endIndex     — 无（无按终点+长度分桶的路径索引）
hashIndex    — 无（无路径级规范哈希去重）
length bucket — 无（增量配对无长度裁剪）
rollingHash  — 无（路径哈希每次全算）
Booth        — 无（环去重用 sort().join）
invariant    — 无（派生结果无健康监控）
rebalance    — 无（派生结果无局部重组）
NFA          — 无（存在性判断走全量遍历）
```

## 三、映射分析：璇玑图概念 → 项目结构

### 3.1 图空间 G = (V, E, Σ, τ, A) → 既有 GraphData

项目已有 `GraphData { nodes, edges, metadata }`，边有 `type`（call/import/extend/...），节点有 `properties`。
**映射**：`V`=nodes, `E`=edges, `Σ`=edge.type 枚举, `τ`=edge.type, `A`=node.properties。
**差距**：`AdjacencyCache` 缺 `edgeMap: Map<"u->v->etype", Edge>`（多重边场景），当前 `edgeIdMap` 只按 `"u->v"` 键，同源同目标不同类型的边会覆盖。

### 3.2 路径规则 R = (S, Φ, Λ, Ψ, Ω, Δ) → 既有 RuleEngine + 分析器

项目的每个分析器本质上都是一条隐式路径规则：

| 分析器 | 对应规则 R | S（起点） | Φ（边类型） | Λ（长度） | Ψ（节点） | Δ（规范化） |
|--------|-----------|----------|------------|----------|-----------|------------|
| CycleDetector | 环枚举 | 全部 | call/import/dep | [1, V] | 无 | sort().join **(应改 Booth)** |
| DeadCodeAnalyzer | 入口可达 | entry points | 非 contains | [0, ∞) | 无 | none |
| ImpactAnalyzer | 影响传播 | {nodeId} | 全部（反向） | [1, maxDepth] | 无 | none |
| PathFinder | 最短路 | {source} | 全部 | [0, V] | 无 | none |
| CoreFunctionAnalyzer | 影响范围 | {每个函数} | call | [0, MAX_BFS] | function | none |
| RuleEngine.forbidden-edge | 禁环 | 全部 | edgeTypes | [1, V] | 无 | sort().join |

**关键发现**：这些规则**各自独立遍历**，`RuleEngine` 每条规则各建一次 `buildFilteredForwardAdjacency`。璇玑图的**规则组合代数**（X1）可以让多条规则共享一次遍历。

### 3.3 路径索引 PathIndex → 既有 AdjacencyCache（差距最大）

`AdjacencyCache` 是图层索引（邻接表缓存），但**没有路径层索引**。每次 `detectCycles()` / `computeImpact()` / `findPath()` 都从邻接表**从零遍历**。璇玑图的 `startIndex`/`endIndex`/`hashIndex`/`edgeToPaths` 正是补这一层。

### 3.4 增量维护 → 既有 incrementalUpdate（半步）

`incrementalUpdate.ts` 已实现**图层增量**（文件级 diff → GraphDelta → apply），但派生分析（环、死代码、核心函数）在 `useAnalysisPanels` 中是**收到新图后全量重算**。璇玑图的 `onEdgeAdded`/`onEdgeRemoved` 把增量推到**路径层**。

### 3.5 不变量 → 既有 incrementalCluster 的 changeRatio（雏形）

`incrementalCluster.ts` 已有 `changeRatio > MAX_CHANGE_RATIO` 的降级判断——这正是璇玑图不变量 I4（`stale/total ≤ θ`）的雏形。但只用于聚类，未推广到环/死代码/核心函数。

## 四、优化方案（不造轮子）

> 每条方案标注：**复用**（既有结构）、**改造**（改既有代码）、**新增**（新文件/新结构）。

### 方案 A：AdjacencyCache 增量失效——从全量重建到 O(k) 局部失效

**问题**：`AdjacencyCache.invalidate()` 设 `valid=false`，下次任何 `getForwardAdjacency` 触发**全量 rebuild**。一次单边添加就重建整个邻接表。

**璇玑图映射**：§5.3 `onEdgeRemoved` 用 `edgeToPaths` 定位受影响条目，O(k)。

**方案**（改造 `AdjacencyCache.ts`）：
- 新增 `addEdge(s, t, eId)` / `removeEdge(s, t, eId)` 方法，直接 patch `forward`/`backward`/`undirected`/`edgeIdMap` 四个 Map，**不设 `valid=false`**。
- 保留 `invalidate()` 全量重建作为**降级回退**（对应璇玑图 §5.4 查询未命中回退）。
- 新增 `version` 计数器（对应 §4.1 `GraphSpace.version`），patch 时 `version++`。

**复杂度**：单边 patch O(1)，全量重建 O(V+E) 仅在 `invalidate()` 时发生。
**不造轮子**：复用既有四个 Map，不引入新结构。

---

### 方案 B：环去重从 sort().join 到 Booth O(L)

**问题**：`CycleDFS.ts` 第 41 行 `cycleKey = [...cycleNodes, target].sort().join('|')`，每条环做 O(L log L) 排序生成去重键。同一环的不同起点会重复排序。

**璇玑图映射**：§2.3 `canonical` 策略用 Booth 最小表示 O(L)，幂等。

**方案**（改造 `CycleDFS.ts`）：
- 新增 `boothMinimalRotation(arr: string[]): string[]` 函数（~20 行，标准 Booth 算法），返回字典序最小旋转。
- 环去重键改为 `boothMinimalRotation(cycleNodes).join('|')`，O(L) 且天然处理循环等价。
- `RuleEngine.ForbiddenEdgeDetector` 同步受益（它调用 `detectCyclesDFS`）。

**复杂度**：O(L) 替代 O(L log L)，且消除"同环不同起点"的重复排序。
**不造轮子**：纯函数加在既有 `CycleDFS.ts`，不引入依赖。

---

### 方案 C：派生分析增量更新——从全量重算到 delta 驱动

**问题**：`useAnalysisPanels.ts` 在每次图变化后全量调用 `hotspotAnalyzer.analyze` / `coreFunctionAnalyzer.analyze` / `deadCodeAnalyzer.analyze`。一次单文件改动触发三次 O(V+E) ~ O(V×(V+E))。

**璇玑图映射**：§5.2 `onEdgeAdded` 只处理经过新边的路径；§5.3 `onEdgeRemoved` 标记 stale。

**方案**（改造分析器 + 新增 delta 适配）：
1. **DeadCodeAnalyzer**：新增 `applyDelta(prevResult, delta, nodes, edges)` —— 只对 `delta.removedEdges` 的源做"是否仍可达"重判，对 `delta.addedEdges` 的目标做"是否新可达"扩展。大部分 delta 只动几条边，重算量 O(ΔE × deg)。
2. **CycleDetector**：新增 `affectedCycles(delta)` —— 只对 `delta.addedEdges` 的两端做"新环"检测（§5.2 前缀×e×后缀），不重跑全图 DFS。
3. **CoreFunctionAnalyzer**：`computeInfluenceReach` 的逐节点 BFS 改为**增量**——只有 `delta` 涉及的节点重算 reach，其余复用 `prevResult`。

**降级**：当 `graphDeltaSize(delta).edges / edges.length > θ`（复用 `incrementalCluster` 的 changeRatio 思路），回退全量重算（对应 §5.4 回退契约）。

**复杂度**：增量 O(ΔE × deg)，全量 O(V+E) 仅在大 delta 时发生。
**不造轮子**：改造既有分析器方法签名，复用 `GraphDelta` 结构，不引入路径索引全套结构。

---

### 方案 D：AdjacencyCache 多重边键修复

**问题**：`AdjacencyCache.edgeIdMap` 用 `${s}->${t}` 键，两条同源同目标不同类型的边（如 `call` + `import`）会互相覆盖。`CycleDetector.getEdgeIdMap` 同样问题。

**璇玑图映射**：§4.1 契约"`edgeMap` 在多重边场景下需支持 `Map<"u->v->etype", Edge>`"。

**方案**（改造 `AdjacencyCache.ts` + `CycleDetector.ts`）：
- `edgeIdMap` 键改为 `${s}->${t}->${etype}`。
- `CycleDetector.detectCyclesDetailed` 中边查找同步改键。

**不造轮子**：改键格式，结构不变。

---

### 方案 E：CoreFunctionAnalyzer 从输入敏感到输出敏感

**问题**：`computeInfluenceReach` 对每个函数节点跑一次 `bfsReachCount`，O(V × (V+E))。2000 节点图 = 2000 次 BFS。

**璇玑图映射**：§5.1 "输出敏感时为 O(|O_R| · L)"；§六 "约束越强，剪枝越有效"。

**方案**（改造 `CoreFunctionAnalyzer.ts`）：
- **反向单次 BFS 批量计算**：从所有入度为 0 的节点做一次反向 BFS，途中累计每个节点的"被影响集大小"。将 V 次 BFS 降为 1 次 O(V+E)。
- **或 SCC 缩点**：用 graphology 既有 `stronglyConnectedComponents`（如可用）缩点后 DAG 上拓扑序累计，O(V+E)。

**复杂度**：O(V+E) 替代 O(V × (V+E))。
**不造轮子**：复用 `GraphBFS` 的 BFS 框架 / graphology 的 SCC。

---

### 方案 F：RuleEngine 规则组合——共享遍历

**问题**：`RuleEngine.check` 逐规则调用 `detector.detect`，`ForbiddenEdgeDetector` 每次自建 `buildFilteredForwardAdjacency` + `detectCyclesDFS`。5 条规则 = 5 次邻接构建。

**璇玑图映射**：§2.4 规则组合代数——并集 R₁∪R₂ 谓词析取，一次遍历服务多规则。

**方案**（改造 `RuleEngine.ts`）：
- `check` 前先聚合所有 enabled 规则的 `edgeTypes` 并集，构建一次邻接表。
- 各 detector 接收**预构建邻接表**而非原始 edges，避免重复构建。
- `MaxIndegree` / `MaxOutdegree` 共用一次度数统计 Map。

**复杂度**：邻接构建从 O(R × (V+E)) 降为 O(V+E)，R=规则数。
**不造轮子**：改造既有 `RuleEngine` 内部，不改 detector 接口契约。

---

### 方案 G：存在性判断走
 NFA/早终止（可选，低优先级）

**问题**：`RuleEngine.ForbiddenEdgeDetector` 只需判断"是否存在环"，但 `detectCyclesDFS` 枚举**所有环**（最多 1000 条）。

**璇玑图映射**：§5.6 NFA 乘积——仅需存在性时 O(|Q|²) 插入、O(|Q|) 查询。

**方案**（新增，低优先级）：
- 新增 `hasCycle(adjacency): boolean` —— DFS 遇到第一个 back edge 即返回 true，不枚举。
- `ForbiddenEdgeDetector` 当 `severity === 'error'` 时只需存在性，调用 `hasCycle`。
- 需要详细环列表时仍用 `detectCyclesDFS`。

**复杂度**：存在性 O(V+E) 早终止，平均远小于全枚举。
**不造轮子**：加一个早终止变体函数，复用 `CycleDFS` 的迭代框架。

## 五、优先级与实施路径

| 优先级 | 方案 | 收益 | 风险 | 工作量 |
|--------|------|------|------|--------|
| **P0** | B（Booth 环去重） | O(L) 替 O(L log L)，正确性等价 | 极低（纯函数） | 0.5d |
| **P0** | D（多重边键修复） | 修复潜在数据丢失 | 低（改键格式） | 0.5d |
| **P1** | A（AdjacencyCache 增量失效） | 单边变化免全量重建 | 中（需保证一致性） | 1d |
| **P1** | F（RuleEngine 共享遍历） | 规则数倍加速 | 低（内部重构） | 1d |
| **P2** | E（CoreFunction 输出敏感） | V 倍加速核心函数分析 | 中（算法改写） | 2d |
| **P2** | C（派生分析增量更新） | 单文件改动免全量重算 | 中高（需 delta 正确性测试） | 3d |
| **P3** | G（存在性早终止） | 环检测平均加速 | 低（加变体） | 0.5d |

### 实施顺序

```
P0: B → D          （低风险高确定性，先落地）
P1: A → F          （缓存与规则层，互不依赖）
P2: E → C          （E 改算法，C 接 delta，C 依赖 A 的增量缓存）
P3: G              （可选优化）
```

### 验证方式

- **B**：既有 `CycleDFS` 测试 + 新增 Booth 幂等性测试 `Δ(Δ(p)) === Δ(p)`。
- **D**：构造同源同目标不同类型双边图，验证 `edgeIdMap` 不覆盖。
- **A**：patch 后 `version` 递增，`getForwardAdjacency` 返回与全量重建逐边一致。
- **C**：增量结果与全量结果在相同 (nodes, edges) 上逐节点一致（幂等对照测试）。
- **E**：`influenceReach` 值与旧实现逐节点一致，性能基准对比（复用 `scripts/perf-gate.mjs`）。

## 六、不引入的璇玑图结构及理由

| 璇玑图结构 | 不引入理由 |
|-----------|-----------|
| 完整 `PathIndex`（startIndex/endIndex/hashIndex/edgeToPaths 全套） | 项目路径查询是**单点最短路**和**单点影响**，非"多规则多长度路径枚举"。物化全套路径索引的内存开销 > 重算开销。方案 A+C 用轻量增量替代。 |
| NFA 乘积自动机 | 项目规则数量少（5 条预设），NFA 编译成本 > 遍历成本。方案 G 用更简单的早终止替代。 |
| 规则热插拔 + 版本管理 | 项目规则是编译期预设，无运行时增删需求。 |
| 滚动哈希幂次表 | 项目路径长度短（最短路/影响深度 ≤ 几十），全算哈希成本可忽略。全图指纹已有 FNV-1a。 |
| `RuleRegistry` | 项目 `RuleEngine` 已是注册表模式（`detectors: Map`），无需额外抽象。 |

## 七、总结

璇玑图规范为**通用图空间路径枚举**设计，其全套结构（PathIndex/NFA/RuleRegistry）面向"多规则、多长度、高频查询"场景。本项目是**代码图谱可视化**，路径查询模式是"少量规则、单点查询、中频触发"，因此**不照搬全套结构**，而是提取六条思维内核（X1-X6）映射到既有代码：

- **X2 增量优先** → 方案 A（缓存增量失效）+ C（派生分析增量）
- **X6 规范化幂等** → 方案 B（Booth 环去重）
- **X5 输出敏感** → 方案 E（CoreFunction 批量 BFS）
- **X1 内容规则分离** → 方案 F（规则共享遍历）
- **X4 不变量驱动** → 复用既有 `changeRatio` 降级，推广到方案 C
- **X3 长度分桶** → 方案 C 中 `ImpactAnalyzer` 的 depth 分层天然就是长度分桶

**预期收益**：单文件改动场景下，派生分析从 O(V×(V+E)) 降为 O(ΔE×deg)；环检测去重从 O(L log L) 降为 O(L)；规则检查从 O(R×(V+E)) 降为 O(V+E)。
