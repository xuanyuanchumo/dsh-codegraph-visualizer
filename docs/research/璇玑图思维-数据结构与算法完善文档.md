## 一、璇玑图的文化本质与算法思维

### 1.1 历史与文化定位

璇玑图是前秦时期（约公元 350—360 年）秦州刺史窦滔之妻**苏蕙**所织的回文诗章，距今约一千七百年。它以五彩丝线在一方八寸的锦缎上绣出**横竖各 29 字、共 841 字**的方阵。这 841 个汉字并非线性排列的诗篇，而是一个**二维字符网格**——通过不同的路径遍历规则，从中读出数百乃至数千首诗。

它被公认为中国乃至世界文学史上**今传最早、最完整的回文诗**，也是文字游戏与文学创作结合的巅峰之作。武则天曾为之作序，刘勰在《文心雕龙》中称"回文所兴"。其名"璇玑"取自北斗七星前四星（天文观测仪器），暗含**旋转、循环、多角度观测**之意。

### 1.2 璇玑图的十种读法——天然的路径规则族

据《天水织锦巷与苏蕙的璇玑图》及明代康万民《璇玑图诗读法》，璇玑图有十种读法，皆成诗章：

| 读法 | 遍历方式 | 算法对应 |
|------|---------|---------|
| **顺读** | 从左至右、从上至下正向遍历 | 正向路径枚举 |
| **回读** | 从右至左、从下至上逆向遍历 | 反向路径枚举（reverse 等价） |
| **横读** | 逐行水平遍历 | 行约束路径 |
| **斜读** | 沿对角线方向遍历 | 斜向边类型路径 |
| **交互读** | 正反交替遍历 | 正反向边交替路径 |
| **蛇行读** | 蛇形曲折遍历 | 方向交替路径 |
| **退一字读** | 每读一字退一字再进 | 带回退的路径 |
| **重一字读** | 关键字重复读 | 带重复节点的路径 |
| **间一句读** | 隔句读取 | 带跳跃的路径（stride） |
| **左右旋读** | 以中心为轴左右旋转读 | 循环旋转等价类（canonical） |

**这十种读法就是十条路径规则 R₁…R₁₀**，它们共享同一个图空间（841 字方阵），却各自定义不同的起点谓词 S、边谓词 Φ、长度区间 Λ、节点约束 Ψ 和规范化策略 Δ。

### 1.3 璇玑图的五重算法思维内核

从这一文化 artifact 中，可以提取出五重可迁移的算法思维：

| 内核 | 璇玑图原型 | 抽象含义 |
|------|-----------|---------|
| **一图多读** | 841 字方阵 → 数千首诗 | 一个图空间 G，多套路径规则 R，输出 O_R(G) 各不相同。**内容与规则分离**。 |
| **循环等价** | 同一首诗从不同字起读，仍是同一首 | 路径在循环旋转下等价，取规范代表元（Booth 最小表示）。**规范化幂等**。 |
| **增量局部** | 改一字只影响经过该字的诗 | 图变化时只维护受影响路径，而非全量重建。**增量优先于全量**。 |
| **输出远超输入** | 841 字 → 数千首诗 | 算法复杂度应按输出规模衡量，而非输入规模。**输出敏感**。 |
| **不变量守护** | 方阵的对称性、中心性保证读法成立 | 索引健康度的可检查条件，违反触发局部重组。**不变量驱动**。 |

这五重内核正是 `璇玑图思维算法.md` 规范的 §2.2（规则分离）、§2.3（规范化）、§5.2-5.3（增量）、§5.1（输出敏感）、§4.4（不变量）的文化原型。

## 二、从璇玑图到代码图谱：图空间的同构映射

### 2.1 两个图空间的对照

| 维度 | 璇玑图（苏蕙） | 代码图谱（本项目） |
|------|--------------|-------------------|
| **图空间 G** | 29×29 字符方阵 | `GraphData { nodes, edges, metadata }` |
| **节点 V** | 841 个汉字格 | 函数/类/模块/文件节点 |
| **边 E** | 格间相邻关系（横/竖/斜） | call/import/extend/dependency 边 |
| **边类型 Σ** | 横、竖、斜、对角 | call、import、extend、implement、contains… |
| **节点属性 A** | 字符本身、颜色（五色丝） | label、type、filePath、properties |
| **路径规则 R** | 十种读法 | 各分析器（Cycle/DeadCode/Impact/Path/CoreFunc/Rule） |
| **合法路径** | 一首可诵读的诗 | 一条满足约束的调用链/依赖路径 |
| **输出 O_R** | 诗章文本 | 环列表/死代码集/影响树/最短路/核心函数列表 |
| **规范化 Δ** | 循环旋转取代表诗 | 环去重（当前 sort().join，应改 Booth） |

### 2.2 核心洞察

> **璇玑图的 841 字方阵是"一个图空间 + 十条路径规则"的最早实例。本项目的代码图谱是"一个 GraphData + 六个分析器"的同构实例。**

璇玑图的天才在于：它没有为每首诗单独织一段锦，而是**一个结构 + 多套读法 = 海量输出**。本项目当前的问题恰恰相反：每个分析器各自遍历、各自构建邻接表，相当于为每首诗单独织锦。璇玑图思维指出的优化方向是——**共享图空间，分离路径规则，增量维护，输出敏感**。

## 四、映射分析：璇玑图概念 → 项目结构

### 4.1 图空间 G = (V, E, Σ, τ, A) → 既有 GraphData

项目已有 `GraphData { nodes, edges, metadata }`，边有 `type`（call/import/extend/...），节点有 `properties`。
- **映射**：V=nodes, E=edges, Σ=edge.type 枚举, τ=edge.type, A=node.properties
- **差距**：`AdjacencyCache.edgeIdMap` 用 `"u->v"` 键，同源同目标不同类型的边（如 call + import）会覆盖。璇玑图 §4.1 契约要求 `Map<"u->v->etype", Edge>`。

### 4.2 路径规则 R = (S, Φ, Λ, Ψ, Ω, Δ) → 既有分析器

项目的每个分析器本质上都是一条隐式路径规则，正如璇玑图的每种读法：

| 分析器 | 对应读法 | S（起点） | Φ（边类型） | Λ（长度） | Δ（规范化） |
|--------|---------|----------|------------|----------|------------|
| CycleDetector | 左右旋读（环） | 全部 | call/import/dep | [1, V] | sort().join **→ Booth** |
| DeadCodeAnalyzer | 顺读（可达） | entry points | 非 contains | [0, ∞) | none |
| ImpactAnalyzer | 斜读（影响） | {nodeId} | 全部（反向） | [1, maxDepth] | none |
| PathFinder | 顺读（最短） | {source} | 全部 | [0, V] | none |
| CoreFunctionAnalyzer | 交互读（影响范围） | {每个函数} | call | [0, MAX_BFS] | none |
| RuleEngine.forbidden-edge | 左右旋读（禁环） | 全部 | edgeTypes | [1, V] | sort().join |

**关键发现**：这些规则**各自独立遍历**，相当于为每首诗单独织锦。璇玑图的**规则组合代数**可以让多条规则共享一次遍历——正如璇玑图的方阵只织一次，十种读法共享同一块锦缎。

### 4.3 路径索引 PathIndex → 既有 AdjacencyCache（差距最大）

`AdjacencyCache` 是**图层索引**（邻接表缓存），但没有**路径层索引**。每次 `detectCycles()` / `computeImpact()` / `findPath()` 都从邻接表从零遍历。这相当于每次读诗都要重新审视整个 841 字方阵。璇玑图的 `startIndex`/`endIndex`/`hashIndex`/`edgeToPaths` 正是补这一层——把已经读出的诗（路径）物化存储，下次直接返回。

### 4.4 增量维护 → 既有 incrementalUpdate（半步）

`incrementalUpdate.ts` 已实现**图层增量**（文件级 diff → GraphDelta → apply），但派生分析在 `useAnalysisPanels` 中是收到新图后**全量重算**。这相当于改了锦缎上一个字，却要把所有诗重新读一遍。璇玑图的 `onEdgeAdded`/`onEdgeRemoved` 把增量推到路径层——改一字只重读经过该字的诗。

### 4.5 不变量 → 既有 incrementalCluster 的 changeRatio（雏形）

`incrementalCluster.ts` 已有 `changeRatio > MAX_CHANGE_RATIO` 的降级判断——这正是璇玑图不变量 I4（`stale/total ≤ θ`）的雏形。但只用于聚类，未推广到环/死代码/核心函数。正如璇玑图的方阵对称性是全局守护条件，本项目的派生结果也需要自己的健康不变量。

## 五、优化完善方案（不造轮子）

> 每条方案标注：**复用**（既有结构）、**改造**（改既有代码）、**新增**（新文件/新结构）。
> 每条方案关联璇玑图思维内核（§1.3 的五重内核）。

### 方案 A：AdjacencyCache 增量失效——从全量重建到 O(1) 局部 patch

**关联内核**：增量局部（改一字只影响经过该字的诗）

**问题**：`AdjacencyCache.invalidate()` 设 `valid=false`，下次任何 `getForwardAdjacency` 触发**全量 rebuild**。一次单边添加就重建整个邻接表——相当于改了一个字，要把整块锦缎重新织一遍。

**璇玑图映射**：§5.3 `onEdgeRemoved` 用 `edgeToPaths` 定位受影响条目，O(k)。

**方案**（改造 `AdjacencyCache.ts`）：
1. 新增 `addEdge(s, t, eId, etype)` 方法：直接 patch `forward`/`backward`/`undirected`/`edgeIdMap` 四个 Map，不设 `valid=false`。
2. 新增 `removeEdge(s, t, eId, etype)` 方法：直接从四个 Map 中删除对应条目。
3. 保留 `invalidate()` 全量重建作为**降级回退**（对应 §5.4 查询未命中回退）。
4. 新增 `version` 计数器（对应 §4.1 `GraphSpace.version`），patch 时 `version++`。

**复杂度**：单边 patch O(1)，全量重建 O(V+E) 仅在 `invalidate()` 时发生。
**不造轮子**：复用既有四个 Map，不引入新结构。

---

### 方案 B：环去重从 sort().join 到 Booth O(L)——循环等价的规范代表

**关联内核**：循环等价（同一首诗从不同字起读，仍是同一首）

**问题**：`CycleDFS.ts` 第 41 行 `cycleKey = [...cycleNodes, target].sort().join('|')`，每条环做 O(L log L) 排序生成去重键。同一环的不同起点会重复排序。这相当于把一首回文诗的每个起始位置都当成不同的诗。

**璇玑图映射**：§2.3 `canonical` 策略用 Booth 最小表示 O(L)，幂等。璇玑图的"左右旋读"正是循环旋转等价类——同一首诗无论从哪个字起读，都取同一个规范形式。

**方案**（改造 `CycleDFS.ts`）：
1. 新增 `boothMinimalRotation(arr: string[]): string[]` 函数（~20 行，标准 Booth 算法），返回字典序最小旋转。
2. 环去重键改为 `boothMinimalRotation(cycleNodes).join('|')`，O(L) 且天然处理循环等价。
3. `RuleEngine.ForbiddenEdgeDetector` 同步受益（它调用 `detectCyclesDFS`）。

**Booth 算法伪代码**：
```
booth(s):  // 返回最小旋转的起始下标
  n = len(s), f = [-1] * (2*n)
  k = 0
  for j in 1..2n-1:
    i = f[j - k - 1]
    while i != -1 and s[j] != s[k + i + 1]:
      if s[j] < s[k + i + 1]: k = j - i - 1
      i = f[i]
    if i == -1 and s[j] != s[k + i + 1]:
      if s[j] < s[k + i + 1]: k = j
      f[j - k] = -1
    else:
      f[j - k] = i + 1
  return k  // s[k..] + s[..k] 是最小旋转
```

**复杂度**：O(L) 替代 O(L log L)，且消除"同环不同起点"的重复排序。
**不造轮子**：纯函数加在既有 `CycleDFS.ts`，不引入依赖。

### 方案 C：派生分析增量更新——从全量重算到 delta 驱动

**关联内核**：增量局部（改一字只重读经过该字的诗）

**问题**：`useAnalysisPanels.ts` 在每次图变化后全量调用 `hotspotAnalyzer.analyze` / `coreFunctionAnalyzer.analyze` / `deadCodeAnalyzer.analyze`。一次单文件改动触发三次 O(V+E) ~ O(V×(V+E))。相当于改了一个字，要把所有诗重新读一遍。

**璇玑图映射**：§5.2 `onEdgeAdded` 只处理经过新边的路径；§5.3 `onEdgeRemoved` 标记 stale。

**方案**（改造分析器 + 新增 delta 适配）：

1. **DeadCodeAnalyzer**：新增 `applyDelta(prevResult, delta, nodes, edges)`
   - 对 `delta.addedEdges` 的目标做"是否新可达"扩展（从入口 BFS 增量前沿）
   - 对 `delta.removedEdges` 的源做"是否仍可达"重判（局部 BFS）
   - 大部分 delta 只动几条边，重算量 O(ΔE × deg)

2. **CycleDetector**：新增 `affectedCycles(delta)`
   - 只对 `delta.addedEdges` 的两端做"新环"检测（§5.2 前缀×e×后缀）
   - 不重跑全图 DFS

3. **CoreFunctionAnalyzer**：`computeInfluenceReach` 增量化
   - 只有 `delta` 涉及的节点重算 reach，其余复用 `prevResult`

**降级机制**（不变量守护）：当 `graphDeltaSize(delta).edges / edges.length > θ`（复用 `incrementalCluster` 的 changeRatio 思路），回退全量重算。对应 §5.4 回退契约——索引不可用时回退宿主枚举。

**复杂度**：增量 O(ΔE × deg)，全量 O(V+E) 仅在大 delta 时发生。
**不造轮子**：改造既有分析器方法签名，复用 `GraphDelta` 结构，不引入路径索引全套。

---

### 方案 D：多重边键修复——图空间契约对齐

**关联内核**：一图多读（图空间必须精确，否则所有读法都错）

**问题**：`AdjacencyCache.edgeIdMap` 用 `${s}->${t}` 键，两条同源同目标不同类型的边（如 `call` + `import`）会互相覆盖。`CycleDetector.getEdgeIdMap` 同样问题。这相当于锦缎上两个字叠在同一个格子里，所有读法都会漏字。

**璇玑图映射**：§4.1 契约——"`edgeMap` 在多重边场景下需支持 `Map<"u->v->etype", Edge>`"。

**方案**（改造 `AdjacencyCache.ts` + `CycleDetector.ts`）：
1. `edgeIdMap` 键改为 `${s}->${t}->${etype}`。
2. `CycleDetector.detectCyclesDetailed` 中边查找同步改键。

**不造轮子**：改键格式，结构不变。

---

### 方案 E：CoreFunctionAnalyzer 从输入敏感到输出敏感

**关联内核**：输出远超输入（841 字 → 数千首诗，算法应按输出规模衡量）

**问题**：`computeInfluenceReach` 对每个函数节点跑一次 `bfsReachCount`，O(V × (V+E))。2000 节点图 = 2000 次 BFS。这相当于对 841 个字逐字问"从你能读出多少首诗"，每个字都全盘扫描。

**璇玑图映射**：§5.1 "输出敏感时为 O(|O_R| · L)"；§六 "约束越强，剪枝越有效"。璇玑图的天才在于 841 字产出数千首诗——算法应按诗的数量（输出）而非字的数量（输入）衡量。

**方案**（改造 `CoreFunctionAnalyzer.ts`）：
- **反向单次 BFS 批量计算**：从所有入度为 0 的节点做一次反向 BFS，途中累计每个节点的"被影响集大小"。将 V 次 BFS 降为 1 次 O(V+E)。
- **或 SCC 缩点**：用 graphology 既有 `stronglyConnectedComponents` 缩点后 DAG 上拓扑序累计，O(V+E)。

**复杂度**：O(V+E) 替代 O(V × (V+E))。
**不造轮子**：复用 `GraphBFS` 的 BFS 框架 / graphology 的 SCC。

---

### 方案 F：RuleEngine 规则组合——共享遍历

**关联内核**：一图多读（方阵只织一次，十种读法共享同一块锦缎）

**问题**：`RuleEngine.check` 逐规则调用 `detector.detect`，`ForbiddenEdgeDetector` 每次自建 `buildFilteredForwardAdjacency` + `detectCyclesDFS`。5 条规则 = 5 次邻接构建。相当于为每种读法单独织一块锦缎。

**璇玑图映射**：§2.4 规则组合代数——并集 R₁∪R₂ 谓词析取，一次遍历服务多规则。璇玑图的方阵只织一次，十种读法共享同一块锦缎。

**方案**（改造 `RuleEngine.ts`）：
1. `check` 前先聚合所有 enabled 规则的 `edgeTypes` 并集，构建一次邻接表。
2. 各 detector 接收**预构建邻接表**而非原始 edges，避免重复构建。
3. `MaxIndegree` / `MaxOutdegree` 共用一次度数统计 Map。

**复杂度**：邻接构建从 O(R × (V+E)) 降为 O(V+E)，R=规则数。
**不造轮子**：改造既有 `RuleEngine` 内部，不改 detector 接口契约。

---

### 方案 G：存在性判断走早终止

**关联内核**：输出敏感（只需知道"有没有诗"，不需枚举所有诗）

**问题**：`RuleEngine.ForbiddenEdgeDetector` 只需判断"是否存在环"，但 `detectCyclesDFS` 枚举所有环（最多 1000 条）。相当于只想知道"这块锦缎能不能读出回文诗"，却把所有诗都读了一遍。

**璇玑图映射**：§5.6 NFA 乘积——仅需存在性时 O(|Q|²) 插入、O(|Q|) 查询。

**方案**（新增，低优先级）：
1. 新增 `hasCycle(adjacency): boolean` —— DFS 遇到第一个 back edge 即返回 true，不枚举。
2. `ForbiddenEdgeDetector` 当 `severity === 'error'` 时只需存在性，调用 `hasCycle`。
3. 需要详细环列表时仍用 `detectCyclesDFS`。

**复杂度**：存在性 O(V+E) 早终止，平均远小于全枚举。
**不造轮子**：加一个早终止变体函数，复用 `CycleDFS` 的迭代框架。

## 六、不引入的璇玑图结构及理由

璇玑图规范为**通用图空间路径枚举**设计，其全套结构面向"多规则、多长度、高频查询"场景。本项目是**代码图谱可视化**，查询模式是"少量规则、单点查询、中频触发"。因此**不照搬全套结构**，而是用轻量替代：

| 璇玑图结构 | 不引入理由 | 轻用替代 |
|-----------|-----------|---------|
| 完整 `PathIndex`（startIndex/endIndex/hashIndex/edgeToPaths 全套） | 物化全套路径索引的内存开销 > 重算开销 | 方案 A+C 轻量增量 |
| NFA 乘积自动机 | 项目规则数量少（5 条预设），NFA 编译成本 > 遍历成本 | 方案 G 早终止 |
| 规则热插拔 + 版本管理 | 项目规则是编译期预设，无运行时增删需求 | 既有 `RuleEngine.detectors: Map` |
| 滚动哈希幂次表 | 路径长度短（最短路/影响深度 ≤ 几十），全算哈希成本可忽略 | 既有 FNV-1a 全图指纹 |
| `RuleRegistry` | 项目 `RuleEngine` 已是注册表模式 | 既有结构 |

## 七、优先级与实施路径

| 优先级 | 方案 | 关联内核 | 收益 | 风险 | 工作量 |
|--------|------|---------|------|------|--------|
| **P0** | B — Booth 环去重 | 循环等价 | O(L) 替 O(L log L)，正确性等价 | 极低（纯函数） | 0.5d |
| **P0** | D — 多重边键修复 | 一图多读 | 修复潜在数据丢失 | 低（改键格式） | 0.5d |
| **P1** | A — AdjacencyCache 增量失效 | 增量局部 | 单边变化免全量重建 | 中（需一致性） | 1d |
| **P1** | F — RuleEngine 共享遍历 | 一图多读 | 规则数倍加速 | 低（内部重构） | 1d |
| **P2** | E — CoreFunction 输出敏感 | 输出远超输入 | V 倍加速核心函数分析 | 中（算法改写） | 2d |
| **P2** | C — 派生分析增量更新 | 增量局部 | 单文件改动免全量重算 | 中高（delta 正确性） | 3d |
| **P3** | G — 存在性早终止 | 输出远超输入 | 环检测平均加速 | 低（加变体） | 0.5d |

### 实施顺序

```
P0: B → D          （低风险高确定性，先落地）
P1: A → F          （缓存与规则层，互不依赖）
P2: E → C          （E 改算法，C 接 delta，C 依赖 A 的增量缓存）
P3: G              （可选优化）
```

### 验证方式

| 方案 | 验证方法 |
|------|---------|
| B | 既有 `CycleDFS` 测试 + 新增 Booth 幂等性测试 `Δ(Δ(p)) === Δ(p)` |
| D | 构造同源同目标不同类型双边图，验证 `edgeIdMap` 不覆盖 |
| A | patch 后 `version` 递增，`getForwardAdjacency` 返回与全量重建逐边一致 |
| C | 增量结果与全量结果在相同 (nodes, edges) 上逐节点一致（幂等对照测试） |
| E | `influenceReach` 值与旧实现逐节点一致，性能基准对比（复用 `scripts/perf-gate.mjs`） |
| F | 规则检查结果与旧实现逐违规一致，邻接构建次数减少 |
| G | `hasCycle` 返回值与 `detectCyclesDFS.length > 0` 一致 |

## 八、不变量体系——从璇玑图方阵对称性到派生结果健康监控

璇玑图方阵的对称性、中心性是保证各种读法成立的全局守护条件。本项目的派生分析结果也需要自己的不变量体系。以下将璇玑图规范 §4.4 的 I1—I5 映射到项目：

| 璇玑图不变量 | 项目映射 | 检查方式 | 违反动作 |
|------------|---------|---------|---------|
| **I1** 边类型覆盖 | 每种边类型至少出现在一条物化路径中 | 遍历结果统计覆盖 | 对缺失类型采样重算 |
| **I2** 角色覆盖 | 每种节点类型至少出现在一条分析结果中 | 按类型聚合统计 | 角色索引局部重建 |
| **I3** 深度均衡 | 各边类型的平均路径长度差 ≤ θ_depth | 按类型聚合长度均值 | 对偏离类型触发局部重组 |
| **I4** 失效比例 | stale / total ≤ θ_stale | 增量计数器 O(1) 读取 | 批量重建 stale 条目 |
| **I5** 版本一致性 | PathEntry.version ≤ GraphSpace.version | 抽样校验 | 标记不一致条目为 stale |

**落地建议**：方案 C 的降级机制就是 I4 的实例化。方案 A 的 `version` 计数器为 I5 提供基础。I1—I3 可在方案 C 之后渐进引入，作为派生结果的周期性健康检查。

## 九、总结：璇玑图思维的工程映射

### 9.1 一句话总结

> **璇玑图用 841 个字、一块锦缎、十种读法，产出了数千首诗。它的算法思维是"一个图空间 + 多套路径规则 + 循环等价规范化 + 增量局部维护 + 输出敏感复杂度"。本项目当前是"一个图空间 + 六个分析器各自遍历 + 排序去重 + 全量重算 + 输入敏感"。优化方向就是把璇玑图思维的五重内核映射到既有代码，不造轮子。**

### 9.2 五重内核 → 七条方案的映射

```
一图多读 ──────────→ 方案 D（图空间精确）+ F（规则共享遍历）
循环等价 ──────────→ 方案 B（Booth 环去重）
增量局部 ──────────→ 方案 A（缓存增量失效）+ C（派生分析增量）
输出远超输入 ──────→ 方案 E（CoreFunction 批量 BFS）+ G（存在性早终止）
不变量守护 ─────────→ 方案 C 降级机制 + §八 不变量体系
```

### 9.3 预期收益

| 场景 | 现状 | 优化后 | 改善 |
|------|------|--------|------|
| 单文件改动 → 派生分析 | O(V×(V+E)) 全量重算 | O(ΔE×deg) 增量 | ~V 倍 |
| 环检测去重 | O(L log L) 排序 | O(L) Booth | ~log L 倍 |
| 规则检查 | O(R×(V+E)) 各自遍历 | O(V+E) 共享遍历 | ~R 倍 |
| 核心函数分析 | O(V×(V+E)) 逐节点 BFS | O(V+E) 批量 BFS | ~V 倍 |
| 缓存失效 | O(V+E) 全量重建 | O(1) 单边 patch | ~V+E 倍 |

### 9.4 文化启示

璇玑图之所以能以 841 字产出数千首诗，关键不在字数多寡，而在**读法的多样性与组合性**。同理，代码图谱的分析能力不在于遍历次数多寡，而在于**规则的可组合性与遍历的共享性**。璇玑图思维提醒我们：当多个分析器各自遍历同一张图时，应当像十种读法共享一块锦缎那样——**织一次，读十遍**，而非**织十遍，各读一遍**。
