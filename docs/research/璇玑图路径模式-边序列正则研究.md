## 2. 缺口：扁平 `edgeTypes` 表达不了序列

### 2.1 现状字段

`PathRule` 的边类型约束是一个扁平集合（`src/xuanji/core/path-rule.ts:40-41`）：

```ts
  /** Φ：允许的边类型集合 Σ_R。 */
  readonly edgeTypes: ReadonlySet<EdgeType>;
```

它在 `isLegalPath` 里的用法是**逐步独立**的存在性判定
（`src/xuanji/core/path-rule.ts:315-317`）：

```ts
  for (let i = 0; i + 1 < nodes.length; i++) {
    if (!graph.hasEdgeOfType(nodes[i]!, nodes[i + 1]!, rule.edgeTypes)) return false;
  }
```

`hasEdgeOfType` 的语义是「u→v 上任意一条 type ∈ types 的边存在即通过」
（`src/xuanji/core/graph-space.ts:221`）。于是 `edgeTypes = {call, import, dependency}`
表达的是「**每一步**可以走这三种里的任意一种」，而不是「第一步 call、第二步 import」。

### 2.2 缺口的具体形态

设图中存在两条 2 步路径：

- `a --call--> b --import--> c`
- `a --import--> b --call--> c`

用 `edgeTypes = {call, import}` 查 `a→c`，**两条都会返回**。用 ρ = `call . import`，
**只有第一条合法**。这个差别在本轮有直接对照用例：
`tests/unit/xuanji/path-pattern.test.ts:409-420`（"同一张图：只交换边类型顺序，ρ 从拒绝翻转为接受"）。

> 上表第 48-50 行的任务描述已漂移：`PathRule.edgeTypes` 的实际位置是
> `path-rule.ts:40-41`，不是 `:48-50`。本轮按代码写。

### 2.3 为什么这个缺口值得补

研究方案 §4 的三种统一表达（`:77`）全部依赖序列：

| §4 原文的查询 | ρ 形式 | 扁平 `edgeTypes` 能否表达 |
|---|---|---|
| `get_downstream_dependencies` | `calls+` | 能（退化为单类型闭包） |
| `get_blast_radius` | `calls+` ∪ `imports+` ∪ `inherits+` | 能，但只能取并（丢掉了「闭包是一段同类型重复」这个信息） |
| 登录请求到数据库 | `handles · calls* · queries` | **不能** |

第三种是真正的新能力：它要求「前半段可以任意长度、然后切换到另一种关系」。
扁平集合表达不了任何切换。

## 3. 形式化：ρ 是 Σ 上的正则表达式

### 3.1 定义

设边类型字母表 `Σ`（本仓的 `Σ` 来自 `src/types/index.ts:64`，9 个值），
路径 `p = (v_0, e_1, v_1, …, e_L, v_L)` 的**标签序列**为 `τ(p) = (type(e_1), …, type(e_L))`。

ρ 是 `Σ` 上的正则表达式，定义语言 `L(ρ) ⊆ Σ*`。路径 `p` 满足 ρ 当且仅当
`τ(p) ∈ L(ρ)`。

与 `PathRule` 现有字段的对应关系：

| 形式化符号 | ρ 侧来源 | 写入 `PathRule` 的字段 |
|---|---|---|
| `Σ_R`（剪枝用字母表） | ρ 中**出现过的所有类型**的并集 | `edgeTypes` |
| `Λ`（长度区间） | ρ 的长度区间 ∩ 调用方 `minHops`/`maxHops` | `lMin` / `lMax` |
| 序列约束本体 | `L(ρ)` 的成员判定 | `pathConstraint` |
| `S`（起点）、终点、`Ψ` | ρ 语法之外，由调用方传 | `start` / `end` / `nodeConstraint` |

> **注意 `edgeTypes` 的角色被降级了**：在 ρ 路径下它不是判据，只是**剪枝超集**。
> 这是本仓已固化的分工（`path-rule.ts:280-283` 的 `isLegalPath` 头注：
> 「枚举器只做剪枝，最终是否物化以本函数为准——剪枝可以是超集，判据必须精确」）。

### 3.2 Thompson 构造：本仓的实际实现

`path-pattern.ts:281-370` 是 `NfaBuilder` + `compileNode` + `compileRepeat`，
即标准 Thompson 构造（ε 边 + 子片段拼接）。状态的转移标签不是单个字符，
而是一个**类型集合**（`NfaState.transitions: Array<{ types: ReadonlySet<EdgeType>; to: number }>`，
`path-pattern.ts:249-262`），因此并集分支可以合并成一条转移，状态数比逐字符构造少。

各构造式的状态数（实测，`compilePathPattern(...).stateCount`）：

| ρ | 状态数 \|Q\| | minEdges | maxEdges |
|---|---|---|---|
| `call` | 2 | 1 | 1 |
| `call?` | 4 | 0 | 1 |
| `call*` | 4 | 0 | ∞ |
| `call+` | 6 | 1 | ∞ |
| `call{2,4}` | 10 | 2 | 4 |
| `call{1,8}` | 18 | 1 | 8 |
| `call.import` | 4 | 2 | 2 |
| `(call\|import)+` | 14 | 1 | ∞ |
| `extend? . call+` | 10 | 1 | ∞ |
| `call+ . import? . dependency` | 12 | 2 | ∞ |

**`{n,m}` 是展开的、不是循环的**：`path-pattern.ts:281-287` 的注释明确写
「`repeat` 的 `max` 在编译期被展开为有限份拷贝」，代价是 `|Q|` 与 `m` 线性相关。
实测 `call{1,50}` = 102 状态、`call{1,500}` = 1002 状态，约为 `2m + 2`。

### 3.3 匹配：NFA 子集模拟，O(L·|Q|·|T|)

`runNfa`（`path-pattern.ts:489-505`）对每一步：

1. 取当前状态集 `current`（已做 ε 闭包）；
2. 对 `current` 的每个状态、每条转移、该步的每个并列标签，能匹配就收集目标状态；
3. 若目标集为空 ⇒ 立即返回 `false`（早退）；
4. 做 ε 闭包，进入下一步。

最终只要状态集里含任一接受态即为匹配。复杂度
`O(L · |Q| · |T|)`，`L` = 路径边数、`|Q|` = 状态数、`|T|` = 该节点对上同时存在的候选类型数。

**实测这一步的成本几乎与 `|Q|` 无关**（本文 §6.2 有数据）：因为路径短（≤ 10 步）时
ε 闭包与状态集规模都很小，`|Q|` 只影响「闭包里可能有多少个状态」，
而不是每步都要扫全表。这一点与教科书上「O(L·|Q|)」的上界不矛盾——
上界是上界，常数项由路径长度主导。

### 3.4 多重边语义：并列标签，不是「取第一条」

图空间允许多重边：`edgeKey` 是 `source->target->type`
（`graph-space.ts:84`），因此同一对节点可以同时挂 `call` 与 `import` 两条边。

此时一条「节点对」在类型层面是**一组并列标签**。匹配语义必须是
「存在一种标签指派使序列匹配 ρ」（`path-pattern.ts:29-45` 模块头注有完整说明）。
实现上：`edgeTypesBetween` 返回**数组**（`path-pattern.ts:524`），
`matchesLabelSequence` 对每步的全部标签取转移并集（`path-pattern.ts:479-482`）。

**这里曾是一个真实缺陷，且被修掉了**：早期 `edgeTypesBetween` 返回单个
`EdgeType | null`，按候选集迭代序取第一条命中的类型。后果是
`u→v` 同时有 `call` 与 `import` 时，ρ = `import` 的判定结果**取决于 `Set` 的构造顺序**
——同一张图、同一条 ρ，两种答案。这不是假设，`path-pattern.ts:39-45` 的注释把它
记为「与 cycle-111 的 `pathWeight` 同族」，`tests/unit/xuanji/path-pattern.test.ts:275-296`
用「同一张图两种候选集构造顺序」把结论钉死。

> 这个 bug 与 `pathWeight` 的同族性值得记住：**「取第一条命中的边」在这张图上
> 是错误来源，不是优化**。`query-engine.ts` 的 `pathWeight` 用 `max` 而不是「第一条」
> 修过同一个坑（`query-engine.ts:71-82` 的注释）。

### 3.5 为什么**不**走 NFA 乘积索引

规范 §5.6 提议过「NFA 与图做乘积，`O(|Q|²)` 插入、`O(|Q|)` 查询」
（`docs/research/璇玑图思维算法.md:339-347`）。本仓**否决了它**，理由有三层：

1. **它已经被删过一次**。`src/xuanji/core/nfa.ts` 在 cycle-111 / XJ-08 被删除，
   `src/xuanji/index.ts:11-16` 留了墓碑注释：「它只有 `states = lMax - lMin + 1`
   一个减法，`compileLengthNfa` 全仓 0 生产调用点」。删掉的东西原样加回来，
   等于那次决策被静默推翻。
2. **存在性需求已经有实现**。`existsWalk`（`query-engine.ts:324`）就是
   `(node, depth)` 乘积状态 BFS，复杂度 `O(V·lMax)`（`query-engine.ts:312` 头注）。
   乘积索引要解决的问题（「只问有没有，不问是哪一条」）它已经解决了。
3. **ρ 需要的不是索引，是终判**。乘积索引的价值在于「多个规则共享一次图遍历」；
   而 ρ 是**每条查询一份**的编译产物，生命周期 = 一次调用。为一个一次性对象建
   跨规则乘积索引，是为不存在的问题写代码。

**当前 ρ 的 NFA 是什么**：`path-pattern.ts:23-27` 的自述——
「一次性的编译产物（每规则一份、长度 = 正则规模），用于路径终判，
**不做跨规则乘积、不进哈希索引**」。这个边界必须保持，否则会重演 XJ-08。

> 墓碑守卫仍在：`tests/unit/xuanji/publicApi.test.ts:233-240` 断言
> `src/xuanji/core` 目录清单逐字等于 `['graph-space.ts','path-entry.ts','path-pattern.ts','path-rule.ts']`。
> `path-pattern.ts` 是被**显式加进白名单**的（该测试 `:238-244` 有注释说明它与 `nfa.ts`
> 不是同一件事），不是清单漏检。这条是「加文件必须显式改清单」的正确用法。

## 4. 落地路径：编译成现有 `PathRule`

### 4.1 三分工（缺一不可）

`compilePathRule`（`path-pattern.ts:576`）的文档把分工写死在 `:564-575`：

| 字段 | 取自 | 语义 |
|---|---|---|
| `edgeTypes` | ρ 中出现过的**所有类型的并集** | 超集剪枝：不会误剪合法路径，只可能多走几步 |
| `pathConstraint` | 精确的 NFA 终判 | 序列匹配；返回 `false` 的路径不物化 |
| `lMin` / `lMax` | ρ 长度区间 ∩ 显式跳数区间 | **交集**，不是替换 |

长度取交集这一点有专门的回归用例
（`tests/unit/xuanji/path-pattern.test.ts:327-336`）：
`call . import` + `maxHops: 10` 必须仍是 `lMin = lMax = 2`。
「替换」会让 `call{2,4}` + `maxHops: 10` 静默接受 10 跳——那是静默放宽，
与本仓「非法规则不得静默近似」（`path-rule.ts:130-136`）直接冲突。

空集边界也要说清：ε 模式（空 ρ）的 `edgeTypes` 是**空集**，
`enumerate` 的 `outNeighbors(node, 空集)` 返回空，因此只可能物化 `lMin = 0`
的单节点路径（`path-pattern.ts:568-571`；用例 `path-pattern.test.ts:422-430`）。

### 4.2 复用 `enumerate` 免费获得的四件事

`enumerate`（`query-engine.ts:140`）是一个有 316 条用例（12 个测试文件，实跑全绿）的引擎
（`tests/unit/xuanji/` 下 12 个测试文件）。把 ρ 编译成 `PathRule` 后，四件事不需要重做：

| 能力 | 实现位置 | 自己写引擎要付的代价 |
|---|---|---|
| 分页游标 `nextCursor` | `query-engine.ts:291` `readPathPage` | 要重新定义「游标 = 已返回条数」的语义并证明对截断仍成立 |
| Booth 规范化去重 | `path-entry.ts:55` `canonicalNodes` + `booth.ts` | 要重写最小旋转、并处理闭合路径「旋转开核」的坑（`path-entry.ts:44-53` 有专门的注释记录这个坑） |
| 增量索引物化 | `index/incremental.ts` | 要重做 `applyDelta` 与失效条目的惰性回收 |
| 不变量检查 | `ops/invariants.ts` | 要重做 I1–I5 |

最贵的是 Booth 那一条：`path-entry.ts:44-53` 记录了「对含重复首节点的闭合序列直接旋转
会得到非法路径表示」这个坑，修法是「只对开核旋转」。重写引擎的人大概率会再踩一次。

### 4.3 为什么不是新造一个枚举引擎

三条理由都落在本仓已固化的教训上：

1. **剪枝/判据分离是本库的核心不变量**。用同一个 `isLegalPath`
   （`path-rule.ts:284`）做终判，等于继承了「超集剪枝 + 精确终判」的完备性证明。
   新引擎要重新证明一遍，而且要证明的对象是指数级搜索——这是最容易「看起来对」的地方。
2. **宿主侧已经有一层适配**。`XuanjiAdapter.pathsByPattern`
   （`src/shared/analysis/XuanjiAdapter.ts:836`）走的是
   `compilePathRule` → `assertRule` → `enumerate` → `readPathPage` 同一个链路
   （`:877` / `:888` / `:890-894`），因此 ρ 与 `findPathsBetween` / `cycles`
   共享校验闸门与分页语义。新引擎会凭空多出一条「另一套语义」。
3. **新引擎的空态与错态会分叉**。ρ 的错误面有两类（语法错 / 类型不在图上），
   处理它们需要与 `PathPatternError`、`RuleCompositionError`、`assertRule` 三方对齐。
   复用链路时这些对齐是既成的；新引擎要重新对齐，而「两套语义漂移」正是本仓
   反复记录的缺陷家族（例如 `tests/unit/cycle*.test.ts` 的双实现引用相等断言）。

## 5. 面向 LLM 的 ρ 语法

设计取向：**务实优先**。语法只覆盖「LLM 会真的写出来的东西」，不追求正则完备性
（没有字符类、没有锚点、没有反向引用）。

### 5.1 词法与优先级

```
ρ        := union
union    := concat ('|' concat)*           // 优先级最低
concat   := quantified (('.'? quantified))*  // '.' 可省，`a b` == `a.b`
quantified := atom ('*' | '+' | '?' | '{' n (',' m?)? '}')?
atom     := TYPE | '(' union ')'
TYPE     := [A-Za-z0-9_-]+
```

- 空白（空格 / Tab / 换行）是分隔符，不是语法成分（`path-pattern.ts:109-111`）。
- 拼接是最松的隐式运算符（`path-pattern.ts:144-145` 的注释）。
- 量词绑定到**紧邻的 atom**，`call import+` = `call . (import+)`，不是 `(call.import)+`。

### 5.2 边类型名（单数）

本仓 Σ 的 9 个值（`src/types/index.ts:64`）：

```
call  import  extend  implement  dependency
contains  association  aggregation  composition
```

**是单数，不是复数**。这是 LLM 最容易写错的地方，见 §5.5。

### 5.3 量词

| 写法 | 含义 | 等价展开 |
|---|---|---|
| `T?` | 0 或 1 次 | `ε | T` |
| `T*` | 0 次或多次 | Kleene 星 |
| `T+` | 1 次或多次 | `T · T*` |
| `T{n}` | 恰好 n 次 | n 份拷贝 |
| `T{n,}` | 至少 n 次 | n 份 + 星 |
| `T{n,m}` | n 到 m 次 | n 份必需 + (m−n) 份可选 |

### 5.4 ≥ 8 条真实有用的 ρ 实例

状态数为实测值（`compilePathPattern(...).stateCount`），语义列为自然语言说明。

| # | ρ | 自然语言语义 | \|Q\| | 长度区间 |
|---|---|---|---|---|
| 1 | `call+` | 传递调用闭包：从某函数出发，沿调用边走至少一步能到哪 | 6 | 1..∞ |
| 2 | `import+` | 传递依赖闭包：一路只走 `import` | 6 | 1..∞ |
| 3 | `call* . import` | 「先（可任意次）调用，最后跨一次文件导入」——查「某个逻辑最终落在哪个模块」 | 6 | 1..∞ |
| 4 | `implement . call+` | 从接口实现出发向下展开调用：实现类自己以及它调出去什么 | 8 | 2..∞ |
| 5 | `call{2,4}` | 2~4 跳调用链：排除直接调用（1 跳）与过远传播（>4 跳） | 10 | 2..4 |
| 6 | `(import\|dependency)+` | 任一依赖关系闭包：不区分是 `import` 还是 `dependency` 的传递闭包 | 14 | 1..∞ |
| 7 | `extend? . call+` | 可选继承一步之后展开调用：起点可能本身就是被继承者 | 10 | 1..∞ |
| 8 | `call+ . import? . dependency` | 研究方案 §4 原文那条跨视图路径（`docs/research/基于璇玑图思维的代码图谱研究方案.md:77`）：调用若干层 →（可选）跨文件导入 → 落到一条依赖关系 | 12 | 2..∞ |
| 9 | `(call . import)+` | 成对出现：「每一轮都是先调用再导入」，用于识别「调用触发了模块加载」的链 | 10 | 2..∞ |
| 10 | `contains . call+` | 从文件/类节点下钻到其成员，再从成员展开调用（结构边 + 行为边的拼接） | 8 | 2..∞ |

第 10 条要注意：`contains` **不在** `DEFAULT_PATH_EDGE_TYPES` 里
（`src/shared/analysis/XuanjiAdapter.ts:55-61` 只含 call/import/extend/implement/dependency），
原因是「结构包含边不构成调用/依赖路径」（同处 `:54` 注释）。ρ 走 `pathsByPattern`
时不受该默认值限制（它由 ρ 文本自身决定类型集合），但扁平路径读法要显式传 `contains`。

用例覆盖：#1/#3/#5/#6/#7/#8 均在 `tests/unit/xuanji/path-pattern.test.ts:141-215`
有逐条手算对照；#8 另在 `tests/unit/patternEnumerationAdapter.test.ts:99` 有端到端用例。

### 5.5 语法错误 vs 零结果：两类必须可区分

这是本轮**行为最值得记住的一处**。返回面有三个分支：

| 情形 | 表现 | 证据 |
|---|---|---|
| ρ 语法错误（`call.`、`(call`、`call{3,2}`） | **抛 `PathPatternError`**，工具层渲染成带 `^` 指位的诊断 | `path-pattern.ts:84`、`:626`；`tools.test.ts:414-431` |
| ρ 合法但类型**在当前图上一个都不存在** | **零结果**（`paths: []`，**没有** `error` 字段） | `XuanjiAdapter.ts:855-862` |
| ρ 合法、类型存在，但没有路径 | 零结果 | `patternEnumerationAdapter.test.ts:163-168` |

**为什么类型不存在是零结果而不是错误**：那是一次**合法的空查询**。
ρ 语法没错，只是这张图上没有那种关系。这与 `graph_cycles` 在没有环的图上返回空同族。
`XuanjiAdapter.ts:840-853` 的注释把三选一（裁剪 / 抛错 / 零结果）的取舍写清了：
**裁剪会把 `call . deadtype` 静默降级成 `call`**（静默近似，本仓最忌讳），
**抛错会把合法空查询误判成非法规则**。

这条在实测中有一个直接后果——**拼错的类型名会静默返回零结果**：

```
ρ = "calls+"   （复数，拼错）→ OK total=0  types=calls
ρ = "Call+"    （大小写错）  → OK total=0  types=Call
ρ = "call+"    （正确）      → OK total=1
```

三个查询在返回面**长得一模一样**（都是 `paths: []` + 无 `error`）。
唯一能区分的是 `patternEdgeTypes` 回显——它把 ρ 解析出的类型名原样带回
（`XuanjiAdapter.ts:860`）。**调用方必须读这个字段**，否则「写错了」和「真的没有」
无法区分。

这是本文要如实登记的**已知不足**：`patternEdgeTypes` 是诊断通道而不是守卫。
正确的做法是让工具层在「类型不在 Σ 里」时也给出提示（例如
`unknownEdgeTypes: ['calls']`），但当前**没有实现**。见 §9。

### 5.6 大小写与空白

- 类型名**大小写敏感**（`tokenize` 不归一化，`path-pattern.ts:129-135`）。
  `Call+` 被当作类型 `Call`，在 Σ 里不存在 ⇒ 零结果。
- 空白宽松：`" call + "` 与 `"call+"` 等价（实测状态数都是 6）。

## 6. 复杂度与预算

> 本节所有数字是**本机实测**（Windows，Node v24.14.0，2026-11-01），
> 用 `node --experimental-strip-types` 直接 import 库源码运行。
> 它们是**量级证据**，不是可写死的常量——换机器会变，复核时请重跑。

### 6.1 编译成本：O(|ρ|)，与 `|Q|` 线性

| ρ | \|Q\| | 编译耗时 |
|---|---|---|
| `call+` | 6 | ≈ 20 µs |
| `call{1,50}` | 102 | ≈ 31 µs |
| `call{1,500}` | 1002 | ≈ 153 µs |
| `call{1,2000}` | 4002 | ≈ 465 µs |
| `(call\|import\|extend\|implement\|dependency)+` | 26 | ≈ 24 µs |

结论：编译成本可忽略（同一量级下枚举是毫秒到秒）。**`{n,m}` 的 m 是唯一的爆炸源**，
`call{1,2000}` 才 0.5 ms，但要记住它同时消耗 4002 个状态对象的内存。

### 6.2 终判成本：几乎与 `|Q|` 无关

同一条路径长度下，不同 `|Q|` 的单次 `matchesLabelSequence` 成本（6 步路径，5 万次取均值）：

| ρ | \|Q\| | ns/条（6 步） | ns/条（20 步） |
|---|---|---|---|
| `call+` | 6 | ≈ 4 000 | ≈ 12 500 |
| `call{1,50}` | 102 | ≈ 3 300 | ≈ 12 400 |
| `call{1,200}` | 402 | ≈ 3 700 | ≈ 10 600 |
| `call{1,500}` | 1002 | ≈ 4 100 | ≈ 10 700 |

**这一步是反直觉但重要的**：状态数从 6 涨到 1002（167 倍），终判成本**没有变化**。
原因在 §3.3：每一步只遍历**当前活跃状态集**的转移，而不是全表；
路径短、ε 闭包浅时活跃集很小。所以 `call{1,500}` 在运行期不比 `call+` 贵多少。

**真正的成本在 union 宽度**（每步的并列标签数）：

| ρ | \|Q\| | 标签/步 | ns/条（6 步） |
|---|---|---|---|
| `(call\|import)+` | 14 | 2 | ≈ 7 500 |
| `(call\|import\|extend)+` | 18 | 3 | ≈ 11 000 |
| `(call\|import\|extend\|implement\|dependency)+` | 26 | 5 | ≈ 15 000 |

⇒ **给调用方的实践规则**：想省时间就收窄**并列标签数**（少用 `|`），
而不是收窄 `{n,m}` 的 `m`。这个结论与「`|Q|` 大会慢」的直觉相反。

### 6.3 枚举成本由路径条数主导，不由 ρ 主导

完全二分层图（每层宽 w、层数 d，相邻层两两连 `call` 边）上枚举 `call+`，
起点只有一个，`maxPaths` 不设限：

| 形状 | 节点 | 边 | 路径数 | 扁平 `edgeTypes` | ρ = `call+` |
|---|---|---|---|---|---|
| 6 层 × 8 宽 | 48 | 320 | 37 448 | 656 ms | 1 062 ms |
| 6 层 × 10 宽 | 60 | 500 | 111 110 | — | 1 701 ms |
| `call{2,4}`（同 6×8 图） | 48 | 320 | 4 672 | — | 92 ms |

三点：

1. ρ 版本比扁平版本慢约 **1.6 倍**（1 062 vs 656 ms）。慢的部分全是终判——
   `isLegalPath` 多跑了一次 NFA 模拟。这是**用时间换表达力**的定价，不是缺陷。
2. 路径数从 4 672 涨到 37 448（8 倍）时，时间从 92 ms 涨到 1 062 ms（11.5 倍）——
   超线性，因为每条物化路径还要付 `makeEntry`（hash 计算）与索引插入。
3. **收窄 ρ 的长度区间是最有效的降本手段**：`call{2,4}` 把 37 448 条降到 4 672 条。

无界 ρ 的兜底：`call*` 的 `lMax = ∞`，`effectiveMaxEdges` 用 `|V|` 兜底
（`path-rule.ts:137`）。实测 600 节点链上 `call*`（simple=true）跑 878 ms、
返回 300 条——它能跑完，但**代价与 `|V|` 同阶**，图大了就不该用无界 ρ。

### 6.4 `lMax` 与状态数的联合预算（对齐 `TOP_K_CANDIDATE_BUDGET`）

`TOP_K_CANDIDATE_BUDGET = 100_000`（`query-engine.ts:55`）的标定口径写在
`query-engine.ts:30-54`：候选数 ≈ `w^d`，调用方的手柄是 `rule.lMax`（层数）
与 `rule.edgeTypes`（宽度），实测 6 层 × 10 宽恰好用尽（100 000）、
7 层 × 8 宽（262 144）抛错。

**ρ 引入后这个标定需要补一维**，因为 ρ 多了一个 `|Q|`。实测 `top-k-weight` 在 ρ 下的表现：

| 形状（ρ = `call+`，maxHops=d） | 候选数 | `candidateBudget` 缺省 | 显式 400 000 |
|---|---|---|---|
| 6 层 × 8 宽 | 37 448 | OK | OK |
| 7 层 × 8 宽 | 262 144 | **抛 `RuleCompositionError`** | OK |

⇒ 三条结论：

1. **`|Q|` 不是预算维度，`lMax` 与并列标签数才是**。§6.1/§6.2 已证明 `|Q|` 在
   编译与终判上都是小项。因此**不需要为 `|Q|` 单独设上限**。
2. **`candidateBudget` 的语义对 ρ 完全不变**：它数的是「候选路径条数」，
   与 ρ 无关（`query-engine.ts:166-176` 的 `accept` 里只 push 路径数组）。
3. **联合预算的建议形态**（不是强制，是给调用方的算式）：
   `候选数 ≈ (每步平均出度)^lMax`，其中「每步平均出度」由 ρ 的并列标签数与图的
   实际度数共同决定。把 `lMax` 乘进指数之前先看 `|Q|`——但 `|Q|` 大不构成风险，
   **`lMax` 每 +1 就是一次乘法**。

> **无机器守卫**：`candidateBudget` 与 `lMax` 之间**没有**任何自动关联。
> `call+` + `maxHops: 12` 在一个稠密图上照样会把候选撑爆（然后抛错）。
> 抛错是设计（响亮失败），不是缺陷，但「先算一下大概多少條」这一步**只能靠人**。

## 7. 与 graphify / codegraph 的对照

### 7.1 graphify：关键词 → 种子 → BFS/DFS → 预算内文本

graphify 的查询链路在 `docs/research/graphify-研究.md:509-517` 记全了：

```
问题文本 → 分词 → 打分 → 选种子 → 建无向视图 → BFS/DFS → 预算内文本
```

它的检索面**没有路径模式**：

| graphify 的能力 | 形态 | 有没有 ρ |
|---|---|---|
| `query_graph` | 关键词 + `mode: bfs\|dfs` + `depth: 1-6` + `token_budget` | **没有**（`graphify-研究.md:614`） |
| `shortest_path` | 两点最短路径（MCP tool 之一） | **没有**（`graphify-研究.md:611`） |
| CLI `graphify path A B` | 两点路径 | **没有**（`graphify-研究.md:266`、`:610`） |
| `context_filter` / `--<relation>` | 按关系名**过滤**（子集），不是序列约束 | **没有**（`graphify-研究.md:420`） |

⇒ **ρ 是本项目的差异化能力**。两个差异点要说准：

1. **序列约束**：graphify 只能「限定允许的关系」或「按关系过滤」，不能表达
   「先 `call` 再 `import`」。`context_filter` 是集合语义，不是序列语义。
2. **模式即接口**：研究方案 §4 的原始动机是「减少 MCP 工具数量」
   （`基于璇玑图思维的代码图谱研究方案.md:77` 末句）。`p = (v_s, ρ, v_t)` 让
   `get_downstream_dependencies` / `get_blast_radius` 这类命名查询坍缩成一个参数。

### 7.2 但**不要吹**：graphify 的 BFS 子图检索在「找相关代码」上更实用

必须诚实写下来的三点：

1. **入口不同**。graphify 的输入是**自然语言问题**，ρ 的输入是**本来就懂图结构的人**。
   Agent 问「登录怎么走到数据库」时，它需要先知道这个仓里那些边叫什么；
   不知道就只能猜。graphify 的 `query_graph` 不需要这个前置知识。
2. **输出形态不同**。graphify 输出 token 预算内的**可读文本**（种子优先 + 显式截断，
   `graphify-研究.md:587-599`）；ρ 输出的是 JSON 路径数组
   （`paths: string[][]`）。对 LLM 消费而言，前者更省事。
3. **graphify 有查询日志**（`graphify-研究.md:616`，JSONL 落到
   `~/.cache/graphify-queries.log`）。本项目**没有**——因此 ρ 的检索质量
   无法被评估，只能靠感觉。这一条是真实差距，不是「以后再说」。

⇒ 正确的定位：**ρ 是「懂图的人的精确工具」**，graphify 的 BFS 子图是
「不懂图的人的发现工具」。两者不互相替代。研究方案 §4 说 ρ 能「显著提升 Agent 的
组合查询能力」——这句话**当前没有实测支撑**，它是一条待验证的假设，
不是已证明的结论。

### 7.3 codegraph（上游 dsh-codegraph / lens）的对照

上游的读侧契约是 nodes/edges 双表 + `kind` 列
（`src/adapters/codeGraphRows.ts:26-40` 的 `EDGE_KIND_MAP`）。它把上游的
`call`/`calls` 压平成 `call`（`codeGraphRows.ts:96-97`），把 `imports` → `import`、
`extends` → `extend`、`implements` → `implement`、`depends` → `dependency`，
未知 `kind` 一律 `dependency`（`codeGraphRows.ts:268`）。

⇒ 上游**有** call 边（它是索引方），但**没有**任何路径模式查询能力；
本项目的 ρ 是建立在上游数据面之上的新一层。这一点与 §10.3 的「共享数据契约，
不复制实现」一致（`基于璇玑图思维的代码图谱研究方案.md:206-216`）。

### 7.4 本轮新增的第三个对照：原生通道自己的 call 边

cycle-134 之前，原生通道（上游双缺席时的第三级数据源）**一条 call 边都不产**——
`src/adapters` 全目录 `call_expression` 命中数为 0
（`src/adapters/treeSitterExtractors.ts:19-22` 的注释是这条缺陷的现场记录）。
它造成的后果恰好落在 ρ 最强的那些用例上：`DEFAULT_PATH_EDGE_TYPES`
（`XuanjiAdapter.ts:54-61`）含 `'call'`，但图上没有 call 边，于是
`call+` / `call* . import` / `implement . call+` 这一族**全部返回零结果**。

本轮（T2，与本文并行落地）补上了它，两层分工明确：

| 层 | 职责 | 位置 |
|---|---|---|
| `TreeSitterAdapter` | 只收**语法事实**：`CallSite = { callerId, calleeName, line }`，被调方只记末段简单名，不猜 | `treeSitterExtractors.ts:238`（`maybeCollectCallSite`）、`:123`（`CALL_EXPRESSION_TYPES`）、`TreeSitterAdapter.ts:398`（`callSitesByFile` 随 `batchScan` 返回） |
| `FileSystemAdapter` | 做**语义裁决**：先用同文件符号集，miss 了再用已解析出的 import 目标文件 | `FileSystemAdapter.ts:338-363`；`resolveCallEdges` 在 `treeSitterExtractors.ts:369` |

证据分两档，跟着 `properties` 走（`treeSitterExtractors.ts:428-438`）：

| 档 | 条件 | `properties.edgeOrigin` |
|---|---|---|
| `exact` | 被调名在**同一个文件**的符号集里唯一命中 | `'ast'` |
| `inferred` | 同文件未命中，靠 import 目标文件里的唯一同名符号补上 | `'heuristic'` |
| 多义 / 未解析 | **跳过而不是猜**（`ambiguous++` / `unresolved++`） | 不产边 |

> **必须说清的两点**：
> 1. 这是**名字级解析**，不是类型系统级解析。`a.b()` 只知道被调名叫 `b`，
>    不知道 `a` 的类型（`src/types/index.ts:216-218` 的注释明说「不做按接收者类型找方法」）。
>    因此 `inferred` 档的边**可能是错的**，且错法不可预测。
> 2. **`resolveCallEdges` 没有任何测试**。`grep -rn "resolveCallEdges|callSitesByFile|CALL_EXPRESSION_TYPES" tests/`
>    = 0 命中——exact / inferred / ambiguous / unresolved 四个分支、以及
>    `edgeOrigin` 的 ast/heuristic 分档，全部**无机器守卫**。
>    这条必须写进任何「call 边已落地」的报告里，否则就是拿「写完了」冒充「验证过」。

对 ρ 的直接影响：§5.4 的 #1/#3/#4/#5/#7/#8/#9/#10 现在**在原生通道上也有数据可查**
（前提是被解析出来的调用点足够多）。但由于上面第 2 点，**ρ 在这些边上的结果
目前无法被证明是对的**——ρ 的终判逻辑有 65 个用例（库层 50 + 适配层 15），边本身没有。

## 8. 诚实边界：ρ **不能**表达什么

逐条给理由，不给「以后可以」。

| 不能表达 | 为什么 | 现有的替代 |
|---|---|---|
| **按节点属性过滤**（「只要 `isExported === true` 的函数」） | ρ 的字母表是边类型，不含节点谓词 | `PathRule.nodeConstraint`（`path-rule.ts:46`）——`compilePathRule` 的选项里有透传（`path-pattern.ts:546`），但 `XuanjiAdapter.pathsByPattern` **没有**把它暴露出来（`PatternEnumerationOptions` 在 `XuanjiAdapter.ts:129-151` 无该字段） |
| **跨 commit 时间谓词**（「只看过去 30 天新增的调用边」） | 没有数据面：`XJEdge` 无时间字段，原生通道不产 commit 切片；`churn` 是**节点级**热点（`src/shared/churn.ts:2-19`），不是边级时间索引 | 无。研究方案 §5.3 的「时序视图」仍是愿景 |
| **节点身份模式**（「起点必须是 `class` 类型」） | 同上，ρ 只管边 | `start` 谓词 |
| **负向约束**（「路径中间不能经过测试文件」） | 需要节点谓词或求差 | `differenceRules`（`path-rule.ts:260`）+ 手工 `pathConstraint` |
| **长度与内容的关联**（「恰好 3 跳且必须是简单路径」） | 长度能表达（`{3}`），简单性不能 | `simple` 在 `PathPatternRuleOptions` 里有（`path-pattern.ts:557`），但适配层透传了（`XuanjiAdapter.ts:881`）；用户侧工具无此参数 |
| **跨图/跨仓** | ρ 只在单个 `GraphSpace` 上跑 | 无 |
| **边属性上的数值条件**（「权重 > 0.8 的边」） | 字母表是类型不是数值 | `truncation: 'top-k-weight'` 只能排序，不能过滤 |

另外两条**行为层面**的边界，比语法边界更容易踩：

### 8.1 闭合 ρ 不做 Booth 去重（实测差异）

`pathsByPattern` 构造规则时**没有传 `normalize`**（`XuanjiAdapter.ts:877-885`），
于是 `normalize` 取 `compilePathRule` 的缺省 `'none'`（`path-pattern.ts:604`）。

后果：同一个三角形的三条旋转等价路径**各算一条**。实测（三节点 call 环，
`ρ = call+`, `closed: true`, `maxHops: 3`）：

```
pathsByPattern → total = 3   [["a","b","c","a"], ["b","c","a","b"], ["c","a","b","c"]]
cycles()       → total = 1   [["a","b","c","a"]]
```

也就是说**同一个环，`graph_path_pattern`（closed）与 `graph_cycles` 报的条数不同**。
`cycles()` 用 `normalize: 'canonical'`（`XuanjiAdapter.ts:793`），ρ 用 `'none'`。

> **无机器守卫**：上述差异**没有**对应用例。`tests/unit/patternEnumerationAdapter.test.ts`
> 全文不含 `closed` 字样（`grep -c closed tests/unit/patternEnumerationAdapter.test.ts` = 0），
> `tests/unit/xuanji/path-pattern.test.ts` 里 `closed` 也不作为选项出现。
> `PathPatternRuleOptions.closed`（`path-pattern.ts:558-559`）在库层可以被测，
> 但**适配层到工具层的这条路径没有一条用例**。
>
> 这是本轮最重要的未闭合项：闭合 ρ 的语义已经实现、但既没有去重、也没有守卫。

### 8.2 `existsWalk` 会忽略 `pathConstraint`

`existsWalk`（`query-engine.ts:324`）的头注明确写它「也不检查整路径谓词
`pathConstraint`」（`:315`）。因此对 ρ 编译出的规则，`existsWalk` 会给**偏乐观**的答案：

```
图：a --import--> b --call--> c
ρ = call . import（要求先 call 后 import）
enumerate   → []
existsWalk(a→c) → true      ← 顺序反了也说"存在"
```

这不是 bug（头注已声明语义边界：`false` 是可靠的否定下界，`true` 不代表存在合法简单路径），
但如果有人在 ρ 规则上调 `existsWalk` 来「先判存在再决定要不要枚举」，就会**多枚举一轮**。
当前 `existsWalk` 在 `src/` 内**没有 ρ 相关的调用点**（`grep -rn existsWalk src/ | grep -v query-engine.ts` = 0 命中），
所以这条目前是「语义陷阱」而不是「现场缺陷」。

### 9.1 call 边已落地，但它的判据**完全没有守卫**

`resolveCallEdges`（`src/adapters/treeSitterExtractors.ts:369`）有四个出口
（`exact` / `inferred` / `ambiguous` / `unresolved`，见 `:389-436`），
以及 `properties.edgeOrigin` 的 ast/heuristic 分档（`:430`）。
`grep -rn "resolveCallEdges|callSitesByFile|CALL_EXPRESSION_TYPES" tests/` = **0 命中**。

⇒ 现状是：**ρ 的终判逻辑有 65 个用例，喂给它的 call 边一条用例都没有**。
这意味着「ρ 在原生通道上查 call+ 得到的结果是对的」这句话**当前无法被证明**。
ρ 侧的行为可复核（§6 全部实测），边侧的行为不可复核。

这不是 ρ 的缺陷，但它决定了 ρ 现在的可信上限：**ρ 对边类型的处理可信，
边本身从哪来、对不对，不在 ρ 的保证范围内。**
