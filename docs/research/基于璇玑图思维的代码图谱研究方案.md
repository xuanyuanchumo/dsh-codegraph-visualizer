# 面向 dsh 宿主的大模型代码仓库项目空间图谱：基于璇玑图思维的研究与优化方案

**摘要** 本文以“璇玑图思维”为认知框架，系统研究如何为 DeepSeek Harness（dsh）宿主构建可被大模型 Agent 高效调用的项目空间代码图谱。璇玑图的核心结构特征——有限离散空间、可枚举遍历规则、多向自洽连接——为代码图谱的多粒度组织与路径枚举查询提供了直接的映射范式。在综述 2025—2026 年间 bot-brain、code-nexus、kula、code-spider、pigeongraph、Codebase-Memory、CodeGraph 等开源代码图谱系统的基础上，本文提出一个面向 dsh 的四层架构：可切片图模型层、算法与建模层、MCP 工具契约层、行为采纳与可视化层。核心论点是：面向 Agent 的代码图谱，**“图建得对”只是必要条件，“模型在决策点真的用图”才是充分条件**；图谱设计必须与宿主 Agent 的行为机制协同优化。本文给出完整的研究文档，包括形式化模型、算法选型论证、可视化方案、dsh 集成路径与分阶段实施路线。


## 1. 问题背景与核心张力

大模型编码 Agent 在仓库级任务中的典型失败模式，不是“不会写代码”，而是“找不到该读的代码”。Agent 通常以 grep → read → grep 的循环探索仓库，在中等以上规模的项目中消耗数万至数十万 token 才能拼出有限的调用链理解。CodeGraph 的基准测试显示，在 VS Code、Tokio 等真实仓库上，无图谱时 Agent 的工具调用多出 89%，token 消耗多出 69%。Codebase-Memory 的论文数据进一步量化了这一收益：以 83% 的答案质量（对比文件探索 Agent 的 92%）换取 10 倍的 token 缩减和 2.1 倍的工具调用缩减。这说明代码图谱的价值命题是成立的，但同时也揭示了一个关键权衡：**图谱查询在“结构性问题”上接近或超越探索式 Agent，在“需要细粒度语义判断”的问题上仍有差距**。

然而，更隐蔽的问题出现在工程落地层面。dsh-codebase-memory 的作者在实测中发现：某会话 228 次工具调用中，代码图谱被使用 **0 次**；另一个会话 12 次 MCP 调用中 10 次失败后模型迅速放弃。当提示只写在 system prompt 开头时，模型在“第 50 步”的实际决策点上早已忘记了图谱工具的存在。@hyzyn/dsh-codegraph 的采纳率数据也印证了这一点：窄口径（发现类调用为分母）下的采纳率为 28.8%，宽口径（含 read/view）下仅 2.2%。因此，本文的核心设计立场是：**代码图谱的研究对象不应止于“图本身”，而应扩展到“图—Agent—决策点”的联合系统**。


## 2. 璇玑图思维的结构提炼与映射

璇玑图的传统解读多停留在回文诗的文字游戏层面，但从信息结构的角度看，它本质上是一个高度工程化的二维离散信息编码系统。其可操作的结构特征可以提炼为三条：

**（1）有限离散空间**。璇玑图为 29×29 网格，841 字固定于格点，无脱落、无重复位置。每个字符拥有唯一的空间地址，任何遍历路径都在这个闭合空间中展开。

**（2）可枚举的遍历规则**。纵、横、斜、交互、正读、反读、退一字、迭一字等规则构成一个规则集合，每一种规则在固定网格上诱导出一条或一族线性序列。璇玑图的“可读性”不是单一的，而是规则参数化的。

**（3）多向自洽连接**。同一组字符在不同遍历规则下产出语义连贯的诗句，意味着空间邻接关系与语义连贯关系之间存在多对多的映射。一个字符既是横向诗句的组成部分，也是纵向和斜向诗句的组成部分。

将这三条特征映射到代码图谱，可以得到一个直接而有力的对应：

| 璇玑图特征     | 代码图谱对应物                                           | 操作含义                                 |
| -------------- | -------------------------------------------------------- | ---------------------------------------- |
| 有限离散空间   | 仓库的符号—关系图在给定 commit 下是有限闭集              | 图谱必须有明确的边界与版本锚定           |
| 可枚举遍历规则 | 调用链、依赖链、数据流、继承链、测试覆盖链等路径语义     | 查询不是“搜节点”，而是“在规则下枚举路径” |
| 多向自洽连接   | 同一符号同时属于结构视图、时序视图、所有权视图、领域视图 | 图谱需要多视图切片，而非单一扁平图       |

璇玑图思维给本文的关键启示是：**代码图谱的第一等公民应当是“路径”与“视图”，而非“节点”与“边”** 。Agent 问“登录请求怎么到达数据库”，本质上是在问一条满足特定边类型约束的路径，而非在找某个孤立的符号。现有系统虽然提供 `get_downstream_dependencies`、`get_blast_radius` 等工具，但多数仍以节点为中心组织查询接口，路径枚举的规则化程度不足。本文将璇玑图的“可枚举遍历规则”形式化为图谱上的**路径模式查询**，作为工具契约设计的核心抽象。


## 3. 参考基线：开源代码图谱系统的能力谱系与结构性缺口

2025—2026 年间涌现的代码图谱系统已经形成了一个可辨识的能力谱系，但没有任何单一系统同时满足 dsh 宿主场景的全部要求。下表从六个维度对代表性系统进行定位：

| 系统                | 存储/引擎          | 语言覆盖        | 时序能力         | Agent 接口        | 可视化                       | 关键强项 / 缺口                                              |
| ------------------- | ------------------ | --------------- | ---------------- | ----------------- | ---------------------------- | ------------------------------------------------------------ |
| **bot-brain**       | SQLite + FAISS     | 8+              | 无显式时序       | MCP，20 工具      | 无                           | 混合检索（BM25+向量 RRF），零 LLM 依赖                       |
| **code-nexus**      | rustworkx + SQLite | 3（Py/TS/Rust） | **Git 时序叠加** | MCP               | **WebGL 3D，10k 节点 60fps** | 时序可视化强，语言覆盖窄                                     |
| **kula**            | RDF，单二进制      | 多语言          | Git 锚定记忆     | MCP + 工作流      | 交互地图                     | 代码锚定记忆、架构评审、fence 机制                           |
| **code-spider**     | **Neo4j 5**        | Py/TS/JS        | CI 触发          | MCP               | 无内建                       | 跨服务 REST/Kafka 流、Cypher 查询能力                        |
| **pigeongraph**     | SQLite (WAL+FTS5)  | 多语言          | 文件监听         | MCP，单轮 explore | 内建 UI                      | 多图层、动态 dispatch 合成、96% token 缩减                   |

| **CodeGraph**       | SQLite + FTS5      | **20+**         | 增量重同步       | MCP               | 无                           | 极致的性能工程（Linux kernel 12 min）、大量真实基准          |
| **codeknow**        | NetworkX DiGraph   | 25+             | drift 快照       | 独立 CLI/HTML     | vis.js                       | **架构债务评分、onboard 导览**，图分析内建                   |
| **codeskeleton**    | petgraph (Rust)    | 7               | SHA256 增量      | 独立 HTML/JSON    | vis.js                       | 极简、零依赖、“god nodes”分析                                |
| **gry**             | SQLite，单二进制   | **68 语法**     | 增量索引         | MCP + CLI         | 无内建                       | **代码+文档+配置+基础设施统一图模型**，证据分级（exact/inferred/ambiguous） |

**能力谱系的结构性缺口** 可以归纳为四点，它们构成了本文方案的设计输入：

**缺口一：多粒度切片与路径枚举的分离**。bot-brain 的混合检索强在“找相关文本”，pigeongraph 的 `explore` 强在“单轮符号查找”，但很少有系统将“在给定边类型规则下枚举路径”作为一等工具契约暴露给 Agent。codeknow 的 `onboard` 和 `impact` 接近这一目标，但其路径语义偏重分析报告而非可组合的查询原语。

**缺口二：时序维度与结构维度的深度融合**。code-nexus 提供了时间旅行滑块，kula 将记忆锚定到代码，但时序信息更多是“叠加层”而非“图本身的维度”。对于 Agent 而言，“这个函数在过去三次修改中调用方增加了哪些”应当是一个可以直接查询的结构—时序联合谓词，而非先查结构图再查 Git log 的拼接操作。

**缺口三：行为采纳的系统性缺失**。绝大多数开源系统假设“工具暴露后 Agent 自然会用”，而 dsh 插件生态的实测数据反复证伪了这一假设。代码图谱工具的设计必须包含**决策点触发机制**和**失败自愈机制**，否则图谱的工程投入无法转化为 Agent 的行为改变。

**缺口四：dsh 原生的可视化与图工具协同**。dsh-plugin-kit 已经提供了 Codegraph 集成的可视化卡片（索引状态、符号搜索、调用链、影响面、一键 sync-index），但可视化主要是“给人看的”，尚未形成“人通过可视化引导 Agent 查询，Agent 的查询结果回写可视化”的闭环。


## 4. 形式化建模：璇玑图谱的四维切片模型

借鉴璇玑图的“规则参数化遍历”思想，本文将 dsh 宿主下的项目空间代码图谱形式化为一个四维切片图：

$$\mathcal{G} = (V,\; E,\; \Sigma,\; \mathcal{T},\; \Pi)$$

其中 $V$ 是符号节点集（文件、类、函数、模块、测试、配置项、文档段落），$E$ 是带类型标签的边集，$\Sigma$ 是边类型字母表（`calls`, `imports`, `inherits`, `implements`, `tests`, `documents`, `configures`, `deploys` 等），$\mathcal{T}$ 是时间索引（commit 或 commit 区间），$\Pi$ 是**视图划分函数** $\Pi: V \cup E \to 2^{\mathcal{V}_{\text{view}}}$，将节点和边映射到多个正交视图上。

**视图定义**。本文定义四个与 dsh 编码场景直接相关的视图：

- **结构视图** $\mathcal{V}_{\text{struct}}$：AST 抽取的符号与静态关系。这是所有系统共有的基础视图。
- **时序视图** $\mathcal{V}_{\text{temp}}$：以 commit 为切片单位，记录节点/边的出现、消失、修改频率与 churn 率。对于边 $(u,v,t)$，定义其**挥发度** $\text{vol}(u,v)=\frac{|\{t: (u,v,t)\in E\}|}{|\{t: u,v \text{ 均存在}\}|}$，衡量关系的稳定性。
- **所有权/知识视图** $\mathcal{V}_{\text{own}}$：Git blame 派生的作者—符号关联，以及 bus factor、知识孤岛度量。codeknow 的 `owners` 命令展示了这一视图的实用价值。
- **领域视图** $\mathcal{V}_{\text{dom}}$：通过社区发现将结构图投影到功能域/业务域。codeskeleton 的 label propagation 社区检测和 codeknow 的 debt 评分都依赖这一投影。

**路径模式查询**。璇玑图“可枚举遍历规则”的形式化对应物是一个路径模式 $P = (v_s,\; \rho,\; v_t)$，其中 $v_s,v_t$ 是起止节点（或节点模式），$\rho$ 是一个正则表达式式的边类型序列约束，例如 $\rho = \texttt{calls}^+ \cdot \texttt{imports}? \cdot \texttt{configures}$。查询语义为在给定 commit 切片 $t$ 下枚举所有从 $v_s$ 到 $v_t$ 且边标签序列匹配 $\rho$ 的路径。这一抽象的统一性在于：`get_downstream_dependencies` 是 $\rho=\texttt{calls}^+$，`get_blast_radius` 是 $\rho=\texttt{calls}^+ \cup \texttt{imports}^+ \cup \texttt{inherits}^+$ 的反向闭包，而“登录请求到数据库”是 $\rho=\texttt{handles} \cdot \texttt{calls}^* \cdot \texttt{queries}$ 的跨视图路径。将工具接口建立在路径模式而非固定命名的查询上，可以显著提升 Agent 的组合查询能力，同时减少 MCP 工具的数量（工具爆炸是 Agent 选择困难的重要诱因）。

**图谱的“璇玑地址”** 。借鉴璇玑图为每个字符赋予唯一空间地址的做法，本文为每个符号分配一个**稳定坐标** $(\text{file\_hash},\; \text{byte\_offset},\; \text{symbol\_kind})$ 以及一个**语义指纹**（AST 子树哈希的 MinHash）。稳定坐标使增量索引和精确跳转成为可能；语义指纹使“跨文件查找结构相似函数”成为可查询的操作，而不依赖 LLM 的语义判断。gry 的“证据分级”（exact / inferred / ambiguous / unresolved）为这一设计提供了工程先例。


## 5. 算法层：从图构建到仓库级表示学习

### 5.1 图构建管线

基础管线沿用已被验证的 Tree-sitter AST 抽取路径：文件检测 → SHA256 增量缓存 → 并行 AST 解析 → 符号/边抽取 → 图组装 → 社区检测 → 导出。在 dsh 场景下，需要强化两点：**调用解析的多策略级联**和**证据分级**。code-spider 的 6 策略启发式级联提供了可参考的工程方案。建议级联顺序为：精确 AST 引用 → 类型约束匹配 → 导入图可达性 → 同名启发式 → 字符串/反射回退。每一条解析出的边附带置信度标签，Agent 查询时可以按置信度过滤，避免“把推断当成事实”。

### 5.2 社区发现与中心性

社区发现用于领域视图的投影和“god node”识别。Leiden 算法在模块度优化上优于 Louvain，且支持多分辨率参数，适合代码图谱中存在层次性社区结构的场景。Infomap 基于 Map Equation，提供信息论意义上的社区划分，其“map equation centrality”可以将节点重要性置于社区语境中度量，对于识别“跨社区的桥接节点”尤其有用。中心性方面，PageRank 适合识别全局结构性枢纽，betweenness 适合识别“如果移除则图断裂”的关键路径节点，degree 的简单变体（如 codeskeleton 的 god nodes）适合快速概览。建议对 dsh 暴露的工具中，中心性查询不单独暴露为独立工具，而是作为路径枚举的排序参数，避免工具集膨胀。

### 5.3 增量更新与时序演化

增量更新的核心是“只处理变化的影响闭包”。codeknow 和 codeskeleton 的 SHA256 文件缓存提供了第一层过滤。更深层的增量需要**符号级 diff**：当文件内容变化时，AST diff 给出新增/删除/修改的符号集，更新操作限制在这些符号及其直接邻接边上。gry 报告的增量性能——10,000 文件仓库单文件编辑 p50 约 233 ms——表明这一目标在工程上是可达到的。时序视图的构建需要将每次索引结果与前一 commit 的图快照做结构 diff，计算节点/边的挥发度、churn 率和新增跨社区边。这些时序特征应作为节点/边的属性持久化，使路径枚举可以附加时序谓词，例如“只返回过去 30 天内新增的调用边”。

### 5.4 图神经网络与仓库级表示学习的定位

GREPO 基准将仓库表示为对应于 commit 的图快照序列，并评测 GNN 在缺陷定位上的表现，这为代码图谱的表示学习提供了重要的方法论参照。然而，在 dsh 的即时 Agent 场景下，GNN 的离线训练—推理循环与“会话内低延迟查询”的需求存在张力。本文的建议是**分层引入**：第一阶段以符号级嵌入（用于语义相似性）和图结构启发式为主；第二阶段在积累足够的“图谱查询—Agent 采纳—任务结果”日志后，训练轻量 GNN 或图注意力模型，用于对路径枚举结果做重排序，而非替代符号级查询。这样既保持了系统的可解释性和低延迟，又为长期的表示学习留出了空间。


## 6. 可视化方案：多粒度语义缩放与“人—Agent”协同

代码图谱可视化面临的核心矛盾是：**全图视图必然成为“毛球”（hairball）** 。在 1,447 节点、360,823 边的真实代码图上，力导向布局会产生严重的视觉混乱。因此，可视化方案必须从“把图画出来”转向“在正确的粒度上呈现正确的子图”。

**布局策略的组合**。对于结构—层次关系（目录包含、继承层次、模块依赖），Sugiyama/Dagre 层次布局是推荐的首选，它提供了清晰的上下方向和结构可读性。对于领域视图和跨社区关系，力导向布局（ForceAtlas2 或社区感知的力模型）仍然有价值，但应与社区检测联合使用：先以社区为单位做粗粒布局，再在社区内部展开。对于时序视图，时间轴不应作为第三维挤入空间布局，而应作为独立的“时间旅行”滑块叠加在当前视图上，code-nexus 的 time-travel slider 是这一交互的成熟先例。

**语义缩放的离散层级**。CodeViz 的 5 级语义缩放提供了一个可操作的设计参数：不同缩放级别展示不同的信息密度和抽象层级。本文建议面向 dsh 的图谱可视化采用四级语义缩放：**仓库级**（模块/包为节点，边为聚合依赖）→ **文件级**（文件为节点，边为 import/call 聚合）→ **符号级**（函数/类为节点，边为 calls/inherits）→ **行内级**（点击符号后展示源代码片段与直接调用点）。每一级只渲染该粒度下有意义的边类型，其余边类型折叠或聚合。这直接对应璇玑图“不同遍历规则产出不同视图”的思想。

**渲染性能的技术选型**。大规模图渲染必须依赖 WebGL 或 WebGPU。code-nexus 使用 react-force-graph-3d 实现了 10k 节点 60fps 的 3D 渲染；helios 展示了 WebGPU + Three.js 在客户端进行语义嵌入和 3D 力导向可视化的完整管线。对于 dsh 的 Web UI 集成，建议采用**2D 为主、3D 为辅**的策略：2D（React Flow / Sigma.js）用于精确的符号级导航和代码阅读场景，3D 用于领域视图的宏观探索和“结构引力”感知。Sigma.js 的 WebGL 渲染器已被 CodeViz 验证可支撑 10,000+ 文件规模的交互。

**人—Agent 协同的可视化闭环**。dsh 的独特优势在于 Agent 和用户共享同一个 Web UI。可视化不应只是“给人看的报告”，而应成为**引导 Agent 查询的界面**。具体设计包括：（1）用户在可视化中框选一个子图或标记一条路径，该选择自动注入下一次 Agent 调用的上下文，作为 `focus_path` 参数；（2）Agent 的路径枚举查询结果高亮显示在可视化中，用户可以直接看到 Agent“正在看什么”；（3）当 Agent 的查询采纳率在某项目上持续偏低时，可视化界面主动提示用户“当前项目图谱可能缺少某类边，是否重新索引或补充解析规则”。这一闭环将可视化的角色从“事后解释”提升为“行为塑形”。


## 7. dsh 集成架构：MCP 工具契约与行为采纳机制

### 7.1 插件形态与 MCP 工具集

dsh 的“一切皆插件”架构和 Cordis 微内核意味着代码图谱应以**独立插件**形态接入，而非修改宿主源码。已有的 `dsh-codebase-memory`、`dsh-codegraph-project` 和 `@hyzyn/dsh-codegraph` 验证了这一路径的可行性。本文建议的 MCP 工具集遵循“少而组合性强”的原则，核心工具控制在 6—8 个：

- `graph_query(pattern, commit?, filters?)`：路径模式查询的统一入口，`pattern` 采用前述路径正则语法。这一工具取代大量命名的固定查询，降低 Agent 的选择负担。
- `graph_node(symbol_id, view?)`：获取符号的多视图详情（结构、时序、所有权、领域），带证据置信度。
- `graph_slice(view, granularity, focus?)`：获取指定视图和粒度下的子图，直接对接可视化。
- `graph_impact(symbol_id, depth?, edge_types?)`：影响面分析，本质是反向路径闭包，但作为高频任务保留为快捷工具。
- `graph_index_status(project_path)`：返回索引状态、语言覆盖、证据分级统计，供 Agent 判断是否需要触发索引。
- `graph_sync(project_path)`：增量同步。

工具描述（description）的写法至关重要。基于 dsh-codebase-memory 的失败经验，描述中应包含**反例和决策点提示**，而不仅仅是功能说明。例如 `graph_query` 的描述可以写成：“当需要理解跨文件调用链、依赖关系或修改影响面时，使用本工具。如果已经用 grep 找到了候选符号名，不要继续逐个 read 文件来拼调用链——直接调用本工具查询路径。”

### 7.2 决策点注入与失败自愈

dsh-codebase-memory 的“nudge”机制提供了可复用的范式：不是在 system prompt 开头一次性提醒，而是在**工具管线中的决策点**注入提示。本文建议在 dsh 插件中实现三个触发条件：

- **grep 后触发**：当 Agent 完成一次 grep 或 glob 并得到非空结果后，在结果末尾附加一条简短提示：“如需了解这些符号之间的调用关系，可调用 `graph_query`。”
- **连续 read 触发**：当同一会话中连续读取超过 N 个文件（建议 N=3）且尚未调用图谱工具时，注入提示。
- **MCP 调用失败触发**：当 `graph_query` 返回空结果或报错时，自动分析失败原因（如项目未索引、路径模式语法不匹配），在下一次决策点注入修正建议，而非让模型连续重试后放弃。

**采纳率作为一等指标**。@hyzyn/dsh-codegraph 将采纳率定义为“图谱工具命中数 / 发现类工具调用数”，并区分窄口径与宽口径。本文建议 dsh 代码图谱插件内建采纳率仪表，按项目分组统计，并将采纳率低于阈值的项目标记为“需要可视化引导或索引修复”。采纳率不应作为惩罚模型的指标，而应作为**诊断图谱设计是否有效的信号**。


## 8. 实施路线与评估框架

**阶段一：最小可行图谱与基线测量（4—6 周）** 。以 Python/TypeScript 为目标语言，基于 Tree-sitter 构建结构视图，实现 `graph_query`、`graph_node`、`graph_index_status` 三个核心工具。在 dsh 中以插件形态接入，启用 grep 后触发提示。收集 5—10 个真实项目的采纳率、token 消耗、任务完成质量基线。这一阶段的目标不是追求图谱的完备性，而是验证“决策点注入”能否将采纳率从个位数提升到可用的量级。

**阶段二：时序视图与路径模式扩展（6—8 周）** 。引入 Git 时序叠加，实现挥发度、churn 率、时序谓词过滤。扩展路径模式语法，支持跨视图边类型（`calls` + `configures` + `documents`）。在可视化中接入 2D 语义缩放和路径高亮，开启人—Agent 协同选择闭环。评估重点转向“时序感知的查询是否提升了 Agent 在变更影响分析任务上的准确性”。

**阶段三：领域视图、3D 探索与表示学习预备（8—12 周）** 。集成 Leiden/Infomap 社区发现，暴露 `graph_slice(view="domain")`。接入 3D 领域视图用于宏观探索。开始积累“查询—采纳—结果”日志，为路径重排序模型准备训练数据。这一阶段还需要完成 dsh 插件包的发布、配置 schema、以及多项目索引管理（每个会话自动绑定当前项目索引）。

**评估指标体系** 应包含四个层次：**结构层**（索引覆盖率、增量延迟、证据分级比例）；**Agent 行为层**（采纳率窄/宽口径、首次图谱调用前的探索步数、失败后重试率）；**任务效果层**（在调用链问答、影响面分析、测试推荐等结构性子任务上的准确率与 token 效率）；**人机协同层**（可视化交互是否改变了后续 Agent 查询、用户对图谱结果的信任度）。CodeGraph 和 Codebase-Memory 的公开基准可以作为任务效果层的参照基线。


## 9. 结论

璇玑图给代码图谱研究的真正启示，不在于“回文”的文学形式，而在于它展示了一种**规则参数化的空间信息组织方式**：同一有限空间在不同遍历规则下产生多种自洽解读。将这一思维迁移到 dsh 宿主的代码图谱上，意味着图谱的核心抽象应从“节点+边”上升到“视图+路径模式”，工具契约应从“固定命名的查询”上升到“可组合的路径枚举”，评估标准应从“图建得全不全”上升到“模型在决策点用不用、用得对不对”。

现有开源系统已经证明代码图谱在 token 效率和结构理解上的显著收益，但 dsh 生态的实测数据同时表明，**接入不等于使用，使用不等于有效**。因此，本文方案将行为采纳机制、决策点注入和失败自愈作为与图算法同等重要的设计对象。只有将“璇玑式”的多视图路径枚举能力与 dsh 的插件化 Agent 运行时深度咬合，代码图谱才能从一个“被动查询的数据库”转化为 Agent 仓库级工作的**认知基础设施**。

#### 11.1.1 缺口一：路径查询表达不了「序列」

### 12.2 `unknownEdgeTypes`：把「Σ 里没有」与「图上没有」分开

§11.3 记录的问题是：`calls+` 与「图上没有 call 边」在返回面上同形
（都 `paths: []` 且无 `error`）。本轮把适配层的「缺失」判断拆成两半：

```ts
// src/shared/analysis/XuanjiAdapter.ts
const present = this.space.edgeTypes();
const unknownEdgeTypes = [...compiled.edgeTypes]
  .filter((type) => !KNOWN_ADAPTER_EDGE_TYPES.has(type as AdapterEdgeType))
  .sort();
const absentFromGraph = [...compiled.edgeTypes]
  .filter((type) => KNOWN_ADAPTER_EDGE_TYPES.has(type as AdapterEdgeType) && !present.has(type))
  .sort();
if (unknownEdgeTypes.length > 0 || absentFromGraph.length > 0) {
  return { paths: [], ..., unknownEdgeTypes };
}
```

`KNOWN_ADAPTER_EDGE_TYPES` 是 Σ 全集（`GraphEdge.type` 的 9 个取值域）。
关键区别：

| ρ | `unknownEdgeTypes` | `paths` | 语义 |
|---|---|---|---|
| `calls+` | `['calls']` | `[]` | **用户拼错了**（Σ 里没有 `calls`） |
| `Call+` | `['Call']` | `[]` | 同上（`tokenize` 不归一化大小写） |
| `contains+`（图上没有 contains 边） | `[]` | `[]` | **合法的零结果**（Σ 里合法，只是图上没有） |
| `association . aggregation . composition` | `[]` | `[]` | 同上（Σ 成员但全仓无生产者） |
| `call . calls` | `['calls']` | `[]` | 混合：只报拼错的，不报合法的 |

这同时绕开了 `assertRule` 的 Σ_R ⊆ Σ 静态校验——那个校验按「边类型必须出现在图里」
判非法规则，对 ρ 会把「合法的零结果」误判成「非法规则」。

### 12.3 Σ 是宿主侧事实，客户端不得复制

Σ 是 `GraphEdge.type` 的取值域，由宿主定义。客户端复制一份会静默分叉
（本仓库反复记录过这类缺陷）。因此语法预检路由在 `ok` 响应里回显 `edgeTypes`：

```
GET /api/v1/codegraph/path-pattern/syntax?pattern=call+
→ 200 { ok: true, pattern: "call+", edgeTypes: ["aggregation","association","call",...] }
```

客户端用它做类型名提示区，不硬编码。

### 12.4 语法预检：单独路由 + 语法错也返回 200

- **单独路由**：`parsePathPattern` 在 `src/xuanji`，打进客户端 bundle 会让
  Host/Client 隔离的意图落空。
- **语法错返回 200**：预检的语义是「这条 ρ 文本能否被解析」，把「错」也当正常回答，
  便于界面逐键校验。用 HTTP 状态码区分「语法错」与「服务端故障」会让 UI 逻辑分叉。
- **预检不返回 `unknownEdgeTypes`**：拼错类型名**语法合法**，只有**枚举**时才能
  发现它不在 Σ 里。预检只回答「能不能解析」，不回答「类型名对不对」。

### 12.5 客户端面板：五态互斥

`pathPatternStatus` 用枚举而非 `isLoading + error + result` 三件套：
`idle / loading / ready / empty / invalid / not-found / unknown-types / error / timeout`。

**核心不变量**：`unknownEdgeTypes` 非空时落到**与 `empty` 可区分**的终态
`'unknown-types'`，面板渲染 `.cg-pathpattern-unknown`（黄边），文案
「ρ 里有不认识的边类型：{types}」——绝不显示「没有匹配」。
组件测试用成对正/反向 DOM 断言钉住：`empty` 态不渲染 `.cg-pathpattern-unknown`，
`unknown-types` 态不渲染 `.cg-pathpattern-empty`，且两者可见文案互不相同。
