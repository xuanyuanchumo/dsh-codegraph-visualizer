## 二、P0 功能可行性评估

### FR-25 路径查找

| 维度 | 评估 |
|------|------|
| **DSH 规范** | ✅ 纯 Client 端功能，不涉及 Host 通信，无违规 |
| **数据结构** | 邻接表（Cytoscape.js 内部已有 `eles.dijkstra()` 和 `eles.aStar()` API）；起点/终点选择状态需在 graphStore 中新增 `pathStartId` 和 `pathEndId` |
| **算法** | Dijkstra 最短路径 O(V+E)；Cytoscape.js 内置，无需自实现 |
| **设计模式** | **Command 模式** — 将"查找路径"封装为可撤销命令，配合 FR-31 历史记录 |
| **开发原则** | SRP：路径查找逻辑独立为 `PathFinder` 类，不混入 CytoscapeRenderer |
| **可行性** | ✅ **可行** — Cytoscape.js 内置 `eles.dijkstra()`，仅需 UI 交互层（选择起点/终点）和结果高亮 |

**实现方案：**
```
src/client/renderer/PathFinder.ts  — 路径查找逻辑
src/client/components/PathBar.tsx  — 路径查找 UI（起点/终点选择 + 结果展示）
```

- 在 `IRenderer` 接口新增 `findPath(sourceId: NodeId, targetId: NodeId): NodeId[]`
- 在 `CytoscapeRenderer` 中实现：调用 `cy.elements().dijkstra(sourceNode, weightFn).pathTo(targetNode)`
- 在 `graphStore` 中新增 `pathStartId`、`pathEndId`、`pathResult` 状态
- 在 `GraphPanel` 中新增 `PathBar` 组件，显示路径结果和操作按钮

### FR-32 架构健康评分

| 维度 | 评估 |
|------|------|
| **DSH 规范** | ✅ 评分计算在 Client 端执行（基于已有图谱数据），无需 Host 通信 |
| **数据结构** | 评分模型：`{ coupling: number; cohesion: number; cyclicDependencyRate: number; modularity: number; overall: number }`；邻接矩阵（从 GraphData 构建） |
| **算法** | 耦合度：模块间边数/总边数 O(E)；内聚度：模块内边数/模块总边数 O(E)；循环依赖率：已有 `detectCycles()` O(V+E)；模块度：Louvain 社区检测 O(V+E)（可选，简化版可用聚类策略替代） |
| **设计模式** | **Strategy 模式** — 不同评分维度可独立计算，类似 ClusterStrategy |
| **开发原则** | SRP：每个评分维度独立为 Scorer 类；OCP：新增评分维度不需修改现有代码 |
| **可行性** | ✅ **可行** — 基础数据（节点、边、循环依赖）均已可用，评分算法复杂度低 |

**实现方案：**
```
src/client/analysis/HealthScorer.ts        — 健康评分主类
src/client/analysis/CouplingScorer.ts      — 耦合度评分
src/client/analysis/CohesionScorer.ts      — 内聚度评分
src/client/analysis/CyclicDepScorer.ts     — 循环依赖率评分
src/client/analysis/ModularityScorer.ts    — 模块度评分
src/client/components/HealthScoreCard.tsx  — 评分展示卡片
```

- 评分计算基于 `rawNodes` 和 `rawEdges`，不依赖聚类后的数据
- 评分卡片作为浮动面板显示，类似 StatsPanel
- 总分 = 加权平均（耦合度 25%、内聚度 25%、循环依赖率 25%、模块度 25%）

## 四、CytoscapeRenderer 重构方案（ISS-03）

### 4.1 问题分析

当前 `CytoscapeRenderer.ts` 500+ 行，包含以下职责：
- Cytoscape 实例管理（init/destroy）
- 数据更新（updateData + 批量添加 + RAF 队列）
- 布局管理（4种布局 + 自动降级 + 去重叠）
- 高亮管理（节点高亮 + 调用链 + 循环依赖 + 影响分析 + 继承层次）
- 导出（PNG/SVG/JSON）
- 视口管理（缩略图 + 视口信息）
- 主题管理

违反 SRP（单一职责原则），需拆分。

### 4.2 重构方案

采用 **Facade + Strategy** 模式拆分：

```
src/client/renderer/
  CytoscapeRenderer.ts       — Facade，实现 IRenderer，委托各 Controller
  LayoutController.ts        — 布局管理（4种布局 + 自动降级 + 去重叠 + 新增径向/树形）
  StyleController.ts         — 样式与主题管理
  InteractionController.ts   — 交互事件处理（tap/dbltap/hover）
  HighlightController.ts     — 高亮逻辑（调用链/循环依赖/影响分析/继承层次/路径查找）
  ViewportController.ts      — 视口管理（缩略图/聚焦/BFS/虚拟滚动）
  DataController.ts          — 数据更新（增量添加 + 批量队列 + RAF）
```

**重构原则：**
- CytoscapeRenderer 作为 Facade，持有 `cy: Core` 实例，将各职责委托给 Controller
- 每个 Controller 通过构造函数注入 `cy: Core` 和回调函数
- Controller 之间无直接依赖，通过 CytoscapeRenderer 协调
- IRenderer 接口不变，外部调用者无感知

### 4.3 重构步骤

1. 提取 `LayoutController`（布局逻辑 + removeOverlaps）
2. 提取 `HighlightController`（高亮逻辑 + detectCycles）
3. 提取 `DataController`（updateData + batchQueue + processBatchQueue）
4. 提取 `StyleController`（getStylesheet + updateTheme）
5. 提取 `InteractionController`（事件绑定）
6. 提取 `ViewportController`（getThumbnail + getViewportInfo + focusNeighborhood）
7. CytoscapeRenderer 简化为 Facade

## 六、开发原则合规性检查

| 原则 | v0.2.0 合规策略 |
|------|-----------------|
| **SRP** | CytoscapeRenderer 拆分为 6 个 Controller；每个评分维度独立 Scorer；每种规则检测器独立 Detector |
| **OCP** | 聚类策略注册表模式（已有 `registerClusterStrategy`）；规则检测器注册表；布局类型可扩展 |
| **LSP** | 所有新 Controller 遵循 IRenderer 接口契约；TreeSitterAdapter 实现与现有 Adapter 相同接口 |
| **ISP** | IRenderer 接口可能过大 — 考虑拆分为 IGraphRenderer + IGraphAnalysis + IGraphInteraction |
| **DIP** | 规则检测器依赖抽象 RuleDetector 接口；评分器依赖抽象 Scorer 接口 |
| **DRY** | 复用已有 `fetchMergedGraph`、`computeClusteredGraph`、`detectCycles`；路径查找复用 Cytoscape.js 内置算法 |
| **KISS** | 规则引擎使用 JSON 配置而非自定义 DSL；健康评分使用简单加权平均而非复杂模型 |
| **YAGNI** | P2 功能（3D视图、鱼眼透镜、太阳爆发）推迟到 v0.3.0；MCP Server 和 CLI 作为可选模块 |

## 七、DSH 九条红线合规检查

| 红线 | v0.2.0 合规策略 |
|------|----------------|
| **注册即 effect** | 所有新工具注册在 `ctx.effect` 中；所有新事件监听在 `ctx.effect` 中 |
| **Waterfall 必须委托** | Tree-sitter 解析在 Client Web Worker 中执行；版本对比 Git 操作在 Host 端执行 |
| **Branded ID** | 新增 NodeId/EdgeId 类型保持 Branded；新数据源节点 ID 使用相同 Branded 类型 |
| **声明合并事件** | 新增事件通过 `declare module '@deepseek-ai/cordis'` 扩展 Events 接口 |
| **ESM only** | 所有新文件使用 ESM；`web-tree-sitter` 支持 ESM 导入 |
| **Host/Client 隔离** | Tree-sitter WASM 在 Client 端运行，结果通过 CustomEvent 传给 Host；健康评分在 Client 端计算 |
| **能力缝三角色** | 新增 IGraphAnalysisService（分析服务定义）；Host 端实现；Client 端消费 |
| **配置显式化** | 规则配置通过 VisualizerConfig 管理；Tree-sitter 语言列表通过配置指定 |
| **不可变数据** | GraphData/HealthScore/RuleViolation 均为不可变接口；状态更新通过 store setter |

## 十、结论

v0.2.0 的 5 项 P0 功能和 18 项 P1 功能**均可行**，其中：

- **5 项 P0**：全部可直接实现，无阻塞风险
- **18 项 P1**：15 项可直接实现，3 项有条件可行（Tree-sitter WASM 体积、Web Worker 布局迁移、虚拟滚动超大规模）
- **ISS-03 重构**：作为 Phase 1 优先执行，为后续功能开发扫清障碍

现有架构的扩展性良好：
- **策略模式**（聚类策略注册表）可复用于规则检测器、评分器、布局类型
- **适配器模式**（数据源适配器）可复用于 Tree-sitter、依赖图谱
- **Cordis 事件声明合并**机制可无缝扩展新事件类型
- **IRenderer 接口**已预留 `focusNeighborhood` 等扩展点

建议按 Phase 1→10 顺序开发，确保依赖关系满足，每个 Phase 完成后进行测试验证。
