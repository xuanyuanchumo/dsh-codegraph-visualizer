# DSH CodeGraph Visualizer

## Commands
- Build: `pnpm run build`
- Test: `pnpm run test`
- Lint: `pnpm run lint`
- Typecheck: `pnpm run typecheck`
- Coverage: `pnpm run test:coverage`
- E2E: `pnpm run test:e2e`

## Verifying your work
- Run build, test, and lint before reporting done.
- Paste output as evidence.

## Conventions
- ESM only: `"type": "module"` in package.json, `.ts` extensions in imports
- Host/Client isolation: tsconfig.host.json and tsconfig.client.json separate compilation
- Branded types: NodeId, EdgeId, RepoId prevent ID mixing across boundaries
- Plugin lifecycle: ctx.effect() for side effects, return disposer for cleanup
- State management: Zustand with persist middleware, graphStore as single source of truth
- Rendering: Cytoscape.js via IRenderer interface abstraction
- Logging: scoped() logger from shared/Logger.ts, not console directly
- i18n: All user-facing text via t() from i18n/index.ts
- CSS: cg- prefix for all class names, CSS variables for theming
- Testing: vitest for unit/component, Playwright for E2E

- A dev-server that injects initial data via `init(container, payload)` never calls `apply(ctx)`, so bootstrap/restore paths do not run there at all. Asserting "zero data requests on first paint" is both reachable AND stronger than the acceptance text's "exactly one bootstrap"; do not fabricate the unreachable assertion to match the document
- When a shared helper returns a wrong-shaped result, prove the fix introduced no new failures with a three-run comparison (clean HEAD / old helper / new helper): 11 failed-28 passed on both of the first two with an IDENTICAL failure list, 10-31 on the third. Only then can you claim "turned one case green and broke nothing"
- "A screenshot was saved" is not "visual regression": the 13 shots existed, every element assertion passed, and the file was named visual regression — while nothing compared a single pixel. Two runs of the SAME code differed on 12 of 13 images (19.38% average, up to 35.75%, max channel delta 217-241 i.e. structural displacement, not antialiasing). No behavioural test, no coverage number and no lint rule can see this class of defect; only a source-shape guard (no bare `page.screenshot` under `tests/e2e`) can
- Pixel comparison is only as good as the determinism behind it, and the failure mode of getting this wrong is worse than having no baseline: an unstable baseline goes randomly red, everyone learns to pass `--update-snapshots`, and the baseline degrades into "a record of whatever it looked like" while still LOOKING like a safety net
- A `randomize: true` layout cannot be fixed by waiting longer: after 3 seconds (far beyond the animation) node positions still differed by 34-526 px and even `zoom` differed. cytoscape/cose expose NO randomSeed option (`grep randomSeed node_modules/cytoscape/dist/cytoscape.cjs.js` = 0 hits), so overriding `Math.random` in the page is the only lever. Confirm the randomness comes from a DEPENDENCY first — `grep Math.random src/` = 0 hits was the step that made the override provably sufficient
- Freeze a clock only in its ARGUMENT-LESS form: `new Date()` / `Date.now()` / `Date()` must be pinned, but `new Date(ts)` must pass through via `Reflect.construct`. Freezing the argument-carrying form too would rewrite the real timestamps inside the test data — that is tampering with the input under test, not removing nondeterminism
- "Two consecutive samples agree" is the weakest possible stability predicate: one brief plateau satisfies it. Combine EVERY quantity that participates in framing (panel geometry + container rect + zoom + pan + all node coordinates) into one signature and require it unchanged for a window that STRADDLES a known event gap — 300 ms was needed because the two initial cose layouts land at 2594 ms and 3017 ms, so a 100 ms window falls between them
- "Wait for nodes to exist" and "wait for the picture to be stable" are different things: `waitForGraphReady` only waits for `cy.nodes().length > 0`, while the panel height goes 240px → 720px at ~2714 ms and two layouts run at startup. Treating the former as the latter is the direct cause of 12-of-13 instability
- A diff budget must be bracketed from BOTH ends — the noise floor AND the magnitude of real change. Only measuring the floor (residual 10-391 px after freezing the layout) produced 1500, which measurement then showed would ABSORB a real 726 px change. The floor is 34 px and real changes are 726 px / 770k px, so 500 (~14.7x the floor) is the value that separates them. A too-loose threshold is the likelier error because the instinct is to make the test go green
- "The baseline did not go red" has TWO explanations — an empty baseline or a lazy probe — and the second one looks exactly like the first. Probe A changed `--cg-accent` inside a `body[data-ds-dark-theme]` block that never matches on the dev-server shell (`html[data-theme=dark]`), and probe A' changed a `var(--dsw-accent, …)` fallback that the shell already defines. Prove the mutation actually took effect (read the live CSS variable back) BEFORE concluding anything about the baseline
- An "optimization" that cannot be observed should not be kept: the value-equality short-circuit in `setPlacement` read plausibly ("avoids per-frame re-render") but removing it changed nothing measurable — render counts were identical (`rendersBefore=2 / childRenders=6`), `MutationObserver` on the style attribute reported 0 (React writes the same style string back without a mutation), and N scrolls inside one `act()` all batch to a single render at exit. Deleted it; only the scroll listener + rAF coalescing are load-bearing (removing the listener turned 2 cases red)
- `position: fixed` plus viewport coordinates REQUIRES a scroll listener: `Dropdown` measured `trigger.getBoundingClientRect()` (viewport coords) and rendered with `position: fixed`, but only listened for `resize` — so a 100 px scroll moved the gap from 6 px to 106 px while the trigger walked away. The listener must use `capture: true` because a scrolling ancestor's `scroll` event does not bubble to `window`
- A source scanner must strip comments AND preserve newlines: the first version of `visualBaselineContract.test.ts` was tripped by its own header comment (which quotes `toHaveScreenshot(...)` in prose) and reported line 12 as a missing `installDeterminism`. This is the THIRD occurrence in this repo (`e2eSelectorContract.test.ts:25-28`, `a11yFormSemantics.test.ts:87-89`), so reuse that shape for any new scanner. Blank out block comments character-for-character instead of deleting them, or every reported line number shifts upward and points at the wrong place
- A CI job must never report "no baseline yet" as "comparison passed": the visual job branches on whether `tests/e2e/__screenshots__/visual-linux/` exists — present ⇒ strict compare (a real gate), absent ⇒ generate + upload as an artifact + `::warning::`. Either alternative is worse: a job that is red from day one gets ignored, and one that runs `--update-snapshots` is green forever. Once the Linux baselines are committed the job becomes a real gate with no config change
- Platform differences belong in the snapshot PATH, not in a threshold: `snapshotPathTemplate` carries `{platform}` because Windows and Linux font rendering/antialiasing differ, so one PNG set cannot serve both. Without it the locally generated baselines go wholesale red on `ubuntu-latest` and the job gets ignored
- "The validator is reachable" is NOT "the validator value is reachable": five on-demand routes could already answer 304, but `checkEtag` writes `etag` ONLY in the 304 branch and `sendJson` never wrote it at all, so the client never held a value to send back. Every existing check was green — the `resource: GraphEtagResource` parameter existed, all 6 resources had contract-guard assertions, `computeGraphEtag` was unit-tested, and the 304 path worked when tested directly. The whole mechanism was dead code and NO test observed the 200 response headers. Test the artifact, not only its shape
- A parameterised route's validator needs a REQUEST KEY dimension, not just a resource dimension: with one cached graph slot, scoping by (workspace, revision, resource) alone made `children(nodeA)` and `children(nodeB)` compute the SAME validator, so asking B with A's value returned 304 and B could never load. Same family as P0-R16-02 but one level deeper — the validator must bind to THAT REQUEST, not merely to that resource
- Every dimension in a request key must be COMPUTED, never written as a constant on each side: the client never sends `budget`, so both sides derive it via `resolveAstBudget`. Had each side hardcoded `SYMBOL_AST.MAX_NODES`, a future budget change would silently fork the two keys, validators would never match again, and NO test would go red
- Merge "compute the validator" and "return the validator" into ONE return value: writing them separately is precisely what produced the dead-code defect above. `etagGuard` returns `{handled, etag}` so doing only half is structurally impossible, with a source-scanning guard (`etagContract.test.ts`) asserting all 20 `sendJson(res, 200, …)` call sites pass `etagHeader`
- 304 and network failure MUST be distinguished: the four on-demand fetchers return `T | null` and `null` was already taken by "failed". Since `res.ok` is `false` for 304, reusing `if (!res.ok) return null` turns "the server says nothing changed" into "the client has no data" and silently blanks the panel. `EtagSink.notModified` is the only way to tell them apart
- Register a validator only AFTER its subject has been APPLIED: the first implementation called `rememberEtag` on every 200, including responses the caller then discarded on a generation/token check. The next request carried that validator, got 304, and the client — which never applied the payload — was left permanently blank with no error visible. `commitEtag` moves registration from "response received" to "payload applied"; this is the single correctness fulcrum of the whole mechanism
- A genuine 304 is STILL wrong when the client no longer holds the payload: 304 only promises the SERVER copy is unchanged. `setGraphData` / `setBootstrapData` / `clearGraph` / `applyGraphDelta` / `disposeStore` each replace `rawNodes` wholesale and reset derived containers via `emptyEdgeState()`, discarding merged outline/AST/children. All five must call `clearEtagCache()` — the payload lifetime and the validator lifetime must be aligned
- Cache invalidation direction may be deliberately asymmetric: the validator encodes (resource, workspace, revision, request key), so a stale value can only MISMATCH and yield 200 — never falsely match a newer revision. "Sending it once too often" is the safe direction, which is why the cache needs no workspace-switch invalidation list and cannot become a cross-workspace contamination channel. Same trade-off as `graphEtag` on the `/data` path
- Cross-origin visibility must go through the shared header builder: `sendJson` gained an `extraHeaders` parameter rather than letting call sites `writeHead` directly, because bypassing it drops `buildCorsHeaders` and desktop / dsh-remote-web-ui clients cannot read the etag — conditional requests silently stop working for cross-origin consumers while same-origin tests stay green
- A contract guard's regex must not recognise only one spelling: `crossWorkspaceGuardContract.test.ts` asserted `returnIfEtagMatch\([^)]*'${resource}'`, so migrating the call sites to `etagGuard` turned it red. That is NOT a defect — the guard was written too narrowly — but it must not be loosened to "the string appears somewhere" either. The correct shape accepts both spellings AND carries a two-way reverse self-check (a negative sample for `'children'` must not match the `'outline'` regex)
- Adding an export to a module turns every factory-style `vi.mock` of that module red: `createEtagSink` / `commitEtag` on `src/client/api/index.ts` broke three test files with `No "createEtagSink" export is defined` (49 failures). Fix by `vi.mock(path, async (importOriginal) => ({ ...await importOriginal(), fetchX: mock }))` — override only the function under test and let every other export stay real. The factory shape that replaces the whole module is the wrong default
- Signature growth that forces assertion updates is not test fragility: adding the 8th parameter `sink` to four fetchers required `expect.any(Object)` in 12 `toHaveBeenCalledWith` calls. That is evidence the assertions are bound to the real call shape; a test written loosely enough to survive the change unchanged would have been the genuinely fragile one
- A shared key function makes a defect OBSERVABLE — reuse is not just DRY: `etagKeyForOutline` is the same implementation on host and client, so dropping the node dimension degrades BOTH sides at once and produces a false 304. If each side had its own copy, one-sided drift could only cause "mismatch ⇒ extra 200" (the safe direction), the false 304 could never occur, and no test could ever catch it
- Negative contracts can only be asserted at the network layer: "must not carry A's validator", "must not be blanked", "must not register early" all look identical to "there was never any data" on screen. Recording requests process-side via `page.on('request')` is the only way; `page.route()` stubs the response and changes the behaviour under test
- A scope budget is bracketed from both ends exactly like a pixel budget: too narrow a request key ⇒ two different responses share one validator ⇒ false 304 ⇒ permanently blank; too wide ⇒ the validator never matches ⇒ every request returns 200 and you merely lose one transfer. When the two error costs are asymmetric, bias toward the cheap one and write the bias into the comments, or a later "optimisation" will remove it
- A per-shot budget without a CEILING is the same defect wearing a finer disguise: replacing one global `MAX_DIFF_PIXELS = 500` with a 13-entry table still leaves "just make the number bigger" as the minimum-resistance path the next time the baseline goes red. Pair the table with a hard `SCREENSHOT_BUDGET_CEILING` and throw on exceedance, so changing a budget becomes an explicit contract edit rather than a one-token tweak
- Do not turn a measured noise floor into a per-item threshold when the noise is NOT a property of the item: four full `visual` runs with `maxDiffPixels: 0` each showed the SAME 34 px maximum but on a DIFFERENT image every round (`e2e-10-impact`, then `e2e-07-call-chain`, then `e2e-07`+`e2e-08`) with all other images byte-identical. Writing one measured value per image freezes that round's random sample and guarantees the next round fails on a different image — the same value for every shot, justified by the shared distribution, is the correct reading
- State what a threshold CANNOT see, or it will be read as total coverage: cycle-90 measured a real CSS-variable regression at 25 px, which is BELOW the 34 px noise floor, so no pixel budget can ever catch it. Say so in the file and name the source-level guards (`tokensContract` / `styleSelectorContract`) that own that class instead of implying the pixel gate covers everything
- Extracting a helper can silently EMPTY the guards that surround it: replacing 13 `expect(page).toHaveScreenshot(...)` call sites with `expectSnapshot(page, name)` left exactly one `toHaveScreenshot` in the file — inside the helper — and the helper MUST be exempted from the position-based guards (it sits before every `test()`). Deleting a case's `installDeterminism(page)` then left all 13 cases green. Every exemption must come with (a) a span function that returns null when the helper is renamed or deleted, (b) the same guard re-applied at the NEW call sites, and (c) a non-empty-scan assertion
- "The probe did not go red" must be read as a statement about the GUARD first: the M4 mutation (removing `installDeterminism` from one visual case) reported 13 passed, and the temptation was to call the probe lazy. The probe was correct — the guard had been silently emptied by the refactor in the previous bullet. Order of suspicion: guard shape, then probe efficacy, then the code under test
- A tool that TRUNCATES its own write cannot be trusted to report success: a `write` of a ~46 KB markdown file reported `operation: "update"` and the subsequent `read` showed only 508 of 1899 lines, silently destroying the staged 1900-line `docs/测试体系.md`. Always check the resulting size/line count against the input before moving on; recovering needed `git checkout -- <file>` back to the INDEX (not HEAD) and re-applying the addition with `edit` anchored on an existing line
