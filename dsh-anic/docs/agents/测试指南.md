# dsh-anic 测试指南

> 本文件描述**实际配置的**测试分层，每层能看到什么、看不到什么，以及写守卫测试时必须遵守的三条纪律。
>
> 读取本文件的时机：新增测试、判断一个缺陷该由哪一层拦截、或新增守卫测试时。

## 1. 四层金字塔

编排入口是 `scripts/run-tests.mjs`（54 行）。它按 `STEPS` 顺序执行，**任一层失败即跳过后续层**（fail-fast，`run-tests.mjs:11` 注释），最后打印 `=== 测试汇总 ===` 表并以 `ALL GREEN` / 退出码 1 收尾。

| # | 层 | 命令 | 执行者 | 数量 |
| --- | --- | --- | --- | --- |
| 1 | DSH 规范符合性门 | `pnpm run lint` / `--only=validate` | `scripts/validate-dsh.mjs`（155 行，C1–C12） | 12 项检查 |
| 2 | 单元 + 契约守卫 | `pnpm run test:unit` / `--only=vitest` | `scripts/run-vitest.mjs`（35 行）→ vitest | 269 个 `it()` |
| 3 | 机制冒烟（stub 宿主） | `pnpm run test:smoke` / `--only=smoke` | `scripts/offline-smoke.mjs`（193 行） | 21 个 `check()` |
| 4 | 真实宿主 E2E | `pnpm run test:live`（`--live`）或 `pnpm run j0` | `scripts/j0-probe.mjs`（148 行） | J0-1…J0-6b，共 8 条 |

**默认 `pnpm run test` 只跑前三层** —— 第 4 层必须显式 `--live`（`run-tests.mjs:26` `if (live) STEPS.push(...)`）。

第 2 层内部还有两个子目录（`vitest.config.ts` 的 `include: ['tests/**/*.test.ts']` 一并收集）：

| 目录 | 文件数 | 用例数 | 性质 |
| --- | --- | --- | --- |
| `tests/unit/` | 21 | 245 | 纯函数与宿主路由行为 |
| `tests/contract/` | 2 | 24 | 源码形状 + 构建产物契约 |

**vitest 本体不在 `dsh-anic`**。`scripts/run-vitest.mjs` 从 `PLUGIN_ROOT` 向**上最多 6 层**查找 `node_modules/vitest/vitest.mjs`（在 `link:` 安装下即父工程），找不到则打印「请先在父工程（仓库根）`pnpm install`」并 **exit 2**。这是 TD-A1 过渡态的可见后果。

配置 `vitest.config.ts`：`environment: 'node'`、`testTimeout: 30000`、`pool: 'forks'`（注释：宿主路由测试会改 `process.cwd`，必须每文件独立 worker 隔离）。

## 2. 每层能看到什么 / 看不到什么

这是本指南最重要的部分 —— **选错层会让一个真实缺陷永远不被任何测试看见**。

### 第 1 层 `validate-dsh.mjs`（规范门）

- **能看**：`package.json` 清单（`type` / `manifestVersion` / `client.platform` / `client.inject` / `exports` / `icon`）、locale 文件的形状与键集对齐、`dist/client.js` 与 `dist/host.js` 的存在性 + `node --check` 语法 + 加载契约、`dsh.bundle.patch` 文件存在、`README.md` 存在。
- **看不到**：任何 `src/` 的行为。它**不读源码**。
- **惰性**：C9 / C10 读 `dist/`，因此**对 `src/` 的修改无感，必须先 `pnpm run build`**。

### 第 2 层 vitest

`tests/unit/`：

- **能看**：纯函数输入/输出（`snapshotCore` / `stepTrace` / `flows` / `tokens` / 各 runtime 模块）、宿主路由 handler 的响应码与体（`snapshotRoute.test.ts` 241 行、`runtime.test.ts` 331 行是最大的两个）、工具注册与 presentCall 契约、渲染函数的元素树形状（`orgStatusRender.test.ts`、`graphA11y.test.ts`）。
- **看不到**：真实 DSH 宿主的行为；真实浏览器渲染；`dist/` 的内容；父工程的任何东西。

`tests/contract/`：

- **能看**：**源码的文本形状**（regex 扫描）与 `dist/` 的加载契约。这是唯一能拦截「行为正确但形状错误」的层。
- **看不到**：语义。守卫只能断言「某个形状在场/不在场」，无法断言「这段代码是对的」。

### 第 3 层 `offline-smoke.mjs`（stub 宿主）

- **能看**：`dist/client.js` 在**桩宿主**下的完整装配 —— 它复现 DSH 的 `window.__ModuleLoader__.load({ id, factory })` 契约，用 `new Function('window','require', bundle)(sandboxWindow, resolver)` 执行（bundle 是经典脚本，不是 ESM），`require` 只解析 `react` 到一个记录 `{ type, props, children }` 的桩 `createElement`。
- **看不到**：真实宿主、真实 DOM、真实网络。桩 `useState` 只返回初始值、`useEffect` 是 no-op，**因此桩永远不会触发 fetch** —— 任何依赖数据加载后的行为在这里都观察不到。
- **惰性**：读 `dist/client.js` 与 `artifacts/workflow-snapshot.json`，**对 `src/` 变更惰性，必须先 build**。

### 第 4 层 `j0-probe.mjs`（真实宿主）

- **能看**：真实浏览器 + 真实宿主。经 CDP 连 `http://127.0.0.1:9222`，用 `@playwright/test`（经 `createRequire(join(REPO_ROOT,'package.json'))` 加载，失败则 exit 2），挑选匹配 `/127\.0\.0\.1:3080|localhost:3080/` 的页面。
- **看不到**：单元级细节。它只断言端到端可见的事实。
- **前置条件**：必须先 `pnpm run test:dsh:start`（`scripts/start-dsh-test.mjs`，676 行）。**探针自身绝不启动或停止宿主**（`j0-probe.mjs` 头部注释），这是刻意的：探针在验证别人的宿主，不应改变它的生命周期。

**八条判据**（`j0-probe.mjs:6-11`）：J0-1 标签可见、J0-1b 与既有标签共存、J0-2 图渲染（`circles >= 100 && lines >= 100 && nodes > 0`）、J0-3 遥测通道 `registered === true`、J0-4 来源如实标注（`/live|嵌入快照|snapshot/i`）、J0-5 热卸载/恢复（`unregister()` → `registered=false` → `reregister()` → `registerCount >= 2`）、J0-6 kill-switch（`localStorage['anic-workflow-tab']='off'` + reload → `skipped === 'flag-off'`）、J0-6b 开关恢复（`--keep-switch` 时跳过）。

每条判据各自包 try —— 一条崩溃不吞掉整份报告。

## 3. 三层各自的「诚实边界」

**一个缺陷落在哪一层，决定了它能否被发现**。以下三类是已知的盲区：

| 盲区 | 哪一层都看不见的原因 | 实际防线 |
| --- | --- | --- |
| 渲染成字符串而非元素树 | React 转义字符串子节点，DOM 断言里「元素没渲染」与「渲染成一段文本」长得一样 | 源码形状守卫 `clientRenderContract.test.ts:115-124` |
| 裸 `var(--anic-*)` | 变量未注入时颜色回退到 `initial`，元素仍在、测试仍绿 | 源码形状守卫 `clientRenderContract.test.ts:140-151` |
| 死样式规则 / 错误的选择器 | 元素照常渲染，只是颜色/边框/z-index 不对，无断言失败 | 需要样式读回或源码守卫（本工程目前无 CSS 文件，见 [开发规范-守卫与约束.md](开发规范-守卫与约束.md) §6） |

**共同点**：它们都**不改变行为**，只改变外观或语义。行为测试、覆盖率、lint 都看不见这一类。唯一能守的是**源码形状守卫**。

## 4. 守卫测试的三条纪律

来自 `tests/contract/dshConformance.test.ts:4-7` 与 `tests/contract/clientRenderContract.test.ts:15-18`（两处同形）：

### ① 反向自检（reverse self-check）

**每个负向断言，先证明它的正例样例能被匹配**。否则一个写坏的 regex 会永远绿 —— 它什么都不匹配，于是「没有违规」永远成立。

```ts
// clientRenderContract.test.ts:109-113
it('反向自检：字符串渲染器 regex 真的能匹配（否则守卫永远绿）', () => {
  expect(RENDER_STRING_RE.test(RENDER_STRING_SAMPLE)).toBe(true);
  expect(RENDER_STRING_RE.test(RENDER_ELEMENT_SAMPLE)).toBe(false);   // 且不误伤正确形态
});
```

```ts
// clientRenderContract.test.ts:135-138
it('反向自检：裸 var(--anic-*) regex 能匹配，且不误伤 token() 调用', () => {
  expect(BARE_VAR_RE.test(BARE_TOKEN_SAMPLE)).toBe(true);
  expect(BARE_VAR_RE.test(GOOD_TOKEN_SAMPLE)).toBe(false);
});
```

**注意第二行**：只证明「正例被匹配」是不够的，还必须证明**正确写法不被误伤** —— 否则守卫会逼人写出错误的代码来讨好它。

### ② 不匹配自身（never match own sample literals）

守卫扫描 `src/` 时，**样例字面量若以原文写在测试文件里，而测试文件又在扫描集内，守卫会匹配自己**。

本工程的解法是**拼接构造**（`clientRenderContract.test.ts:86-92`）：

```ts
const RENDER_STRING_SAMPLE = ['export function renderX(d: D): ', 'string', ' { return ""; }'].join('');
const RENDER_ELEMENT_SAMPLE = ['export function renderX(d: D): ', 'ReactElement', ' { return null; }'].join('');
const BARE_TOKEN_SAMPLE = ['style: { color: ', '`var(--anic-pass)`', ' }'].join('');
const GOOD_TOKEN_SAMPLE = ['style: { color: ', 'token(', "'anic-pass'", ')', ' }'].join('');
```

拼接后，测试文件里**不存在连续的** `export function renderX(...): string` 或 `` `var(--anic-pass)` `` 形状，因此扫描不到自己。`dshConformance.test.ts:42` 同法：`const CONSOLE_SAMPLE = ['console', '.', 'log("x");'].join('');`。

**另一种解法**是把样例放在扫描目录之外 —— 但拼接更简单且不依赖目录布局。

### ③ 扫描集非空（assert the scan set is non-empty）

**静默的空扫描等同永久绿**。若 `walkTs()` 因为路径写错而返回空数组，所有「没有违规」的断言都会通过。

```ts
// clientRenderContract.test.ts:95-98
it('扫描集非空（静默空扫描 = 永久绿）', () => {
  expect(SRC_FILES.length).toBeGreaterThanOrEqual(20);
  expect(CLIENT_FILES.length).toBeGreaterThanOrEqual(5);
});
```

`dshConformance.test.ts:118-121` 同形，断言 `SRC_FILES.length > 3` 与 `CLIENT_FILES.length > 0`。

**反空转（anti-vacuity）是第 ③ 条的加强形态** —— 当守卫豁免某个文件时，必须证明那个文件里**真的有**被豁免的东西：

```ts
// dshConformance.test.ts:204-208
const sinkText = readFileSync(SANCTIONED[0] ?? '', 'utf8');
const consoleHits = sinkText.match(/console\.(log|warn|error|info|debug)\(/g) ?? [];
expect(consoleHits.length, 'logger.ts 的 consoleSink 必须真的调用 console').toBeGreaterThanOrEqual(3);
```

否则「豁免 logger.ts」会退化成「如果 logger.ts 被清空，守卫仍然绿」。

### 补充：去注释必须保留行号

`clientRenderContract.test.ts:40-75` 的 `stripComments` **逐字符清空块注释、只清行注释内容，全程保留 `\n`**，因此报错行号与磁盘一致。注释（`:41-43`）：「行号必须与磁盘一致，否则报错行号指向别处」。

若直接删除注释，后面所有行号会上移，守卫报告的 `file:line` 全部指错位置。`clientRenderContract.test.ts:100-107` 有一条专门测试这一性质：

```ts
it('stripComments 保留行号（去掉注释后行数不变）', () => {
  const sample = ['a();', '/* c1', 'c2 */', 'b(); // tail'].join('\n');
  const stripped = stripComments(sample);
  expect(stripped.split('\n')).toHaveLength(4);
});
```

**这也是为什么守卫自身的中文注释必须小心**：一条引用 `toHaveScreenshot(...)` 或块注释终结符的散文注释，会被扫描器当成真实代码。

## 5. 变更探针纪律（mutation probe）

**一条新的回归测试在你能证明它会红之前，是不可信的。**

流程：

1. 写测试，确认它在**修复存在**时是绿的。
2. `git stash` **只暂存修复**（保留测试），或在工作区手动还原修复。
3. 重跑测试，确认它**变红**，且红的原因正是你预期的断言。
4. 恢复修复，确认重新变绿。

**为什么必须做**：一条写坏的断言（选择器写错、扫描集为空、条件恒真）在修复存在时同样是绿的，因此「新测试是绿的」**不能**证明它守住了任何东西。只有「移除修复后它变红」才是证据。

**本工程已付代价的实例**（均记录在源码注释里）：

- `dshConformance.test.ts:186-191`：原断言「`src/` 全域零 `console.*`」在 logger 落地前为真；logger 引入后它变成恒假，需要改成「console 只准在 `logger.ts`」并加上反空转断言（`:208`）。
- `dshConformance.test.ts` 注释记录的聚合器泄漏：聚合器一度写成 `cleanups[0]?.()`，只清理第一条路由。**「被调用过」的断言对此恒绿** —— 必须断言 `toHaveBeenCalledTimes(routes.length)`。
- `truthAuditChecks.ts:101-102` 注释：T4 首版只扫 `tools.ts` 单文件，工具拆分后**漏报 7 个**。改成扫整个工具域 glob `/^tools.*\.ts$/`。

**探针本身的常见失效**（做 probe 时先怀疑这两点，再怀疑被测代码）：

- **探针没有真正生效**：改了 `dist/` 相关的东西却没 rebuild，smoke 读的是旧产物。同理，改了 `src/` 但 vitest 命中缓存。
- **守卫已被重构清空**：把 13 个 `expect(page).toHaveScreenshot(...)` 抽成 `expectSnapshot(page, name)` 后，位置型守卫可能因为找不到旧形状而静默失效 —— 此时「探针不红」是关于**守卫**的事实，不是关于被测代码的。

**顺序**：先查守卫形状，再查探针是否生效，最后才怀疑被测代码。

## 6. 常用命令

```bash
pnpm run test              # 第 1–3 层（validate + vitest + smoke）
pnpm run test:unit         # 只跑 vitest（--only=vitest）
pnpm run test:smoke        # 只跑 smoke（--only=smoke）
pnpm run test:live         # 第 1–4 层（追加 j0-probe，需宿主已启动）
pnpm run j0                # 只跑 j0-probe
pnpm run lint              # = validate-dsh.mjs（第 1 层）
pnpm run typecheck         # tsconfig.client + tsconfig.host（向上查父工程 tsc）
pnpm run build             # client bundle + host bundle（tsdown）
pnpm run snapshot          # 重新生成 src/client/workflowGraphData.ts
pnpm run test:dsh:start    # 启动真实宿主测试环境（j0 的前置）
pnpm run test:dsh:stop     # 停止
pnpm run test:dsh:status   # 查看状态
```

**两个必须记住的因果**：

1. **改了 `src/` 想看 smoke 或 lint 的效果 → 先 `pnpm run build`**，否则它们读的是旧 `dist/`。
2. **`pnpm run typecheck` 依赖父工程 `node_modules/typescript`**（TD-A1 过渡态，`CLAUDE.md` 已记录）—— 独立安装 `dsh-anic` 的依赖**不会**让 typecheck 可用。
