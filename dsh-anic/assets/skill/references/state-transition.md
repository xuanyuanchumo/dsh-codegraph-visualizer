# 状态流转机制

> 完整的状态机定义：阶段流转、门禁流转、质量评审流转、自主级别流转、熔断流转。
> 读取本文件的时机：需要理解状态如何流转、什么条件下推进或回退时。

## 状态机总览

```
┌──────────────────────────────────────────────────────────────────────┐
│                        AI-Native Iteration Cycle                     │
│                         完整状态流转机制                               │
└──────────────────────────────────────────────────────────────────────┘

  ┌──── 宏观阶段流转 ────┐    ┌──── 门禁流转 ────┐    ┌──── 质量评审流转 ────┐
  │                      │    │                  │    │                      │
  │  Plan → Design →     │    │  G0 → G1 →       │    │  Q1-Q8 评审          │

  │  Deploy → Maintain   │    │                  │    │  → 验收判定          │
```

## 1. 宏观阶段流转

### 阶段定义

| 阶段 | ID | 入口条件 | 出口条件 | 产物 |
|---|---|---|---|---|
| Plan | `plan` | 用户想法/控制带突破 | intent.md 接受 | intent.md |
| Design | `design` | intent.md 接受 | spec.md 批准 | spec.md |
| Build | `build` | spec.md 批准 | PR 合并 | plan.md + cycle-{N}/ + 代码 + PR |
| Test | `test` | PR 创建 | G2 通过 | eval 结果 + 回归 evals |
| Deploy | `deploy` | PR 合并 | release 授权 | 授权发布 + 交付清单 |
| Maintain | `maintain` | release 授权 | 控制带突破→新 intent | 诊断 → 新 intent.md |

### 流转规则

1. **顺序推进**：每个阶段只能推进到下一阶段，不能跳过
2. **门禁依赖**：推进需通过当前阶段的门禁（人类门 + 收敛门）
3. **闭环**：Maintain 阶段通过控制带突破回到 Plan，形成闭环
4. **不可回退**：阶段不可回退，但可通过新 intent.md 重新进入 Plan

### 状态持久化

状态保存在 `.cycles/workflow-state.json`：

```json
{
  "currentPhase": "build",
  "currentCycle": "cycle-1",
  "phaseHistory": [
    { "phase": "plan", "exitedAt": "2026-09-14T10:00:00Z" },
    { "phase": "design", "exitedAt": "2026-09-14T11:00:00Z" }
  ],
  "createdAt": "2026-09-14T09:00:00Z",
  "updatedAt": "2026-09-14T12:00:00Z"
}
```

### 阶段推进命令

```bash
# 查看当前状态
node scripts/workflow-state.mjs <project-dir> status

# 推进到下一阶段（需门禁通过）
node scripts/workflow-state.mjs <project-dir> advance

# 检查是否可以推进
node scripts/workflow-state.mjs <project-dir> check
```

## 2. 门禁流转

### 收敛门 G0-G3

| 门禁 | 阶段 | 判定内容 | 通过条件 | 失败后果 |
|---|---|---|---|---|
| G0 | Plan/Design | 评估基线就绪 | 评估报告已产出 + 事实基座抽验通过 | 禁止进入拆测/验证 |
| G1 | Build | 任务清单清零 | P0-P3 全部完成 + 无未分配测试 | 禁止进入下一循环 |
| G2 | Test | 测试报告零错误 | 失败=0 + RTM无缺口 + 旅程全过 | 禁止进入 Release |
| G3 | Deploy | 构建零失败 | Debug+Release 构建通过 + 冒烟全过 | 禁止提交/交付 |

### 人类门 H1-H5

| 人类门 | 阶段 | 决策者 | 判定依据 | 记录方式 |
|---|---|---|---|---|
| H1 intent接受 | Plan→Design | 产品负责人 | intent.md 六要素齐全 | git 合并/关闭 |
| H2 spec批准 | Design→Build | 产品负责人+技术负责人 | spec 解决 intent 问题 | git 合并/关闭 |
| H3 plan批准 | Build内部 | 工程师/技术负责人 | plan.md 可独立实现 | 计划接受提交 |
| H4 PR合并 | Build→Deploy | 代码所有者 | 评审通过+测试通过+plan同步 | PR 合并 |
| H5 release授权 | Deploy→Maintain | 发布经理 | 门禁全绿+性能未退+审计完整 | 哈希链审批账本 |

### 门禁执行顺序

```
G0 → G1 → G2 → G3
↑                    ↑
│                    │
人类门并行判定，任一失败即停止
```

### 门禁记录

所有门禁结果记录在哈希链账本 `.cycles/gates/ledger.json`：

```bash
# 记录门禁结果
node scripts/gate-ledger.mjs <project-dir> --gate G0 --result PASS --detail "..."

# 验证账本完整性
node scripts/gate-ledger.mjs <project-dir> --verify

# 列出所有记录
node scripts/gate-ledger.mjs <project-dir> --list
```

## 3. 质量评审流转

### 评审维度 Q1-Q8

| 维度 | 名称 | 评审时机 | 通过条件 |
|---|---|---|---|
| Q1 | 功能与业务 | Plan/Build/Test | 覆盖率≥90% + RTM无缺口 |
| Q2 | 测试体系 | Build/Test | 覆盖率≥门限 + 分层完整 |
| Q3 | 性能与运维 | Test/Deploy/Maintain | 无退化>5% + 可观测完整 |
| Q4 | 安全与合规 | Deploy/Maintain | 无高危漏洞 + 合规满足 |
| Q5 | 架构约束 | Design/Build | 无跨层违规 + 无循环依赖 |
| Q6 | 前端与体验 | Design/Build/Test | a11y AA合规 + 响应式完整 |
| Q7 | 代码与工程 | Build | lint零警告 + 复杂度在预算内 |
| Q8 | 评审与验收 | 全阶段 | 证据完整 + 验收达标 |

### 评审流转规则

```
评审触发 → 评审执行 → 评审报告 → 验收判定
                                    │
                          ┌─────────┴─────────┐
                          │                   │
                       PASS → 推进          FAIL → 修复→重评
```

1. **评审触发**：每个阶段结束时自动触发该阶段的重点评审维度
2. **评审执行**：运行 `eval-runner.mjs` 执行评审
3. **评审报告**：生成质量评审报告写入 `.cycles/cycles/cycle-{N}/quality-review.md`
4. **验收判定**：所有启用的评审维度 PASS 才可推进；WARN 需人工确认；FAIL 必须修复

### 评审与门禁的关系

- G0 门禁包含 Q1（功能与业务）和 Q5（架构约束）的评审结果
- G2 门禁包含 Q2（测试体系）的评审结果
- G3 门禁包含 Q3（性能与运维）和 Q4（安全与合规）的评审结果
- 人类门 H4（PR合并）包含 Q7（代码与工程）和 Q8（评审与验收）的结果

## 4. 自主级别流转

### 级别定义

| 级别 | 名称 | 特征 | 人类介入频率 |
|---|---|---|---|
| L1 | 辅助执行 | AI 按人类指令执行单步 | 每步 |
| L2 | 协作模式 | AI 自主执行，人类审批关键决策 | 每产物 |
| L3 | 监督自主 | AI 自主决策执行，仅检查点确认 | 仅检查点 |
| L4 | 全自动模式 | AI 全流程自主，检查点自动审计 | 仅事后审计 |

### 级别切换条件

| 切换方向 | 条件 |
|---|---|
| L1→L2 | 连续 3 个产物人类无修改接受 |
| L2→L3 | 连续 3 个循环门禁全绿 + 评估趋势上升 |
| L3→L4 | 连续 5 个循环门禁全绿 + 评估趋势上升 + 无熔断 |
| L4→L3 | 熔断条件触发 |
| L3→L2 | 连续 2 次门禁失败 |
| L2→L1 | 连续 3 次门禁失败或人类主动要求 |

### 级别持久化

自主级别记录在 `cycles/config.yml` 的 `autonomy_level` 字段，切换时更新配置。

## 5. 熔断流转

### 熔断条件（先修复后降级——任一触发后先诊断根因并尝试自动修复，只有修复失败才回退）

| # | 条件 | 先修复后降级行为 | 修复失败后回退 |
|---|---|---|---|
| 1 | 同一异常连续 3 次自动修复失败 | 先进行失败模式分析（重复性/级联性/瞬态），尝试更深层次修复 | L4→L3 |
| 2 | 门禁自动判定存疑且无法自动定论 | 先重新运行门禁检查获取更详细证据 | L4→L3 |
| 3 | 涉及真实用户数据/明文凭据且无隔离 | 先尝试添加 .gitignore 保护或创建隔离方案 | L4→L3 |
| 4 | 破坏性操作影响范围不可评估/不可回滚 | 先尝试初始化 git 基线或拆分变更批次 | L4→L3 |
| 5 | 性能指标超预警且 1 轮优化未恢复 | 先尝试优化热点文件或调整配置 | L3→L2 |
| 6 | 人类主动要求审计/切换 | 无需自动修复，人类已主动介入 | 到指定级别 |
| 7 | 无人值守超时/资源上限 | 先尝试启动新会话释放资源 | L4→L3 |
| 8 | 累计重试 >10 次或熔断 >3 次 | 先尝试清理旧事故记录重置计数 | L4→L3 |

### 熔断恢复条件

| 级别 | 恢复条件 |
|---|---|
| L1→L2 | 人类确认问题已修复 + 重新授权 L2 |
| L2→L3 | 连续 3 个循环门禁全绿 |
| L3→L4 | 连续 5 个循环门禁全绿 + 无熔断 |

### 熔断记录

熔断事件记录在 `.cycles/incidents/` 目录，包含触发条件、影响范围、恢复方案。

## 6. 微观迭代流转

### 七步微观迭代

```
评估 → 规划 → 拆测 → 验证 → 修复 → 门禁 → 复盘
  │      │      │      │      │      │      │
  E1-E8  子规划  分层    测试    根因   G0-G3  量化
  Q1-Q8  plan   用例    报告    诊断   判定   指标
```

### 微观迭代状态

每个微观迭代步骤有独立状态：

| 步骤 | 状态 | 产物 |
|---|---|---|
| 评估 | pending/done | 评估报告 |
| 规划 | pending/done | plan.md / 子规划 |
| 拆测 | pending/done | 功能→测试映射 |
| 验证 | pending/done | 测试报告 |
| 修复 | pending/done | 缺陷登记+修复 |
| 门禁 | pending/pass/fail | 门禁判定 |
| 复盘 | pending/done | 复盘报告 |

### 微观迭代流转规则

1. **顺序执行**：评估→规划→拆测→验证→修复→门禁→复盘
2. **修复循环**：验证失败→修复→重新验证，直到通过
3. **门禁阻断**：门禁失败必须修复后重新执行
4. **复盘闭环**：复盘产出量化指标，指导下一循环的评估

## 7. 控制带流转（Maintain 阶段）

### 控制带层级

| 层级 | 响应 | 对应熔断条件 |
|---|---|---|
| 1σ | 仅记录 | 无 |
| 2σ | Agent 只读诊断 | 性能超预警且1轮未恢复（熔断条件5） |
| 3σ | Agent 通过门控路径行动 | 破坏性操作不可评估（熔断条件4） |

### Western Electric 规则触发

| 规则 | 含义 | 响应 |
|---|---|---|
| Rule 1 | 单点超 3σ | 立即诊断 |
| Rule 2 | 2/3点在同侧2σ外 | 趋势预警 |
| Rule 3 | 4/5点在同侧1σ外 | 漂移检测 |
| Rule 4 | 8点在同侧 | 系统性偏移 |
| Rule 5 | 6点持续递增/递减 | 趋势确认 |
| Rule 6 | 14点交替 | 不稳定信号 |
| Rule 7 | 15点在1σ内 | 变异过小（可能掩盖问题） |
| Rule 8 | 8点在1σ外 | 变异过大 |

### 控制带流转

```
指标采集 → 控制带检测 → 规则判定
                          │
              ┌───────────┼───────────┐
              │           │           │
           1σ 记录    2σ 诊断    3σ 行动
              │           │           │
              │           │      开 PR → 门禁评审
              │           │      或触发 runbook
              │           │
              └───────────┴───────────┘
                          │
                    诊断 → 新 intent.md → 回到 Plan
```
