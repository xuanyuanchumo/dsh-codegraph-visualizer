> 读取本文件的时机：需要执行质量评审、配置评审维度、或理解评审判定标准时。

## 七大评审维度

### Q1 — 功能与业务

**关键问题**：功能是否完整实现业务需求？功能域覆盖率是否达标？

**评审范围**：
- 功能域清单覆盖率（已实现/部分/未实现）
- 业务规则正确性（边界条件、状态转换、数据流）
- 需求追溯矩阵（RTM）完整性
- 用户旅程正反向覆盖

**评审流程**：
1. 从 `.cycles/config.yml` 的 `journeys` 或功能清单获取功能域列表
2. 对照已实现代码标记每个功能域状态
3. 检查 RTM 映射：每个需求→测试用例→代码实现
4. 运行用户旅程正反向场景验证

**判定标准**：
- PASS：覆盖率 ≥ 90%、RTM 无缺口、旅程 100% 通过
- WARN：覆盖率 70%-90% 或 RTM 有 1-3 个缺口
- FAIL：覆盖率 < 70% 或 RTM 有 3+ 个缺口或旅程有失败

**评分方法**：1分（<50%）→ 5分（100%覆盖+RTM完整+旅程全过）

---

### Q2 — 测试体系

**关键问题**：分层测试是否完整？覆盖率是否达标？混沌用例是否覆盖？

**评审范围**：
- 分层测试完整性（单元/集成/E2E/契约）
- 覆盖率门限（行/分支/函数）
- RTM 缺口（需求→测试映射）
- 混沌用例覆盖（韧性测试）
- 测试报告六要素（通过/失败/断言/日志/复现/手工）

**评审流程**：
1. 运行测试套件，收集通过/失败/跳过
2. 检查覆盖率报告对照门限
3. 检查 RTM 映射完整性
4. 检查分层测试各层是否有测试
5. 检查混沌用例覆盖情况

**判定标准**：
- PASS：覆盖率 ≥ 门限、RTM 无缺口、分层完整、混沌覆盖
- WARN：覆盖率低于门限 10% 或 RTM 1-3 个缺口
- FAIL：覆盖率低于门限 10%+ 或分层缺失或混沌未覆盖

---

### Q3 — 性能与运维

**关键问题**：性能是否满足非功能性需求？运维是否可观测可恢复？

**评审范围**：
- 性能基线对比（帧率/内存/延迟/吞吐量）
- 性能退化检测（对比上一循环基线）
- 可观测性（日志/指标/追踪/告警）
- 可恢复性（回滚方案/数据备份/故障恢复）
- 资源效率（CPU/内存/磁盘/网络使用率）

**评审流程**：
1. 获取或建立性能基线
2. 运行性能测试收集关键指标
3. 对比基线计算退化百分比
4. 检查控制带阈值（默认 5%）
5. 检查可观测性配置（日志级别、指标暴露、告警规则）
6. 检查回滚方案和故障恢复流程

**判定标准**：
- PASS：无指标退化 >5%、可观测性完整、回滚方案存在
- WARN：1-2 个指标退化 5%-15% 或可观测性部分缺失
- FAIL：任何指标退化 >15% 或关键指标退化 >5% 或无回滚方案

---

### Q4 — 安全与合规

**关键问题**：是否引入安全漏洞？是否满足合规要求？

**评审范围**：
- 安全漏洞扫描（XSS/CSRF/SQL注入/路径穿越）
- 凭据管理（硬编码检测、.env 保护、密钥轮换）
- 依赖审计（已知漏洞、版本锁定）
- 权限最小化（权限面分析、越权检测）
- 合规检查（数据保护、审计日志、访问控制）
- 隐私保护（数据脱敏、用户数据隔离）

**评审流程**：
1. 运行安全扫描检查常见漏洞
2. 搜索硬编码凭据和敏感信息
3. 运行依赖审计（npm audit 或等效）
4. 检查 .env 文件是否在 .gitignore
5. 检查权限模型和访问控制
6. 检查合规要求（GDPR/等保/行业规范）

**判定标准**：
- PASS：无安全漏洞、依赖无高危、凭据管理规范、合规满足
- WARN：1-2 个低危漏洞或合规部分缺失
- FAIL：任何高危漏洞或硬编码凭据或 XSS 漏洞或合规不满足

---

### Q5 — 架构与设计约束

**关键问题**：架构是否满足设计约束？分层边界是否清晰？

**评审范围**：
- 分层架构合规（层间依赖方向、跨层调用检测）
- 适配器模式隔离（外部服务/数据源通过适配器接入）
- 循环依赖检测
- 接口契约一致性（API 契约、数据契约、事件契约）
- 设计模式合规（项目约定的设计模式是否遵循）
- 可扩展性评估（扩展点是否预留、耦合度是否可控）

**评审流程**：
1. 识别项目分层结构
2. 检查跨层调用（搜索 import/require 标记违规）
3. 检查适配器模式使用
4. 分析依赖图检测循环依赖
5. 检查接口契约一致性
6. 评估可扩展性

**判定标准**：
- PASS：无跨层违规、无循环依赖、适配器完整、契约一致
- WARN：1-3 个跨层违规或 1 个循环依赖
- FAIL：3+ 个跨层违规或 2+ 个循环依赖或契约不一致

---

### Q6 — 前端与体验（UX/UI）

**关键问题**：前端体验是否达标？UX/UI 标准是否遵循？

**评审范围**：
- 可访问性（ARIA 属性、键盘导航、对比度、屏幕阅读器）
- 响应式设计（多设备适配、断点处理）
- 交互体验（加载状态、错误提示、反馈及时性）
- 视觉一致性（设计系统遵循、组件复用、样式规范）
- 国际化（i18n 支持、文案完整性、RTL 支持）
- 性能体验（首屏加载、交互延迟、动画流畅度）

**评审流程**：
1. 检查 ARIA 属性和语义化 HTML
2. 验证键盘导航完整性
3. 检查对比度（WCAG AA 标准）
4. 检查响应式断点和多设备适配
5. 检查加载状态和错误提示
6. 检查设计系统遵循度
7. 检查 i18n 覆盖率
8. 测量首屏加载和交互延迟

**判定标准**：
- PASS：a11y AA 合规、响应式完整、交互反馈完善、i18n 完整
- WARN：a11y 有少量缺失或响应式部分缺失或 i18n 有缺口
- FAIL：a11y 严重缺失或无响应式或无错误提示或 i18n 缺失关键文案

---

### Q7 — 代码与工程规范

**关键问题**：代码是否遵循工程规范？工程化是否完善？

**评审范围**：
- 代码规范（命名、格式、注释、复杂度）
- Lint 清洁度（零警告、零错误）
- 代码复用（DRY 原则、组件/模块复用率）
- 错误处理（异常捕获、错误传播、降级策略）
- 日志规范（日志级别、结构化日志、敏感信息脱敏）
- 版本控制（提交规范、分支策略、合并策略）
- 构建配置（构建优化、环境隔离、产物管理）
- 依赖管理（版本锁定、依赖审计、最小依赖）

**评审流程**：
1. 运行 lint 检查
2. 检查代码复杂度（对照预算）
3. 检查命名和格式规范
4. 检查错误处理模式
5. 检查日志规范
6. 检查版本控制实践
7. 检查构建配置
8. 检查依赖管理

**判定标准**：
- PASS：lint 零警告、复杂度在预算内、错误处理完善、日志规范
- WARN：lint 有 1-5 个警告或复杂度接近上限
- FAIL：lint 有错误或复杂度超预算或错误处理缺失

---

### Q8 — 评审与验收

**关键问题**：评审流程是否完整？验收标准是否满足？

**评审范围**：
- 评审证据完整性（每条发现引用文件/行号+证据）
- 评审严重度分级（bug/安全/合规 vs nit）
- 验收标准达成度（门禁全绿、性能未退、审计完整）
- 交付清单完整性（8项必备）
- 技术债务登记（新债务登记、旧债务收敛）
- 复盘质量（根因聚类、改进措施、量化指标）

**评审流程**：
1. 检查评审发现是否有证据支撑
2. 检查严重度分级是否合理
3. 检查验收标准达成度
4. 检查交付清单 8 项完整性
5. 检查技术债务台账更新
6. 检查复盘报告质量

**判定标准**：
- PASS：证据完整、分级合理、验收达标、交付清单完整
- WARN：1-2 项缺失或证据不充分
- FAIL：验收未达标或交付清单缺失关键项

---

## 配置方式

在 `.cycles/config.yml` 中配置评审维度：

```yaml
quality_review:
  Q1:
    name: "功能与业务"
    enabled: true
    threshold:
      pass: 90    # 覆盖率%
      warn: 70
    checklist_ref: "docs/feature-checklist.md"
  Q2:
    name: "测试体系"
    enabled: true
    coverage_threshold: 80
  Q3:
    name: "性能与运维"
    enabled: true
    degradation_limit: 5   # 退化百分比上限
    baseline_source: "previous_cycle"
  Q4:
    name: "安全与合规"
    enabled: true
    compliance_standard: "GDPR"  # 或 "等保2.0" 等
  Q5:
    name: "架构约束"
    enabled: true
    layer_rules: "docs/architecture-rules.md"
  Q6:
    name: "前端与体验"
    enabled: true
    a11y_standard: "WCAG_2.2_AA"
  Q7:
    name: "代码与工程"
    enabled: true
    complexity_budget: 100
  Q8:
    name: "评审与验收"
    enabled: true
    delivery_checklist: true
```
