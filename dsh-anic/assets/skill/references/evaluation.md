# 评估维度、连续 Evals 与 KPI

> 融合 Cycles E1-E8 评估维度 + AI-Native SDLC 连续 Evals。
> 读取本文件的时机：需要执行评估、配置评估维度、或理解评估判定标准时。

## E1-E8 评估维度详解

> **词表对齐声明（v1.7.0，修 S-2 双词汇漂移）**：维度 id→名称的唯一来源是
> `scripts/lib/dimensions.mjs` 注册表——**E1 意图对齐 / E2 规格符合 / E3 测试覆盖 /
> E4 代码质量 / E5 性能基线 / E6 安全检查 / E7 文档同步 / E8 回归完整性**。
> 评估报告（`eval-runner` 写入）与配置文件必须且只能使用注册表名称。
> 下文各维度的"评估流程/判定标准/评分方法"是项目级深度方法论指引，
> 其中部分小节的措辞沿用了历史版本的项目级词汇，执行时以注册表维度语义为准；
> 与注册表名称冲突的旧称（如"功能覆盖/架构健康/技术债务"）**已废弃，不得出现在报告或配置中**。

每个维度包含：评估流程、判定标准、评估工具、评分方法（1-5分制）、输出格式。

### E1 — 功能覆盖

**关键问题**：对照功能域清单还缺什么？已实现功能是否达验收标准？

**评估流程**：
1. 从 `.cycles/config.yml` 的 `journeys` 或功能清单中获取功能域列表
2. 对照已实现代码（src/ 目录下的模块/组件），标记每个功能域的状态：已实现/部分实现/未实现
3. 对已实现功能域，检查是否有对应的测试用例（RTM映射）
4. 计算功能覆盖率 = 已实现功能域数 / 总功能域数

**判定标准**：
- PASS：覆盖率 ≥ 90% 且无未实现的核心功能域（P0级）
- WARN：覆盖率 70%-90% 或有1-2个P0级未实现
- FAIL：覆盖率 < 70% 或有3+个P0级未实现

**评估工具**：`grep`/`glob` 搜索功能关键词；测试报告检查RTM映射

**评分方法**：1分（<50%）→ 5分（100%覆盖+RTM完整）

**输出格式**：
```
E1 功能覆盖: [PASS|WARN|FAIL] (覆盖率: X%)
  已实现: N/M 功能域
  未实现P0: [列表]
  RTM缺口: N项
```

### E2 — 架构健康

**关键问题**：分层边界是否清晰？依赖方向是否合理？适配器模式隔离是否充分？

**评估流程**：
1. 识别项目的分层结构（从 `.cycles/config.yml` 的 `layers` 配置）
2. 检查跨层调用：搜索 import/require 语句，标记违反分层方向的依赖
3. 检查适配器模式：数据源/外部服务是否通过适配器接入
4. 检查循环依赖：分析依赖图是否存在环

**判定标准**：
- PASS：无跨层违规调用、无循环依赖、适配器隔离完整
- WARN：1-3个跨层违规 或 1个循环依赖
- FAIL：3+个跨层违规 或 2+个循环依赖 或 无适配器隔离

**评估工具**：`grep` 搜索 import 语句；项目依赖分析工具

**评分方法**：1分（严重架构问题）→ 5分（完美分层+无循环依赖）

### E3 — 技术债务

**关键问题**：未收敛循环遗留项、TODO/FIXME 密度、依赖版本锁定

**评估流程**：
1. 扫描代码中的 TODO/FIXME/HACK/XXX 标记，计算密度 = 标记数 / 千行代码
2. 检查 `.cycles/tech-debt/` 目录中的技术债务台账
3. 检查 `package.json`/`go.mod` 等依赖文件中是否有未锁定版本
4. 检查上一个循环的遗留项是否已收敛

**判定标准**：
- PASS：TODO密度 < 2/千行、依赖版本锁定、无未收敛遗留项
- WARN：TODO密度 2-5/千行 或 1-2个未锁定依赖
- FAIL：TODO密度 > 5/千行 或 3+个未锁定依赖 或 有未收敛遗留项

**评估工具**：`grep -r "TODO\|FIXME\|HACK\|XXX"`；依赖文件检查

### E4 — 测试成熟度

**关键问题**：分层测试缺口、RTM 未映射功能、覆盖率是否达门限

**评估流程**：
1. 运行测试套件，收集通过/失败/跳过数量
2. 检查覆盖率报告（行/分支/函数），对照 `.cycles/config.yml` 的 `coverage_threshold`
3. 检查 RTM（需求追溯矩阵）：每个功能需求是否有对应测试用例
4. 检查分层测试完整性：单元/集成/E2E 各层是否有测试

**判定标准**：
- PASS：覆盖率 ≥ 门限、RTM无缺口、分层测试完整
- WARN：覆盖率低于门限10%以内 或 RTM有1-3个缺口
- FAIL：覆盖率低于门限10%以上 或 RTM有3+个缺口 或 分层测试缺失

**评估工具**：`npm test`/`make test`；覆盖率报告；RTM检查脚本

### E5 — 性能与稳定

**关键问题**：渲染帧率/内存占用/数据更新时延对比基线

**评估流程**：
1. 建立或获取性能基线（上一循环的性能数据或项目初始基线）
2. 运行性能测试，收集关键指标（帧率、内存、延迟、吞吐量）
3. 对比基线，计算退化百分比
4. 检查是否有性能退化超过控制带阈值（默认5%）

**判定标准**：
- PASS：无指标退化超过5%
- WARN：1-2个指标退化5%-15%
- FAIL：任何指标退化超过15% 或 关键指标（帧率/响应时间）退化超过5%

**评估工具**：性能测试框架；Chrome DevTools；监控指标

### E6 — 安全与可访问

**关键问题**：XSS 转义/路径校验/权限面、a11y、依赖审计

**评估流程**：
1. 安全扫描：检查 XSS 漏洞（未转义的 HTML 输出）、路径校验（`..` 路径注入）、硬编码凭据
2. 检查 `.env` 文件是否在 `.gitignore` 中
3. 依赖审计：运行 `npm audit` 或等效命令检查已知漏洞
4. 可访问性检查：检查 ARIA 属性、键盘导航、对比度

**判定标准**：
- PASS：无安全漏洞、依赖无高危漏洞、a11y基本合规
- WARN：1-2个低危漏洞 或 a11y有少量缺失
- FAIL：任何高危漏洞 或 硬编码凭据 或 XSS漏洞

**评估工具**：`npm audit`；`grep` 搜索硬编码凭据；a11y检查工具

### E7 — 创新差异化

**关键问题**：是否有独特差异化价值？长期愿景评分趋势？

**评估流程**：
1. 对照项目的愿景声明（intent.md 中的 Proposed outcome），评估当前实现是否体现了差异化价值
2. 检查 `.cycles/config.yml` 的 `vision_benchmarking` 中定义的对标维度
3. 与对标工具/项目对比，识别独特功能和差距
4. 评估差异化评分趋势（与上一循环对比）

**判定标准**：
- PASS：有明确的差异化功能且趋势上升
- WARN：差异化不明显但无退化
- FAIL：差异化退化 或 无任何独特价值

**评估工具**：多源对照矩阵；愿景评分趋势

### E8 — 多源对照增强

**关键问题**：对照主流工具机制是否对齐并可增强？

**评估流程**：
1. 从 `.cycles/config.yml` 的 `vision_benchmarking` 获取对标工具列表
2. 对照每个对标工具的核心机制，标记：已对齐/部分对齐/未对齐/超越
3. 识别可借鉴的机制和可增强的方向
4. 生成对照矩阵

**判定标准**：
- PASS：核心机制已对齐且有超越项
- WARN：核心机制部分对齐
- FAIL：核心机制未对齐

**评估工具**：对照矩阵模板；开源项目分析

## 评估维度配置

每个维度在 `.cycles/config.yml` 中可配置：

```yaml
evaluation:
  E1:
    name: "功能覆盖"
    checklist_ref: "docs/feature-checklist.md"  # 项目特定的功能域清单
    evidence_source: "测试报告 + RTM映射"
    threshold:
      pass: 90    # 覆盖率%
      warn: 70
  E2:
    name: "架构健康"
    checklist_ref: "docs/architecture-rules.md"
    evidence_source: "依赖分析"
  # ... E3-E8 同理
```

## 连续 Evals

Evals 是 AI-Native 等价于阶段门 QA。在 Agent 配置变更时运行的套件——新模型、重写提示词、编辑 CLAUDE.md/Skills/Hooks。

### Eval 套件构建

1. 从最近工作中收集 20-50 个真实任务及其预期或接受结果
2. 每个任务写为 eval：提示词 + 定义可接受的检查
3. 在 CI 中非交互运行套件——按计划和任何配置变更时运行
4. 对结果门控配置变更：降低通过率的变更在合并前评审
5. 每个生产事故获得一个 eval，作为回归测试留在套件中

### Eval 格式

```json
{
  "id": "eval-001",
  "prompt": "实现一个用户注册功能",
  "expected_output": "注册端点+测试通过+符合安全规范",
  "checks": [
    { "type": "test", "command": "make test", "expect": "all pass" },
    { "type": "lint", "command": "make lint", "expect": "zero warnings" },
    { "type": "security", "expect": "no hardcoded secrets" }
  ]
}
```

### eval-runner.mjs 接口

```
输入: node scripts/eval-runner.mjs <project-dir> [--dimensions E1,E2,...] [--cycle N]
输出: 评估报告写入 .cycles/cycles/cycle-{N}/项目评估报告.md（v1.8.2 修正：旧文档写的 .cycles/cycle-{N}/eval-results.md 路径与文件名都错了；部分维度运行时与既有报告按维度行合并，未运行维度继承原结果）
退出码: 0=全部通过, 1=有维度未通过
参数:
  --dimensions: 指定运行的维度（逗号分隔），默认 all
  --cycle: 指定循环编号，默认最新循环
```

## KPI（关键绩效指标）

| 指标 | 目标 | 测量方法 | 采集点 | 自动化方案 |
|---|---|---|---|---|
| 测试通过率 | 100% | 测试报告 | 每循环测试报告 | CI自动采集 |
| 缺陷逃逸率 | ≤5% | 生产发现缺陷/总缺陷 | Release后 | 手动记录+issue跟踪 |
| 全量回归耗时 | ≤30分钟 | 回归计时 | 每循环回归记录 | CI计时 |
| RTM缺口 | 0 | RTM映射检查 | 每循环RTM | 脚本自动检查 |
| 旅程通过率 | 100% | J1-JN正反向 | 每循环旅程验证 | E2E自动运行 |
| 首次实现通过率 | 趋势上升 | 首次CI成功/总变更 | CI系统 | CI自动采集 |
| 评审时间 | 趋势下降 | 首次评审到合并耗时 | PR元数据 | git/PR平台API |
| 需求周期 | 周→小时 | 意图到提交耗时 | git时间戳 | git log自动计算 |

## 成熟度模型

| 级别 | 特征 | 对应自主级别 |
|---|---|---|
| 1 | 基础组件、手动测试、无自动化 | L1 |
| 2 | 组件化、单元测试、初步自动化 | L2 |
| 3 | 状态管理、E2E测试、CI自动化 | L2-L3 |
| 4 | 性能优化、a11y、分层验证完整 | L3 |
| 5 | 自动化发布、监控闭环、全自主 | L4 |

## 混沌用例定义

混沌用例是故意引入异常条件（如网络延迟、服务不可用、资源耗尽）来验证系统韧性的测试。与普通测试用例的区别：

| 特性 | 普通测试用例 | 混沌用例 |
|---|---|---|
| 目标 | 验证功能正确性 | 验证系统韧性 |
| 条件 | 正常环境 | 异常环境（延迟/故障/资源限制） |
| 期望 | 精确输出匹配 | 系统不崩溃、优雅降级、可恢复 |
| 频率 | 每次循环 | 定期（如每Release） |

混沌用例在 `.cycles/config.yml` 的 `evaluation.chaos` 中配置。

## 多源对照矩阵（可选）

对照主流开源工具机制，识别可借鉴机制。度量对象为项目最终形态，非每循环必测。

配置方式：在 `.cycles/config.yml` 的 `vision_benchmarking` 中定义对标维度和标杆工具。
