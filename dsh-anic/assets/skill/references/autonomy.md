# 自主性分级、熔断与 Agent Org

> 融合 Cycles L1-L4 自主分级 + AI-Native SDLC Agent Org。
> 读取本文件的时机：需要确定自主级别、理解熔断条件、或配置 Agent 组织时。

## 自主性分级

| 级别 | 名称 | 特征 | 人类介入频率 |
|---|---|---|---|
| L1 | 辅助执行 | AI 按人类逐条指令执行单步操作 | 每步 |
| L2 | 半自动 | AI 自主执行常规步骤，产物须人类审核 | 每产物 |
| L3 | 监督自主 | AI 自主决策并执行全流程，仅检查点请求人类确认 | 仅检查点 |
| L4 | 全自主 | AI 全流程自主（含 Release 自动交付与版本管理），检查点自动审计化 | 无（仅事后审计） |

### 自主性边界 — 量化切换标准

**L1→L2 切换条件**（全部满足）：
- Agent 连续产出 5 个产物无需返工（人类审核直接通过）
- CLAUDE.md/AGENTS.md 已配置项目约定（构建/测试/lint命令）
- 至少 1 个构建时 Hook 已部署（如 test-protection.sh）
- init-workflow.mjs 已成功初始化工作流骨架

**L2→L3 切换条件**（全部满足）：
- CLAUDE.md 已调优（<1页，包含常见错误记录）
- 至少 3 个 Skills 已编码组织标准（安全/API设计/UX等）
- Hooks 阻止不安全操作（production-gate.sh 已部署）
- 测试套件可运行且覆盖率 ≥ 配置门限
- 连续 3 个循环 G0-G3 全部通过
- 连续 10 个产物人类审核无需返工

**L3→L4 切换条件**（全部满足）：
- H1-H4 检查点可自动评估（脚本化判定，无需人类主观判断）
- 熔断条件可靠触发（连续 3 次熔断均正确触发，无误报）
- 连续 5 个 Release 无生产事故
- 控制带监控已部署且稳定运行 ≥30 天
- 审批账本完整（所有门禁结果有记录）
- 回滚机制已验证（至少 1 次成功回滚演练）

### 初始级别评估

新项目默认 L2。评估初始级别的方法：

| 条件 | 满足时推荐级别 |
|---|---|
| 无 CLAUDE.md、无 Skills、无 Hooks | L1 |
| 有 CLAUDE.md + init-workflow 已运行 | L2 |
| 有 3+ Skills + Hooks + 测试套件 + 3循环全通过 | L3 |
| 有自动审计 + 5 Release无事故 + 控制带稳定 | L4 |

在 `config.yml` 中设置：`autonomy_level: L2`（或评估后的级别）

### 熔断条件（先修复后降级——任一触发后先诊断根因并尝试自动修复，只有修复失败才回退 L3）

1. 同一异常连续 3 次自动修复失败
2. 门禁自动判定存疑且无法自动定论（H4）
3. 涉及真实用户数据/明文凭据且无隔离方案（H1）
4. 破坏性操作影响范围不可评估或不可回滚（H2）
5. 性能指标超预警阈值且 1 轮优化后仍未恢复
6. 人类主动要求审计/切换到 L3
7. 无人值守超时/资源上限（单会话 >24h 或上下文水位 >85%）
8. 自动化资源上限（累计重试 >10 次或熔断 >3 次）

**上下文水位测量**：通过 token 计数估算。当对话历史 + 工具输出 + 文件内容 的总 token 数超过模型上下文窗口的 85% 时触发。

### 失败恢复

熔断后恢复路径：
1. 熔断触发 → 自动回退 L3 → 记录熔断事件到审计日志
2. L3 模式下人类介入诊断 → 确定恢复条件
3. 恢复条件满足 → 恢复 L4（或保持 L3 如条件不满足）
4. 熔断/恢复记录写入审计日志

**恢复条件定义**：
- 熔断条件1（修复失败）：根因已定位且修复已验证 → 可恢复
- 熔断条件2（门禁存疑）：门禁判定逻辑已修正 → 可恢复
- 熔断条件3（数据/凭据）：隔离方案已部署 → 可恢复
- 熔断条件4（破坏性操作）：影响范围已评估且回滚方案已验证 → 可恢复
- 熔断条件5（性能）：性能已恢复到预警阈值以内 → 可恢复
- 熔断条件6（人类要求）：人类明确指示恢复 → 可恢复
- 熔断条件7（超时/资源）：新会话已启动且资源已释放 → 可恢复
- 熔断条件8（自动化上限）：重试计数已重置 → 可恢复

## Agent Org — 自主代理组织

Agent Org 是 AI-Native SDLC 循环之上的操作层。它回答循环本身留下的三个问题：Agent 是*谁*、*如何*报告和互相评审、需求*从哪里*进入系统。

### 组织模型

默认角色（由 `scripts/init-workflow.mjs --org` 脚手架，可在 `org/org-chart.yaml` 中编辑）：

```
CEO（人类，所有者）
 └── CTO（Agent）—— 路由工作、派遣评审、解决冲突
      ├── 产品经理（Agent）—— 每个意图的首审
      ├── 产品工程 Agent（Agent）—— 准入→工单→意图
      └── 工程师（Agent）—— 计划和构建
           └── 评审者（Agent）—— 空闲时同行评审
```

### 角色卡片

**编排者 (Orchestrator / CTO)**
- 职责：分解任务、分配给子 Agent、汇总结果、解决冲突
- 权限：可派遣其他角色、可合并评审结论、不可直接修改代码
- 产出：任务分配记录、评审汇总、冲突裁决
- 限制：不评审自己的派遣结果

**构建者 (Builder / Engineer)**
- 职责：编写代码、创建测试、修复缺陷、更新文档
- 权限：可修改代码和测试、可创建子规划、不可直接合并 PR
- 产出：代码提交、测试报告、子规划文档
- 限制：必须遵循 plan.md，偏离时须同步更新计划

**审查者 (Reviewer)**
- 职责：审查代码、验证规格符合度、安全审计、证据收集
- 权限：可批准/驳回评审、可要求修改、不可直接修改代码
- 产出：评审报告（REVIEW.md）、发现清单（按严重度排序）
- 限制：不评审自己的工作；每轮最多 5 条 nit

**评估者 (Evaluator)**
- 职责：运行 E1-E8 评估维度、生成评估报告、趋势分析
- 权限：可运行测试和扫描工具、可标记评估失败、不可修改代码
- 产出：项目评估报告、评估趋势数据
- 限制：评估必须基于证据，不可主观判断

**门禁守卫 (Gatekeeper)**
- 职责：执行 G0-G3 门禁检查、记录结果、阻止未通过流转
- 权限：可阻止流转、可记录门禁结果、不可修改门禁标准
- 产出：门禁判定记录、门禁账本
- 限制：门禁标准由人类配置，守卫只执行不修改

### 报告协议

1. 每个 Agent 提交其产物（intent.md, spec.md, plan.md, 代码+测试, 评审发现）并附证据
2. 状态变更与产物在同一提交中——提交链即审计轨迹
3. 报告向上流动一级：工程师→CTO；PM/产品→CTO；CTO→CEO
4. CEO 在门禁处和升级时阅读状态和产物提交

### 同行评审

- 写作者从不评审自己的工作
- 产物完成时，写作者请求 CTO 评审；CTO 从 status.yaml 分配 idle 评审者
- 评审者写 `org/reviews/<artifact>-<id>.md`——严重度排序的发现+证据+裁决（approved/changes）
- 两轮未解决升级到 CTO，然后 CEO 处理 spec/plan 冲突
- 评审标准与基础工作流相同：REVIEW.md 通过项、证据要求、5-nit 上限

### 人类介入

| 门禁 | 谁决定 |
|---|---|
| Intent | 产品经理首审；CEO 处理歧义 |
| Spec/Plan | 同行评审；两轮未解决后 CEO |
| PR 合并 | 人类（CEO） |
| Release | 人类（CEO）—— production-gate.sh + 审批账本 |

### 准入渠道

需求通过三个渠道到达，落地为 `org/intake/` 中的版本化 markdown 记录：
- `github/` — `scripts/sync_issues.py pull` 拉取开放 issue
- `forms/` — 表单提交
- `email/` — 邮件消息

产品工程 Agent 整合记录，提交公开功能工单，从模板起草 intent.md。PM 在进入 Design 前评审每个意图。

### 升级规则

- 意图歧义 → PM → CEO
- Spec/plan 分歧 → 写作者↔评审者（最多2轮）→ CTO → CEO
- 任何会在无人类批准下越过门禁的事 → 停止并报告

### 框架兼容

Agent Org 框架无关。Claude Code 项目将角色卡片映射到 `.claude/agents/*.md`；Codex 项目通过 Codex subagent 配置运行。产物、协议和脚本相同。

## 自主性 × 采用路径映射

自主级别不是选择而是采用深度的自然结果：

| 自主级别 | 采用层 | 典型场景 |
|---|---|---|
| L1 辅助 | 第1层（意图捕获 + CLAUDE.md） | 团队刚开始用 AI，每步都需人类指导 |
| L2 半自动 | 第2-3层（Skills + Evals + 设计会话） | Agent 能自主执行常规步骤，但产物须人类审核 |
| L3 监督自主 | 第4层（CI/CD + 门禁） | 护栏成熟，Agent 自主决策，仅检查点请求确认 |
| L4 全自主 | 第5层（闭环 + Agent Org） | 检查点自动审计化，Agent 全流程自主，仅事后审计 |
