# 多 Agent 门禁评估机制

> L4 全自主模式下，不同 AI agent 从不同角度多次评估人工门禁，提高门禁信任程度。
> 读取本文件的时机：自主级别为 L4 或需要理解多 Agent 门禁评估机制时。

## 核心理念

在 L4 全自主模式下，人类门禁由多个不同角色的 AI agent 从不同维度进行独立评估。每个 agent 从其专业角度出发，独立判定门禁是否应该通过。多个 agent 的评估结果综合后，根据预设阈值做出最终推荐。

**核心原则**：多 Agent 评估的目标是提高门禁信任程度——通过多个独立视角的交叉验证，减少单一视角的盲区和偏差。不同 Agent 的评估维度互不重叠，确保覆盖面。

**信任梯度**：
- 全部通过（3/3）：高信任度，`--auto-approve` 时自动执行
- 多数通过（2/3）：中信任度，推荐执行但记录到审计日志
- 少数通过（<2/3）：低信任度，不推进，需人工审查
- 平均信任度≥70% 且 `--auto-approve`：自动根据推荐执行
- 平均信任度<70%：需人工审查，不自动执行

**多 Agent 评估研究后默认根据推荐**：
- `--auto-approve` 启用时：3 个 Agent 独立评估 → 综合判定 → 信任度≥70% → 自动根据推荐执行
- `--auto-approve` 未启用：3 个 Agent 独立评估 → 综合判定 → 输出推荐 → 等待人类确认
- PR 门和 Release 门要求 3/3 全部通过（因为涉及代码集成和生产部署，风险更高）

## 5 个人工门 × 3 个评估 Agent

| 人工门 | 评估 Agent 1 | 评估 Agent 2 | 评估 Agent 3 | 通过阈值 |
|---|---|---|---|---|
| intent 接受→Design | 产品经理(业务价值) | 架构师(技术可行性) | 评估者(需求完整性) | 2/3 |
| spec 批准→Build | 架构师(设计合理性) | 安全审查(安全合规) | 评估者(规格完整性) | 2/3 |
| plan 批准→代码 | 工程师(实现可行性) | 评估者(测试覆盖) | 审查者(代码规范) | 2/3 |
| PR 合并→Deploy | 审查者(代码质量) | 安全审查(安全扫描) | 门禁守卫(G0-G3) | 3/3 |
| release 授权→生产 | 门禁守卫(全门禁) | 安全审查(合规) | 评估者(性能基线) | 3/3 |

## 各门禁评估维度详解

### intent 接受门 → Design

| Agent | 维度 | 评估内容 |
|---|---|---|
| 产品经理 | 业务价值评估 | intent.md 是否清晰描述了问题、提议结果、受影响用户、约束、范围外 |
| 架构师 | 技术可行性评估 | intent.md 提出的问题在当前技术栈下是否可解决，是否有明显技术障碍 |
| 评估者 | 需求完整性评估 | intent.md 是否包含必要要素：问题陈述、期望结果、约束条件、范围外说明、开放问题 |

**判定逻辑**：2/3 通过 → 推荐接受意图，进入 Design 阶段

### spec 批准门 → Build

| Agent | 维度 | 评估内容 |
|---|---|---|
| 架构师 | 设计合理性评估 | spec.md 的设计是否合理，是否遵循项目架构规范，是否有架构风险 |
| 安全审查 | 安全合规评估 | spec.md 是否涉及安全敏感操作，是否有安全风险，是否符合安全规范 |
| 评估者 | 规格完整性评估 | spec.md 是否解决了 intent.md 中的所有问题，开放问题是否回答或延续 |

**判定逻辑**：2/3 通过 → 推荐批准规格，进入 Build 阶段

### plan 批准门 → 代码实现

| Agent | 维度 | 评估内容 |
|---|---|---|
| 工程师 | 实现可行性评估 | plan.md 是否命名了变更文件、工作顺序、风险、证明测试；从未见过此对话的工程师能否仅从计划实现变更 |
| 评估者 | 测试覆盖评估 | plan.md 是否为每个变更项定义了测试策略，测试用例是否覆盖关键路径 |
| 审查者 | 代码规范评估 | plan.md 是否遵循项目编码规范，是否有明确的代码组织结构 |

**判定逻辑**：2/3 通过 → 推荐批准计划，进入代码实现

### PR 合并门 → Deploy

| Agent | 维度 | 评估内容 |
|---|---|---|
| 审查者 | 代码质量评估 | 代码评审通过项（bug/安全/合规）是否全过，是否有证据支持每条发现 |
| 安全审查 | 安全扫描评估 | 是否涉及安全敏感操作（H1），是否有凭据泄漏风险 |
| 门禁守卫 | G0-G3门禁评估 | G0-G3 是否全部通过，门禁账本是否完整 |

**判定逻辑**：3/3 全部通过 → 推荐合并 PR，进入 Deploy 阶段（PR 门要求全部通过，因为涉及代码集成）

### release 授权门 → 生产部署

| Agent | 维度 | 评估内容 |
|---|---|---|
| 门禁守卫 | 全门禁评估 | 门禁全绿（G0-G3），审计日志完整，哈希链账本验证通过 |
| 安全审查 | 合规评估 | 非功能验证通过，安全扫描无高危项，合规检查通过 |
| 评估者 | 性能基线评估 | 性能未退 >5%，控制带监控稳定，回归测试全通过 |

**判定逻辑**：3/3 全部通过 → 推荐授权发布（发布门要求全部通过，因为涉及生产部署）

## 评估 Agent 角色定义

### 产品经理 Agent
- **关注维度**：业务价值、用户影响、需求清晰度
- **评估依据**：intent.md 中的问题描述、受影响用户、期望结果
- **判定标准**：业务问题描述清晰，用户影响范围明确
- **评估深度**：
  - 问题陈述是否清晰（谁受影响、什么无法做到）
  - 期望结果是否可度量（成功标准、验收条件）
  - 约束条件是否合理（技术约束、时间约束、资源约束）
  - 范围外说明是否明确（避免范围蔓延）

### 架构师 Agent
- **关注维度**：技术可行性、架构合理性、设计风险
- **评估依据**：技术栈约束、架构规范、设计文档
- **判定标准**：设计在当前技术栈下可行，无重大架构风险
- **评估深度**：
  - 技术方案是否与现有架构兼容
  - 是否引入不必要的复杂性
  - 接口变更是否影响现有契约
  - 数据流是否合理（无循环依赖、无数据丢失风险）
  - 是否遵循分层架构规范

### 工程师 Agent
- **关注维度**：实现可行性、工作顺序、变更文件
- **评估依据**：plan.md 中的文件列表、步骤描述、风险标注
- **判定标准**：计划包含足够的实现细节，工程师可据此独立实现
- **评估深度**：
  - 变更文件列表是否完整（无遗漏）
  - 工作顺序是否合理（依赖在前）
  - 风险标注是否充分（哪些步骤最危险）
  - 测试5策略是否覆盖关键路径
  - 从未见过此对话的工程师能否仅从计划实现变更

### 审查者 Agent
- **关注维度**：代码质量、规范遵循、证据完整性
- **评估依据**：REVIEW.md 评审标准、代码规范、评审发现
- **判定标准**：评审通过项全过，每条发现有证据支持
- **评估深度**：
  - 评审发现是否按严重度排序（bug/安全/合规 vs nit）
  - 每条发现是否有文件/行号+具体证据
  - nit 是否在 5 条上限内
  - 评审通过项（bug/安全/合规）是否全过

### 安全审查 Agent
- **关注维度**：安全合规、凭据管理、漏洞扫描
- **评估依据**：安全扫描结果、凭据检查、合规要求
- **判定标准**：无安全敏感操作或已有隔离方案，无凭据泄漏风险
- **评估深度**：
  - 是否涉及真实用户数据/明文凭据（H1 检查）
  - 是否有 .env 文件未在 .gitignore 中
  - 是否有硬编码凭据
  - 依赖审计是否有高危漏洞
  - 合规检查是否通过（GDPR/等保等）

### 评估者 Agent
- **关注维度**：需求完整性、测试覆盖、性能基线
- **评估依据**：E1-E8 评估维度、Q1-Q8 质量评审、性能基线数据
- **判定标准**：需求要素完整，测试覆盖关键路径，性能未退化
- **评估深度**：
  - 需求要素完整性（问题/结果/受影响/约束/范围外/开放问题）
  - 测试覆盖关键路径（RTM 无缺口）
  - 性能基线对比（退化不超过 5%）
  - 评估维度 E1-E8 是否全部通过

### 门禁守卫 Agent
- **关注维度**：G0-G3 门禁、账本完整性、审计轨迹
- **评估依据**：gate-ledger.json、门禁检查结果、审计日志
- **判定标准**：G0-G3 全部通过，哈希链账本验证通过
- **评估深度**：
  - G0 评估基线是否就绪（评估报告已产出 + 事实基座抽验通过）
  - G1 任务清单是否清零（P0-P3 全部完成）
  - G2 测试报告是否零错误（失败=0、错误=0）
  - G3 构建是否零失败（Debug+Release 通过）
  - 门禁账本哈希链是否完整（无篡改）

## 与 HITL 审计的关系

HITL 审计（H1-H4）是面向**操作风险**的自动检查，关注"这个操作是否危险"。
多 Agent 门禁评估是面向**决策质量**的自动评估，关注"这个决策是否正确"。

两者互补：
- HITL 审计检测操作风险 → 先尝试自动修复 → 修复失败才熔断回退
- 多 Agent 门禁评估检测决策质量 → 推荐或驳回 → 信任度≥70% 且 `--auto-approve` 时自动执行

在 L4 全自主模式下，两者同时运行：
1. 多 Agent 门禁评估 → 判定是否推荐通过人工门
2. HITL 审计 → 检测是否有操作风险需要熔断
3. 两者都通过 → 自动推进
4. 多 Agent 评估未通过 → 不推进，记录到审计日志
5. HITL 熔断 → 先尝试修复 → 修复失败才回退 L3，请求人工介入

**执行顺序**：先运行 HITL 审计（检测操作风险），再运行多 Agent 门禁评估（检测决策质量）。HITL 熔断优先级高于多 Agent 评估——如果 HITL 熔断，即使多 Agent 评估通过也不推进。

## 脚本接口

```bash
node scripts/multi-agent-gate.mjs <project-dir> [--gate intent|spec|plan|pr|release|all] [--auto-approve]
```
