# Playbook — 六阶段 × 微观迭代操作手册

> 本文档是 Skill 的核心参考，详细描述宏观六阶段中每个阶段的微观迭代操作。
> 读取本文件的时机：进入某个阶段需要了解完整操作步骤时。

## 治理原则

1. **产物即证据** — 所有产物提交 git，提交链即审计轨迹：谁要求了什么、Agent 产出了什么、谁批准了什么
2. **双层护栏** — Skills/CLAUDE.md 为建议层（使合规行为大概率发生）；Hooks&Hooks 为确定层（使违规几乎不可能）。必须始终持有的策略须有 Hook 支撑
3. **人类持判断位** — Agent 生成/执行/机械验证；高风险操作和最终批准保留给人类。Agent 走到生产门——但不越过
4. **不丢弃现有工具** — Jira/Figma/GitHub/Slack 保留。为每个产物指定一个系统为真相源（仓库 markdown 或遗留系统），双向保持交叉引用

## 传统 vs AI-Native 转变

| 阶段 | 传统 | AI-Native |
|---|---|---|
| Plan | 委员会收集需求，研讨会蒸馏，手工编写 | Agent 从源头直接综合为 intent.md——人类可读且机器可执行 |
| Design | 分析师写规格，设计师解析 | 需求与设计压缩为一个会话，标准编码为 Skills，版本化在 git |
| Build | 手写测试和代码，文档事后写 | AI 生成测试和代码；制度知识维护为版本化 CLAUDE.md 和 Skills |
| Test | 阶段边界的 QA 门 | 连续 Evals 贯穿实现过程 |
| Deploy | 人类逐行评审；治理在评审周期中 | 分层代理评审；人类评审保留给受监管和关键代码；治理以 Hook 为审批门 |
| Maintain | 人类监控生产寻找 bug | Agent 监控部署；任何突破的控制带被诊断并写回为新 intent.md |

## Phase 1 — Plan：捕获意图为 intent.md

### 宏观流程

想法不再等待某人编写。意图被捕获一次，以提出者自己的语言，作为版本化产物——下一个阶段可以直接行动。

**执行步骤**：
1. 提出者用自己的语言描述问题——什么无法做到、谁受影响、更好的样子、什么在范围外。不需要正式语言
2. 头脑风暴直到想法具体化：Agent 提出分析师会问的问题（范围、用户、约束、成功标准）
3. 将结果写为 `intent.md`，使用组织模板（可编码为 Skill）。包含：问题、提议结果、受影响用户和系统、约束、范围外、开放问题
4. 提出者修正 Agent 误解的任何内容
5. 提交 `intent.md` 到共享位置。作者和时间戳加入记录

### 微观迭代（嵌入）

| 步骤 | 内容 | 产物 |
|---|---|---|
| 评估 | E1 意图对齐——对照意图六要素识别偏差 | 偏差清单 |
| 规划 | 生成意图捕获访谈大纲 | 访谈问题列表 |
| 拆测 | 将意图分解为可验证的需求项 | 需求项分解 |
| 验证 | 意图完整性检查（问题/结果/受影响/约束/范围外/开放问题六要素齐全） | 完整性报告 |
| 修复 | 与提出者迭代修正 | 修正后的 intent.md |
| 门禁 | G0 评估基线——intent.md 已产出且覆盖范围 | G0 判定 |
| 复盘 | 意图存活率、从对话到提交的耗时 | 度量记录 |

### 产物：intent.md

```markdown
# Intent: [标题]
Author: [姓名/角色]. Status: draft.

## Problem
[什么无法做到今天，谁受影响]

## Proposed outcome
[更好的样子]

## Affected users and systems
[受影响的用户和系统]

## Constraints
[约束条件]

## Out of scope
[明确排除的部分]

## Open questions
[待解决的问题]
```

### 人类门：产品负责人接受 → 触发 Design

### 度量
- **领先指标**：从首次对话到提交 intent.md 的时间（预期：周→小时）
- **滞后指标**：存活率——产品负责人接受进入 Design 的 intent.md 占比；intent.md 在首个 spec.md 提交后的变更次数

## Phase 2 — Design：需求与设计在一个会话中

### 宏观流程

需求与设计压缩为一个与 Agent 的工作会话，由编码为 Skills 的标准引导，版本化在 git 中。

**执行步骤**：
1. 产品负责人打开一个会话，组织 Skills 可用，附上 intent.md
2. 提示词："阅读附上的 intent.md 并为将其集成到现有代码库产出需求和设计规格。应用可用的 Skills 使计划符合我们的品牌指南、安全策略和 UX 标准。将规格完整记录为 spec.md，准备好交给工程团队。清晰描述任何关切区域，特别是无法满足矛盾策略的地方。"
3. 先手工运行；然后编码为组织级 slash command；然后让 intent.md 的接受成为触发器——非交互作业在合并时触发
4. 产品负责人对照意图评审规格：是否解决了所述问题？开放问题是否回答或延续？
5. 与策略负责人解决标记的关切点
6. 提交 spec.md 与 intent.md 并列。文件对记录了要求什么和决定了什么
7. 人类决定规格和意图是否进入 Build

### 微观迭代（嵌入）

| 步骤 | 内容 | 产物 |
|---|---|---|
| 评估 | E2 规格符合——规格条款与实现逐条对照 | 符合性结论 |
| 规划 | 加载组织标准 Skills，规划设计会话 | 设计会话计划 |
| 拆测 | 将规格分解为功能模块 × 分层 | 功能×分层矩阵 |
| 验证 | 规格完整性检查——是否解决意图中的问题？关切点是否标记？ | 完整性报告 |
| 修复 | 与策略负责人解决标记的关切点 | 关切解决记录 |
| 门禁 | G0——spec.md 已产出且覆盖范围 | G0 判定 |
| 复盘 | 需求返工率、意图到规格的耗时 | 度量记录 |

### 产物：spec.md

包含：需求规格、设计决策、关切标记、受影响模块、接口变更、安全考量。

### 人类门：规格批准 → 触发 Build

### 度量
- **领先指标**：intent.md 提交到 spec.md 提交的耗时
- **滞后指标**：Build 开始后的需求返工——spec.md 在首个 plan.md 提交后的提交次数

## Phase 3 — Build：无已接受计划不实现

### 宏观流程

#### 计划模式优先

工程师以计划模式启动会话，给 Agent intent.md 和 spec.md，要求实现计划——命名变更文件、工作顺序、证明测试。质询计划：这可能破坏什么？哪步最危险？拒绝了哪些选项？迭代直到从未见过此对话的工程师能仅从计划实现变更。提交批准的计划为 plan.md。

#### 循环工作区（cycle-{N}/）

Build 阶段内部以循环驱动验证。每个循环创建独立工作区：

```
.cycles/
├── config.yml
├── workflow-graph.yaml
├── REVIEW.md
├── intent/
│   └── intent.md
├── cycles/
│   └── cycle-{N}/
│       ├── 项目评估报告.md
│       ├── 当前循环总规划.md
│       ├── 任务清单.md
│       ├── 当前循环页面状态.md
│       ├── 审计日志.md
│       ├── subplans/
│       ├── test-reports/
│       ├── 非功能验证报告.md
│       └── 交付清单.md
├── gates/
>├── incidents/
├── retrospectives/
├── tech-debt/
└── evals/
```

#### CLAUDE.md 作为仓库记忆

给 Agent 新加入者需要的上下文：约定、命令、架构、团队最常见的错误。工作规则：当 Agent 犯同一错误两次，修正写入 CLAUDE.md。保持在一页以内。

#### Skills 作为制度知识

为必须一致应用的知识写 Skill（安全标准、API 设计约定、品牌规则）；不要为属于 CLAUDE.md 或提示词的组件写 Skill。

#### Hooks 作为构建时护栏

构建阶段 Hooks 在文件编辑和 shell 命令上运行：阻止对受保护路径的编辑、编辑后运行格式化器和 linter、将凭据排除在 diff 之外。

#### 并行会话与 Subagent

将工作拆分为触及不同文件的任务；每个并行任务有自己的 git worktree。两到三个会话是合理的起点。将重复工作转为 Subagent。

#### 反馈循环

始终给 Agent 一种在人类看到之前验证自己工作的方式：运行测试、构建、截图。Agent 迭代直到检查通过。

### 微观迭代（嵌入）

| 步骤 | 内容 | 产物 |
|---|---|---|
| 评估 | E1-E8 全维度评估 → 产出《项目评估报告》 | 项目评估报告.md |
| 规划 | 计划模式 → plan.md → 创建 cycle-{N} → 循环总规划 + 子规划（每个子规划绑定≥1测试用例ID） | plan.md + 循环总规划 + 子规划 |
| 拆测 | 功能→分层用例映射 + 用户旅程正反向映射 + RTM | 功能→测试用例映射 |
| 验证 | 分层串行验证 → 产出测试报告/页面状态 | 测试报告 + 页面状态 |
| 修复 | 根因诊断 → 影响范围 → 修复+文档 → 强制构建 → 冒烟(P0) → 全量回归 | 缺陷登记 + 修复 |
| 门禁 | G0-G3 全部通过 | 门禁对照 |
| 复盘 | 量化指标 + 根因聚类 + 改进措施 + 技术债务台账 | 复盘报告 |

### 子规划硬性要求

每个子规划必须：
1. 绑定至少一个测试用例 ID
2. 包含文档变更验证项
3. 声明涉及的文件、接口、测试修改
4. 声明所需工具/技能

命名：`cycle-{N}-subplan-{type}-{name}`（type ∈ feature/fix/complex）

### 产物：plan.md → cycle-{N}/ → 代码+测试 → PR

### 人类门：计划批准 → 代码；PR 合并 → 触发 Deploy

### 度量
- **领先指标**：首次实现通过率；计划批准到合并 PR 的耗时
- **滞后指标**：每个变更的返工周期；合并 diff 与 plan.md 的匹配率

## Phase 4 — Test：持续 Evals 在 CI 中

### 宏观流程

Evals 是 AI-Native 等价于阶段门 QA。实际上是一个在 Agent 配置变更时运行的套件——新模型、重写提示词、编辑 CLAUDE.md/Skills/Hooks。

**执行步骤**：
1. 从最近工作中收集 20-50 个真实任务及其预期或接受结果
2. 将每个任务写为 eval：提示词 + 定义可接受的检查（测试通过、lint 清洁、行为不变、策略遵循）
3. 在 CI 中非交互运行套件——按计划和任何 CLAUDE.md/Skills/Hooks 变更时运行
4. 对结果门控配置变更：降低通过率的 Skill 变更在合并前评审
5. 每个生产事故获得一个 eval，由负责团队编写，作为回归测试留在套件中

### 微观迭代（嵌入）

| 步骤 | 内容 | 产物 |
|---|---|---|
| 评估 | E4 代码质量——lint 门禁、复杂度控制带、错误处理完备性 | 质量评估 |
| 规划 | 收集 20-50 个真实任务作为 eval 套件 | eval 套件计划 |
| 拆测 | 分层测试（自定义分层）+ 用户旅程覆盖 | 分层测试矩阵 |
| 验证 | eval 套件在 CI 中运行——配置变更时回归测试 | eval 结果 |
| 修复 | 每个生产事故添加 eval 作为回归测试 | 新 eval 用例 |
| 门禁 | G2 测试报告零错误——失败=0、错误=0、RTM 无缺口 | G2 判定 |
| 复盘 | eval 通过率趋势、CI 中捕获的回归 vs 生产中发现的回归 | 度量记录 |

### 产物：eval 结果 + 回归 evals

### 人类门：配置变更降通过率须评审

### 度量
- **领先指标**：eval 通过率随时间变化；生产事故成为永久 eval 的耗时
- **滞后指标**：CI 中捕获的回归 vs 生产中发现的回归

## Phase 5 — Deploy：双向评审，Agent 止于生产门

### 宏观流程

#### AI 在 PR 评审循环中

每个 PR 获得相同的评审通过项——bug 和逻辑错误、安全和漏洞、对照 spec.md/plan.md/设计原则的合规性——发现按严重度排序。REVIEW.md 定义什么算 Important vs Nit、跳过什么、5-nit 上限。

评审是双向的：Agent 评审传入的 PR 并处理自己 PR 上的评审评论。当评审第二次标记同一错误时，修正进入 CLAUDE.md。

#### Hooks 作为审批门

发布门是典型示例：production-gate.sh 阻止任何未经人类授权的生产部署。工程领导与变更管理和合规列出必须存活的人类审批门。每个门成为可以 allow/ask/block 的 Hook 脚本。

#### CI/CD 集成

在管道中非交互运行 Agent 用于判断步骤——分类失败构建、总结不稳定测试、起草变更日志——然后在现有门后添加写步骤。Agent 写的任何东西通过分支保护到达 PR；没有直达 main 的路径。

### 微观迭代（嵌入）

| 步骤 | 内容 | 产物 |
|---|---|---|
| 评估 | E6 安全检查——凭据泄漏/路径越界/权限面/依赖审计 | 安全评估 |
| 规划 | 发布构建流程规划 | 发布计划 |
| 拆测 | 非功能验证——性能基线对比、安全检查 | 非功能验证矩阵 |
| 验证 | Release 构建 → 全流程回归 → 非功能验证报告 | 非功能验证报告 |
| 修复 | 发布阻断项修复 | 修复记录 |
| 门禁 | G3 构建零失败 + H3 交付闸（门禁全绿+性能未退>5%+审计日志完整） | G3 + H3 判定 |
| 复盘 | 门禁违反到达生产的前后对比 | 度量记录 |

### 交付清单（8项必备）

1. Release 构建产物
2. 最终测试报告（全部结果及覆盖率）
3. 非功能验证报告
4. 验证签名
5. 文档更新记录
6. 环境配置说明
7. 数据清理记录
8. 审计日志（H1-H4 自动评估记录 + 熔断/恢复记录）

### 产物：授权发布 + 交付清单

### 人类门：显式发布授权（production-gate.sh 强制）

### 度量
- **领先指标**：首次评审时间（目标：分钟）；无需人类触碰分支解决的评审评论占比
- **滞后指标**：合并前捕获的缺陷和漏洞 vs 逃逸到生产的

## Phase 6 — Maintain：闭环

### 宏观流程

触发——控制带突破、工单、频道消息或计划——调用 Agent，没有人参与调用路径。Agent 诊断，仅通过门控路径行动，将发现写为 intent.md，重新进入 Plan。

**执行步骤**：
1. 选择一个有稳定滚动基线的指标——CI 测试失败率、部署后 5xx 率、PR 周期时间
2. 编写检测脚本：滚动窗口的均值和标准差，Western Electric 规则，使控制带捕获缓慢漂移和尖峰
3. 在版本控制配置中定义响应层级（bands.yaml）：1σ 仅记录；2σ 调用 Agent 只读诊断；3σ Agent 可以行动，但仅通过开 PR 进入门禁评审或触发预批准 runbook
4. Agent 无状态非交互运行。因为不需要人启动它，循环可以自行开始和结束
5. Agent 将诊断写为 intent.md——异常及其证据、提议结果、受影响系统、开放问题——像其他任何东西一样流过管道
6. 服务负责人或值班工程师分诊队列：立即修复、排期或驳回。驳回调整控制带减少噪音
7. 当修复发布时，为事故添加 eval，使该类问题在未来受到保护

### 微观迭代（嵌入）

| 步骤 | 内容 | 产物 |
|---|---|---|
| 评估 | E5 性能基线——控制带监控（1σ/2σ/3σ） | 控制带状态 |
| 规划 | 定义响应层级——1σ 记录 / 2σ 诊断 / 3σ 行动（仅通过门控路径） | 响应层级定义 |
| 拆测 | 事故诊断 → 影响范围分析 | 诊断报告 |
| 验证 | 回滚路径演练 | 回滚验证 |
| 修复 | 3σ 触发 → 开 PR 进入门禁评审 或 触发预批准 runbook | 修复 PR |
| 门禁 | 所有行动通过门控路径，无人工可用时循环暂停 | 门禁记录 |
| 复盘 | 事故 → eval → 写入 intent.md → 重新进入 Plan | 新 intent.md |

### 控制带与熔断融合

控制带响应层级与熔断条件融合：

| 控制带层级 | 响应 | 对应熔断条件 |
|---|---|---|
| 1σ | 仅记录 | 无 |
| 2σ | Agent 只读诊断 | 性能超预警且1轮优化未恢复（熔断条件5） |
| 3σ | Agent 通过门控路径行动 | 破坏性操作不可评估或不可回滚（熔断条件4） |

### 产物：诊断 → intent.md（重新进入 Plan）

### 人类门：值班工程师分诊——修复/排期/驳回

### 度量
- **领先指标**：从控制带突破到 intent.md 在分诊队列的时间
- **滞后指标**：发现成为合并修复的占比；同类重复事故（应随修复添加 eval 而下降）
