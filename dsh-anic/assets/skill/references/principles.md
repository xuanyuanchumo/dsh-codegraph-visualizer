# 驱动原则详解

> 融合 Cycles 19 项红线 + AI-Native SDLC 8 条硬规则，共 15 条硬性规则（去重合并后）。
> 每条包含：规则本身、为什么重要、如何应用。

## 硬性规则（15 条）

### R01 — 人类门禁不可跳过

**规则**：意图接受→设计；规格批准→构建；计划批准→代码；PR合并→部署；发布授权→生产。每个门禁须有人类明确决策。

**为什么**：Agent 可以生成、验证和执行机械工作，但判断决策须由人类持有。跳过门禁意味着 Agent 自行决定什么进入生产——这在受监管环境中不可接受。

**如何应用**：每个阶段的产物提交后，Agent 须明确请求人类评审和批准，不得自行推进到下一阶段。门禁决策记录为 git 提交（合并或关闭评审）。

### R02 — 永不越过生产门

**规则**：Agent 生成的变更止于合并/发布边界。高风险操作（生产配置、迁移、发布）须人类显式授权，由 Hook 强制。

**为什么**：生产环境的影响是不可逆的。Agent 可能产生看起来正确但在生产中失败的变更。人类授权是最后一道防线。

**如何应用**：production-gate.sh Hook 阻止任何未经授权的生产部署。发布授权须记录在哈希链审批账本中。Agent 可以做到生产门——但不越过。

### R03 — 验证先于评审

**规则**：先自行运行构建/测试/lint/截图，修复失败项，再提交人类评审。

**为什么**：人类评审时间是最宝贵的资源。如果 Agent 提交未验证的工作，评审者会花时间发现 Agent 本可自行发现的问题——这是浪费。

**如何应用**：CLAUDE.md 中定义验证命令（make test/build/lint），Agent 在报告任务完成前必须运行并粘贴输出。对于 bug 修复，先写失败测试，确认失败原因，再修复。

### R04 — 评估先行

**规则**：功能验证前先做项目/功能业务架构评估。

**为什么**：没有评估就验证，可能验证了错误的东西或遗漏了关键维度。评估建立基线，验证才有对照。

**如何应用**：每个循环 Phase 0 先执行 E1-E8 评估，产出《项目评估报告》，通过 G0 门禁后才进入拆测/验证。

### R05 — 证据纪律

**规则**：每次验证必须产出测试报告，包含六要素：通过数/失败数/断言明细/日志/复现步骤/手工操作记录。

**为什么**：没有证据的"通过"声明不可信。测试报告是 G2 门禁判定的唯一依据。

**如何应用**：使用测试报告模板，每次验证后填写。失败项必须逐条落实到任务清单。

### R06 — 不降级

**规则**：不因赶进度降低验收标准。

**为什么**：降级一旦开始就会持续——每个循环都找理由降级，最终标准形同虚设。

**如何应用**：门禁标准在项目配置中固定，循环内不得中途修改。如需调整门禁标准，须在循环间通过正式流程修改配置。

### R07 — 不条件通过

**规则**：任何"仅当X才通过"均不成立。门禁要么通过要么不通过，没有条件通过。

**为什么**：条件通过意味着存在未解决的问题被暂时忽略——这些问题会在后续循环中爆发。

**如何应用**：门禁判定为布尔值——全部满足才通过，任一不满足即失败。不得登记"部分通过"或"带条件通过"。

### R08 — 缺陷闭环

**规则**：发现→登记→根因→修复→回归→关闭→逃逸度量。缺陷不能只登记不修复。

**为什么**：未闭环的缺陷会累积成技术债务，最终拖垮项目质量。

**如何应用**：每个发现的缺陷必须在任务清单中登记，关联测试用例 ID，修复后回归验证，最后度量逃逸率（多少缺陷逃逸到生产）。

### R09 — 计划模式优先

**规则**：无已接受计划不实现；实现偏离计划时同提交更新 plan.md。

**为什么**：没有计划的实现意味着变更范围、风险和影响不可控——评审者看到的是已完成 diff，此时返工代价高。

**如何应用**：Build 阶段先进入计划模式，产出 plan.md，人类批准后才实现。plan-sync-check 脚本在 PR/CI 时检查 diff 与 plan.md 的同步。

### R10 — 重复教训编码化

**规则**：同一错误出现两次→写入 CLAUDE.md/AGENTS.md、Skill 或 Hook。

**为什么**：Agent 没有跨会话记忆。如果不将教训编码为文件，同一错误会在每个新会话中重复。

**如何应用**：第一次错误→口头修正。第二次同一错误→写入 CLAUDE.md（工作知识）或 Skill（制度知识）或 Hook（强制约束）。选择哪个层取决于错误的严重度和必须持有的程度。

### R11 — 评审须有证据

**规则**：每条发现引用文件/行号+具体证据，按严重度排序，每轮最多5条 nit。

**为什么**：没有证据的评审意见无法验证、无法追踪、无法度量改进。nit 过多会淹没重要发现。

**如何应用**：REVIEW.md 定义评审通过项（bug/安全/合规）、证据要求、严重度分级、5-nit 上限。评审发现不直接批准或阻止 PR——分支保护仍须代码所有者批准。

### R12 — Subagent 须命名可见

**规则**：Subagent 以功能性命名（verifier/researcher/code-simplifier），提交定义到 git，派遣时解释原因，报告须含证据。

**为什么**：匿名 Subagent 是黑箱——无法审计它做了什么、为什么做、是否正确。可见性是问责的基础。

**如何应用**：Subagent 定义在 `.claude/agents/*.md`（或等效位置），每个定义包含 name/description/tools。派遣时主 Agent 说明为什么派遣、总结返回了什么。Subagent 报告须含"运行了什么、看到了什么、没有检查什么"。

### R13 — 工具可用性门禁

**规则**：验证开始前先检查核心工具可用性，不可用先自动修复。

**为什么**：在不可用的工具上运行验证会产出误导性结果——看起来通过但实际没有真正验证。

**如何应用**：Phase 0 检查核心工具（构建/测试/lint/E2E）可用性。不可用→尝试自动修复→仍不可用→出具环境问题报告并暂停。

### R14 — 事实基座抽验

**规则**：抽验文档引用的≥5条路径/命令在仓库真实存在。

**为什么**：文档与代码脱节是常见问题——文档引用的路径可能已重命名/删除/从未存在。在脱节的文档上做评估会产出错误结论。

**如何应用**：G0 门禁包含事实基座抽验步骤——从评估报告中随机抽取≥5条路径/命令，验证其在仓库中真实存在。失败→先修文档再进入后续阶段。

### R15 — 旅程全覆盖

**规则**：用户旅程正反向场景100%通过。

**为什么**：用户旅程代表真实用户路径。正向验证"正常流程能走通"，反向验证"异常流程能正确处理"。只覆盖正向会遗漏大量边界情况。

**如何应用**：每个旅程定义正向路径和反向/异常场景。测试报告中须填写旅程覆盖情况——涉及旅程的正反向用例通过率。未涉及的旅程标注"本循环不涉及"。覆盖缺口登记并在循环内补齐。

## 三层护栏体系

每条规则通过三层护栏保障执行：

| 层 | 机制 | 强度 | 适用场景 |
|---|---|---|---|
| 原则层 | 本文档中的规则定义 | 价值观约束 | 所有场景——定义"应该做什么" |
| 建议层 | Skills / CLAUDE.md | 使合规行为大概率发生 | 常规场景——Agent 读到指令就大概率遵守 |
| 确定层 | Hooks / 脚本 | 使违规几乎不可能 | 必须始终持有的场景——如生产门禁、计划同步 |

**选择原则**：
- 策略必须始终持有 → 确定层（Hook）
- 策略应一致应用但允许例外 → 建议层（Skill）
- 策略是价值观/工作方式 → 原则层（本文档）
