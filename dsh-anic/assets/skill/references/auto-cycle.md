# L4 全自主循环编排指南

> AI 在 L4 全自主模式下如何编排完整的微观迭代循环，无需人类介入。
> 读取本文件的时机：自主级别为 L4 或准备升级到 L4 时。

## L4 全自主的核心原则

1. **AI 是编排器**：AI 自主调用脚本工具，编排"评估→规划→拆测→验证→修复→门禁→复盘"七步微观迭代
2. **人类门禁自动审计化**：H1-H4 检查点由 `scripts/hitl-audit.mjs` 自动评估，仅熔断时回退 L3
3. **不可直接降级/熔断**：遇到任何问题（验证失败、门禁未通过、熔断条件触发），必须先进行问题评估研究找出根本原因并尝试修复完善优化，只有修复失败才考虑降级/熔断。这是 L4 模式的最高优先级原则
4. **多 Agent 门禁评估**：每个人工门由 3 个不同角色的 AI agent 从不同维度独立评估，信任度≥70% 且 `--auto-approve` 时自动根据推荐执行
5. **熔断自动回退（先修复后降级）**：`scripts/org-status.mjs --auto-fallback` 检测熔断条件后，先诊断根因并尝试自动修复，只有修复失败才降级自主级别
6. **阶段自动推进**：门禁通过后 AI 自主调用 `workflow-state.mjs advance` 推进到下一阶段
7. **修复循环自动化**：`scripts/auto-fix-loop.mjs` 实现"验证失败→根因诊断→修复→重新验证"的自动循环，达到重试上限后先进行失败模式分析，只有分析后仍无法修复才触发熔断

## L4 全自主循环编排流程

```text
AI 自主启动
    │
    ▼
Phase 0: 工具与数据基线就绪
    ├── run quick-validate.mjs (skill 包自检)
    ├── run fact-base-verify.mjs (事实基座抽验)
    └── run eval-runner.mjs (E1-E8 + Q1-Q8 评估)
    │
    ▼
Phase 1: 规划
    ├── 读取评估报告 → 生成当前循环总规划
    ├── 生成子规划（每个绑定≥1测试用例ID）
    └── run workflow-state.mjs check (检查门禁状态)
    │
    ▼
Phase 2: 拆测
    ├── 功能→分层用例映射
    ├── 用户旅程正反向映射
    └── 生成任务清单
    │
    ▼
Phase 3: 验证
    ├── run config.yml 中的 test_cmd
    ├── 生成测试报告到 test-reports/
    ├── run config.yml 中的 lint_cmd
    ├── run eval-runner.mjs --dimensions E3,E4,E8,Q2
    └── run band-detector.mjs (Western Electric 复杂度漂移检测，
        连续 2 轮超 budget → CB5 熔断条件，结果供 org-status 读取)
    │
    ▼
Phase 4: 修复循环（先评估研究找根因，不可直接降级/熔断）
    ├── run auto-fix-loop.mjs (自动修复循环)
    │   ├── 识别失败项
    │   ├── 失败模式分析（重复性/级联性/瞬态）
    │   ├── 根因诊断（基于错误信息和代码上下文）
    │   ├── 修复代码/测试
    │   ├── 重新验证
    │   └── 循环直到失败=0 或达到重试上限
    ├── 达到重试上限 → 先进行失败模式分析
    │   ├── 重复性失败 → 根因可能在于架构层面 → 尝试更深层次修复
    │   ├── 级联失败 → 根因可能在于依赖链 → 尝试隔离修复
    │   └── 瞬态失败 → 偶发性错误 → 尝试增加重试或调整配置
    └── 只有失败模式分析后仍无法修复 → run org-status.mjs --auto-fallback
    │
    ▼
Phase 5: 门禁判定
    ├── run gate-check.mjs --gate all --quality --record（判定结果自动入账本，FAIL 也记）
    ├── G0 未通过 → 回到 Phase 0
    ├── G1 未通过 → 回到 Phase 2
    ├── G2 未通过 → 回到 Phase 4
    ├── G3 未通过 → 回到 Phase 4
    └── 全部通过 → 门禁记录已在 --record 时写入 gate-ledger
    │
    ▼
Phase 6: HITL 自动审计 + 多 Agent 门禁评估（先修复后降级）
    ├── run hitl-audit.mjs (H1-H4 自动评估，先修复后降级)
    │   ├── H1 安全敏感 → 先尝试修复（如将 .env 添加到 .gitignore），修复后重新审计
    │   ├── H2 破坏性操作 → 先尝试修复（如初始化 git 基线），修复后重新审计
    │   ├── H3 Release交付闸 → 先尝试修复（如创建审计日志），修复后重新审计
    │   ├── H4 门禁仲裁 → 先尝试修复（如补充账本详情），修复后重新审计
    │   └── 修复后仍失败 → 熔断回退 L3，记录到 incidents/
    ├── run multi-agent-gate.mjs (多 Agent 门禁评估)
    │   ├── 每个人工门由 3 个不同角色 Agent 独立评估
    │   ├── 综合判定：通过数≥阈值 → 推荐通过
    │   ├── 信任度≥70% 且 --auto-approve → 自动根据推荐执行
    │   ├── 信任度<70% → 不推进，需人工审查
    │   └── 评估结果记录到审计日志和评估报告
    └── 多 Agent 评估未通过 → 不推进，记录到审计日志
    │
    ▼
Phase 7: 复盘
    ├── 生成复盘报告到 retrospectives/
    ├── 更新技术债务台账
    ├── 更新性能基线
    └── run org-status.mjs review (循环评审摘要)
    │
    ▼
阶段推进
    ├── run workflow-state.mjs advance (推进到下一阶段)
    └── 循环回到 Phase 0（下一循环）
```

## H1-H4 自动审计判定逻辑

### H1 — 安全敏感操作

**自动评估内容**：
- 扫描变更是否涉及真实用户数据/明文凭据
- 检查是否有隔离方案（测试数据 vs 生产数据）
- 检查 .env 文件是否在 .gitignore

**判定逻辑**：
```
if (涉及真实用户数据 && 无隔离方案) → 熔断，回退 L3
else if (涉及明文凭据) → 熔断，回退 L3
else → PASS，记录到审计日志
```

### H2 — 破坏性操作

**自动评估内容**：
- 识别破坏性操作（.gitignore 修改、数据库迁移、配置删除等）
- 影响范围分析（受影响的文件/模块数量）
- 回滚方案核对（是否有 git revert 路径）

**判定逻辑**：
```
if (影响范围不可评估) → 熔断，回退 L3
else if (无回滚方案) → 熔断，回退 L3
else → PASS，记录到审计日志
```

### H3 — Release 交付闸

**自动评估内容**：
- 门禁全绿（G0-G3 全部 PASS）
- 性能未退 >5%（对比上一循环基线）
- 审计日志完整（H1-H4 评估记录齐全）

**判定逻辑**：
```
if (门禁未全绿) → 熔断，回退 L3
else if (性能退化 >5%) → 熔断，回退 L3
else if (审计日志不完整) → 熔断，回退 L3
else → PASS，记录到审计日志
```

### H4 — 门禁仲裁

**自动评估内容**：
- 复核门禁判定依据（G0-G3 的判定证据是否充分）
- 检查判定依据是否有冲突
- 检查证据是否足够支持判定

**判定逻辑**：
```
if (判定依据冲突) → 熔断，回退 L3
else if (证据不足) → 熔断，回退 L3
else → PASS，记录到审计日志
```

## 多 Agent 门禁评估机制

在 L4 全自主模式下，每个人工门由 3 个不同角色的 AI agent 从不同维度独立评估，综合判定门禁是否应该通过。

### 门禁与评估 Agent 映射

| 人工门 | Agent 1 | Agent 2 | Agent 3 | 通过阈值 |
|---|---|---|---|---|
| intent 接受→Design | 产品经理(业务价值) | 架构师(技术可行性) | 评估者(需求完整性) | 2/3 |
| spec 批准→Build | 架构师(设计合理性) | 安全审查(安全合规) | 评估者(规格完整性) | 2/3 |
| plan 批准→代码 | 工程师(实现可行性) | 评估者(测试覆盖) | 审查者(代码规范) | 2/3 |
| PR 合并→Deploy | 审查者(代码质量) | 安全审查(安全扫描) | 门禁守卫(G0-G3) | 3/3 |
| release 授权→生产 | 门禁守卫(全门禁) | 安全审查(合规) | 评估者(性能基线) | 3/3 |

### 信任梯度与自动执行

| 信任度 | 通过情况 | 行为 |
|---|---|---|
| 高信任度 | 全部通过(3/3) | `--auto-approve` 时自动执行 |
| 中信任度 | 多数通过(2/3) | 推荐执行但记录到审计日志 |
| 低信任度 | 少数通过(<2/3) | 不推进，需人工审查 |
| 自动执行阈值 | 平均信任度≥70% | `--auto-approve` 时自动根据推荐执行 |
| 人工审查阈值 | 平均信任度<70% | 不自动执行，需人工审查 |

### 多 Agent 评估研究后默认根据推荐

当 `--auto-approve` 启用时：
1. 3 个 Agent 独立评估 → 各自产出评估结论和置信度
2. 综合判定：通过数≥阈值 → 推荐通过
3. 平均信任度≥70% → 自动根据推荐执行（推进到下一阶段）
4. 平均信任度<70% → 不推进，记录到审计日志，等待人工审查
5. PR 门和 Release 门要求 3/3 全部通过（因为涉及代码集成和生产部署）

### 与 HITL 审计的关系

- **HITL 审计**（H1-H4）：面向**操作风险**的自动检查，关注"这个操作是否危险"
- **多 Agent 门禁评估**：面向**决策质量**的自动评估，关注"这个决策是否正确"
- 两者互补：在 L4 全自主模式下同时运行，两者都通过才自动推进

详见 `references/multi-agent-gate.md`。

## 熔断自动回退机制（先修复后降级）

`scripts/org-status.mjs --auto-fallback` 执行以下三阶段逻辑：

1. **Phase 1 — 诊断根因**：检测到熔断条件后，先分析根因（如修复失败是重复性/级联性/瞬态失败）
2. **Phase 2 — 尝试自动修复**：根据根因诊断结果尝试自动修复（如补充账本详情、创建审计日志文件等）
3. **Phase 3 — 只有修复失败才降级**：修复尝试失败后，才自动更新 config.yml 中 autonomy_level，记录熔断事件到 `.cycles/incidents/`，输出回退报告

**核心原则**：不直接降级/熔断，先进行问题评估研究找出根本原因修复完善优化，只有修复失败才考虑降级。

## 自动修复循环机制（先评估研究找根因，不可直接熔断）

`scripts/auto-fix-loop.mjs` 执行以下逻辑：

1. 读取最新测试报告，识别失败项
2. 对每个失败项：
   a. 失败模式分析（重复性/级联性/瞬态）
   b. 根因诊断（基于错误信息和代码上下文）
   c. 修复代码或测试
   d. 重新运行验证
   e. 循环直到失败=0 或达到重试上限
3. 达到重试上限（3次）→ **必须先进行失败模式分析**：
   - **重复性失败**：同一错误反复出现 → 根因可能在于架构层面 → 尝试更深层次修复（如重构、修改接口契约）
   - **级联失败**：不同错误连锁出现 → 根因可能在于依赖链 → 尝试隔离修复（先修复主失败，可能解决次失败）
   - **瞬态失败**：偶发性错误 → 尝试增加重试次数或调整超时配置
4. **不可直接熔断**：只有失败模式分析后仍无法修复时，才触发熔断条件1
5. 熔断触发后仍不直接降级 → 运行 `org-status.mjs --auto-fallback` 进入"先修复后降级"流程
6. 输出修复报告

## L4 全自主的边界

即使在 L4 全自主模式下，以下操作仍需人类介入：

1. **生产部署的最终授权**：production-gate.sh 强制要求人类授权
2. **熔断后的恢复**：熔断回退 L3 后，需人类确认问题已修复
3. **新意图的提出**：Maintain 阶段控制带突破产生的新 intent.md 需人类分诊
4. **门禁标准修改**：G0-G3 的判定标准由人类配置，AI 只执行不修改

这些边界由 Hooks（确定层）强制保障，不是 Skill（建议层）的软约束。
