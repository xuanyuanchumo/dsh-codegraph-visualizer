# 双层门禁判定标准

> 融合 AI-Native SDLC 人类门 + Cycles G0-G3 收敛门，构成双层门禁体系。

## 门禁体系总览

```
人类门（判断决策）         收敛门（自动化判定）
─────────────────         ──────────────────
intent 接受 → Design       G0 评估基线就绪
spec 批准 → Build           G1 任务清单清零
plan 批准 → 代码            G2 测试报告零错误
PR 合并 → Deploy            G3 构建零失败
release 授权 → 生产
```

**双层关系**：人类门和收敛门独立判定，任一失败即停止。人类门关注"是否应该推进"，收敛门关注"质量是否达标"。

## 收敛门禁 G0-G3

### G0 — 评估基线就绪

**判定标准**（全部满足才通过）：
1. 本循环《项目评估报告》已产出且覆盖本循环范围
2. 事实基座抽验通过——抽验本循环将引用的 ≥5 条文档路径/命令在仓库真实存在

**违反后果**：禁止进入拆测/验证

**执行方式**：
- 评估报告由 AI 自主产出（E1-E8 八维评估）
- 事实基座抽验由 `scripts/fact-base-verify.mjs` 自动执行
- 抽验失败→先修文档→重新抽验→通过后才进入后续阶段

### G1 — 任务清单清零

**判定标准**（全部满足才通过）：
1. P0-P3 全部任务已登记（含归属层标注）
2. 无未分配的测试用例
3. 无未登记的遗留 TODO

**违反后果**：禁止进入下一循环

**执行方式**：
- 任务清单按 P0-P3 分级 + 拓扑排序（依赖在前）
- 每项绑定测试用例 ID 与文档变更项
- 归属层标注（如前端/后端/契约）
- 全部完成（含文档项）才可标记 completed

### G2 — 测试报告零错误

**判定标准**（全部满足才通过）：
1. 最新测试报告中：失败=0、错误=0
2. RTM（需求追溯矩阵）无缺口
3. 用户旅程覆盖零缺口（正反向场景 100% 通过）
4. 既有混沌用例全过、缺口已登记

**违反后果**：禁止进入 Release

**执行方式**：
- 测试报告必须包含六要素：通过数/失败数/断言明细/日志/复现步骤/手工操作记录
- 旅程覆盖：涉及旅程的正反向用例通过率 100% 无跳过
- 混沌覆盖：既有混沌用例通过情况随报告存档；缺口实验登记任务清单

### G3 — 构建零失败

**判定标准**（全部满足才通过）：
1. Debug 构建通过（项目配置中的 build 命令）
2. Release 构建通过（build + 发布卫生检查）
3. 冒烟(P0) 与全量回归全通过

**违反后果**：禁止提交、禁止交付

**执行方式**：
- 构建命令从 `config.yml` 读取，不硬编码
- 冒烟测试先跑 P0 核心路径，通过后再全量回归
- 构建失败→构建修复子流程→重新执行 G3

### 门禁执行顺序

G0 → G1 → G2 → G3。任何门禁失败即停止流转并登记。不得跳过前置门禁直接判定后续门禁。
G0-G3 的判定结果经 `gate-check.mjs --record`（v1.8.0）自动登记入哈希链审批账本（同门同结果去重；**FAIL 也登记**——org-status 熔断条件 CB2 依赖账本中的 FAIL 记录），无需手工补录。

## 人类门禁

### intent 接受 → 触发 Design

**谁决定**：产品负责人
**判定依据**：intent.md 是否清晰描述了问题、提议结果、受影响用户、约束、范围外、开放问题
**记录方式**：git 合并或关闭评审

### spec 批准 → 触发 Build

**谁决定**：产品负责人，高风险项咨询技术负责人
**判定依据**：spec.md 是否解决了 intent.md 中的问题；开放问题是否回答或延续；关切点是否已与策略负责人解决
**记录方式**：git 合并或关闭评审

### plan 批准 → 触发代码实现

**谁决定**：工程师（常规变更）或技术负责人（高风险变更）
**判定依据**：plan.md 是否命名了变更文件、工作顺序、风险、证明测试；从未见过此对话的工程师能否仅从计划实现变更
**记录方式**：计划接受提交

### PR 合并 → 触发 Deploy

**谁决定**：代码所有者（分支保护）
**判定依据**：评审通过项（bug/安全/合规）全过；测试通过；plan.md 与 diff 同步
**记录方式**：PR 合并

### release 授权 → 触发生产部署

**谁决定**：发布经理
**判定依据**：门禁全绿（含 G3）；性能未退 >5%；审计日志完整；非功能验证通过
**记录方式**：哈希链审批账本中的授权记录；production-gate.sh 验证 `RELEASE_APPROVAL=ledger:<id>`

## 门禁检查点（HITL → L4 自动审计化）

| 检查点 | 触发条件 | L4 自动评估内容 | 熔断条件 |
|---|---|---|---|
| H1 | 安全敏感操作 | 核对是否涉及真实用户数据/明文凭据 | 涉及真实用户数据且无隔离方案 |
| H2 | 破坏性操作 | 影响范围分析 + 回滚方案核对 | 影响范围不可评估或不可回滚 |
| H3 | Release 交付闸 | 门禁全绿 + 性能未退 >5% + 审计日志完整 | 门禁不过/性能退化未调查 |
| H4 | 门禁仲裁 | 复核判定依据 | 判定依据冲突或证据不足 |

**L4 规则**：每个触发的检查点由 AI 自动执行"触发→评估→记录"三步；仅当触发熔断条件时回退 L3 请求人工。
